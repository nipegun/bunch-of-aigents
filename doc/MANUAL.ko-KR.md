## 하는 일

- **에이전트는 Linux 사용자입니다.** 웹 인터페이스에서 에이전트를 하나
  만들면 시스템에 `agent-007`이 생기고, 다른 어떤 에이전트도 읽을 수 없는
  홈 디렉터리도 함께 생깁니다. 그것이 격리입니다. Python으로 작성한
  샌드박스가 아니라 커널의 격리입니다.
- **에이전트는 자기 일정대로 실행됩니다.** 에이전트마다 자기 crontab이
  있고, 그 소유자도 실행자도 에이전트 자신의 사용자입니다. 그래서
  에이전트는 깨어나서 일을 하고 종료합니다.
- **에이전트와 대화합니다.** 에이전트를 클릭하면 채팅이 열립니다. 무언가를
  시키면 에이전트는 자기 도구를 써서 일하고, 끝나면 답합니다. 대화는
  기억됩니다.
- **사람마다가 아니라 에이전트마다 대화가 하나입니다.** 시각이 된 카드는
  실행이 시작될 때 바로 그 채팅에 올라오고, 답은 그 아래에 나타납니다.
  그래서 에이전트의 채팅에는 당신이든 다른 에이전트든 누군가가 그
  에이전트에게 시킨 모든 일과, 그에 대해 에이전트가 한 일이 다 들어
  있습니다.
- **칸반 보드를 함께 씁니다.** 에이전트들은 카드를 추가하고, 옮기고, 서로의
  작업을 봅니다. 당신은 로그를 읽는 대신 `/kanban/`에서 지켜봅니다.
- **클라우드든 자체 운영이든, 어떤 모델이든.** 공급자 스물다섯 곳이 기본으로
  들어 있습니다. Anthropic, OpenAI, Google, DeepSeek, Mistral, Qwen, xAI
  등과, 그 앞에 서는 라우터인 OpenRouter, Groq, Together, Vercel 등, 그리고
  자기 하드웨어에서 돌리는 Ollama, llama.cpp, vLLM입니다. 에이전트마다 자기
  모델을 고르고, 그 모델이 멈췄을 때를 위한 예비 모델도 둡니다.
- **실제로 멈추게 하는 지출 상한.** 에이전트마다 토큰, 단계, 초, 하루 실행
  횟수에 상한을 둡니다. 그렇지 않으면 유료 API 위에서 아무도 지켜보지 않는
  에이전트는 백지 청구서나 다름없습니다.
- **설정할 수 있는 메모리.** 각 에이전트의 메모리 한도를 그 설정에서
  1,000자부터 1,000,000자까지(기본값 8,000자) 고르세요. 한도를 넘는 쓰기는
  거부되며, 텍스트를 잘라 내거나 저장된 메모리를 바꾸지 않습니다.
- **에이전트마다 하나의 문서 라이브러리.** PDF, EPUB, TXT, Markdown 형식의
  책을 올리세요. 텍스트 추출, OCR, 벡터화는 로컬에서 이루어지고, 에이전트는
  관련 구절을 검색해 출처를 인용합니다. **RAG**에서 설정합니다. 벡터화
  모델은 기본적으로 EmbeddingGemma 300M이며, 프로세서와 메모리에 여유가
  있는 기기라면 **설정 → RAG**에서 Qwen3-Embedding 0.6B로 바꿀 수 있습니다.
- **옮길 수 있는 에이전트.** 에이전트의 **내보내기** 탭은 그 에이전트를
  `.zip`으로 내려받습니다. 원하면 메모리, 모델, 라이브러리, 홈 파일까지
  담지만 키는 절대 담지 않습니다. 그리고 **+** 버튼으로 이 설치나 다른 설치에서
  가져옵니다. 미리 만들어 둔 에이전트는
  [템플릿 저장소](https://github.com/nipegun/bunch-of-aigents-templates)에서
  옵니다.
- **확장할 수 있는 도구.** 도구 하나는 `/opt/boa/tools/` 안의 `.py` 파일
  하나입니다. 새 파일을 넣으면 **설정 → 도구**에 나타나며, 자동화나
  브라우저 같은 하위 탭으로 묶입니다.
- **함께 쓰는 스킬.** `/opt/boa/skills/`에 한 번 적어 둔 절차는 원하는 만큼
  많은 에이전트에게 줄 수 있습니다. 에이전트가 혼자 배운 것은 자기 메모리
  안에서 끝나지만, 스킬은 그렇지 않습니다.
- **각자의 세션을 가진 각자의 브라우저.** 에이전트는 페이지를 읽기만 하는
  것이 아니라 사이트에 로그인하고, 양식을 채우고, 클릭할 수 있습니다. 쿠키는
  에이전트 자신의 0700 홈에 있으므로, 한 에이전트의 로그인이 모든
  에이전트의 로그인이 되지는 않습니다.
- **Telegram, Discord, X, Slack 또는 Mattermost에서 대화합니다.** Telegram의
  `/agents`, Slack의 `/boa agents`, Discord와 Mattermost의 `!agents`로
  목록을 봅니다. 에이전트를 지정하거나 메시지에 회신하면 실행이 시작되고
  답변을 받습니다. 양쪽 내용은 에이전트 웹 채팅에도 표시됩니다.
- **Telegram 오디오.** **설정 → 오디오**에서 로컬 whisper.cpp를 고르거나,
  이미 저장된 API 키로 OpenAI, Groq, Mistral, Together AI, Hugging Face,
  Cloudflare 중 하나를 고릅니다. 로컬 모델 30종이 모두 제공되며, 필요할 때
  내려받습니다. 음성 답장은 원래의 에이전트에게 텍스트로 전달되어 웹 채팅에
  나타나고, 원하면 오디오도 재생할 수 있습니다.
- **각자의 공유 폴더.** 모든 에이전트의 `samba/` 폴더는 그 Linux 사용자의
  이름을 딴 SMB 공유이므로, Windows, Linux, macOS에서 파일을 넣을 수
  있습니다.
- **열다섯 개 언어.** 독일어, 영어(영국, 미국), 스페인어(스페인, 아르헨티나),
  프랑스어, 히브리어, 힌디어, 이탈리아어, 일본어, 한국어, 포르투갈어(브라질,
  포르투갈), 러시아어, 중국어 간체. 인터페이스, 에이전트에게 어느 언어로
  답할지 알려 주는 줄, 그리고 각 채널의 봇이 하는 말까지 해당합니다.

한 사람이 자기 LAN에서 운영하도록 만들어졌습니다.

## 실행 환경

두 가지 시스템이며, 각각에서 init은 세부 사항이 아니라 요구 사항의
일부입니다.

- **systemd가 PID 1인 Debian.** 열한 개의 서비스는 systemd 유닛입니다.
  다른 것으로 부팅하는 Debian에는 그것들을 시작해 줄 주체가 없으므로,
  설치 프로그램은 기기를 건드리기 전에 `systemctl is-system-running`을
  확인하고 systemd가 없으면 거부합니다. 그런 기기에서는 시도하지 마세요.
  답은 바뀌지 않습니다.
- **OpenRC를 쓰는 Alpine.** 열한 개의 서비스는 `supervise-daemon`이 감독하는
  OpenRC 스크립트입니다. 미리 설치해 둘 것은 없습니다. 기기에 `openrc`가
  없으면 설치 프로그램이 직접 추가합니다.

Debian에서는 `systemctl is-system-running`으로 확인하세요. 응답(`running`,
`degraded`, `starting`)이 와야 하며, “System has not been booted with
systemd as init system (PID 1)”을 출력해서는 안 됩니다. 컨테이너라면
`systemd systemd-sysv dbus`가 설치되어 있고 명령이 `/sbin/init`이어야
합니다.

init 시스템 외에 필요한 것은 다음과 같습니다.

- `root` 권한. 두 설치 프로그램 모두 `sudo`를 쓰지 않으며, 필요로 하지도
  않습니다.
- 애플리케이션과 그 Python 환경을 위한 약 500 MB의 디스크.
- 설치 프로그램이 설치하는 `haproxy`. 이것이 TLS를 종료합니다. 기기의
  HAProxy가 보내는 PROXY 헤더는 TLS 핸드셰이크보다 먼저 도착하고, 그
  지점에서 그것을 읽을 수 있는 것은 프록시뿐이기 때문입니다.
- 대화할 모델. 클라우드 공급자의 API 키, 또는 접속할 수 있는 어딘가에서
  실행 중인 Ollama, llama.cpp, vLLM 중 하나.

설치 프로그램은 또한 `/opt/boa/whisper/`에 **whisper.cpp v1.9.4**를
빌드하고, FFmpeg를 설치하며, 다국어 `base` 모델(추가로 약 142 MiB)을
내려받습니다. 컴파일, 시스템 의존성, 브라우저에는 디스크 공간이 더
필요합니다. Python 인터프리터가 없으면 버전을 확인하기 전에 먼저
설치합니다.

이 매뉴얼의 나머지 내용은 두 시스템에서 모두 같습니다.

## Alpine을 쓴다면

이 매뉴얼에서 `systemctl`이나 `journalctl`이 나오는 명령은 모두
Debian용입니다. Alpine에서도 애플리케이션은 같고, 달라지는 것은 init
시스템과 로그가 쌓이는 곳입니다.

| Debian에서 | Alpine에서 |
|---|---|
| `systemctl status boa-web` | `rc-service boa-web status`, 열 개 전부는 `rc-status` |
| `systemctl restart boa-web` | `rc-service boa-web restart` |
| `journalctl -u boa-web -f` | `tail -f /opt/boa/logs/boa-web.log` |
| `install-update-reinstall-debian.sh` | `install-update-reinstall-alpine.sh` |

거기에는 빠진 기능이 하나 있고, 앞으로도 돌아오지 않습니다. Playwright가
musl용 빌드를 내놓지 않기 때문에 브라우저가 없습니다. 브라우저 도구는
목록에 그대로 남아 있고, 에이전트가 그중 하나를 호출하면 그렇다고 알려
줍니다.

## 설치하기

배포판마다 설치 프로그램이 하나씩 있고, 둘 다 같은 플래그를 받습니다.
`root`로 실행하세요.

### Debian에서

> **기기에서 systemd가 실행 중이어야 합니다.** 먼저 `systemctl is-system-running`을
> 실행하세요. “System has not been booted with systemd as init system
> (PID 1). Can't operate.”가 출력되면 여기서 멈추세요. 이 프로그램이
> 설치하는 서비스는 모두 systemd 유닛이라 시작해 줄 주체가 없습니다. 그래서
> 설치 프로그램은 아무것도 제공하지 못하는 설치를 남기는 대신 거부합니다.

```bash
curl -fsSL https://raw.githubusercontent.com/nipegun/bunch-of-aigents/main/deploy/install-update-reinstall-debian.sh \
  | bash -s -- --install --email you@example.com
```

`curl`이 설치되어 있지 않다면(최소 구성의 Debian에는 `curl`도 `wget`도 없는
경우가 많습니다) 먼저 설치하세요. 그러지 않으면 위의 줄은 `curl: command not
found`를 출력하고 멈춥니다.

```bash
apt-get update && apt-get install -y curl
```

또는 설치 프로그램을 먼저 내려받아 실행하기 전에 읽어 보세요. 그쪽이 더
좋은 습관입니다.

```bash
wget https://raw.githubusercontent.com/nipegun/bunch-of-aigents/main/deploy/install-update-reinstall-debian.sh
less install-update-reinstall-debian.sh
chmod +x install-update-reinstall-debian.sh
./install-update-reinstall-debian.sh --install --email you@example.com
```

### Alpine Linux에서

플래그는 같고 스크립트가 다릅니다. systemd 유닛 대신 OpenRC 서비스를
만듭니다. 한 줄이며, `wget`을 쓰고 `sh`로 파이프합니다. 갓 설치한
Alpine에는 `curl`도 bash도 없고, `wget`과 `sh`는 둘 다 BusyBox의 것이기
때문입니다.

```bash
wget -qO- https://raw.githubusercontent.com/nipegun/bunch-of-aigents/main/deploy/install-update-reinstall-alpine.sh \
  | sh -s -- --install --email you@example.com
```

`curl`이 있는 기기에서는 `wget -qO-` 대신 `curl -fsSL`을 쓰세요. 다만 그렇게
한다면 그 줄을 잘 지켜보세요. `sh`로 파이프된 `curl: not found`는 오류를
출력한 뒤, 아무것도 설치하지 않은 채 **성공**하기 때문입니다.

설치 프로그램이 bash가 아니라 POSIX 셸로 작성된 것도 `wget`과 같은
이유입니다. 갓 설치한 Alpine에는 `| bash -s --`가 닿을 bash가 없습니다.
설치 프로그램은 진행하는 도중에 bash를 설치하므로(모든 에이전트는 bash
셸을 받습니다), 이미 bash가 있는 기기에서는 `| bash -s --`도 똑같이
동작합니다.

또는 먼저 내려받아 실행하기 전에 읽어 보세요.

```bash
wget https://raw.githubusercontent.com/nipegun/bunch-of-aigents/main/deploy/install-update-reinstall-alpine.sh
less install-update-reinstall-alpine.sh
chmod +x install-update-reinstall-alpine.sh
./install-update-reinstall-alpine.sh --install --email you@example.com
```

설치가 끝나고 나면 두 가지가 다르며, 둘 다 결정이 아니라 시스템
때문입니다.

- **브라우저 없음.** Playwright는 musl용 빌드를 내놓지 않고 Alpine도
  패키지를 제공하지 않으므로, 에이전트가 `browser.open` 등을 호출하면
  그렇다고 알려 줍니다. `web.fetch`와 `rss.fetch`는 다른 곳과 똑같이
  동작합니다.
- **`systemctl status` 대신 `rc-status`**, 그리고 `systemctl restart
  boa-web` 대신 `rc-service boa-web restart`.
  [Alpine을 쓴다면](#alpine을-쓴다면)을 참고하세요.

Alpine에서는 서비스가 설치 프로그램의 SSH 출력을 붙잡고 있지 않으므로,
설치 프로그램은 끝나면 세션의 제어권을 돌려줍니다.

### 설치 프로그램이 하는 일

1. `boa` 시스템 사용자와 `/opt/boa/` 아래의 디렉터리 트리를 만듭니다.
2. `/opt/boa/venv/`에 Python 의존성을 설치합니다.
3. 자체 서명 TLS 인증서를 생성합니다. 단, `/opt/boa/certificates/`에 직접
   준비한 `fullchain.pem`과 `privkey.pem`을 넣어 두었다면 생성하지 않습니다.
4. 애플리케이션을 80과 443의 HAProxy 뒤에서 11080/11443으로 제공할지,
   80과 443에서 직접 제공할지 묻습니다. 미리 답하려면 `--ports
   proxied|direct`를 넘기세요. 답은 기억되므로 `--update`는 다시 묻지도,
   몰래 바꾸지도 않습니다. `direct`를 고르면 기기 자체의 HAProxy를
   물러나게 합니다. 멈추고, 모든 런레벨에서 빼거나 마스킹하며, 그
   `/etc/haproxy/haproxy.cfg`는 이 설치 프로그램이 쓴 것이면 삭제하고 다른
   누군가가 쓴 것이면 `haproxy.cfg.before-boa.<date>`로 보관합니다. 다음
   부팅 때 아무것도 80과 443을 차지하지 않게 하려는 것입니다. haproxy
   패키지 자체는 남습니다. 애플리케이션 자신의 프록시가 바로 그
   바이너리이기 때문입니다.
5. 에이전트 하나를 만듭니다. 오케스트레이터인 `manager`입니다. 그 밖의
   것은 모두 **+** 버튼을 누를 때 고르는 빈 에이전트, 에이전트에서 내보낸
   `.zip`, 또는
   [템플릿 저장소](https://github.com/nipegun/bunch-of-aigents-templates)의
   템플릿(`web-navigator`, `os-watcher`, `mail-watcher` 등)입니다. 빈
   에이전트가 첫 번째 선택지로 제시됩니다.
6. [서비스](#서비스)에 나열된 서비스를 설치하고 시작합니다. Debian에서는
   systemd 유닛, Alpine에서는 `supervise-daemon`이 감독하는 OpenRC
   서비스입니다.
7. 자신이 한 일과 로그인 비밀번호를 `/opt/boa/logs/install.log`(root, 모드
   0600)에 기록합니다.
8. 끝났다고 말하기 전에 애플리케이션에 로그인 페이지를 요청합니다. 페이지가
   오지 않으면 그렇다고 말하고, 그 순간 기기의 상태(curl이 요청을 어떻게
   처리했는지, 그 포트에서 무언가 듣고 있는지, 서비스의 상태, 서비스가
   출력한 마지막 줄들)를 같은 로그에 기록하며, 성공을 보고하는 대신 그
   로그를 알려 줍니다. `--update`는 그에 앞서 이전 버전을 되돌려 놓기도
   합니다.

### 비밀번호가 있는 곳

입력한 이메일 주소가 유일한 로그인 계정입니다. 비밀번호는 자동으로
생성되며, 다음 명령으로 읽습니다.

```bash
cat /opt/boa/logs/install.log
```

그 파일 하나가 두 가지 역할을 합니다. 설치의 전체 로그이자, 설치가 생성한
인증 정보입니다. 로그인 페이지가 그 파일을 알려 주므로, 위치를 기억해 둘
필요가 없습니다.

## 업데이트와 재설치

```bash
./install-update-reinstall-debian.sh --update      # 에이전트와 데이터를 유지합니다
./install-update-reinstall-debian.sh --reinstall   # 먼저 모든 것을 삭제합니다
```

Alpine에서도 같은 두 플래그를 다른 스크립트에 씁니다.

```bash
./install-update-reinstall-alpine.sh --update
./install-update-reinstall-alpine.sh --reinstall
```

`--reinstall`은 모든 에이전트, 홈 디렉터리, crontab, 그리고 칸반 보드를
삭제합니다. `--yes`를 넘기지 않으면 확인을 요청합니다.

도중에 중단된 설치(다운로드 실패, 네트워크 끊김)는 `--install`을 다시
실행하면 마무리됩니다. 멈춘 지점부터 이어서 진행하며, `--update`는 그런
설치를 발견하면 그렇다고 알려 줍니다.

백업 플래그 `--backup`과 `--restore`는
[백업과 복원](#백업과-복원)에서 설명합니다.

## 접속하기

기본값인 `proxied` 모드에서는 애플리케이션 자신의 HAProxy가
`127.0.0.1:11443`(HTTPS)과 `127.0.0.1:11080`(HTTP, 리디렉션)에서 듣습니다.
이 포트들은 서버 밖에서 접근할 수 없습니다. LAN에 서비스하는 것은 기기
자체의 HAProxy이며, 실제 클라이언트 주소가 살아남도록 `send-proxy-v2`로
11443에 전달합니다. `direct` 모드에서는 애플리케이션이 앞에 아무것도 두지
않고 직접 80과 443에서 듣습니다.

그렇게 준비되었으면 다음 주소를 여세요.

```
https://your-server/
```

`/opt/boa/certificates/`에 직접 준비한 인증서를 넣어 두지 않았다면
인증서는 자체 서명이므로, 브라우저가 한 번 경고합니다. 비밀번호를 입력하기 전에 아래 설명대로 지문을 확인하세요.

### 인증서 확인

자체 서명 인증서는 아무도 보증하지 않는 인증서입니다. 처음 연결할 때 브라우저는 이 서버의 인증서와 네트워크의 다른 누군가가 대신 내미는 인증서를 구별할 수 없으므로, 경고만으로는 아무것도 증명되지 않습니다. 지문은 증명합니다. 서버에서 직접, 콘솔이나 SSH로 `root` 권한으로 실행하세요.

```bash
boa fingerprint
```

인증서의 이름과 SHA-256 지문이 표시됩니다. 설치 프로그램도 설치, 업데이트, 재설치, 복원이 끝날 때마다 지문을 보여 주고 `/opt/boa/logs/install.log`에 기록합니다. 브라우저에서 경고 페이지나 자물쇠 아이콘으로 인증서 세부 정보를 열고 그 SHA-256 지문을 이것과 비교하세요. 일치할 때만 비밀번호를 입력하세요. 경고가 더 이상 보이지 않게 하려면, 지문이 일치한 뒤 `/opt/boa/certificates/fullchain.pem`을 브라우저나 운영 체제의 신뢰할 수 있는 인증서로 가져오세요.

새 인증서에는 머신의 이름, `localhost`와 그 주소가 들어 있고 서버 인증서로 표시됩니다. 이전 설치는 기존 인증서를 그대로 유지합니다. 새로 만들려면 `/opt/boa/certificates/`에서 `fullchain.pem`과 `privkey.pem`을 지우고 `--update`를 실행하세요. 지문이 바뀌므로 다시 확인하세요.

### 이 기기의 HAProxy가 갖춰야 할 모습

이 애플리케이션을 가리키는 백엔드에는 두 가지가 필요합니다.

```
backend https-out
  mode tcp
  server srv-https-out 127.0.0.1:11443 check port 11080 send-proxy
```

- **`send-proxy`** 옵션은 실제 클라이언트 주소가 애플리케이션에 닿게 합니다.
  이것이 없으면 모든 요청이 127.0.0.1에서 온 것처럼 보이고, 로그인 시도
  제한이 더 이상 주소별로 작동하지 않습니다.
- **`check port 11080`** 설정은 상태 확인이 TLS 포트가 아니라 평문 HTTP 포트를
  두드리게 합니다. TLS 포트를 향한 TCP 확인은 연결했다가 핸드셰이크 없이
  끊고, 애플리케이션 자신의 HAProxy는 그것을 하나하나 SSL 핸드셰이크
  실패로 기록합니다. 2초마다 한 줄씩, 끝없이. 두 포트는 한 프로세스에
  속하므로, 하나가 응답하면 다른 하나도 있다는 뜻입니다.
  `check-send-proxy`는 추가하지 마세요. 11080은 PROXY 프로토콜을 받지
  않습니다.
- **`option ssl-hello-chk`는 쓰지 않습니다.** 그 ClientHello는 TLS 1.2보다
  오래된 것이라, TLS 1.2를 요구하는 백엔드(이 애플리케이션도, 최신 Apache나
  nginx도 그렇습니다)는 확인에 실패해 영원히 다운으로 표시됩니다. 증상은
  완벽하게 돌아가는 서비스에서 나오는 503입니다. 평범한 `check`만으로도
  포트가 응답하는지는 이미 확인됩니다.

## 로그인

`https://your-server/`를 열고, 설치 프로그램에 준 이메일 주소와 설치
프로그램이 생성한 비밀번호로 로그인하세요. 비밀번호가 없다면 다음을
실행하세요.

```bash
cat /opt/boa/logs/install.log
```

그 파일은 설치 로그 전체이고 끝부분에 인증 정보가 있으며, 로그인 페이지는
바로 이런 순간을 위해 그 파일을 알려 줍니다.

**로그아웃**을 누르면 화면 가운데에 확인 창이 열립니다. 세션을 끝내려면
확인하고, 로그인 상태를 유지하려면 **취소**를 고르거나 Esc 키를 누르세요.

계정은 하나뿐입니다. 비밀번호는 **설정 → 계정**에서 바꿉니다. 바꿀 때는
현재 비밀번호도 묻습니다. 그래야 열린 브라우저를 발견한 누군가가 아니라
당신이 바꾸는 것이 됩니다. 또한 다른 모든 기기의 다른 모든 세션을
한꺼번에 끝냅니다. 다른 누군가가 비밀번호를 알고 있다고 생각될 때
비밀번호를 바꾸는 이유가 바로 그것입니다.

업데이트 후 처음 애플리케이션을 열면 다시 로그인하라고 합니다. 업데이트
이전의 세션에는 언제 허가되었는지에 대한 기록이 없고, “알 수 없음”에 대한
답은 다시 묻는 것이기 때문입니다.

같은 주소에서 열 번 실패하면 15분 동안 로그인이 닫히며, 올바른 비밀번호도
예외가 아닙니다. 그 15분 동안 모든 주소를 합쳐 100번 실패하면, 횟수가 줄어들 때까지 모두에게 닫힙니다. 주소는 서버의 어떤 프로그램이든 쓸 수 있는 헤더에서 오므로, 주소별 제한만으로는 주소를 바꿔서 피할 수 있기 때문입니다.

### 터미널에서 비밀번호 재설정

설치, 재설치 및 업데이트는 `/usr/local/bin/boa`를 설치합니다. 서버 터미널에서 웹 계정을 재설정하려면 `root`로 실행하세요.

```bash
boa passwd
```

새 비밀번호를 화면에 표시하지 않고 두 번 입력받습니다. 최소 8자가 필요합니다. 이메일은 유지되고 기존 세션은 모두 즉시 취소됩니다. 이전 비밀번호나 서비스 재시작은 필요하지 않습니다.

`/opt/boa/logs/install.log`에 `administrator_password_changed`라는 JSON 기록을 추가하며 UTC 날짜, 이메일 및 읽을 수 있는 새 비밀번호를 담습니다. 이전 로그는 보존됩니다. 파일은 `root:root 0600`을 유지하고 없으면 다시 만듭니다. 로그인 정보를 복구할 때는 마지막 해당 기록을 확인하세요.

자동화에서는 `boa passwd --password-stdin`으로 표준 입력에서 최대 64 KiB의 UTF-8 한 줄을 읽습니다. 비밀번호는 명령행 인수나 성공 출력에 나타나지 않습니다.

## 첫 실행

1. 이메일과 생성된 비밀번호로 로그인합니다.
2. 에이전트가 클라우드 공급자를 쓸 예정이라면, 먼저 **설정 → API 키**에 그
   키를 저장하세요. 공급자 목록에는 키가 있는 클라우드 공급자만 나옵니다
   ([API 키](#api-키) 참고).
3. 사이드바의 **+** 버튼을 눌러 첫 에이전트를 만듭니다.
4. 공급자와 모델을 고릅니다. 같은 기기의 Ollama라면 기본값이 이미 맞습니다.
   이 에이전트 하나만 다른 계정으로 청구되게 하려면 자기 키를 주세요
   ([에이전트에 모델 지정하기](#에이전트에-모델-지정하기) 참고).
5. 시스템 프롬프트를 씁니다. 무엇을 위한 에이전트인지, 그리고 “완료”가
   무엇을 뜻하는지.
6. 필요한 도구를 줍니다. 칸반 도구부터 시작하세요.
7. **지금 실행**을 누르고 보드를 지켜봅니다.
8. 원하는 대로 동작하면 일정을 줍니다.

## 인터페이스

원형의 파란 로고에는 밝은 얼굴 패널, 어두운 바이저, 파란 눈을 가진 로봇
에이전트 셋이 검은 정장, 흰 셔츠, 어두운 넥타이 차림으로 그려져 있습니다.
허리 위만 보이며, 가운데 에이전트가 더 큽니다. 로고는 로그인 페이지,
사이드바, 브라우저 탭에 나타납니다.

왼쪽 사이드바에는 에이전트가 나열됩니다. 각각 id, 이름, 실행 횟수, 사용한
토큰 수를 보여 줍니다. 상자는 모두 높이가 같으므로 긴 이름은 말줄임표로
잘립니다. 마우스를 올리면 전체를 읽을 수 있습니다. id를 둘러싼
사각형은 에이전트가 켜져 있으면 초록색, 꺼져 있으면 빨간색 테두리를
두릅니다.

**에이전트가 일하는 동안에는 빛나는 조각이 그 초록 테두리를 따라 시계
방향으로 돕니다.** 이것은 에이전트가 바로 지금 실행 중이라는 것을 알려
줍니다. 무엇을 하는지가 아니라, 무언가를 하고 있다는 것만입니다. 채팅
메시지를 보내거나 **지금 실행**을 누르는 즉시 돌기 시작하고, 실행이 끝나면
멈춥니다. 실행이 당신에게서 왔든, 일정에서 왔든, 시각이 된 카드에서 왔든
마찬가지입니다. 테두리는 몇 초마다 확인하므로 잠깐 늦을 수 있습니다.

사이드바 맨 아래의 점 두 개는 백그라운드 서비스가 실행 중인지 보여
줍니다. 어느 하나라도 빨간색이면 에이전트는 실행되지 않습니다.
[무언가 작동하지 않을 때](#무언가-작동하지-않을-때)를 보세요.

**+** 버튼은 에이전트를 만듭니다.

## 처음부터 있는 에이전트

설치는 정확히 하나를 만듭니다.

**`manager` (agent-000)** 에이전트는 다른 에이전트들을 조율합니다. 목표를 카드로
쪼개 나눠 줍니다. 처음부터 켜져 있습니다.

일부러 그것이 전부입니다. 아무도 요청하지 않은 에이전트를 달고 오는
설치는 무언가를 끄는 일부터 시작하게 만듭니다. 그 밖의 모든 것은 **+** 버튼을
누를 때 제시되는, 템플릿 저장소의 **템플릿**이나 누군가 내보낸 `.zip`입니다.

## 새 에이전트의 출발점

**+** 버튼을 누르면 어디서 시작할지 묻습니다.

| 선택지 | 하는 일 |
|---|---|
| **빈 에이전트** | 프롬프트도, 도구도, 일정도 없습니다. 직접 쓰세요. |
| **.zip 파일에서 가져오기** | 이 설치나 다른 설치에서 **내보내기** 탭으로 내보낸 에이전트. |
| **GitHub 템플릿에서 가져오기** | 템플릿 저장소의 에이전트 중 하나를 목록에서 고릅니다. |

**빈 에이전트**가 목록 맨 위에 있습니다. 언제나 옳은 유일한 답이고, 다른
모든 선택지는 그것으로 가는 지름길이기 때문입니다.

### GitHub의 템플릿

템플릿은 별도의 저장소인
[bunch-of-aigents-templates](https://github.com/nipegun/bunch-of-aigents-templates)에
템플릿마다 폴더 하나씩 들어 있으므로, 새 템플릿은 설치를 업데이트하지
않아도 당신의 설치에 닿습니다. **GitHub 템플릿에서 가져오기**를 고르면
서버는 그 저장소를 내려받고(`.tar.gz` 하나, 5분 동안 보관) 그 안의
에이전트를 알파벳순으로 나열합니다. 각각 당신의 언어로 된 설명, 함께 오는
도구 계열, 깨어나는 빈도, 라이브러리를 켜는지 여부를 보여 줍니다. 이 설치에
없는 도구는 빠지며, 목록이 그렇다고 알려 줍니다. 확인을 통과하지 못한
템플릿은 제시되지 않고, 몇 개가 빠졌는지 한 줄로 알려 줍니다.

현재 저장소에 있는 템플릿은 다음과 같습니다.

| 템플릿 | 하는 일 |
|---|---|
| **backup-watcher** | 백업이 실행되었는지, 최근 것인지, 수상할 만큼 작지는 않은지 확인합니다. |
| **cert-watcher** | TLS 인증서가 곧 만료될 때, 아직 시간이 있을 때 경고합니다. |
| **disk-cleaner** | 무엇이 디스크를 채우고 있는지 찾아 무엇을 지워도 되는지 알려 줍니다. 제안만 하고, 절대 삭제하지 않습니다. |
| **kanban-watcher** | 평일 아침마다 보드를 읽고 짧은 요약 하나를 씁니다. |
| **log-watcher** | 지정한 로그를 읽고, 새로 생긴 것이나 새로 잦아진 것을 보고합니다. |
| **mail-watcher** | 메일함을 지켜보며, 프롬프트에 적어 둔 규칙에 따라 도착한 메일을 처리합니다. |
| **news-watcher** | 프롬프트에 나열한 RSS 피드를 읽고, 규칙에 맞는 것을 보고합니다. |
| **os-watcher** | 이 기기를 지켜봅니다. 디스크, 메모리, 스왑, 부하, 그리고 서비스가 살아 있는지. |
| **rag-consultant** | RAG 라이브러리의 문서를 근거로 질문에 답하며, 각 주장의 근거가 된 구절을 인용하고, 문서가 다루지 않는 내용이면 그렇다고 말합니다. |
| **site-watcher** | 나열한 사이트가 응답하는지, 빠르게 응답하는지, 예전과 같은 내용을 여전히 말하는지 확인합니다. |
| **web-navigator** | 자기 브라우저를 조작해 사이트에서 요청한 일을 합니다. 검색하고, 로그인하고, 양식을 채우고, 클릭해 나아간 뒤, 찾은 것을 보고합니다. |

`web-navigator`와 `rag-consultant`에는 일정이 없습니다. 요청할 때 일하며,
요청이 곧 작업입니다. `web-navigator`는 또한 브라우저가 무엇을 위해
설치되어 있는지 보여 주는 에이전트입니다. 다른 에이전트들이 페이지를
읽는 데서 그칠 때, 이 에이전트는 로그인하고, 클릭하고, 양식을 채웁니다.
비밀번호를 입력하거나, 무언가를 사거나, 보내기 버튼을 누르지는 않습니다.
그 단계까지 가서 멈추고, 어느 버튼을 누르면 일이 끝나는지 말해 줍니다.

`rag-consultant`는 자기 문서 라이브러리를 근거로 답하며, 그 라이브러리를
켠 채로 오는 유일한 템플릿입니다. 라이브러리가 꺼져 있는 동안에는 그
도구들이 주어지지 않습니다. 쓸모가 있으려면 먼저 그 **RAG** 탭에서 문서를
올리고([로컬 문서 라이브러리](#로컬-문서-라이브러리-rag) 참고) 모델을
고르세요. 답변의 각 진술은 그것이 나온 문서의 페이지로 링크되며, 문서가
다루지 않는 내용이면 빈틈을 메우는 대신 그렇다고 말합니다. 토큰
상한(실행당 40,000)이 다른 템플릿보다 높은데, 읽어 들이는 구절도 상한에
포함되기 때문입니다.

모든 템플릿은 고르기 전에 함께 오는 도구 계열과 깨어나는 빈도를 알려
줍니다. 템플릿은 프롬프트인 만큼 권한의 묶음이기도 합니다. “메일함을
지켜봅니다”라는 말만으로는 그 템플릿이 메일을 삭제할 수 있는 상태로
온다는 것을 알 수 없습니다.

모든 템플릿은 **꺼진 상태로, 모델 없이** 옵니다. 하나를 고르면 그
프롬프트, 도구, 제안된 일정을 받고, 그다음에는 당신이 공급자를 고르고
켜 주기를 기다립니다. 켜면 일정이 crontab에 들어갑니다.

템플릿은 출발점입니다. 프롬프트, 도구, 일정 등 무엇이든 바꾸세요. 그중
몇몇은 새벽 세 시에 실패하는 대신, 쓸모가 있으려면 무엇을 채워 넣어야
하는지 자기 프롬프트에 적어 둡니다.

**설정 → 에이전트**는 목록이 어느 저장소와 브랜치에서 오는지 보여 줍니다.
기본값은 프로젝트 자체의 저장소이며, 포크나 같은 구조를 가진 당신만의
저장소를 쓸 수도 있습니다. GitHub에 접속할 수 없는 기기는
`archive/refs/heads/<branch>.tar.gz`가 있는 `file://` 경로를 쓸 수
있으며, 이는 설치 프로그램이 받아들이는 것과 같은 구조입니다. 저장소에
접속할 수 없으면 목록이 어느 주소가 실패했는지 알려 주며, `.zip`
가져오기는 계속 동작합니다. 리디렉션은 `https://` 주소로만 따라가고, 다른 서버로는 공개 서버일 때만 따라갑니다. 따라서 저장소가 서버를 여러분의 네트워크에 있는 머신으로 보낼 수 없습니다. 저장소 아카이브에는 최대 20,000개의 파일이 들어갈 수 있고, 풀었을 때 최대 256 MiB입니다.

### .zip 가져오기

1. `.zip`을 고릅니다. 조각으로 나뉘어 퍼센트와 함께 업로드되므로, 수백
   MiB의 라이브러리도 무사히 도착합니다.
2. 서버는 다른 무엇보다 먼저 패키지 전체를 확인합니다. 그 안의 어떤 것도
   에이전트의 홈 밖을 가리키는 경로, `.ssh`나 `.bashrc` 같은 숨김 파일,
   채팅이나 실행 기록, 명령을 담은 일정이어서는 안 됩니다. 무언가
   잘못되었으면 무엇이 잘못되었는지 알려 주고, 아무것도 만들지 않습니다.
3. 무엇을 가져올지 보여 줍니다. 설명, 도구(그리고 이 설치에 없는 도구),
   일정, 그리고 메모리, 홈 파일, 라이브러리 문서, 모델을 포함하는지.
   확인하고 이름을 주세요.
4. 백그라운드에서 설치되며, 진행 상황이 화면에 표시됩니다. 라이브러리
   문서는 하나씩 업로드되어 여기서 다시 색인됩니다. 중간에 무언가
   실패하면, 에이전트는 반쯤 설치된 채 남는 대신 다시 삭제됩니다.

폴더를 포함해 24,016개가 넘는 항목을 나열하는 `.zip`은 내용을 읽기 전에 거부됩니다. 그보다 많이 담을 수 있는 에이전트는 없습니다. 64 MiB를 넘은 뒤 크기의 200배를 넘게 풀리거나, 항목이 파일에 있는 것보다 많은 데이터를 주장하는 `.zip`도 거부됩니다.

가져온 에이전트도 **꺼진 상태로** 옵니다. 공급자를 지정하고 있다면 그
키는 이 설치에서 설정해야 합니다. 키는 결코 `.zip`에 담겨 오지 않습니다. 일정도 함께 기다립니다. **Cron** 탭에 표시되고, 처음 켤 때 crontab에 들어갑니다. 패키지의 일정은 5분에 한 번보다 자주 실행될 수 없고, 합쳐서 하루 288번을 넘을 수도 없습니다.

아예 묻지 않기를 원한다면 **설정 → 인터페이스**에서 **새 에이전트를
무엇으로 시작할지 묻기**를 끄세요. 그러면 **+** 버튼은 바로 빈 에이전트로
갑니다.

### 어떤 에이전트도 root가 아닙니다

오케스트레이터를 포함해 단 하나도 없습니다. 그것이 격리 모델의 전부이며,
`os-watcher` 같은 에이전트가 무엇을 할 수 있는지를 결정하므로 분명히 해
둘 가치가 있습니다.

- **보는 데는 권한이 필요 없습니다.** `df`, `free`, `uptime`, `nproc`,
  `systemctl is-active`는 모두 일반 사용자로 동작합니다. 에이전트는
  디스크가 가득 차기 훨씬 전에 차오르는 것을 볼 수 있습니다.
- **고치는 데는 대개 권한이 필요하고, 에이전트에게는 그것이 없습니다.**
  프롬프트는 시도했다가 실패하는 대신 무엇을 실행할지 정확히 말하라고
  지시합니다. “root 필요: journalctl --vacuum-size=200M을 실행하면 약
  1.2G를 확보할 수 있음”이라고 적힌 카드가 실패한 시도보다 가치
  있습니다.

무언가를 자동으로 고치고 싶다면 그 명령을 root 자신의 crontab에 넣으세요.
새벽 세 시에 에이전트가 스스로 root로 파일을 삭제하기로 결정하는 것은
누구도 원하지 않는 기능입니다.

## 첫 에이전트 만들기

**+** 버튼을 누르고, 빈 에이전트나 `.zip` 또는 템플릿을 고른 뒤 이름을 주세요.
그러면 서버에 다음이 만들어집니다.

- Linux 사용자 `agent-001`,
- 모드 0700인 홈 `/opt/boa/agents/001/`,
- 그 안의 `info.json`, `system-prompt.md`, API 토큰.

id는 비어 있는 가장 작은 번호입니다. `000`은 오케스트레이터용으로 예약되어
있습니다.

새 에이전트는 칸반 도구만 가지고, 보수적인 상한과 함께 시작합니다. 일정이
없으므로, 일정을 주거나 **지금 실행**을 누를 때까지 아무것도 하지
않습니다.

## 에이전트와 대화하기

사이드바에서 에이전트를 클릭하면 그 채팅이 나옵니다. 시킬 일을 입력하고
Enter를 누르세요. Shift+Enter는 줄을 바꿉니다.

입력하는 상자는 페이지 맨 아래 상태 표시줄 바로 위에 고정되어 있습니다.
그 위의 대화만 스크롤되므로 상자가 가려지는 일이 없고, 상자에 닿으려고
아래로 스크롤할 필요도 없습니다. 비어 있는 동안에는 Enter가 어떻게
동작하는지, 또는 에이전트가 아직 일하고 있다는 것을 회색으로 알려 주며,
좁은 휴대폰에서는 그 안내가 잘리지 않도록 한두 줄 늘어납니다.

메시지 하나가 실행 하나입니다. 에이전트는 도구를 쓰고, 일을 하고, 끝나면
답합니다. 몇 분이 걸릴 수 있으므로 에이전트가 일하는 동안 입력란은
비활성화되고, 답은 도착하면 나타납니다. 각 답에는 비용이 토큰과 단계로
표시됩니다.

답은 markdown으로 렌더링됩니다(제목, 표, 목록, 인용, 코드 블록). 모델이
그렇게 쓰기 때문입니다. 당신의 메시지는 입력한 그대로 보입니다. 링크는
http나 https를 가리킬 때만 링크가 되고, 그 밖의 것은 원래의 텍스트로
남습니다.

대화는 기억됩니다. 메시지마다 마지막 열 번의 주고받음이 모델에게 다시
전달되므로 에이전트는 무슨 이야기를 하고 있었는지 압니다. 그래서 긴
대화는 짧은 대화보다 메시지당 비용이 더 듭니다. **대화 비우기**는
처음부터 다시 시작합니다.

에이전트와의 대화는 하루 실행 상한에 **포함되지 않습니다**. 그 상한은
아무도 지켜보지 않는 일정을 멈추려고 있는 것이지, 당신이 입력하는 것을
막으려고 있는 것이 아닙니다. 토큰, 단계, 시간에 대한 실행당 상한은
적용됩니다.

에이전트마다 자기 홈 디렉터리에 저장된 자기 대화가 있으며, 어떤
에이전트도 당신이 다른 에이전트에게 한 말을 읽을 수 없습니다.

대화는 당신이 입력한 것만이 아닙니다. 에이전트의 카드 중 하나가 시각이
되면, 실행이 시작되는 순간 그 카드가 같은 채팅에 올라오고, 실행의 답이 그
아래에 나타납니다. 그래서 에이전트를 열면 당신이든 다른 에이전트든 그에게
시킨 모든 일과 그에 대해 한 일이 보입니다.
[카드가 실행될 때](#카드가-실행될-때)를 보세요.

### API Calls

에이전트의 이름은 채팅 탭과 API Calls 탭 위에 나타납니다. 기본적으로는
**채팅**만 보입니다. 다른 탭을 표시하려면 에이전트의 렌치를 열고,
**인터페이스**를 선택하고, **API Calls 탭 표시**를 켠 다음 **저장**을
누르세요. 이 선택은 서버에 이 에이전트용으로 저장됩니다. 에이전트를
열거나 다시 불러오면, API Calls가 켜져 있어도 항상 채팅에서 시작합니다.

**API Calls**는 전체 프롬프트, 대화, 도구 정의와 결과가 포함된 전송 JSON을 표시합니다. 요청을 펼쳐야 로드하며 처음에는 모두 접혀 있습니다. 실패한 시도, SDK 재시도와 대체 모델 호출도 기록합니다. 요청당 보기 한도는 2 MiB이며 더 큰 본문은 디스크에 남습니다. 큰 JSON은 숫자 값을 보존하는 일반 텍스트로 표시됩니다.

최근 100개의 완전한 요청은 대화와 따로 보관됩니다. 채팅을 비워도 지워지지
않습니다. 기록은 이 버전부터 시작하며, 그 이전의 요청은 복원할 수
없습니다. 인증 헤더는 기록하지 않습니다.

## 에이전트 설정

제목에는 선택한 에이전트의 id와 함께 **에이전트 001 설정**이 표시됩니다.
**지금 실행**은 채팅과 API Calls가 있는 작업 공간에만 나타납니다.
에이전트를 삭제하려면 **일반 → 에이전트 삭제**를 열고 대화 상자에서 그
이름을 확인하세요. 삭제는 신원 아래의 별도 섹션입니다.


채팅은 에이전트를 클릭하면 나오는 것입니다. 그 밖의 모든 것(모델, 도구,
상한, 시스템 프롬프트, 일정)은 사이드바의 에이전트 상자 오른쪽에 있는
**렌치** 뒤에 있습니다.

## 에이전트 내보내기

에이전트 설정의 마지막 탭인 **내보내기**는 에이전트를 `.zip`으로
내려받으며, 이 파일은 이 설치나 다른 설치에서 **+ → .zip 파일에서
가져오기**로 설치할 수 있습니다. 설정, 시스템 프롬프트, 일정은 항상
들어갑니다. 네 가지는 체크했을 때만 들어가며, 각 상자는 무엇이 추가될지
미리 알려 줍니다.

| 옵션 | 추가되는 것 |
|---|---|
| **메모리** | `memory.md`, 그리고 몇 글자인지 |
| **제공자와 모델** | 어떤 공급자와 모델을 쓰는지. 키는 절대 포함하지 않습니다 |
| **라이브러리 문서** | 라이브러리의 원본과 그 정보(제목, 연도...). 가져오는 곳에서 다시 색인됩니다 |
| **홈 폴더의 파일** | 스크립트, `samba` 폴더, 그 밖에 홈에 두는 모든 것. 공유하고 싶지 않은 내용이 있을 수 있으므로, 내려받기 전에 파일 목록을 보여 줍니다 |

무엇을 체크하든 절대 들어가지 않는 것도 있습니다. API 키, 에이전트 자신의
토큰, 채널 인증 정보, 채팅, 실행 기록, 브라우저 세션, 홈의 숨김 파일.
crontab에서는 에이전트를 실행하는 일정만 옮겨 가며, 누군가 거기에 입력한
다른 명령은 옮겨 가지 않습니다. 명령을 담은 `.zip`은 그것을 가져온
기기에서 그 명령을 실행하게 될 것이기 때문입니다. 에이전트 자신의 키가 들어 있는 `keys/` 폴더는 홈 파일 목록에도 표시되지 않으며, `keys/` 폴더가 든 `.zip`은 가져올 때 거부됩니다.

## Samba 공유 폴더

에이전트마다 홈에 `samba/` 폴더가 있으며, 그 Linux 사용자 이름으로 자동으로
공유됩니다. 예를 들어 공유 **agent-001**은 `/opt/boa/agents/001/samba/`만
가리킵니다. 일반 탭에서 에이전트 이름을 바꿔도 공유 이름은 바뀌지 않습니다.
홈의 나머지 부분과 보호된 설정은 공유되지 않습니다.

1. 에이전트의 **렌치 → Samba**를 엽니다.
2. 8자 이상의 **새 Samba 비밀번호**를 입력하고, 권한을 고른 뒤 **저장**을 누릅니다.
3. 탭에 표시된 Windows 주소나 SMB 주소(Windows에서는 `\\server\agent-001`, Linux와 macOS에서는 `smb://server/agent-001`)를 열고, 표시된 사용자 이름과 그 비밀번호로 로그인합니다.

공유는 켜진 상태로, 서버의 공유 목록에 보이고, 읽기/쓰기 접근으로 설정되어
시작하며, 게스트 접근은 꺼져 있습니다. 처음으로 인증된 연결을 하기 전에 이
탭에서 비밀번호를 설정하세요. 이후 저장할 때 비밀번호 칸을 비워 두면 기존
비밀번호가 유지됩니다. Samba 인증 정보는 Linux 로그인 인증 정보와
별개이며, 그것을 설정해도 에이전트의 Linux 계정이 열리지는 않습니다.

| 설정 | 효과 |
|---|---|
| 이 폴더 공유 | 파일을 삭제하지 않고 이 리소스를 켜거나 끕니다 |
| 인증 | 기본은 에이전트 사용자 이름/비밀번호. 게스트 접근은 명시적으로 고를 때만 |
| 권한 | SMB를 통한 읽기 전용 또는 읽기/쓰기. 에이전트는 여전히 자기 로컬 파일로 작업할 수 있습니다 |
| 표시 여부와 설명 | 서버의 공유 목록에 나타나는지 여부와 그 설명 |
| 새 파일/폴더 권한 | 8진수 Unix 모드, 처음에는 `0600` / `0700`. 기존 파일은 자기 모드를 유지합니다 |

공유 이름과 경로는 고정되어 있습니다. 폴더는 그 Linux 소유자만의 것으로
남습니다. 바뀐 접근 설정을 저장하면 이 공유의 기존 연결이 닫히므로,
클라이언트는 새 권한으로 다시 연결합니다. 다른 에이전트의 공유는 그대로
유지됩니다. 비밀번호 자체는 API가 돌려주지도, `info.json`에 저장되지도
않습니다.

`--update`는 `agent-000`을 포함한 기존 에이전트에 Samba 폴더와 공유를
추가합니다. 에이전트를 삭제하면
홈과 함께 그 공유와 Samba 계정도 제거됩니다. `--backup` / `--restore`는
공유된 데이터, 설정, Samba 비밀번호, 계정 신원을 보존합니다.
복원은 저장된 웹 포트 모드를 확인하며, 443에서 직접 서비스하는 설치도 포함됩니다.

Samba는 웹 프록시와 별개로 TCP **445**를 씁니다. Docker에서는 이 포트를
명시적으로 게시해야 합니다. BoA는 자체 `boa-samba` 서비스를 실행하며, 그
설정과 비밀번호 데이터베이스는 `/opt/boa/samba/` 아래에 따로 있습니다.
다른 Samba 서버의 설정을 덮어쓰거나 가로채지 않으며, 설치 프로그램은
자신이 관리하지 않는 기존 Samba 설치를 넘겨받기를 거부합니다.

서버가 듣고 있는 주소입니다. 기본값은 이 기기의 통상적인 포트로, 모델이
애플리케이션 옆에서 실행될 때 맞는 값입니다. 클라우드 공급자를 고르면
상자가 사라집니다. 그 주소는 고정되어 있고 이 설치가 이미 알고 있으며,
거기에 상자가 있어 봐야 오타 하나로 잘 돌아가는 에이전트를 망가뜨릴 수
있게 할 뿐이기 때문입니다. 예비 모델도 똑같이 동작합니다.

클라우드 공급자라면 가장 간단한 길은 설정의 **API 키** 탭이며, 그 공급자를 쓰는 모든 에이전트가 그 키를 씁니다. 이 에이전트 하나에만 다른 키를 주려면, root로 그 에이전트 자신의 홈에 키를 쓰세요.

```bash
mkdir -p /opt/boa/agents/001/keys
echo "sk-..." > /opt/boa/agents/001/keys/anthropic.key
chown -R agent-001:agent-001 /opt/boa/agents/001/keys
chmod 700 /opt/boa/agents/001/keys
chmod 600 /opt/boa/agents/001/keys/anthropic.key
```

파일 이름이 공급자 이름입니다. 각 에이전트는 자기 키만 읽으므로, 한
에이전트가 다른 에이전트의 예산을 쓸 수 없습니다.

### API 키

설정에는 **API 키** 탭이 있습니다. 클라우드 공급자마다 키 하나이며, 그
공급자를 쓰는 모든 에이전트가 함께 씁니다. 자체 운영 공급자는 키가 필요
없으므로 나열되지 않습니다.

키는 `/opt/boa/config/apikeys/<provider>.key`에 저장됩니다. 디렉터리는
`0700`, 파일은 `0600`이며 둘 다 웹 사용자의 소유이므로, 어떤 에이전트도
그중 어느 것도 읽을 수 없습니다. 다른 공급자의 키도, 자기 키도
마찬가지입니다. 에이전트가 실행되면 에이전트 API는 **그 에이전트에 설정된
공급자의 키만, 다른 것은 주지 않고** 건넵니다. Ollama를 쓰는 에이전트는
Anthropic 키를 요청할 수 없습니다.

이 디렉터리의 이름이 바뀌기 전에 만든 설치는 키를 `/opt/boa/config/keys/`에
두고 있습니다. `--update`가 그것들을 옮기고 이전 디렉터리를 제거합니다.

이것이 무엇을 보호하고 무엇을 보호하지 않는지 분명히 해 둘 가치가
있습니다. 유료 공급자를 정당하게 쓰는 에이전트는 실행하는 동안 그 키를
쥐고 있습니다. 호출하려면 필요하기 때문이며, `bash.run`을 가진
에이전트라면 그것을 출력할 수도 있습니다. 공유 저장소가 막는 것은 한
에이전트가 자신이 쓰지 않는 공급자의 키를 모으는 일입니다. 또한 모든 키를
에이전트 홈 디렉터리 밖에 둡니다. 그곳에 있으면 엉뚱한 곳으로 간 백업
하나만으로 모든 키가 한꺼번에 노출될 것입니다.

한 에이전트를 다른 계정으로 청구되게 하려면 그 에이전트 자신의 홈의
`keys/<provider>.key`에 키를 두세요. 그 키가 공유 키보다 우선합니다.

## 시스템 프롬프트 작성하기

시스템 프롬프트가 곧 에이전트입니다. 에이전트의 홈에 `system-prompt.md`로
저장되며, 인터페이스에서 편집합니다.

효과가 있는 것:

- **에이전트가 무엇을 위한 것인지 말하세요.** 한두 문장으로.
- **“완료”가 무엇을 뜻하는지 말하세요.** 완료의 정의가 없는 에이전트는
  너무 일찍 멈추거나 결코 멈추지 않습니다.
- **막혔을 때 무엇을 할지 말하세요.** 이것이 없으면 모델은 장애물을
  우회할 방법을 지어냅니다. “할 수 없으면 보드에 그렇게 적고 멈춰라”면
  충분합니다.
- **먼저 보드를 읽으라고 하세요.** 실행과 실행 사이에 에이전트가 가진
  유일한 기억입니다.

효과가 없는 것: 어떤 도구를 쓰지 말라고 말하는 것. 도구를 쓰지 않기를
원한다면 그 도구를 주지 마세요. 프롬프트는 제안이고, 도구 목록은
강제됩니다.

## 에이전트가 기억하는 것

에이전트마다 홈 디렉터리에 `memory.md`가 있으며, 그 파일이 한 실행에서 다음
실행으로 가져가는 유일한 것입니다. 간직할 만한 것을 배우면
`memory.append`로 거기에 쓰고, `memory.replace`로 정리합니다.

파일 전체가 실행이 시작될 때마다 불러와지며, 그것이 메모리를 쓸모 있게
하는 동시에 비용이 들게 합니다. 모델을 호출할 때마다 모든 글자에 비용이
듭니다. **에이전트 설정 → 메모리 → 메모리 한도(글자 수)** 칸에서 1,000자부터
1,000,000자까지 한도를 고르세요. 기본값은 기존 에이전트를 포함해
8,000자입니다. 메모리가 한도의 75%를 넘으면 에이전트에게 정리하라고
요청합니다.

카운터는 공백과 줄바꿈을 포함한 현재 글자 수와 선택한 한도를 보여 줍니다.
한 번의 저장으로 한도를 올리면서 더 큰 메모리를 붙여 넣을 수 있습니다.
텍스트가 선택한 한도를 넘으면 그 설정 요청의 어떤 것도 저장되지 않습니다.
텍스트를 줄이거나 한도를 올리세요. 이전 메모리는 그대로 남으며, 새로 쓸 때
`[truncated]`가 붙는 일은 결코 없습니다. 예전에 잘려 나간 텍스트는
원본에서 다시 붙여 넣어야 합니다. 메모리 전체는 여전히 프롬프트, 대화,
도구와 함께 선택한 모델의 컨텍스트에 들어가야 합니다.

간직하기 좋은 것: 무엇이 어디 있는지, 어떤 명령이 결국 무엇이었는지,
당신이 무엇을 선호하는지. 무엇을 했는지 적는 일기는 아닙니다. 그것은
보드의 몫입니다.

에이전트 설정의 **메모리**에서 직접 읽고 고칠 수 있습니다. 에이전트가
잘못된 사실을 계속 근거로 삼고 있다면 손으로 고칠 가치가 있습니다.

## 로컬 문서 라이브러리 (RAG)

에이전트마다 `/opt/boa/agents/<id>/rag/` 아래에 자기 라이브러리가 있습니다.
PDF, EPUB, UTF-8 TXT, Markdown 파일을 지원합니다. 설치 프로그램은 로컬
벡터화 모델(다른 모델을 고르지 않았다면 EmbeddingGemma 300M Q8, 약 318 MiB.
[벡터화 모델 고르기](#벡터화-모델-고르기) 참고)과
그 llama.cpp 엔진, 그리고 OCR을 준비합니다.
텍스트 추출, OCR, 문서 벡터화, 질문 벡터화는 이 서버에서 실행됩니다.
검색된 구절은 에이전트가 선택한 답변 공급자에게 보내지며, 설정되어 있다면
클라우드 공급자도 포함됩니다. 외부 벡터화 엔드포인트는 쓸 수 없습니다.
설치, 업데이트, 문서 가져오기, OCR, 백업/복원은 재부팅 후 서비스 시작까지
포함해 Debian 13과 Alpine 3.24에서 확인했습니다.

1. **설정 → RAG**를 열고 로컬 엔진이 준비되었는지 확인합니다.
2. 에이전트의 **RAG** 탭을 열고, 검색을 켠 뒤 에이전트를 저장합니다.
   **rag-consultant** 템플릿은 검색이 이미 켜진 상태로 옵니다.
3. 파일을 고르고 **문서 업로드**를 클릭합니다. 큰 파일은 조각으로 나뉘어
   전송됩니다. 또는 완성된 파일을 `rag/inbox/`에 복사하고 **rag/inbox 파일
   가져오기**를 클릭하세요. 가져온 원본은 관리되는 문서 저장소로 옮겨집니다.
4. **준비됨**이 될 때까지 기다립니다. 텍스트 추출과 벡터화는 백그라운드에서
   실행되며, 준비된 다른 문서는 계속 검색할 수 있습니다. 페이지에 진행
   상황과 오류가 표시됩니다.
5. **라이브러리 검색**으로 질문을 시험하거나, 평소의 채팅에서 에이전트에게
   물어보세요. 인용은 원본 PDF 페이지나 원본 EPUB/문서로 링크됩니다.

`rag/inbox/`에서 가져올 때의 오류는 문서 목록 위에 나타납니다. 실패한
원본은 고칠 수 있도록 inbox에 남습니다. 색인은 정해진 크기의 묶음 단위로
처리되므로, 작은 문서가 책 한 권 한 권 사이마다 스케줄러가 한 바퀴 도는
것을 기다리지 않습니다. 긴 문서도 색인기를 붙잡고 있지 않습니다. 약 90초가 지나면 이미 추출하고 임베딩한 만큼을 가지고 대기열로 돌아가고, 다음 패스가 거기서부터 이어 가므로 그사이 다른 에이전트의 라이브러리 차례가 옵니다. 색인기는 실행과 같은 2 GiB 메모리와 1024개 작업으로 동작합니다.

**문서 정보** 항목에서는 출판 연도, 제목, 부제, 저자, 버전, 언어, 태그를
이 순서로 편집합니다. 연도는 선택 사항이며 최대 네 자리까지 받습니다.
부제가 있으면 문서 목록에서 제목 바로 아래에 표시됩니다. 부제, 연도, 저자,
버전, 언어는 에이전트가 검색하는 모든 구절과 함께 전달되므로, 에이전트는
제목이 같은 문서를 구별하고, 인용하는 내용의 시점과 출처를 밝히고, 서로
어긋나는 판을 구별할 수 있습니다. 파일을 교체해도 새 파일의 색인이 끝날
때까지는 이전의 검색 가능한
문서가 유지됩니다. 문서를 색인하는 도중에 로컬 벡터화 엔진이
멈추면(업데이트, 재시작), 그 문서는 “Local embeddings are unavailable”이라는
메시지와 함께 **대기 중**으로 돌아가고, 엔진이 다시 응답하면 멈춘 곳부터
이어 갑니다. 다시 색인할 것은 없습니다. 다시 색인은 문서를 새로 만들고, 취소는
남은 작업을 멈추며, 삭제는 이후 검색에서 문서를 뺍니다. 언어와 버전
필터는 입력한 메타데이터를 씁니다. EPUB 인용은 지어낸 페이지 번호가 아니라
장(章)을 가리킵니다. 스캔한 PDF에는 서버에 OCR 언어가 설치되어 있어야
하며, 영어와 스페인어가 기본으로 설치됩니다(`eng+spa`). 지원되지 않거나
암호화된 파일은 비어 있는 색인을 성공으로 보고하는 대신 오류를 보고합니다.

**답변 모드**는 에이전트가 자기 문서 너머로 얼마나 나갈 수 있는지를
정합니다. 목록 아래의 줄이 선택한 모드가 무엇을 하는지 알려 줍니다.

- **문서 및 일반 지식**: 에이전트는 둘 다 쓸 수 있으며, 둘은 구분됩니다.
- **문서 근거 필수**: 에이전트는 답하기 전에 직접 라이브러리를 검색해야
  합니다. 검색하지 않고 내놓은 답은 한 번 에이전트에게 되돌려 보냅니다.
  실행에서 구절을 하나도 찾지 못했다면, 모델이 쓴 내용 대신 “문서
  라이브러리에 이 질문에 답할 만한 정보가 충분하지 않습니다”라는 고정된
  문장을 받습니다.
- **문서만 (검증)**: 앞의 모드와 같으며, 추가로 답변의 모든 단락과 모든
  목록 항목이 그 실행에서 검색한 구절을 인용해야 합니다. 단락마다
  확인합니다. 인용이 없거나, 검색되지 않은 구절을 인용하거나, 인용한
  구절과 의미가 동떨어지면(로컬 벡터화 엔진으로 측정) 그런 단락의 목록과
  함께 답을 한 번 되돌려 보냅니다. 그 뒤에도 뒷받침되지 않는 것은
  삭제되고, 마지막 줄에 몇 단락이 빠졌는지 적힙니다. 뒷받침되는 것이 하나도
  남지 않으면 고정된 문장을 받습니다. 확인을 위해 엔진에 닿을 수 없으면,
  확인되지 않은 답을 보여 주는 대신 답을 보류합니다.

검증 모드가 할 수 없는 것은, 인용된 단락이 그 구절과 정확히 같은 말을
한다는 것을 증명하는 일입니다. 우리의 측정에서 구절과 모순되는 단락이나 같은
주제로 무언가를 덧붙이는 단락은 충실한 단락과 비슷한 점수를 받았습니다.
이 확인이 잡아내는 것은 다른 내용의 구절을 인용하는 단락과, 출처가 아예 없는
단락입니다. 어느 쪽으로도 정확하지는 않습니다. 우리의 테스트에서 충실한
단락 100개 중 약 6개를 삭제했고(대부분 비교할 거리가 적은 짧은 목록 항목과
한 줄 요약이었습니다), 다른 주제의 구절을 가리키는 인용은 100개 중 1개
미만을 통과시켰습니다. 코드 예시는 그것을 소개하는 문장과 함께 판단합니다.
정확성이 중요할 때는 인용된 구절을 검토하세요. 고정된 문장은
**설정 → 에이전트 → 에이전트가 답하는 언어**에서 고른 언어로 쓰이며, 고른
언어가 없으면 영어로 쓰입니다.
인용은 검색된 출처 식별자로만 확인됩니다.

에이전트별 기본값: 파일당 128 MiB, 원본 문서 2,048 MiB, 조각 200,000개,
결과 8개, 실행당 검색된 텍스트 최대 16,000자. 보수적인 바이트 예산이
프롬프트와 기록 옆에 들어갈 수 있는 양도 제한합니다.
**최소 유사도**는 사용 중인 벡터화 모델에서 측정한 값(EmbeddingGemma는
0.20, Qwen3-Embedding은 0.35)에서 시작하며, 칸 아래의 줄이 그 값이 무엇인지
알려 줍니다. 이것은 확률이 아니라 검색 점수이며, 모델마다 척도가 다릅니다.
의미 검색 결과가 너무 넓으면 올리세요.
문자 그대로 일치하는 결과도 함께 반영됩니다.
API는 그 밖에 조각 할당량과 조각의 토큰 크기도 제공합니다.

전역 설정은 벡터화 스레드, 동시 색인 작업, 기본 OCR 언어를 제어합니다.
**동시 색인 작업 수**는 몇 개 에이전트의 라이브러리를 동시에 색인하는지를
뜻합니다(에이전트당 작업 하나, 그 문서는 하나씩 차례로). 작업마다 최대 4GB의
RAM을 쓸 수 있으며, 레이블이 그것을 상기시켜 줍니다. 한 에이전트의
라이브러리를 빠르게 하지는 않습니다. 벡터화 엔진은 한 번에 요청 하나에만
답하기 때문입니다. 더 빨리 벡터화하려면 대신 **벡터화 CPU 스레드 수**를
올리세요. 모델은 공유되고, 라이브러리와 권한은 에이전트별입니다.
처리는 재시작 후에 이어지며, 완료된 문서와
중단된 작업에서 다시 쓸 수 있는 조각은 유지됩니다. 다시 색인에 실패하면
마지막으로 공개된 버전이 유지됩니다. 다운로드가 필요한 것은 모델 설치뿐이며,
평소의 검색은 인터넷 없이도 실행할 수 있습니다. 로컬 엔진을 쓸 수 없으면
그렇다고 보고하며, 결코 외부 벡터화 서비스로 대체하지 않습니다.

`boa-embeddings`는 Unix 소켓으로 모델을 서비스하고, `boa-rag`는 대기열을
관리합니다. 둘 다 systemd 유닛과 OpenRC 유닛이 있으며 시스템 설정에
나타납니다. 백업에는 문서 원본, 메타데이터, 일관된 SQLite/벡터 색인
스냅숏이 포함됩니다. 실행 설정도 포함되며, 그와 함께 선택한 벡터화 모델도
포함됩니다. 모델 바이너리와 내려받은 가중치는 포함되지 않습니다. 복원은
기기에 선택한 모델이 없으면 그것을 내려받으며, 그 다운로드가 실패하면
그렇다고 말하고 계속 진행합니다. 그 뒤 **설정 → RAG**에서 모델을 내려받거나
다른 모델을 고를 수 있습니다. 복원된 백업에서 아직 진행 중이던 업로드는
취소됩니다. 색인된 라이브러리는 일반적인 업데이트에서 살아남습니다.

### 벡터화 모델 고르기

벡터화 모델은 모든 구절과 모든 질문을, 라이브러리를 검색하는 기준이 되는
숫자로 바꿉니다. **설정 → RAG → 벡터화 모델**은 두 가지를 제공하며, 같은
모델이 모든 에이전트에 쓰입니다.

| | EmbeddingGemma 300M (Q8) | Qwen3-Embedding 0.6B (Q8) |
|---|---|---|
| 다운로드 | 318 MiB | 610 MiB |
| 실행 중 엔진의 메모리 | 약 600 MB | 약 1.1 GB |
| 색인 시간(같은 프로세서) | 1× | 약 4× |
| 라이선스 | Gemma Terms of Use | Apache 2.0 |

EmbeddingGemma가 기본값이며 어떤 기기에도 맞습니다. Qwen3-Embedding은
프로세서와 메모리에 여유가 있는 기기를 위한 것입니다. 테스트 라이브러리의
스페인어 Python 책에서, 이 모델은 책에 관한 질문(0.51-0.79)을 관계없는
질문(최대 0.21)과 EmbeddingGemma(0.35-0.67 대 0.17)보다 더 멀리 떼어
놓았고, 구절을 다시 진술하는 단락도 다른 내용의 단락과 더 멀리 떼어
놓았습니다. 프로세서 두 개짜리 테스트 기기에서 조각당 2.2초가 걸렸고,
EmbeddingGemma는 0.5초였습니다.

바꾸는 방법:

1. 목록에서 모델을 고릅니다. 그 아래에 크기, 메모리, 속도, 라이선스, 그리고
   내려받았는지 여부가 보입니다.
2. 내려받지 않았다면 **모델 다운로드**를 클릭하고 막대가 끝날 때까지
   기다립니다. 다운로드는 사용하기 전에 공개된 SHA-256과 대조해 확인합니다.
3. **저장**을 클릭하고 확인합니다. 엔진이 새 모델로 다시 시작하며, 맨 위의
   줄에 몇 초 동안 “엔진이 이 모델을 불러오는 중입니다”가 표시되었다가
   **준비됨**으로 바뀝니다.

바꾸면 일어나는 일:

- 모든 에이전트의 모든 문서가, 새로 업로드한 것처럼 색인 작업 하나에
  라이브러리 하나씩 다시 색인됩니다. 큰 라이브러리에서는 몇 시간이
  걸립니다.
- 차례가 올 때까지 문서는 라이브러리에 남아 있으며, 의미가 아니라 질문의
  단어로 찾아집니다. 그동안의 검색은 몇 개의 문서가 기다리고 있는지
  에이전트에게 알려 주므로, 구절이 빠진 것을 라이브러리가 그 질문을 다루지
  않는 것으로 오해하지 않습니다.
- 이전 모델의 권장값을 그대로 두고 있던 모든 에이전트의 **최소 유사도**는
  새 모델의 권장값으로 바뀝니다. 다른 값을 직접 설정한 에이전트는 그 값을
  유지합니다.
- 검증 모드는 사용 중인 모델로 단락과 구절을 비교하며, 그 모델에서 측정한
  임계값(EmbeddingGemma는 0.36, Qwen3-Embedding은 0.44)을 기준으로 합니다.

이전 모델의 가중치는 디스크에 남으므로 되돌아갈 때 다운로드는 필요
없습니다. 다만 다른 모델로 색인된 모든 문서를 다시 색인하기는 합니다.

## 도구 고르기

**도구**에서 이 에이전트가 쓸 수 있는 것을 체크하세요. 체크하지 않은 도구는
모델에게 보이지 않으며, 요청하더라도 서버가 거부합니다. 그 확인은
프롬프트가 아니라 서버에서 이루어집니다.

기본으로 들어 있는 도구는 다음과 같습니다.

| 도구 | 에이전트가 그것으로 할 수 있는 일 |
|---|---|
| `bash.run` | 자신의 권한 없는 사용자로 셸 명령 실행 |
| `kanban.add_card` | 공유 보드에 작업 올리기 |
| `kanban.assign_card` | 자기 카드 하나를 다른 에이전트에게 넘기기 |
| `kanban.move_card` | 자기 카드 하나를 열 사이에서 옮기기 |
| `kanban.delete_card` | 자기 카드 하나 삭제 |
| `kanban.list_cards` | 보드 읽기: 자기 카드, **manager**라면 모든 카드 |
| `channel.write` | 설정된 채널로 메시지 보내기 |
| `x.post` | X 프로필에 텍스트 게시를 요청합니다. 각 게시물은 나가기 전에 여러분이 비공개 메시지로 승인합니다 |
| `web.fetch` | 공개 웹 페이지 읽기 |
| `rss.fetch` | RSS 또는 Atom 피드를 항목 목록으로 읽기 |
| `memory.append` | 미래의 자신을 위해 무언가 적어 두기 |
| `memory.replace` | 기억하는 내용 정리 |
| `skill.read` | 받은 절차 읽기 |
| `script.write` | 자기 `scripts/` 디렉터리에 스크립트 쓰기 |
| `script.list` | 자기가 쓴 스크립트 나열 |
| `script.delete` | 자기 스크립트 하나를, 그것을 실행하던 cron 줄과 함께 삭제 |
| `cron.add` | 자기 스크립트 하나를 일정에 따라 실행하는 줄을 자기 crontab에 추가합니다. 아무것도 지우지 않습니다 |
| `cron.list` | 자기 crontab 읽기 |
| `cron.remove` | 자기 스크립트 하나를 실행하는 줄을 지웁니다. 그 밖에는 아무것도 하지 않습니다 |
| `mail.read` | 설정된 메일함의 메시지 읽기 |
| `mail.move` | 같은 계정의 다른 폴더로 메시지 정리 |
| `mail.delete` | 메시지를 계정의 휴지통으로 보내기 |
| `mail.forward` | 허용한 주소로 메시지 전달 |
| `rag.search` | 자기 문서 라이브러리 검색 |
| `rag.read` | 검색이 돌려준 조각 읽기 |
| `rag.list` | 라이브러리의 문서 나열 |
| `browser.open` | 쿠키를 유지하며 자기 브라우저로 페이지 열기 |
| `browser.read` | 열린 페이지나 그 링크 읽기 |
| `browser.click` | 그 페이지의 링크나 버튼 클릭 |
| `browser.type` | 입력란 채우기, 원하면 제출까지 |
| `browser.screenshot` | 당신을 위해 그 페이지의 그림 저장 |
| `image.send` | 웹 채팅에, 그리고 대화가 Telegram, Discord, X, Mattermost 또는 Slack에서 시작되었다면 Telegram, Discord, X, Mattermost 또는 Slack 답장에도 PNG 첨부. 이미지는 웹 메시지의 텍스트 영역을 채웁니다 |

계열마다 자기 상자가 있고, 이 에이전트가 그 계열의 도구를 몇 개 가지고
있는지 개수가 표시됩니다. “이 에이전트가 메일함을 읽어도 되는가?”는
하나의 결정이고, 상자 하나로 그려집니다. 에이전트에게 칸반 보드를 켜는
스위치는 **칸반** 상자 맨 아래, 그것이 관장하는 도구들 밑에 있습니다.

- **`bash.run`** — 그 에이전트의 사용자로 실행하는 셸 명령. root는 없고
  얻을 수도 없습니다. 에이전트가 기기에서 실제로 할 일이 있을 때 주세요.
- **`kanban.*`** — 공유 보드. 눈에 보여야 하는 에이전트에게는 적어도
  `list_cards`와 `add_card`를 주세요.
- **`channel.write`** — 당신에게 보내는 메시지. **채널** 탭에서 채널도 체크하세요.
- **`web.fetch`** — 공개 페이지만. 사설 주소와 루프백 주소는
  거부됩니다.
- **`rss.fetch`** — RSS 또는 Atom 피드를 XML 문서가 아니라 항목 목록으로.
  같은 피드를 `web.fetch`로 가져오는 것보다 훨씬 싸고, 에이전트가 파싱할
  수고도 덜어 줍니다. 둘 다 **인터넷** 아래에 있습니다.
- **`script.*`와 `cron.*`** — **자동화** 아래에 있습니다. 에이전트는 생각할
  필요 없는 반복 작업을 위해 자기 `scripts/` 디렉터리에 스크립트를 쓰고
  자기 crontab에 일정을 잡습니다. 스크립트는 혼자 돌고, 토큰을 쓰지 않으며,
  에이전트는 다음 실행 때 결과를 읽습니다. 자기 스크립트만, 5분보다 잦지
  않게 일정을 잡을 수 있으며, 자신을 깨우는 줄은 결코 건드릴 수 없습니다.

에이전트는 자기 홈 안에서는 많은 일을 할 수 있고, 그 밖에서는 아무것도 할
수 없습니다. 다른 에이전트가 존재한다는 것조차 볼 수 없으며, 하물며 그
프롬프트를 읽을 수는 없습니다. 에이전트 디렉터리는 통과할 수는 있지만
목록을 볼 수는 없고, 각 홈은 그 Linux 사용자만의 것이므로, 이것은 Python의
확인이 아니라 커널의 거부입니다.

또한 에이전트는 **자신이 무엇인지**를 다시 쓸 수 없습니다. 부여된 도구,
지출 상한, 시스템 프롬프트, API 토큰은 홈 안에 있는 root 소유의 서랍에
들어 있습니다. 에이전트는 그것들을 읽을 수 있지만 바꿀 수는 없습니다.
당신은 바꾸고, 에이전트는 바꾸지 못합니다. 에이전트가 자기 자신에 대해
편집할 수 있는 유일한 것은 메모리입니다.
- **`mail.*`** — **설정 → 메일**에서 설정한 메일함. 아래를 보세요.
- **`skill.read`** — **스킬** 패널에서 체크한 문서화된 절차. 둘 다
  필요합니다. 여기의 도구와, 거기의 스킬 최소 하나.

### 메일 도구

네 가지이며, **설정 → 메일**에서 IMAP 메일함을 설정해야 합니다. 에이전트는
그 비밀번호를 결코 보지 못합니다. 에이전트가 무엇을 하고 싶은지 말하면,
인증 정보를 쥐고 있는 에이전트 API가 그 일을 합니다.

| 도구 | 하는 일 |
|---|---|
| `mail.read` | 메시지를 읽습니다. **아무것도 읽음으로 표시하지 않으므로**, 당신의 읽지 않은 메일 수는 원래 뜻 그대로입니다. |
| `mail.move` | 메시지를 같은 계정의 다른 폴더로 정리합니다. 폴더는 이미 있어야 합니다. |
| `mail.delete` | 휴지통이 있는 계정이라면 메시지를 휴지통으로 보냅니다. |
| `mail.forward` | 메시지를 전달하되, **당신이 나열한 주소로만** 전달합니다. |

중요한 것은 마지막 것입니다. 받은편지함은 세상의 누구든 쓸 수 있는,
에이전트로 들어가는 유일한 입력이므로, `mail.forward`는 전달할 때마다
하나하나 서버가 당신의 목록과 대조해 확인합니다. 에이전트가 확인하는 것도,
프롬프트에 적힌 무언가가 확인하는 것도 아닙니다. 목록이 비어 있으면 전달은
아예 거부됩니다. 폴더 이름과 검색 텍스트는 일반적인 인쇄 가능한 텍스트로 메일 서버에 전달됩니다. 줄바꿈이나 다른 제어 문자는 그 연결에서 두 번째 명령이 되므로, 서버에 연결하기 전에 거부됩니다.

지켜보기만 하면 되는 에이전트에게는 `mail.read`만 주세요. 정리하려면
`mail.move`를 더하고, `mail.delete`와 `mail.forward`는 두 번 생각한 뒤에
주세요.

맨 아래의 **칸반** 체크박스는 이 에이전트에게서 보드를 완전히 끕니다.
체크를 해제하면 칸반 도구를 전혀 받지 못하고 카드도 더 만들지 않습니다.
하는 일이 보드에 올라갈 성격이 아닌 에이전트에게 쓰는 스위치입니다.

## 에이전트에 스킬 주기

스킬은 글로 적은 절차입니다. 여기서 어떤 일을 어떻게 하는지 단계별로 적은
것입니다. 애플리케이션에는 스킬이 하나도 들어 있지 않습니다. 스킬은 바로
이 기기(이 호스트들, 이 백업, 이 인증서)에 관한 것이므로, 범용 스킬은
아무도 따르지 않는 절차가 될 것입니다. 서버에서 root로 직접 쓰세요.

```bash
mkdir -p /opt/boa/skills/BackupVerification
nano /opt/boa/skills/BackupVerification/SKILL.md
chown -R root:root /opt/boa/skills
chmod 00755 /opt/boa/skills/BackupVerification
chmod 0644 /opt/boa/skills/BackupVerification/SKILL.md
```

파일은 두 개의 `---` 줄 사이에 이름과 한 줄 설명을 두고 시작하며, 나머지가
절차입니다.

```markdown
---
name: BackupVerification
description: How to check that last night's backups actually ran.
---

1. Read /var/log/backup.log ...
```

그러면 `/opt/boa/skills/` 아래의 디렉터리마다 에이전트의 **스킬** 패널에
체크박스로 나타납니다. 하나를 체크하고, **도구**에서 에이전트에게
`skill.read` 도구를 주고, **저장**을 누르세요. 다음 실행부터 에이전트는 그 절차가 있다는 것을 알고, 그 일이 생기면
읽을 수 있습니다.

### 시스템 프롬프트가 이미 있는데 왜 굳이

이유는 세 가지이며, 중요한 것은 세 번째입니다.

- **프롬프트는 에이전트가 무엇을 위한 것인지이고, 스킬은 일을 어떻게
  하는지입니다.** 에이전트 여섯이 절차 하나를 함께 쓸 수 있으며, 여섯 개의
  사본이 각자 따로 낡아 가지 않습니다.
- **스킬은 필요한 만큼 길어도 됩니다.** 시스템 프롬프트는 모든 실행의 모든
  호출마다 비용이 들므로 짧게 유지해야 합니다. 스킬은 그것을 읽는 실행이
  한 번만 비용을 냅니다.
- **에이전트가 혼자 배운 것은 그 에이전트와 함께 사라집니다.** 그 메모리는
  다른 어떤 에이전트도 열 수 없는 홈 안에 있습니다. 다음 에이전트도
  알았으면 하는 것을 두는 곳이 스킬입니다.

### 스킬 작성하기

인터페이스에는 일부러 이를 위한 편집기가 없습니다. 스킬의 내용은 새벽 네
시에 아무도 지켜보지 않는 가운데 실행되는 에이전트의 추론으로 곧장
들어가므로, 도구와 마찬가지로 root의 것입니다. 스킬은 서버에서 씁니다.

```bash
mkdir -p /opt/boa/skills/DatabaseBackup
nano /opt/boa/skills/DatabaseBackup/SKILL.md
```

파일은 두 줄짜리 헤더로 시작하고, 그다음에는 말해야 할 것을 무엇이든
말합니다.

```markdown
---
name: DatabaseBackup
description: How the nightly dump is taken and where it goes.
---

# Database backup

1. Dump with `mysqldump --single-transaction`, never with the table lock.
2. Write it to /srv/backups/, never to /tmp.
...
```

`description`이 가장 중요한 줄입니다. 모든 실행이 비용을 내는 유일한
부분이며, 에이전트가 나머지를 읽을지 결정할 때 근거로 삼는 것입니다.
“How the nightly dump is taken and where it goes”(야간 덤프를 어떻게 뜨고
어디에 두는지)는 이 스킬이 언제 해당되는지 알려 주지만, “Database
stuff”(데이터베이스 관련)는 그렇지 않습니다.

에이전트의 페이지를 다시 불러오면 스킬이 목록에 있습니다.

업데이트는 `/opt/boa/skills/`를 결코 건드리지 않습니다. 거기에 쓴 것은
계속 당신의 것입니다. 웹 인터페이스는 어느 에이전트가 어느 스킬을 받을지
정할 뿐, 스킬을 편집하지는 않습니다.

### 자체 파일을 가진 스킬

디렉터리 안의 다른 모든 것도 함께 따라갑니다.

```
/opt/boa/skills/DatabaseBackup/
  SKILL.md
  dump.sh
  exclude-tables.txt
```

에이전트는 그것들을 읽고 실행할 수 있으므로, 절차에 셸 마흔 줄을 늘어놓는
대신 “이 디렉터리의 `dump.sh`를 실행하라”고 쓰면 됩니다. `skill.read`는
에이전트에게 어떤 파일이 어디에 있는지 알려 줍니다.

### 비용

각 스킬의 이름과 설명만 프롬프트에 들어갑니다. 스킬마다 두 줄 정도입니다.
본문은 그것이 필요하다고 판단한 에이전트가 `skill.read`로 한 번, 그때만
가져옵니다. 에이전트에게 스킬 다섯 개를 주면 실행당 만 토큰이 아니라
이삼백 토큰이 들며, 그래서 청구서 걱정 없이 다섯 개를 줄 수 있습니다.

### 에이전트가 쓰는 스킬을 삭제하면

아무것도 깨지지 않으며, 지킬 수 없는 약속을 하는 에이전트도 남지 않습니다.

- 그 스킬을 가졌던 모든 에이전트의 **프롬프트에서 사라집니다**. 다음
  실행부터입니다. 에이전트는 읽을 수 없는 절차에 대해 듣는 일이 없습니다.
- **스킬 패널에서 사라지므로**, 아무도 다시 체크할 수 없습니다.
- 이름은 무언가가 다시 쓸 때까지 **에이전트의 `info.json`에 남으므로**,
  디렉터리를 되돌려 놓으면 다른 일을 하지 않아도 스킬이 복원됩니다.
- 그래도 에이전트가 그것을 요청하면(이전 실행에서 이름을 기억하고 있을 수
  있습니다), 그 스킬이 자기 목록에 있지만 더 이상 설치되어 있지 않다는 답을
  받고, 그 내용을 짐작하지 말라는 지시도 받습니다.

알아 둘 것 하나: **스킬이 없는 동안 그 에이전트에서 저장을 누르면 스킬이
목록에서 영영 빠집니다.** 인터페이스는 존재하는 스킬만 저장하며, 그래야
삭제된 스킬이 영원히 남아 있지 않습니다. 에이전트를 저장하기 전에
디렉터리를 되돌려 놓거나, 저장한 뒤에 스킬을 다시 체크하세요.

## 에이전트에 브라우저 주기

`web.fetch`는 공개 페이지를 읽는 것 말고는 아무것도 하지 않습니다. 로그인도,
양식도, 버튼도 없습니다. 에이전트가 사이트를 읽는 것이 아니라 *사용*해야
한다면 브라우저가 필요합니다.

브라우저는 기본으로 설치됩니다. 설치 프로그램이 한 번 묻고, 기본값은
예입니다. Chromium 약 600 MB이므로 디스크가 부족한 기기에서는 거절할 수
있으며, 나중에 어느 쪽으로든 마음을 바꿀 수 있습니다.

```bash
./install-update-reinstall-debian.sh --update --browser no    # 빼 둡니다
./install-update-reinstall-debian.sh --update --browser yes   # 다시 넣습니다
```

답은 포트와 마찬가지로 기억됩니다. 그다음 에이전트의 **도구** 패널에서
브라우저 도구를 체크하세요.

Alpine에서는 이 내용이 하나도 해당되지 않습니다. Playwright가 musl용 빌드를
내놓지 않기 때문에 그곳에는 브라우저가 아예 없습니다. 도구는 목록에 남아
있고, 에이전트가 그중 하나를 호출하면 그렇다고 알려 줍니다.

| 도구 | 에이전트가 할 수 있는 일 |
|---|---|
| `browser.open` | 페이지로 이동합니다. 쿠키는 유지됩니다 |
| `browser.read` | 열린 페이지를 다시 읽거나, 그 일부나 링크를 읽습니다 |
| `browser.click` | 보이는 글자나 선택자로 링크나 버튼을 클릭합니다 |
| `browser.type` | 입력란을 채우고, 원하면 Enter를 누릅니다 |
| `browser.screenshot` | 자기 다운로드 디렉터리에 PNG를 저장합니다 |
| `image.send` | 웹 채팅과 Telegram, Discord, X, Mattermost 또는 Slack의 답장에 PNG를 첨부합니다 |


`browser.screenshot`은 서버에 PNG를 저장합니다. 그것을 채팅에 표시하려면
에이전트가 이어서 그 경로로 `image.send`를 호출합니다. **에이전트 설정 →
도구 → 이미지**에서 **image.send**를 부여한 뒤 저장하세요.
**web-navigator**로 새로 만든 에이전트에는 이미 들어 있으며, 기존 에이전트는
현재의 부여 상태를 유지합니다.

이미지는 웹 채팅에서 메시지의 텍스트 영역을 채우며, 가로세로 비율과 전체
높이를 유지합니다. 원래 크기로 열 수도 있습니다. 대화가 Telegram, Discord, X, Mattermost 또는 Slack에서
시작되었다면 그곳에도 보내집니다. 세로로 길거나 큰 캡처는 PNG 문서로
전달됩니다. 업로드가 실패하면, 이미 도착한 텍스트나 이미지를 반복하지 않고
빠진 부분만 다시 시도합니다.

그 에이전트의 홈 안에 있는 PNG 파일만 받으며, 하나당 최대 50 MiB, 답장
하나에 16개까지입니다. 첨부 파일은 비공개로 유지되며, 보려면 로그인한
세션이 필요합니다. 이미 있는 스크린숏은 저장된 경로로 `image.send`를
쓰라고 에이전트에게 요청해 보낼 수 있습니다.

### 각 에이전트의 세션은 그 에이전트만의 것

브라우저 자체는 `/opt/boa/playwright/`에 있는 사본 하나이며, root 소유이고
다른 모두에게는 읽기 전용입니다. 공유되지 **않는** 것은 프로필입니다.

```
/opt/boa/agents/001/browser/profile/     agent-001, 0700
/opt/boa/agents/002/browser/profile/     agent-002, 0700
```

사이트에 로그인한 에이전트는 **다음 실행에서도** 로그인 상태를 유지합니다.
쿠키가 자기 디스크에 있기 때문입니다. 그리고 다른 어떤 에이전트도 로그인한
상태가 아닙니다. 그 디렉터리는 0700이고 그 Linux 사용자의 것이기
때문입니다. 커널이 거부하는 것이며, 잘못될 수 있는 Python의 확인이 있는
것이 아닙니다. 모든 에이전트가 기기 하나를 함께 쓰는 호스팅 제품은 바로 이
분리를 제공할 수 없습니다.

세션 쿠키는 다른 브라우저와 마찬가지로 여기서도 브라우저가 닫히면
끝납니다. 사이트가 유지하라고 표시한 것은 유지됩니다.

### 하지 않는 일

- **사설 주소는 안 됩니다.** `browser.open`은 `web.fetch`와 똑같이
  `192.168.*`, `127.*` 등을 거부합니다. 방금 악의적인 페이지를 읽은
  에이전트가 꾐에 넘어가 당신의 공유기를 열어서는 안 되며, 세션을 가진
  브라우저는 그런 일에 fetch보다 훨씬 좋은 도구가 될 것입니다.
- **화면이 없습니다.** 헤드리스입니다. 에이전트가 본 것을 당신이 보는
  방법은 `browser.screenshot`이며, 에이전트 자신은 그 그림을 볼 수 없습니다.
- **도구 없이는 아무것도 하지 않습니다.** 다른 모든 것과 마찬가지로,
  에이전트에게 주지 않은 도구는 호출할 수 없는 도구이며, 그 확인은
  서버에서 이루어집니다.
- **다운로드 없음.** 페이지가 시작한 다운로드는 거부되므로, 에이전트 홈에 들어가는 파일 수나 바이트 수를 페이지가 정하지 못합니다. `browser.screenshot`은 계속 이미지를 저장합니다.

브라우저가 설치된 적이 없다면 도구는 여전히 목록에 나타나며, 실행해야 할
명령을 답으로 돌려줍니다. 사라지지도, 조용히 실패하지도 않습니다.

## 지출 상한

에이전트마다 상한이 네 가지이며, 모든 실행은 먼저 닿는 상한에서 멈춥니다.

| 상한 | 기본값 | 무엇을 막는지 |
|---|---|---|
| 실행당 토큰 수 | 16384 | 비싼 대화 하나 |
| 실행당 단계 수 | 25 | 도구를 끝없이 부르는 루프 |
| 실행당 초 | 300 | 멈춰 버린 실행 |
| 하루 실행 횟수 | 48 | 지나치게 의욕적인 cron 줄 |

과민한 것이 아닙니다. 상한도 없고 지켜보는 사람도 없이 유료 API 위에서
매시간 깨어나는 에이전트는, 당신이 자는 동안 불어나는 청구서입니다.

BoA는 하루 실행 횟수를 에이전트가 닿을 수 없는 곳에서 직접 셉니다. 에이전트는 자신의 기록을 고쳐 그날의 횟수를 되찾을 수 없습니다. `boa-agent-api`가 멈춰 있어서 그 횟수를 읽을 수 없으면, 예약 실행은 시작하지 않습니다.

에이전트가 실제로 얼마나 쓰는지 **기록** 패널에서 확인한 뒤에 올리세요.

### 예비 모델

**LLM** 아래, 첫 번째 공급자와 모델 밑에 두 번째 공급자와 모델이 있습니다.
주 모델이 **실패할 때만**(키가 없거나, 답이 없거나, 없는 모델일 때) 쓰이며,
실행은 같은 단계에서 그것으로 이어 가고 지금까지 일어난 일을 다시
전달하므로, 이미 한 일이 버려지지 않습니다.

**실행당 한 번** 시도합니다. 예비 모델도 실패하면 실행이 실패합니다. 둘을
번갈아 끝없이 시도하면 장애 동안 상한만 태우고 내놓을 것은 여전히 없을
것이기 때문입니다. 예비로 넘어간 일은 에이전트의 기록에 남습니다. 다른
모델로 조용히 답하고 다른 계정으로 청구되는 실행은 그렇다고 밝혀야 하기
때문입니다.

예비 공급자를 **없음**으로 두는 것이 기본값이며, 실패하면 실행이 끝난다는
뜻입니다.

예비에 **같은 공급자**를 고르면 모델 상자에는 같은 모델이 다시 아니라 그
공급자의 카탈로그에서 *다른* 모델이 채워집니다. 같은 공급자의 같은 모델은
주 모델이 답하지 못한 것을 답할 수 없습니다. 매번 정확히 같은 이유로
실패할 것입니다. 그래도 둘을 똑같이 되돌려 입력하면 칸 아래의 줄이
그렇다고 알려 줍니다. 당신의 에이전트이므로 거부가 아니라 경고입니다.


실행이 토큰 상한이나 단계 상한에서 멈추면, 에이전트에게 한 번 더(도구 없이,
작은 별도 예산으로) 막 내놓으려던 답을 요청합니다. 그래서 예산 전부를
사실을 모으는 데 쓴 실행이 “시스템을 확인해 보겠습니다”로 끝나지 않습니다.
그 답은 잘렸을 수 있으므로 채팅에서 답 아래에 그렇다고 표시합니다. 시간
상한에는 그런 호출이 없습니다. 그 실행은 이미 늦었기 때문입니다.

토큰 한도는 프롬프트를 포함해 각 요청 전체에 적용됩니다. 요청을 보내기 전에 프롬프트를 크기로 추정하고(제공자가 한 번 응답한 뒤에는 그 제공자가 실제로 센 값으로 추정하고), 그 프롬프트와 응답할 여유가 남은 양에 들어갈 때만 요청을 보냅니다. 마무리 호출도 들어갈 때만 합니다. 토큰 한도에 도달한 뒤에는 여유가 거의 없어서, 실행은 에이전트가 그때까지 쓴 내용으로 끝납니다. 따라서 실행은 추정 한 번의 오차를 제외하면 한도 안에 머뭅니다.

### 그 위에 커널이 강제하는 것

네 가지 한도는 실행 자체가 적용합니다. 두 가지는 커널이 적용하므로 실행 자체가 잘못되었을 때도 유지됩니다. 어떤 에이전트도 동시에 1024개가 넘는 프로세스와 스레드를 가질 수 없으므로, 끝없이 fork하는 명령은 머신이 아니라 거기서 멈춥니다. 그리고 각 실행은 2 GiB 메모리를 가진 자체 cgroup(Debian에서는 systemd scope, Alpine에서는 실행기가 준비하는 cgroup)에서 동작하며, 끝날 때 백그라운드에 남겨 둔 것도 종료합니다. 같은 두 제한은 crontab이 시작하는 실행, 예약된 스크립트, 라이브러리 색인에도 적용됩니다. 메모리 한도로 종료된 실행은 다른 실행처럼 기록에는 실패로, 채팅에는 오류로 표시됩니다. 브라우저 하나가 이미 수백 개의 스레드이므로 이 수는 더 작지 않습니다. cgroups를 위임할 수 없는 Alpine에서는 첫 번째 제한만 적용되며, `boa-exec` 로그에 그렇게 기록됩니다.

## 에이전트 일정 잡기

**Cron**에서 에이전트의 crontab을 쓰세요. 그것은 에이전트 자신의 crontab이며,
마치 그 사용자로 `crontab -e`를 실행한 것과 똑같이, 소유자도 실행자도
에이전트 자신의 Linux 사용자입니다.

매시간:

```
0 * * * * /opt/boa/venv/bin/python3 /opt/boa/webapp/backend/core/runner.py --agent-id 001
```

평일마다 08:00:

```
0 8 * * 1-5 /opt/boa/venv/bin/python3 /opt/boa/webapp/backend/core/runner.py --agent-id 001
```

인터페이스는 편집 중인 에이전트에 맞는 정확한 줄을 보여 주므로, 그것을
복사해 시각만 바꾸면 됩니다.

이 줄들은 에이전트를 보호 없이 실행하지 않습니다. 줄이 시작한 runner는 cron이 자신을 실행의 cgroup 밖에서 시작했음을 알아채고 실행기에 실행을 요청한 뒤 종료하므로, 예약된 실행도 인터페이스에서 시작한 실행과 같은 메모리와 작업 제한을 받습니다. 에이전트는 자기 줄을 쓸 수 없습니다. Debian에서는 설치 프로그램이 `/usr/bin/crontab` 실행을 root와 `crontab` 그룹에만 허용하고, Alpine에서는 원래 root의 것입니다.

일정을 없애려면 비워 두세요. 일정은 유지하되 에이전트가 그것을 무시하게
하려면 **켜짐**의 체크를 해제하세요.

시간대에 따라 가격이 달라지는 유료 공급자를 쓴다면(DeepSeek는 피크 시간대에
몇 배 더 받습니다) 그 선택은 여기서 합니다.

## 칸반 보드

페이지에는 탭이 두 개 있습니다. 세 개의 열이 있는 **보드**와, 양식인 **카드
만들기**입니다. 어느 탭이 열려 있는지는 URL에 들어 있으므로, 새로 고침이나
뒤로 가기 버튼을 눌러도 유지됩니다. 카드를 저장하면 보드로 돌아갑니다.

열은 세 개입니다. **할 일**, **진행 중**, **완료**.

보드는 에이전트들이 서로에게 일을 남기는 곳이자, 당신이 실제로 무슨 일이
있었는지 보는 곳입니다. 모든 카드는 자기 이력을 가지고 있습니다. 누가
만들었는지, 누가 옮겼는지, 언제, 왜.

카드에는 제목과 **할 일** 상자가 있습니다. 제목은 카드의 이름이고, 상자는
지시를 적는 곳이며, 에이전트는 둘 다 읽습니다. 상자를 비워 둔 채 에이전트에게
배정한 카드는 에이전트에게 추측을 맡기는 셈이며, 넘겨받은 카드로 에이전트가
아무것도 하지 않는 흔한 이유가 이것입니다.

다른 이유는 에이전트가 보드를 아예 볼 수 없는 경우입니다. 에이전트는
`kanban.list_cards`를 호출해서만 보드를 읽습니다. 보드는 결코 프롬프트에
들어가지 않으므로, 그 도구가 없는 에이전트는 카드가 있다는 것을 결코 알지
못합니다. 그런 에이전트를 고르면 **배정 대상**이 그렇다고 알려 줍니다.
막는 것이 아니라 경고입니다. 카드는 그대로 만들어지며, 그 에이전트의
**도구** 탭에서 도구를 체크하기만 하면 됩니다.

보드의 카드는 누가 만들었는지, 누가 맡고 있는지, 언제 만들어졌는지, 제목의
처음 두 줄, 할 일의 처음 세 줄, 그리고 **언제 실행되는지**를 보여 줍니다.
잘린 제목이나 본문의 전체 내용은 툴팁에 있습니다.

읽어 볼 만한 것은 그 마지막 줄입니다. 시각이 없는 카드는 늦은 것이
아닙니다. 그 카드 때문에 깨어나는 에이전트는 없으며, 담당 에이전트는 다음
예약 실행 때 그것을 발견할 것입니다. 카드를 손으로 옮기는 방법은 **이동할
곳**입니다. 이 보드에는 끌어서 옮기기가 없습니다.

당신은 어떤 카드든 추가하고, 옮기고, 삭제할 수 있습니다. **에이전트는 자기
카드만 보고 바꿉니다.** 자기가 만들었거나 자기에게 배정된 카드가 그
에이전트의 카드입니다.

이것은 선호가 아니라 벽입니다. 에이전트는 다른 에이전트의 작업이 존재한다는
것조차 알 수 없습니다. 제목도, 몇 개인지도, 무언가 있다는 사실도
모릅니다. 에이전트에게 자기 것이 아닌 카드를 옮기라고 하면 그런 자기
카드는 없다는 답을 받습니다. 존재하지 않는 카드에도 같은 문장이 돌아옵니다.
둘을 구별해 주는 거부라면, id 하나씩 보드에 무엇이 있는지 물어보는 수단이
될 것이기 때문입니다.

예외는 오케스트레이터인 **manager**(에이전트 000)입니다. 일을 나눠 주고
후속 조치를 하는 것이 그 일이므로, 보드 전체를 읽습니다. 그래서 조율은
다른 누구도 아닌 manager의 일입니다.

파괴적인 확인 창에는 **기본 버튼이 없습니다**. 포커스가 대화 상자 자체에
놓인 채 열리므로, Enter는 어느 쪽도 하지 않고 당신이 어느 쪽을 뜻하는지
말해야 합니다. Esc는 취소합니다. 진행하려면 빨간 버튼을 클릭하세요.

아무것도 파괴하지 않는 평범한 확인 창은 확인 버튼에 테두리가 둘린 채
포커스가 놓인 상태로 열리며, 거기서 Enter는 예를 뜻합니다.

카드를 삭제해도 그 카드가 존재했다는 것과 누가 삭제했는지 기록하는 줄이
남으므로, 에이전트는 자기가 하던 일의 증거를 지울 수 없습니다.

## 설정

설정은 탭으로 묶여 있고 탭은 URL에 들어 있으므로, 새로 고침이나 북마크로
있던 곳에 그대로 돌아옵니다.

| 탭 | 들어 있는 것 |
|---|---|
| **운영체제** | 이 기기가 무엇인지, 메모리와 디스크가 얼마나 남았는지, 네 서비스가 살아 있는지. 각 서비스는 동작 중이면 초록색, 아니면 빨간색입니다. `os-watcher`가 읽는 방식 그대로, 아무 권한 없이 읽습니다 |
| **계정** | 하나뿐인 이메일 주소와 비밀번호. 비밀번호를 바꾸려면 현재 비밀번호가 필요합니다 |
| **메일** | 무언가를 메일로 당신에게 알려야 할 때를 위한 SMTP |
| **채널** | Discord, X, Mattermost, Slack, Telegram, X를 알파벳순으로. 각각 상자 하나와 자기 저장 버튼이 있습니다 |
| **오디오** | 전사 엔진, 공급자, 모델 다운로드, 언어, Telegram 오디오 보관 |
| **도구** | 설치된 도구. 자동화나 브라우저 같은 하위 탭으로 묶여 있습니다 |
| **에이전트** | 모든 에이전트에 한꺼번에 적용되는 설정, 그리고 템플릿을 가져오는 저장소와 브랜치. 서버에 저장됩니다. cron이 시작한 실행에는 설정을 읽어 올 브라우저가 없기 때문입니다 |
| **채팅** | 메시지 입력란의 동작 방식. Enter로 보낼지, 답마다 비용을 표시할지 |
| **칸반** | 열마다 몇 개의 카드를 보여 줄지, 최근 삭제된 카드를 나열할지 |
| **인터페이스** | 테마, 언어, 팝업 메시지가 머무는 시간, 그리고 **+** 버튼이 새 에이전트를 무엇으로 시작할지 묻는지 여부 |

**운영체제**에서는 서비스 상태가 **이 기기**의 두 번째 열과 나란히
정렬됩니다.

채팅, 칸반, 인터페이스의 설정은 서버가 아니라 당신의 브라우저에
저장됩니다. 이 기기에서 당신이 어떻게 일하는지를 나타내는 것이고, 휴대폰과
데스크톱이 서로 다른 것이 자연스럽기 때문입니다.

### 오디오 전사

Alpine에서는 설치와 업데이트가 끝나면 SSH 세션의 제어권을 돌려주며, OpenRC가 서비스를 계속 실행합니다.

**설정 → 오디오**를 여세요. 이 설정은 서버에 저장되며, Telegram으로 받은 음성 메시지와 오디오 파일에 적용됩니다.

1. **로컬 · whisper.cpp** 또는 **제공업체 API**를 고릅니다. 전사는 꺼진 상태로 시작합니다.
2. 로컬 인식이라면 모델을 고르고, 필요하면 **모델 다운로드**를 클릭합니다. 설치 프로그램은 `base`를 준비하며, 선택 목록은 영어 전용 `.en`과 양자화 변형을 포함한 공식 모델 30종 모두와, `/opt/boa/whisper/models/`에 직접 설치한 `ggml-*.bin` 모델을 제공합니다. 크기와 설치 상태가 표시됩니다. 큰 모델일수록 더 많은 메모리와 CPU 시간이 필요합니다.
3. API라면 먼저 **API 키**에 그 키를 저장하세요. 키를 저장하면 OpenAI, Groq, Mistral, Together AI, Hugging Face, Cloudflare가 나타납니다. 추천 모델을 고르거나 그 공급자의 다른 전사 모델 식별자를 입력하세요. Cloudflare는 지원하는 Whisper 변형 두 가지를 제공하며, `account-id:api-token` 형식의 인증 정보를 씁니다.
4. 언어(`auto` 또는 `en` 같은 코드), 최대 길이, 재생용 오디오를 보관할지 여부를 고르고 **저장**을 클릭합니다. 시험해 보려면 에이전트의 Telegram 메시지에 음성 메시지로 답장하세요. `/agents`로 먼저 에이전트를 고를 수도 있습니다.

처음 한도는 600초이며 30초부터 3600초까지 설정할 수 있습니다. 받은 파일은 20 MiB를 넘을 수 없습니다. 처리는 백그라운드에서 이루어지며, 그 대기열은 업데이트 후에도 살아남습니다. 바쁜 에이전트는 텍스트가 준비되면 저장된 텍스트를 받습니다. 녹음 안에서 에이전트 이름을 말해도 보낼 곳은 바뀌지 않습니다.

웹 채팅에는 전사 텍스트가 표시되고, 보관이 켜져 있으면 플레이어도 표시됩니다. 재생용 Ogg 사본은 로그인 뒤에 보관됩니다. 보관을 끄면 새 메시지는 텍스트만 보관됩니다. 채팅을 비우면 완료된 작업의 저장된 오디오도 삭제됩니다. 백업에는 그 오디오가 포함되며, 내려받은 모델은 업데이트 후에도 남지만 백업되지는 않습니다. 다른 기기로 복원한 뒤에는 빠진 추가 모델을 오디오 탭에서 내려받으세요.

로컬 인식은 당신의 서버에서 오디오를 처리합니다. API 인식은 오디오를 선택한 공급자에게 보내며, 에이전트의 모델 사용과 별개로 요금이 발생할 수 있습니다. 로컬에서 실패해도 결코 자동으로 클라우드 공급자로 바뀌지 않습니다. Whisper는 번역하지 않고 전사합니다. `.en` 모델은 영어만 이해합니다. 오디오는 Telegram을 통해 들어오며, 웹 채팅은 녹음 버튼을 추가하지 않고 결과만 표시합니다.

기존 설치라면 배포판의 설치 프로그램을 root로 `--update`와 함께 실행하세요. `/opt/boa/whisper/` 아래에 FFmpeg, whisper.cpp, base 모델을 설치하며, 전사는 설정할 때까지 꺼진 상태로 남습니다.

히브리어는 오른쪽에서 왼쪽으로 쓰며, 히브리어를 고르면 인터페이스 전체가
좌우로 뒤집힙니다. 사이드바는 오른쪽으로 옮겨 가고 나머지도 그에 따릅니다.
코드, 경로, 명령은 왼쪽에서 오른쪽을 유지하고, 각 채팅 메시지는 자기 언어를
따르므로 히브리어 페이지에서도 영어 답변은 여전히 왼쪽에서 오른쪽으로
읽힙니다.

**설정 → 인터페이스 → 언어**에서 하나를 고르며, 테마와 마찬가지로 당신의
브라우저에 저장됩니다. 한 번도 고른 적이 없는 브라우저는 그 브라우저가
요청하는 언어에 가장 가까운 언어를 받고, 맞는 것이 없으면 영어를 받습니다.

다른 두 가지도 언어를 따르지만 브라우저 설정이 **아닙니다**. cron이 시작한
실행에는 브라우저가 없기 때문입니다.

- **설정 → 에이전트 → 에이전트가 답하는 언어**는 모든 에이전트의 시스템
  프롬프트에 그 언어로 쓴 한 줄을 더합니다.
- **Telegram, Discord, X, Mattermost 및 Slack 봇**도 그 언어로 말합니다. 봇 자신의 문장,
  `/status` 보고,
  그리고 도움말입니다.

## 팝업 메시지

무언가가 저장되면 확인 메시지가 보고 있던 패널 한가운데에 나타났다가 스스로
사라집니다. 일부러 눈에 걸리게 한 것입니다. 예전에는 긴 탭 맨 아래의 저장
버튼이 페이지 맨 위, 보고 있던 곳에서 몇 화면이나 위에 한 줄을 띄웠기
때문에, 저장해도 아무 일도 일어나지 않은 것처럼 보였습니다.

**설정 → 인터페이스 → 팝업 메시지가 화면에 머무는 초**에서 그 시간을 1초부터
30초 사이로 정합니다. 기본값은 3초입니다. “설정을 저장했습니다”를 읽기에는
충분히 길고, 막 입력하려던 상자 위에 머물러 있지 않을 만큼 짧습니다.

오류 메시지는 그 숫자를 무시합니다. `×`나 Esc로 닫을 때까지 남아 있습니다.
화면을 다시 볼 때 여전히 그 자리에 있어야 하는 유일한 메시지가 오류이기
때문입니다.

색은 세 가지 중 무엇이 일어났는지 알려 줍니다.

| 색 | 뜻 |
|---|---|
| 초록 | 저장되었습니다 |
| 주황 | **저장할 변경 사항이 없습니다**. 저장을 눌렀지만 양식에서 바뀐 것이 없었습니다 |
| 빨강 | 실패했습니다. 무엇이 잘못되었는지 말하고, 닫을 때까지 기다립니다 |

주황색 메시지는 저장을 누를 수 있는 모든 곳에 적용됩니다. **설정**(계정,
메일 서버, API 키, 채널, 브라우저 설정)과 에이전트 자신의 설정입니다. 저장을
두 번 누르면, 일어나지 않은 저장을 보고하는 대신 두 번째에 그렇다고 알려
줍니다. 갓 만든 에이전트는 예외입니다. 그 양식은 템플릿의 값을 담고 있고
한 번도 저장된 적이 없으므로, 저장을 누르면 그 값을 기록하고 그 에이전트의
채팅으로 이동합니다.

## 테마

**설정 → 인터페이스**에서 팔레트를 고릅니다.

| 테마 | 무엇인지 |
|---|---|
| **Day** | 부드러운 회색과 밝은 카드. 밝은 방을 위한 테마 |
| **Night** | 어두운 팔레트. 어두운 방을 위한 테마 |
| **Day High Contrast** | 흰 배경, 거의 검은 글자, 뚜렷한 테두리. 여기서는 아무것도 강조색으로 채우지 않습니다. 사이드바의 에이전트 상자는 윤곽선이고, 당신의 메시지는 파란색 대신 부드럽게 한 잉크색으로 채워집니다 |
| **Night High Contrast** | 거의 검은 배경, 밝은 글자, 뚜렷한 테두리. 선택한 에이전트는 회색으로 채워지고, 선택한 탭은 아래 선과 이어지는 닫힌 윤곽선을 가집니다. 당신의 메시지는 흐린 흰색을 씁니다 |

한 번도 고른 적이 없는 브라우저는 Day와 Night 중 운영체제에 맞는 쪽으로
시작하며, 누군가 하나를 고를 때까지 운영체제를 따릅니다. 그 뒤에는 언어와
마찬가지로 선택이 이 브라우저에 저장되므로, 휴대폰과 데스크톱이 같을 필요가
없습니다.

테마는 서버의 `frontend/themes/`에 있는 CSS 파일 하나로, `--colour-*` 변수를
다시 정의합니다. 거기에 파일을 넣으면 테마가 추가됩니다. 코드에서 갱신해야
할 목록은 없습니다. 이름과 설명은 파일 맨 위의 주석에서 옵니다.

```css
/*
name: Midnight
scheme: dark
description: What it looks like, in one line.
*/

:root {
  color-scheme: dark;
  --colour-page: #101014;
  /* ... every --colour-* app.css defines ... */
}
```

변수를 모두 정의하세요. 테마가 빠뜨린 변수는 app.css의 값을 그대로
가지며, 밝은 테마라면 어두운 팔레트의 색 하나가 그 한가운데에 남아 있게
된다는 뜻입니다.

여기에 포함된 테마는 모두 글자를 칠하는 모든 색에서 4.5:1 대비를 넘기며,
고대비 테마 둘은 7:1(WCAG AAA)을 넘깁니다. 테마가 그 기준을 지키지 못하게
되면 실패하는 테스트가 있으며, 각 테마는 이름이 내세우는 기준으로 검사됩니다. 손으로 추가한
테마는 그 검사를 받지 않지만, 같은 질문은 그대로 적용됩니다. 아무도 읽을 수
없는 빨간색으로 다운이라고 표시된 서비스는 아무도 알아채지 못하는
서비스입니다.

## 카드가 실행될 때

카드를 배정하는 것이 에이전트에게 일을 주는 방법이며, 그것을 실행으로 바꾸는
것은 **buzzer**라는 서비스입니다.

    몇 초마다:
      담당자가 있고, 시각이 지났고, 아직 호출하지 않은 카드
        -> 이미 실행 중이 아니라면 그 에이전트를 시작한다
        -> 카드에 호출을 기록한다

카드 추가 양식의 **시점**이 시각을 정합니다.

| 선택지 | 일어나는 일 |
|---|---|
| **즉시** | 카드가 저장되는 대로 에이전트를 깨웁니다. 기본값입니다. 카드를 배정하는 것은 그 일을 요청하는 것이기 때문입니다 |
| **에이전트가 깨어날 때** | 카드는 보드에서 기다립니다. 아무도 깨우지 않으며, 에이전트는 자기 다음 실행 때 그것을 발견합니다 |
| **지정한 시각으로 예약** | UTC 기준 시각. 그때 에이전트를 깨웁니다 |

이미 일하고 있는 에이전트는 방해받지 않습니다. 카드는 순서를 유지한 채
다음 회차에 다시 시도되므로, 바쁜 에이전트에게 예약된 실행은 아예 시작되지
않는 대신 몇 초 늦게 시작하며, 한 에이전트가 동시에 두 실행을 갖는 일은
없습니다. 카드는 한 번만 호출됩니다. 다시 실행하려면 시각을 다시 정하세요.

### 에이전트의 채팅에 나타나는 카드

실행이 시작되면 에이전트의 채팅에 그 카드를 알리는 메시지가 올라옵니다.

    카드로 작업이 배정되었습니다:

    카드 ID: 1284
    제목: 인증서 갱신
    할 일: “--update로 설치 프로그램을 실행하고 보고하세요”
    실행 예정: 즉시

다른 에이전트가 카드를 넘겨준 것이라면 첫 줄이 누구인지 알려 줍니다.
*manager이(가) 새 카드를 배정했습니다*. 카드를 바로 요청한 것이 아니라
예약한 것이라면, 마지막 줄에 대신 시각이 표시됩니다. `a2026m03d31@13:45`,
UTC 기준이며, 보드가 카드에 표시하는 시각과 같습니다.

메시지는 **실행이 시작될 때** 쓰이며, 결코 그 전에 쓰이지 않습니다. 오늘
밤으로 예약했다가 오늘 오후에 삭제한 카드는 채팅에 아무것도 남기지
않습니다. 아무것도 실행되지 않았기 때문입니다.

에이전트는 다른 메시지와 마찬가지로 그 아래에 답하며, 실행에 든 비용도
함께 표시됩니다. 에이전트가 아무것도 하지 않았는데 거기에 줄이 생길 수 있는
경우가 세 가지 있으며, 각각 어떤 경우인지 밝힙니다. 에이전트가 꺼져
있었거나, 그날의 실행 횟수를 이미 다 썼거나, 실행을 아예 시작할 수
없었던 경우입니다. 어느 것도 조용히 넘어가지 않습니다. 알려 놓고 무시된
카드는 일하지 않는 에이전트와 똑같아 보이기 때문입니다.

이 실행이 하지 않는 일 하나는 대화를 읽는 것입니다. 이 실행의 지시는
카드입니다. 앞서 채팅에서 한 말은 당신이 직접 메시지를 보낼 때만 다시
전달됩니다. 그렇지 않으면 모든 예약 실행이 아무도 나누고 있지 않은 대화의
비용을 치르게 될 것입니다.

**manager**에게 넘긴 카드는 다르게 처리됩니다. manager는 누가 그 일을 해야
할지 정하고 `kanban.assign_card`로 카드를 넘기라는 지시를 받습니다. 카드는
id, 지시, 이력을 유지한 채 주인이 바뀌며, 카드를 받은 에이전트는 그 때문에
깨어납니다. 그것이 위임입니다. 같은 일로 두 번째 카드를 만드는 것이
아닙니다.

<a id="channel-setup"></a>

## 채널

**설정 → 채널**에서 에이전트가 글을 쓸 수 있는 곳을 설정하세요.

| 채널 | 필요한 것 |
|---|---|
| Discord | 양방향으로 대화하려면 `bot_token`과 `channel_id`, 보내기만 하려면 웹훅 URL |
| Mattermost | 대화는 `server_url`, `bot_token`, `channel_id`; 알림 발신만 할 때는 `webhook_url` |
| Slack | `bot_token`과 `channel_id`; 수신에는 `app_token`과 Socket Mode도 필요 |
| Telegram | BotFather에서 받은 `bot_token`, 그리고 `chat_id` |
| X | `client_id`, `client_secret`, OAuth 2.0, `recipient_id` |

설정된 채널에는 저장된 API 키와 같은 색인 초록색으로 **설정됨**이
표시됩니다. 설정되지 않은 채널은 중립적인 상태 표시를 유지합니다.

인증 정보는 **어떤 에이전트도 읽을 수 없도록** 저장됩니다. 에이전트는
서버에 보내 달라고 요청하고, 서버가 토큰을 읽어 보냅니다. 메시지 앞에는
서버가 붙인 에이전트 이름이 달려 도착하므로, 어떤 에이전트도 다른 에이전트를
사칭할 수 없습니다.

그다음 각 에이전트의 **채널** 탭에서 그 에이전트가 쓸 수 있는 채널을 체크하세요. `channel.write`와 채널 자체가
둘 다 필요합니다.

### 채널을 연결하기 전에

1. BoA 설치를 마치고 로그인한 다음 에이전트의 **LLM** 탭에서 사용 가능한 제공업체와 모델을 설정합니다. **일반**에서 에이전트를 활성화하고 웹 채팅에서 응답하는지 확인합니다. 아래 예시는 새 설치에 있는 `manager`를 사용합니다. 이름을 바꿨다면 예시의 이름도 바꾸세요.
2. 아래 단계에 따라 자신의 봇 또는 앱과 대상을 만듭니다. 해당 토큰은 언어 모델의 API 키와 다릅니다. BoA는 채널 유형마다 대상 하나를 저장합니다. Telegram, Discord, X, Slack, Mattermost, X는 대화를 지원합니다. X는 설정된 상대의 쪽지를 받고 명시적인 요청에 따라 프로필에 게시할 수 있습니다.
3. 별도 알림을 보내려면 에이전트의 **도구**에서 `channel.write`를 허용하고 **채널** 탭에서 대상을 선택합니다. 수신한 대화에 대한 답변은 BoA가 자동으로 전달합니다. PNG를 첨부하려면 `image.send`도 허용하고 에이전트 홈에 기존 PNG 파일을 준비합니다.

설치 프로그램은 Debian과 Alpine에 리스너 서비스를 만들고 시작합니다. 인증 정보를 입력한 뒤 **설정 → 채널**에서 수신을 켜고 해당 채널 상자의 **저장**를 누릅니다. 녹색 표시는 설정이 저장되었다는 뜻이므로 메시지 테스트도 수행하세요. 저장된 비밀 필드는 비어 있거나 가려져 보이며, 비워 두면 기존 값이 유지됩니다.

봇 또는 Slack 앱 하나당 BoA 설치 한 곳만 수신하도록 합니다. 이 통합은 서비스에 아웃바운드로 연결하므로 공개 BoA URL, 인바운드 포트 전달 또는 공개 HTTPS 인증서가 필요하지 않습니다.

<a id="telegram에서-에이전트에게-답하기"></a>

## Telegram

### 봇 생성 및 채팅 ID 확인

1. Telegram에서 공식 [@BotFather](https://t.me/BotFather)를 열고 `/newbot`을 보낸 뒤 이름과 `bot`으로 끝나는 고유 사용자 이름을 정합니다. 받은 토큰을 복사합니다. 이것이 `bot_token`입니다. [Telegram 봇 생성 안내](https://core.telegram.org/bots/features#creating-a-new-bot)에 각 필드가 설명되어 있습니다.
2. BotFather의 링크로 새 봇을 열고 **시작**을 누른 뒤 짧은 메시지를 보냅니다. 먼저 개인 대화로 시작하세요. ID를 구하는 동안 BoA의 Telegram 수신 옵션은 꺼 둡니다.
3. BoA 서버의 터미널에서 아래 명령을 실행하고 숨겨진 입력 프롬프트에 토큰을 붙여 넣습니다. Telegram [getUpdates](https://core.telegram.org/bots/api#getupdates) API를 사용해 대기 메시지가 있는 각 채팅의 ID, 유형, 이름을 출력합니다. 자신의 대화의 숫자 ID를 `chat_id`에 복사하며, 음수 부호가 있다면 포함합니다. 봇의 사용자 이름이나 토큰이 아닙니다.

```bash
/opt/boa/venv/bin/python3 -c '
import getpass
import requests
vToken = getpass.getpass("bot_token: ")
try:
  dResult = requests.get(
    "https://api.telegram.org/bot" + vToken + "/getUpdates",
    params={"timeout": 0, "allowed_updates": "[\"message\"]"}, timeout=20).json()
except (requests.RequestException, ValueError):
  raise SystemExit("Cannot read Telegram updates.")
if not dResult.get("ok"):
  raise SystemExit(dResult.get("description", "Telegram error."))
if not dResult.get("result"):
  print("Send a new message to your bot, then run this command again.")
for dUpdate in dResult.get("result", []):
  dChat = dUpdate.get("message", {}).get("chat", {})
  if dChat:
    print(dChat["id"], dChat.get("type", ""),
          dChat.get("title") or dChat.get("first_name", ""))
'
```

채팅이 보이지 않으면 새 메시지를 보내고 명령을 다시 실행합니다. 그룹은 봇을 추가하고 그 안에서 `/help@봇_사용자_이름`을 보낸 뒤 같은 방법으로 그룹 자체의 ID를 구합니다. 일반 그룹 메시지를 받으려면 BotFather의 `/setprivacy`에서 봇과 **Disable**을 선택한 후 그룹에서 봇을 제거하고 다시 추가합니다. 설정된 그룹의 모든 구성원이 에이전트에게 요청할 수 있습니다. [개인정보 보호 모드 안내](https://core.telegram.org/bots/features#privacy-mode)에 봇이 받는 메시지가 설명되어 있습니다.

### Telegram 활성화 및 확인

1. **설정 → 채널 → Telegram**을 열어 `bot_token`과 `chat_id`를 입력하고 **Telegram에서 에이전트에게 답할 수 있게 합니다**를 선택한 뒤 **저장**를 누릅니다.
2. 같은 Telegram 채팅에서 `/agents`를 보내 에이전트 목록을 확인합니다. 이어서 `@manager BOA-OK로 답해 주세요`를 보내고 Telegram과 `manager` 웹 채팅의 답변을 확인합니다. 봇의 답변에 다른 질문으로 회신하여 대화가 이어지는지도 확인합니다.
3. 별도 발신 알림을 테스트하려면 앞서 설명한 `channel.write`와 Telegram 권한을 주고, 웹 채팅에서 `channel.write`로 Telegram에 `BOA-OK`를 보내라고 명시적으로 요청합니다.

답이 없으면 **시작**을 눌렀는지, 봇을 차단하지 않았는지, `chat_id`가 맞는지 확인합니다. `401`은 토큰 문제를 가리키며, `409`는 다른 폴링 프로그램이나 이전 webhook 때문일 수 있습니다. 다른 수신 프로그램을 중지하세요. 기존 봇을 재사용한다면 폴링 전에 [deleteWebhook](https://core.telegram.org/bots/api#deletewebhook)으로 webhook을 제거하거나 전용 봇을 만듭니다. Debian에서는 `journalctl -u boa-channel-telegram.service -f`, Alpine에서는 `tail -f /opt/boa/logs/boa-telegram.log`를 확인합니다.

### 명령

| 명령 | 하는 일 |
|---|---|
| `/agents` | 에이전트를 버튼으로 나열합니다. 하나를 누르면 그 에이전트와 대화를 시작합니다 |
| `/status` | 서비스, 보드, 그리고 모든 에이전트와 각각의 모델, 도구, 스킬 |
| `/help` | 이 세 가지, 그리고 에이전트에게 닿는 다른 두 가지 방법 |

### 다른 누구도 보지 못합니다

봇의 사용자 이름은 공개되어 있으므로(찾아낸 사람은 누구든 열 수 있습니다),
메뉴는 **당신의 채팅에만** 쓰입니다. 같은 봇을 연 다른 사람은 빈 채팅을
봅니다. `/` 아래에 명령도 없고, 설명도 없고, 누를 것은 시작 버튼뿐입니다.
그 버튼은 Telegram이 모든 봇에 그리는 것이라 어떤 API로도 없앨 수 없습니다.

그것을 눌러도 아무 일도 일어나지 않습니다. 리스너는 모든 메시지의
`chat_id`를 설정에 있는 것과 비교해, 어떤 명령이 실행되기 전에, 그리고 어떤
에이전트가 선택되기 전에 일치하지 않는 것을 버립니다.

**그리고 아무것도 기록되지 않습니다.** 답도, 로그의 한 줄도, 누군가 무언가를
썼다는 기록조차 없습니다. 당신의 것이 아닌 채팅의 id는 다른 사람의
데이터이며, 그것을 보관한다는 것은 당신의 설치가 누가 봇을 찾아냈는지
목록을 조용히 만들어 간다는 뜻이 될 것입니다.

대가는 `chat_id`를 잘못 설정하면 낯선 사람과 똑같아 보인다는 것입니다. 당신
자신의 메시지가 조용히 버려집니다. 설정된 id는 시작할 때마다 로그에
기록되므로, 비교할 대상은 그것입니다.

```bash
journalctl -u boa-channel-telegram.service | grep "Registered"
```

Debian에서 채널 유닛은 `boa-channel-<channel>.service`를 씁니다. 이전 유닛
이름을 자동으로 옮기려면 설치 프로그램을 `--update`로 실행하세요.
Alpine은 OpenRC 이름인 `boa-telegram`, `boa-discord`, `boa-slack`, `boa-mattermost`, `boa-x`를 유지합니다.

필터는 사람이 아니라 **채팅** 단위입니다. 설정한 `chat_id`가 그룹이라면, 그
그룹의 모든 구성원이 당신의 에이전트와 대화할 수 있습니다.

### 대화 상대 고르기

`/agents`를 누르고 에이전트를 누르면, 그 에이전트가 답합니다.

```
Agente os-watcher:

Envíame tus instrucciones...
```

그때부터 다른 에이전트를 고를 때까지 **당신이 쓰는 모든 것이 그 에이전트에게
갑니다**. 아무 이름도 대지 않고 연달아 네 가지를 물을 수 있으며, 그래서
명령줄이 아니라 대화가 됩니다.

누군가에게 말을 거는 방법은 세 가지이며, 우선순위는 다음 순서입니다.

1. **에이전트가 한 말에 답장하면** 다른 무엇이 선택되어 있든 그 에이전트에게
   갑니다. 그 메시지에 답장하세요(메시지를 밀거나, 길게 누르거나 오른쪽 클릭해 '답장'을 고르세요). 그런 다음 쓰고 보내세요.
2. **이름을 대면**(`@os-watcher check the disk`) 그 에이전트에게 가고, *또한*
   그 에이전트가 선택됩니다. `@001`도 되고, 공백이 들어간 이름도 됩니다.
   `@News Miner what is new`는 두 단어가 아니라 에이전트 하나입니다.
3. **둘 다 아니면** 마지막으로 고른 에이전트에게 갑니다.

그 밖의 어떤 것도 선택을 바꾸지 않으므로, 어쩌다 마지막으로 말한 에이전트라는
이유로 당신의 대화를 넘겨받는 일은 없습니다. 삭제한 에이전트는 모든 것을
계속 받아 내는 대신 선택에서 빠집니다.

아직 아무도 고르지 않았다면, 누구의 이름도 대지 않은 메시지에는 에이전트
목록이 돌아오므로, 아무것도 설명 없이 사라지지 않습니다.

### 돌아오는 답

에이전트는 Telegram에서 당신이 쓴 것에 대한 답장으로, 첫 줄에 자기 이름을
달고 답합니다.

```
os-watcher:
25G free of 28G on /, unchanged since yesterday.
```

**그리고 주고받은 내용 전체가 웹 인터페이스의 그 에이전트 채팅에 있습니다**.
당신의 질문과 그 답이며, 당신이 보낸 것에는 시각 옆에 `(Telegram 경유)`가
붙습니다. 각각을 어느 기기에서 입력했든, 에이전트가 받은 요청과 한 말이
여전히 한 화면에 다 보입니다.

예상해 둘 것 두 가지:

- **바쁜 에이전트는 그렇다고 말합니다.** 이미 무언가에 답하고 있다면,
  대기열에 들어가는 대신 잠시 뒤에 다시 해 보라는 답을 받습니다. 대기열은
  에이전트가 뒤처지고 있다는 사실을 감출 것이기 때문입니다.
- **당신의 채팅만 듣습니다.** 봇의 사용자 이름은 공개되어 있고, 찾아낸
  사람은 누구든 봇에게 쓸 수 있습니다. 다른 채팅에서 온 메시지는 답 없이
  버려지므로, 누가 당신의 에이전트와 대화할 수 있는지는 설정한 `chat_id`가
  정합니다. 잘못 설정하면 아무 일도 일어나지 않습니다.

웹훅이 아니라 롱 폴링입니다. 서버가 Telegram으로 연결해 나가므로, 이것이
동작하기 위해 인터넷 쪽으로 열어 둘 것이 없습니다.

Telegram이 답을 받지 않으면(봇을 차단했거나, chat id가 바뀌었거나, 토큰이
더 이상 유효하지 않으면) 그 답은 Telegram 쪽에서는 바로 버려지며, 한 시간
동안 Telegram에 닿을 수 없을 때도 버려집니다. 하지만 결코 잃어버리지는
않습니다. 그 답을 포함한 대화 전체가 웹 인터페이스의 에이전트 채팅에
있습니다.

### 에이전트의 메시지 모양

모델은 markdown을 쓰고 Telegram은 HTML의 작은 부분 집합을 렌더링하므로, 나갈
때 둘 사이를 변환합니다. 도착하는 것은 별표가 아니라 서식이 적용된
텍스트입니다.

| 에이전트가 쓰는 것 | 휴대폰에서 보이는 것 |
|---|---|
| `**25G free**` | **25G free** |
| `` `df -h` `` | 고정폭 글꼴의 `df -h` |
| `# Disk report` | 굵은 줄 |
| `- item` | • item |
| 표 | 열이 정렬된 고정폭 블록 |
| ```` ```bash ```` | 코드 블록 |
| `[text](https://…)` | 링크 |

Telegram에는 자체적인 제목, 목록, 표가 없으므로, 그 세 가지는 사라지는 대신
가장 가까운 읽기 쉬운 형태가 됩니다.

Telegram이 서식을 거부하는 일이 생기면, **메시지는 잃어버리는 대신 일반
텍스트로 다시 보내집니다**. 어느 쪽이든 내용은 받습니다. 서버 로그에 무슨
일이 있었는지 남으므로, 서식 버그가 끝없이 조용히 품질을 떨어뜨리는 대신
드러납니다.

봇이 스스로 하는 말(에이전트 목록, “아직 다른 일에 답하는 중”, `/status`)은
모두 **설정 → 에이전트**에서 정한 언어로 나오며, 에이전트가 답하는 언어와
같습니다.

## Discord에서 에이전트에게 답하기

Discord도 당신만의 봇으로 Telegram과 똑같이 동작합니다. 한 번, 5분 정도의
설정이면 됩니다.

### 봇 만들기

1. [Discord Developer Portal](https://discord.com/developers/applications)에서 **New Application**을 선택하고 이름을 정합니다. 앱 설치 권한이 있는 서버가 필요합니다.
2. **Bot → Reset Token**을 열고 필요한 인증을 완료한 뒤 토큰을 BoA의 `bot_token`에 복사합니다. Application ID, Public Key, Client Secret이 아닌 봇 토큰입니다.
3. **Installation**에서 **Guild Install**을 켭니다. **OAuth2 → URL Generator**에서 `bot` scope와 **View Channels**, **Send Messages**, **Read Message History**, **Attach Files**를 선택합니다. 생성된 URL을 열고 서버를 선택하여 봇을 승인합니다. [Discord 설치 안내](https://docs.discord.com/developers/quick-start/getting-started)에 서버 설치와 권한이 설명되어 있습니다.
4. 텍스트 채널을 만들거나 선택하고 채널별 권한 설정도 봇에게 이 네 권한을 허용하는지 확인합니다. Discord에서 **사용자 설정 → 고급 → 개발자 모드**를 켠 뒤 채널을 오른쪽 클릭하고 **채널 ID 복사**를 선택합니다. 그 숫자를 `channel_id`에 넣습니다. 서버 ID가 아닙니다. [Discord ID 확인 안내](https://support.discord.com/hc/en-us/articles/206346498-Where-can-I-find-my-User-Server-Message-ID)를 참고하세요.

**Discord Developer Portal → Bot → Privileged Gateway Intents**에서 **Message Content Intent**를 켜고 저장하세요. HTTP 폴링에도 필요합니다. BoA에서 수신을 켜고 저장하면 봇, 채널과 권한을 확인합니다. 오류가 있으면 이전 설정을 유지합니다.

에이전트가 첨부한 PNG 이미지를 Discord에 업로드하며 봇에는 **Attach Files** 권한이 필요합니다. 이미지를 전달할 수 없으면 웹 대화를 확인하라는 안내를 보냅니다. 확인된 텍스트와 이미지 부분을 따로 기록하므로 재시도나 서비스 재시작 시 남은 부분부터 이어집니다. 봇이나 대상을 변경하면 새 커서를 시작하고 선택한 에이전트를 해제합니다. 채널의 이전 메시지는 다시 처리하지 않습니다.

### 켜기

**설정 → 채널 → Discord**에서 토큰과 채널 id를 채우고, **Discord에서
에이전트에게 답할 수 있게 합니다**를 체크한 뒤 저장하세요. 몇 초 안에 어느
봇이 어디에서 듣고 있는지 로그에 나옵니다.

```bash
journalctl -u boa-channel-discord.service | grep "Listening"      # Debian
tail /opt/boa/logs/boa-discord.log                # Alpine
```

켜기 전에 쓴 메시지에는 답하지 않습니다. 첫 회차에서 채널이 어디까지 와
있는지 기록하고, 거기서부터 시작합니다.

### 첫 테스트와 흔한 설정 문제

저장 후 리스너가 연결될 때까지 기다린 다음 자신의 사람 계정으로 설정된 채널에 **새로운** `!agents` 메시지를 보냅니다. 이어서 `@manager BOA-OK로 답해 주세요`를 보내고 Discord와 BoA의 답변을 확인합니다. `@manager`는 일반 텍스트로 입력합니다. BoA 에이전트 이름이며 Discord 봇 멘션이 아닙니다. 해당 답변에 회신하여 대화를 계속합니다.

저장이나 수신에 실패하면 **Message Content Intent**, 봇 토큰, `channel_id`, 채널별 권한을 확인합니다. PNG 전송에는 **Attach Files**가 필요합니다. Webhook은 알림을 보낼 수 있지만 지시를 받지는 못합니다. 별도 발신을 테스트하려면 에이전트에 `channel.write`와 Discord를 허용하고 웹 채팅에서 Discord에 `BOA-OK`를 보내 달라고 요청합니다.

### 에이전트와 대화하기

| 명령 | 하는 일 |
|---|---|
| `!agents` | 에이전트를 나열하고, 각각에게 닿으려면 무엇을 입력해야 하는지 알려 줍니다 |
| `!status` | 서비스, 보드, 그리고 모든 에이전트와 각각의 모델, 도구, 스킬 |
| `!help` | 이 세 가지, 그리고 에이전트에게 닿는 다른 방법들 |

손가락이 그렇게 입력한다면 `/agents`도 됩니다. 여기에는 버튼도, 슬래시
명령 메뉴도 없습니다. 둘 다 *인터랙션*인데, Discord는 이 설치가 일부러 열지
않는 연결을 통해서만 인터랙션을 전달하기 때문입니다.

누군가에게 말을 거는 세 가지 방법은 이미 아는 그대로입니다.

1. **에이전트가 한 말에 답장하면** 다른 무엇이 선택되어 있든 그 에이전트에게
   갑니다. 그 메시지를 오른쪽 클릭 → 답장, 또는 휴대폰에서는 밀어서.
2. **이름을 대면**(`@os-watcher check the disk`) 그 에이전트에게 가고, *또한*
   그 에이전트가 선택됩니다. `!os-watcher`, `@001`, `@News Miner what is new`
   모두 됩니다.
3. **둘 다 아니면** 마지막으로 고른 에이전트에게 갑니다.

### 돌아오는 답

답은 당신의 질문에 대한 답장으로, 첫 줄에 에이전트 이름을 굵게 달고
도착하며, **주고받은 내용 전체가 웹 인터페이스의 그 에이전트 채팅에
있습니다**. 당신이 보낸 것에는 시각 옆에 `(Discord 경유)`가 붙습니다.

긴 답은 잘린 메시지 하나가 아니라 여러 메시지로 도착합니다. Discord는
2000자를 넘는 것을 거부하므로, 답은 줄 사이에서 나뉘어 최대 네 개의
메시지가 됩니다. 그중 어느 것에 답장해도 같은 에이전트에게 닿습니다. 메시지
네 개 분량을 넘으면 마지막 메시지가 `…`로 끝나며, 전체 내용은 그것이 쓰인
웹 인터페이스에 있습니다.

### 누가 에이전트와 대화할 수 있나

**그 채널에 쓸 수 있는 모든 사람입니다.** 이것이 Telegram과의 유일한 실제
차이이며, 1분쯤 들여 생각해 볼 가치가 있습니다. Telegram에서는 봇이 모든
메시지의 chat id를 비교해 일치하지 않는 것을 버리므로, 당신의 봇을 찾아낸
낯선 사람은 아무것도 얻지 못합니다. 여기서는 봇이 채널 하나를 읽으며, 그
채널에 글을 올릴 수 있는 사람은 누구든 당신의 서버에서 실행을 시작할 수
있습니다.

그러니 에이전트는 **비공개 채널**, 즉 당신만, 또는 당신과 당신이 믿는
사람들만 볼 수 있는 채널에 두세요. 봇은 그 밖의 어디에도 접근할 필요가
없습니다.

### 알림만 원한다면

토큰을 비워 두고 대신 **웹훅 URL**을 설정하세요. **채널 편집 → 연동 →
웹후크 → 새 웹후크 → 웹후크 URL 복사**. 그러면 에이전트는 채널에 쓸 수 있고,
그것이 전부입니다. 듣기에는 봇이 필요하므로, 웹훅에서는 그 스위치가
아무것도 하지 않는 대신 거부됩니다.

## Slack

### 앱 생성 및 설치

1. [Slack Apps](https://api.slack.com/apps)에서 **Create New App → From a manifest**를 선택하고 워크스페이스를 고른 뒤 [deploy/slack-app-manifest.json](../deploy/slack-app-manifest.json)의 JSON을 붙여 넣습니다. **Next → Create**로 진행합니다. 매니페스트가 봇, `/boa`, 이벤트, 권한을 설정합니다. [Slack 매니페스트 안내](https://docs.slack.dev/app-manifests/configuring-apps-with-app-manifests/)를 참고하세요.
2. **OAuth & Permissions**를 엽니다. **OAuth Tokens**에서 **Install to Workspace** 또는 **Install to &lt;워크스페이스 이름&gt;**를 누른 뒤 **Allow**를 선택합니다. 같은 작업이 **Install App**에 있을 수도 있습니다. 워크스페이스에 승인 절차가 있으면 관리자가 설치를 승인해야 합니다. OAuth 콜백을 구현할 필요는 없습니다.
3. **OAuth & Permissions**로 돌아와 `xoxb-`로 시작하는 **Bot User OAuth Token**을 BoA의 `bot_token`에 복사합니다. **Client Secret**과 **Signing Secret**은 다른 값입니다.

### 메시지 수신 활성화

1. **Basic Information → App-Level Tokens → Generate Token and Scopes**에서 토큰 이름을 정하고 `connections:write`를 추가한 뒤 **Generate**를 누릅니다. `xapp-` 토큰을 `app_token`에 복사합니다.
2. **Socket Mode**에서 **Enable Socket Mode**가 켜져 있는지 확인합니다. **Event Subscriptions**의 봇 이벤트 `message.channels`, `message.groups`, `message.im`을 확인합니다. 제공된 매니페스트가 이를 설정하며 이 연결에는 **Request URL**이 필요 없습니다. [Slack Socket Mode 안내](https://docs.slack.dev/apis/events-api/using-socket-mode/)에 앱 토큰과 연결이 설명되어 있습니다.
3. Slack에서 채널을 만들거나 열고 `/invite @BoA` 또는 정한 봇 이름을 사용합니다. 채널 이름을 눌러 세부 정보의 **Channel ID**를 찾습니다. 보통 **About** 하단에 있습니다. 채널 링크를 복사해도 됩니다. 채널 식별자는 `C…` 또는 `G…` 부분이며 워크스페이스의 `T…`가 아닙니다. `channel_id`에 저장하고 `#채널-이름`은 입력하지 않습니다.

### BoA 설정 및 첫 테스트

**설정 → 채널 → Slack**에 세 값을 입력합니다.

| BoA 필드 | 복사할 값 |
|---|---|
| `bot_token` | **Bot User OAuth Token** (`xoxb-…`) |
| `app_token` | `connections:write` 권한이 있는 **App-Level Token** (`xapp-…`) |
| `channel_id` | 봇이 들어 있는 채널 ID (`C…` 또는 `G…`) |

**Slack에서 에이전트에게 답할 수 있게 합니다**를 선택하고 **저장**를 누릅니다. BoA가 토큰, 채널 접근, Socket Mode 연결을 확인합니다. 알림만 보내려면 `bot_token`과 `channel_id`를 저장하고 수신은 끕니다.

그 채널에서 `/boa agents`를 보냅니다. 목록이 나오면 일반 메시지로 `@manager BOA-OK로 답해 주세요`를 보냅니다. 스레드를 열어 답변을 확인하고 에이전트 이름을 반복하지 않고 후속 질문을 보냅니다. BoA 웹 채팅에서도 같은 대화를 확인합니다. 별도 발신 테스트는 에이전트에 `channel.write`와 Slack을 허용하고 웹 채팅에서 Slack에 `BOA-OK`를 보내라고 명시적으로 요청합니다.

### Slack이 응답하지 않는 경우

- **설치 버튼이 없음:** 워크스페이스와 **OAuth & Permissions → Bot Token Scopes**의 매니페스트 scope를 확인합니다: `channels:history`, `channels:read`, `chat:write`, `commands`, `files:read`, `files:write`, `groups:history`, `groups:read`, `im:history`, `im:read`. **Install App**도 확인합니다. Scope를 바꾼 뒤에는 워크스페이스에 앱을 다시 설치하여 권한을 부여합니다.
- **`/boa`를 모름:** **Slash Commands**의 `/boa`, 앱 설치 상태, 명령을 입력한 워크스페이스를 확인합니다.
- **`invalid_auth` 또는 `missing_scope`:** 두 종류의 토큰과 필요한 scope를 확인하고 권한 변경 후 재설치합니다.
- **`not_in_channel` 또는 `channel_not_found`:** 봇을 초대하고 ID를 확인합니다. 비공개 채널도 초대가 필요합니다.
- **전송은 되지만 수신이 안 됨:** 수신 옵션, Socket Mode, `app_token`, 이벤트 구독과 수신 중인 설치가 하나뿐인지 확인합니다.

### 전달 및 서비스 로그

`/boa agents`, `/boa status`, `/boa help` 또는 `!agents`, `!status`, `!help`를 사용하세요. `@이름 지시 내용` 또는 `/boa @이름 지시 내용`으로 작업을 시작합니다. 답변은 해당 스레드에 유지되며 사용자마다 선택한 에이전트가 따로 있습니다. 설정한 채널만 수락하며 그곳에 쓸 수 있는 사람은 누구나 에이전트를 실행할 수 있습니다. 수신 메시지에서는 텍스트를 전달하고 에이전트는 PNG 이미지를 반환할 수 있습니다. 대화는 Slack 출처 표시와 함께 웹 채팅에도 나타납니다.

Socket Mode는 버전이 고정된 Slack SDK로 외부 연결을 사용합니다. 수신 확인 전에 입력을 저장하고 이벤트 ID로 재시도나 재시작 후 중복 실행을 막습니다. 전달한 텍스트 부분과 이미지 업로드 단계를 저장하며 속도 제한 시 Slack이 지정한 대기 시간을 따릅니다. 코드를 닫아 유지하며 텍스트를 최대 네 개의 4000자 메시지로 나누고 전체 답변은 웹 채팅에 남깁니다. 처리되지 않은 입력과 대기 답변은 한 시간 뒤 만료됩니다. Slack 앱마다 활성 리스너를 하나만 실행하세요.

```bash
journalctl -u boa-channel-slack.service -f   # Debian
tail -f /opt/boa/logs/boa-slack.log           # Alpine
```

## Mattermost

### 서버와 봇 준비

BoA에서 접근할 수 있는 Mattermost 서버와 봇을 만들 System Admin 권한의 계정이 필요합니다. BoA는 Mattermost에 연결하며 서버 자체를 설치하지는 않습니다. 서버가 없다면 [Mattermost 설치 안내](https://docs.mattermost.com/deployment-guide/server/linux/deploy-tar)를 따르세요.

1. Mattermost의 **System Console → Integrations → Bot Accounts**에서 **Enable Bot Account Creation**을 켜고 저장합니다.
2. **Product menu → Integrations → Bot Accounts → Add Bot Account**를 엽니다. 사용자 이름은 `boa`, 표시 이름은 `BoA` 등으로 정하고 **Member** 역할을 유지한 뒤 **Create Bot Account**를 선택합니다.
3. 성공 화면을 닫기 전에 생성된 **Access Token**을 복사합니다. 이것이 BoA의 `bot_token`이며 Token ID가 아닙니다. 일반 사람 계정의 개인 토큰은 수신용으로 허용되지 않습니다. 생성과 멤버십은 [봇 계정 안내](https://docs.mattermost.com/developers/integrate/reference/bot-accounts)를 참고하세요.
4. 팀 메뉴의 **Invite People → Invite Member**로 봇을 팀에 넣고, **Add Members**로 선택한 채널에도 추가합니다. 파일 업로드에도 채널 멤버십이 필요합니다.
5. **View Info**로 채널 정보를 열고 **Channel ID**를 복사합니다. 26자이며 채널 이름이나 팀 ID와 다른 값입니다.

### BoA 설정 및 연결 테스트

**설정 → 채널 → Mattermost**를 열어 입력합니다.

| 필드 | 값 |
|---|---|
| `server_url` | Mattermost 기본 URL. 예: `https://chat.example.org`. 프록시 하위 경로를 쓴다면 포함 |
| `bot_token` | 봇 계정의 Access Token |
| `channel_id` | 봇이 참여한 채널의 ID |

**Mattermost에서 에이전트에게 답할 수 있게 합니다**를 선택하고 **저장**를 누릅니다. BoA는 저장 전에 봇, 채널, 멤버십을 확인합니다. OAuth 콜백, 슬래시 명령 등록, BoA로의 인바운드 포트 전달은 필요 없습니다. 서비스가 Mattermost REST API를 폴링합니다.

나중에 BoA를 다른 Mattermost 서버로 옮기려면, 새 `server_url`과 같은 저장에서 `bot_token`을 다시 입력하세요. 저장된 토큰은 저장할 때의 서버가 아닌 다른 서버로는 절대 전송되지 않습니다. 입력하지 않으면 저장이 거부되고 아무것도 바뀌지 않습니다.

자신의 사람 계정으로 그 채널에 새 `!agents` 메시지를 보낸 뒤 `@manager BOA-OK로 답해 주세요`를 보냅니다. 답변은 스레드와 에이전트의 웹 채팅에 나타납니다. 같은 스레드에서는 이름을 반복하지 않고 계속할 수 있습니다. `!status`, `!help`도 있습니다. 이는 일반 텍스트 명령이며 Mattermost 슬래시 명령이 아닙니다. 에이전트 선택은 사용자별로 따로 유지되며, 설정된 채널에 쓸 수 있는 사람은 누구나 실행을 시작할 수 있습니다.

별도 발신 테스트는 에이전트의 **도구**와 **채널**에서 `channel.write`와 Mattermost를 허용한 뒤 웹 채팅에서 Mattermost에 `BOA-OK`를 보내 달라고 요청합니다. 이미지는 `image.send`도 허용하고 홈에 있는 PNG 첨부를 요청합니다. 수신 메시지는 텍스트를 제공하며 발신 답변에는 PNG를 넣을 수 있습니다.

### 발신 webhook과 문제 해결

알림만 필요하면 **Integrations → Incoming Webhooks → Add Incoming Webhook**을 만들고 채널을 선택한 뒤 URL을 BoA의 `webhook_url`에 복사합니다. `bot_token`은 비우고 수신은 끕니다. 선택 항목 `channel`과 `username`은 Mattermost가 허용할 때만 webhook 기본값을 재정의합니다. Webhook은 지시를 받을 수 없으며, 봇 토큰이 설정되면 우선 사용됩니다.

응답이 없으면 수신 설정, 기본 URL, 채널 ID, 멤버십을 확인합니다. `401`은 보통 잘못된 토큰, `403`은 접근 권한 부족입니다. PNG 오류는 업로드 권한이나 멤버십 부족일 수 있습니다. TLS 오류에서는 BoA 호스트가 Mattermost 인증서를 신뢰하도록 설정합니다. 잘못된 수신 설정을 저장하면 이전 설정이 유지됩니다.

같은 봇과 채널에는 BoA 한 설치만 수신해야 합니다. 최초 활성화와 명시적 재활성화는 기존 메시지를 건너뛰고, 일반 서비스 재시작은 읽기 위치를 유지합니다. 대기 입력과 답변은 한 시간 후 만료됩니다. 긴 텍스트는 최대 네 개의 4000자 메시지로 나뉘며 전체 답변은 웹 채팅에 남습니다. 로그를 확인하세요.

```bash
journalctl -u boa-channel-mattermost.service -f   # Debian
tail -f /opt/boa/logs/boa-mattermost.log           # Alpine
```


## X

X는 설정한 한 계정과의 비공개 대화와 명시적으로 요청한 승인된 프로필의 텍스트 게시물을 지원합니다. 쪽지에는 서로 다른 X 계정 두 개, [개발자 콘솔](https://console.x.com/)의 앱, API 크레딧이 필요합니다. [현재 요금](https://docs.x.com/x-api/getting-started/pricing)을 확인하고 지출 한도를 설정하세요. BoA는 크레딧을 구매하지 않습니다. 개발자 계정이 앱을 소유하고 다른 계정이 BoA를 승인할 수 있습니다. 공개 멘션, 그룹 채팅, 암호화된 X Chat은 이 연동의 입력 대상이 아닙니다.

1. **New App / Create App**으로 앱을 만들고 개인용 BoA 연동을 설명하세요. **User authentication settings → Set up**에서 OAuth 2.0용 **Web App, Automated App or Bot**을 선택하세요. 웹사이트가 필요하면 프로젝트의 공개 URL을 사용하세요. **설정 → 채널 → X**에 표시되는 콜백 URL을 HTTPS, 호스트, 경로까지 정확하게 등록하세요. 승인 후 브라우저가 LAN의 BoA에 접근할 수 있어야 하며 공개 수신 포트는 필요하지 않습니다.
2. **Client ID**와 **Client Secret**을 `client_id`와 `client_secret`에 복사하고 **저장**를 누르세요. 앱 전용 **Bearer Token**으로 대체할 수 없습니다. 프로필 게시물을 허용하려면 저장하고 승인하기 전에 **X 프로필 게시를 허용합니다(각 게시물은 쪽지로 승인)**를 선택하세요. X 승인 버튼은 OAuth 시작 전에 현재 자격 증명과 게시 권한도 저장합니다. 수신은 승인 후 직접 활성화할 때까지 꺼져 있습니다.
3. **X 승인**를 누르고 BoA가 사용할 계정으로 로그인한 뒤 앱을 승인하세요. BoA는 `tweet.read`, `users.read`, `dm.read`, `dm.write`, `media.write`, `offline.access`를 요청합니다. 게시에는 `tweet.write`도 필요합니다. 마지막 권한은 게시를 허용하고 `offline.access`는 자동 토큰 갱신을 허용합니다. 돌아온 화면에서 승인된 계정을 확인하세요. 나중에 게시를 활성화했다면 다시 승인하세요.
4. **수신자의 X 사용자 이름**에 사람 계정의 @사용자명을 입력하고 **수신자 ID 찾기**으로 `recipient_id`를 채우세요. **설정된 계정의 쪽지를 수신합니다**을 선택하고 **저장**를 누르세요. BoA와 다른 계정이어야 하며 BoA의 쪽지를 받을 수 있어야 합니다. 이 상대와의 일대일 텍스트 메시지만 에이전트를 실행할 수 있습니다.
5. 사람 계정에서 BoA 계정으로 `!agents`, 이어서 `@manager Reply with BOA-OK`를 보내세요. 먼저 공통 채널 준비 사항에 따라 manager의 모델을 설정하세요. 수신까지 약 1분 기다리세요. 다른 이름을 지정할 때까지 이후 메시지도 선택한 에이전트에게 전달됩니다. `!help`와 `!status`도 지원합니다. 이미지 테스트는 `image.send`를 허용한 뒤 에이전트 홈에 있는 5 MiB 이하의 PNG를 요청하세요. 비공개로 도착하며 웹 채팅에도 남습니다.
6. `channel.write`로 나가는 알림은 비공개 DM입니다. 에이전트의 **도구**와 **채널** 탭에서 도구와 X를 허용하세요. `channel.write`는 절대 게시하지 않습니다. 프로필 게시는 아래에서 설명하는 `x.post` 도구입니다.

**프로필 게시.** `x.post` 도구가 있고 채널에 X가 있는 에이전트는 텍스트 게시를 요청할 수 있으며, 요청만 할 수 있습니다. BoA는 정확한 텍스트를 보관하고 일회용 코드와 함께 수신자 계정에 DM으로 보냅니다. 그 계정에서 `!post CODE`로 답하면 게시되고, `!discard CODE`로 답하면 취소됩니다. 코드는 한 번만 쓸 수 있고 60분 뒤 만료됩니다. 요청은 승인된 계정과 수신자에 묶여 있으므로, 다시 승인하거나 수신자를 바꾸면 코드는 쓸모가 없어집니다. 요청하려면 게시 옵션, `tweet.write`를 포함한 승인, 수신 켜기가 필요합니다. 답이 DM으로 오기 때문입니다. BoA는 에이전트 이름을 앞에 붙여 전체 텍스트를 보내고, 글자 수 제한은 X가 확인합니다. 공개 게시물을 자르거나 스레드로 나누지 않습니다. X가 게시를 확인하지 않으면 BoA는 다시 게시하지 않습니다. 프로필을 확인하세요.

같은 계정과 상대에는 하나의 리스너만 실행하세요. 수신을 활성화하면 새 메시지부터 처리하며 서비스 재시작 시 읽기 위치를 유지합니다. API는 15분당 쪽지 읽기 15회를 허용하므로 BoA는 65초마다 확인하고 제한 해제 시간을 따릅니다. 답변은 일반 텍스트이며 긴 답변은 최대 네 개의 쪽지로 나뉩니다.

승인이 실패하면 콜백 URL의 정확한 일치, Client ID/Secret, 권한, API 크레딧을 확인하세요. HTTP 402는 크레딧이나 지출 한도 문제, 403은 권한이나 쪽지 허용 설정 확인, 429는 다음 시간 구간까지 대기를 뜻합니다. 승인을 취소했거나 토큰 갱신이 실패했다면 다시 승인하세요. 전송 확인을 잃으면 BoA는 자동으로 반복하지 않습니다. 다시 보내기 전에 X를 확인하세요. 전달 실패는 다음 로그에서 확인할 수 있으며 전체 답변은 웹 채팅에 남습니다.

크레딧은 구매하거나 대상 프로모션으로 받을 수 있습니다. [현재 무료 크레딧 혜택](https://docs.x.com/x-api/getting-started/free-credits)을 확인하세요. X API 응답 시간에 따라 수신에 1분 이상 걸릴 수 있습니다.

```bash
journalctl -u boa-channel-x.service -f   # Debian
tail -f /opt/boa/logs/boa-x.log          # Alpine
```


## 오케스트레이터

**manager**라고 불리는 `agent-000`은 설치할 때 만들어지는 유일한 에이전트입니다. 삭제할 수 없다는
점만 빼면 모든 면에서 평범한 에이전트입니다.

의도한 사용 방식은 이렇습니다. manager에게 칸반 도구와, 목표를 카드로
쪼개 id로 다른 에이전트에게 배정하라는 프롬프트를 줍니다. 다른 에이전트들에게는
`bash.run`과 그 밖에 필요한 것, 그리고 자기에게 배정된 카드를 처리하라는
프롬프트를 줍니다.

이것은 manager의 카드가 “완료”가 무엇을 뜻하는지 말할 때만 동작합니다.
그렇지 않은 카드는 바람일 뿐이고, 그것을 맡은 에이전트가 알아서 정하게
됩니다.

## 도구 탭

**설정 → 도구**는 서버에 무엇이 설치되어 있는지 보여 줍니다. 계열마다 하위
탭(자동화, 브라우저, 채널, 메일, 이미지, 인터넷, 칸반, 메모리, 운영체제, RAG, 스킬)이 있고 그 안의
도구 수가 표시되며,
도구마다 인자와 그 뜻을 담은 상자가 있습니다. 열린 탭은
URL(`/settings/?tab=tools&family=mail`)에 들어 있으므로, 새로 고침이나 북마크로도 유지됩니다.
예전의 `/tools/` 링크는 여기로 리디렉션되며, 선택한 계열을 유지합니다.

아무도 계열 이름을 정하지 않은 도구(누군가 `/opt/boa/tools/`에 넣어 둔
`.py`)는 **기타**로 들어가며, 그 계열이 자기 상자에 적힙니다. 인터페이스에
이르기까지 여전히 온전한 도구이지만, 자기 탭을 얻지는 못합니다. 그러지
않으면 일회성 스크립트가 생길 때마다 탭 줄이 늘어날 것이기 때문입니다.

어느 에이전트가 어느 도구를 쓸 수 있는지는 여기가 아니라 각 에이전트의
**도구** 탭에서 정합니다.

## API 문서

사이드바의 **API 문서**는 `/api/` 아래의 모든 엔드포인트를 영역별로 묶어,
매개변수와 응답 내용과 함께 나열합니다. 이 설치 자체의 OpenAPI 설명에서
생성되므로 코드와 어긋날 수 없습니다. 맨 위에 링크된 `openapi.json`은
클라이언트 생성기에 넘길 수 있는 파일로서 같은 내용입니다.

인터페이스의 나머지와 마찬가지로 **설정 → 인터페이스**에서 고른 언어로
표시됩니다. 명세 자체는 영어로 남습니다. 이 프로젝트에서는 필드 이름, id,
오류 문자열이 어디서나 영어이며, 번역된 `openapi.json`은 존재하지 않는
API를 설명하게 될 것입니다.

요청 본문은 편집기가 보여 주는 것처럼 색을 입힌 JSON으로 표시됩니다. 필드
이름은 한 색, 값은 다른 색이고, 중괄호와 쉼표는 뼈대일 뿐이므로 흐리게
표시됩니다. 색은 고른 테마에서 오며, 블록을 복사해도 여전히 올바른 JSON을
얻습니다.

이 페이지는 로그인하지 않고도, 사이드바 없이 단독으로 읽을 수 있습니다.
API의 형태를 설명할 뿐, 당신의 데이터는 전혀 담고 있지 않습니다.

## 에이전트가 생각할 필요 없는 일

어떤 일은 반복적이고 기계적입니다. 인증서 확인, 로그 회전, 숫자 하나
모으기. 그런 일로 에이전트를 깨우면, 셸 스크립트라면 공짜로 내릴 결론에
이르기 위해 매번 토큰이 듭니다.

그래서 에이전트는 자신을 위한 스크립트를 쓰고 일정을 잡을 수 있습니다.
**자동화** 도구를 주면 다음을 할 수 있습니다.

1. `script.write` — 자기 `scripts/` 디렉터리에 셸 스크립트를 둡니다.
2. `cron.add` — 자기 crontab에서 그것을 일정대로 실행합니다.
3. 다음 실행 때 결과를 읽고, 그것이 무엇을 뜻하는지 판단합니다.

스크립트는 그 에이전트의 Linux 사용자로, 에이전트와 같은 권한으로 실행되며,
**토큰이 전혀 들지 않습니다**. 모델 호출이 아니라 셸 스크립트이기
때문입니다. 토큰이 드는 것은 나중에 에이전트가 출력을 읽고 어떻게 할지
판단하는 부분입니다. 스크립트는 실행과 같은 2 GiB 메모리와 1024개 작업을 가진 자체 cgroup에서 동작하며, 한 시간이 지나도 동작 중이면 종료됩니다. 아직 동작 중일 때 실행되는 줄은 두 번째 사본을 시작하지 않습니다.

할 수 없는 것:

- 자기 스크립트 말고는 어떤 것도 일정에 넣을 수 없습니다. crontab의 자유
  형식 명령은 나중에 아무도 검토할 수 없는 것이 됩니다.
- 5분보다 잦게 실행할 수 없습니다. 매분 도는 작업은 일정이 아닙니다.
- 자신을 깨우는 줄을 건드릴 수 없습니다. 그 줄은 당신의 것이며, 그 에이전트의
  **Cron** 탭에 있습니다.

당신은 양쪽을 다 봅니다. 그 홈의 스크립트와, Cron 탭에서 당신이 쓴 줄 옆에
있는, 그 스크립트를 실행하는 줄입니다.

### Scripts

모든 에이전트에는 `/opt/boa/agents/<id>/scripts/`의 전용 `~/scripts/` 디렉터리가 있으며 기존 에이전트도 업데이트 후 갖게 됩니다. 실제 시스템 프롬프트에는 스크립트를 그곳에 저장하고, 새로 만들기 전에 기존 파일을 찾으며 그 디렉터리에서 실행하라는 지침이 들어갑니다.

에이전트 설정에서 **Scripts**를 엽니다. 행에는 파일 이름만 표시되며 기본값은 이름순입니다. **정렬 기준**에서 크기나 마지막 수정 시간으로도 양방향 정렬할 수 있습니다. **코드 표시**로 코드를 펼치고 이름 옆과 코드 아래의 **코드 숨기기**로 접습니다. **코드 편집**와 **스크립트 저장**로 편집합니다. 숨기거나 정렬을 바꿔도 초안은 유지됩니다.

**새 스크립트**를 선택하고 이름과 코드를 입력한 뒤 **스크립트 만들기**를 누릅니다. 저장은 즉시 적용되고 파일 소유자는 에이전트가 되며 실행 권한 `0700`이 설정됩니다. 저장해도 실행되지는 않습니다. 코드는 최대 64 KiB의 UTF-8 텍스트여야 합니다. 새 이름은 영문자, 숫자, 점, 하이픈, 밑줄로 최대 64자이며 영문자나 숫자로 시작합니다. 생성 시 기존 이름을 덮어쓰지 않습니다. 편집 중 에이전트가 파일을 바꾸면 오래된 리비전 저장을 거부하고 초안을 유지합니다.

## 실행 보고서가 가는 곳

채팅에서 시작한 실행은 거기서 답합니다. 시각이 된 카드가 시작한 실행도 같은
곳에서 답합니다. 에이전트 **자신의 crontab**이 시작한 실행은 특별히 어디에도
답하지 않습니다. 아무도 묻지 않았기 때문입니다. 그래서 다음과 같이 합니다.

- **항상 기록에**, **최근 실행** 아래에 남습니다. 각 실행이 무엇을 말했는지와
  비용입니다. 에이전트가 무엇을 해 왔는지 궁금할 때 볼 곳이 여기입니다.
- **방해할 가치가 있을 때는 채팅에도** 올라옵니다. 실행이 끝나지 못했거나,
  당신 눈에 보일 무언가(카드, 채널 메시지, 메일함)를 바꾼 경우입니다.
  살펴보기만 한 실행은 기록에만 남습니다. 그러지 않으면 매시간 crontab으로
  도는 에이전트가 하루에 스물네 번씩 “보고할 것 없음” 메시지를 대화에 올릴
  것입니다.

그런 메시지에는 위에 아무도 요청하지 않은 것이라고 적혀 있으며, 모델에게
다시 전달되는 일이 결코 없으므로 다음 메시지를 보낼 때 비용이 들지
않습니다.

**시작되지 않은 실행도 기록에 남으며**, “시작되지 않음”으로 표시됩니다.
API 키가 아직 설정되지 않은 에이전트에서, 또는 에이전트가 이미 실행 중일 때
**지금 실행**을 누르면, 기록의 줄이 둘 중 어느 경우였는지 알려 줍니다.
예전에는 화면에 실행이 시작되었다고만 나오고 그 뒤로 아무것도 나타나지
않았습니다. 이유가 아무도 읽지 않는 곳에 기록되었기 때문입니다. 시작되지
않은 실행은 에이전트의 하루 실행 횟수에 포함되지 않으며, 에이전트의 실패로도
세지 않습니다. 실행된 것이 아무것도 없기 때문입니다.

## 상태 표시줄

모든 페이지 맨 아래를 따라, 사이드바 밑까지 창의 전체 너비로 이어지는 띠는
설치 전체에 관한 것입니다.

- **실행기**와 **에이전트 API**: 실행 중이면 초록색입니다. 어느 하나라도
  빨간색이면 에이전트는 실행되지 않으며, 인터페이스의 다른 어떤 것도 그것을
  알려 주지 않습니다.
- **에이전트**: 전체 중 몇 개가 켜져 있는지.
- **보드**: 각 열의 카드 수.
- **오늘의 토큰**: 자정(UTC) 이후 모든 에이전트가 쓴 전체 양과, 그것에 든
  실행 횟수. 청구서보다 먼저 에이전트가 루프에 빠졌다는 것을 보여 주는
  숫자가 이것입니다.

띠의 오른쪽 끝에 있는 GitHub 마크와 **nipegun**이라는 이름은 프로젝트
저장소 <https://github.com/nipegun/bunch-of-aigents>를 새 탭으로 엽니다.
로그인한 계정은 표시되지 않습니다. 설치에는 계정이 언제나 하나뿐이므로,
그것을 표시해도 이미 아는 것 말고는 아무것도 알려 주지 않습니다.

## 에이전트가 답하는 언어

각 에이전트의 프롬프트를 당신이 생각하는 언어로 쓰면, 에이전트는 그 언어로
답합니다. 채팅은 그것으로 해결됩니다. 에이전트 자신의 crontab이 시작한
실행은 해결되지 않습니다. 아무도 어떤 언어로도 말을 걸지 않았고, 기본 제공
프롬프트는 영어이기 때문입니다. 그래서 스페인어로 운영되는 설치가 예약
보고서를 영어로 받고 있었습니다.

**설정 → 에이전트 → 에이전트가 답하는 언어**가 모든 에이전트에 대해 이것을
한꺼번에 해결합니다. 각 에이전트의 시스템 프롬프트에, 요청하는 언어로 쓴 한
줄을 더하며, 그 줄은 프롬프트가 언어에 대해 무엇을 말하든 그보다 우선한다고
밝힙니다. 기본값으로 두면 아무것도 바뀌지 않습니다. 각 에이전트는 자기
프롬프트의 언어로 답합니다.

이 설정은 브라우저의 선호인 이 인터페이스의 언어와 달리 서버에 저장됩니다.
cron이 깨운 실행에는 브라우저가 없습니다.

## 자기 언어로 프롬프트 쓰기

시스템 프롬프트는 당신이 생각하는 언어로 쓰세요. 시스템의 어떤 것도 영어에
묶여 있지 않습니다. 프롬프트, 메모리, 채팅, 카드 제목, 서비스 사이의
메시지가 모두 처음부터 끝까지 UTF-8이며, 악센트 같은 것도 그대로입니다.

새 에이전트가 받는 기본 프롬프트는 영어이며, 마지막 규칙은 에이전트에게
프롬프트가 쓰인 언어로 답하라고 지시합니다. 전체를 당신의 언어로 다시 쓰면
그 규칙도 함께 따라갑니다. 에이전트는 처음에 받은 프롬프트가 아니라 지금
가진 프롬프트를 따릅니다.

프롬프트는 고정된 열에서 줄을 바꾸지 않고, 한 줄을 통째로 저장합니다.
텍스트 상자는 읽기 쉽도록 화면에서 줄을 바꿔 보여 주지만, 그 줄바꿈을
파일에 넣지는 않습니다. 한 문장인 규칙은 한 줄로 남으며, 그것을 고친다고
문단의 줄바꿈을 다시 맞출 필요가 없습니다.

## 백업과 복원

이 설치를 당신의 것으로 만드는 모든 것은 `/opt/boa/` 아래와 에이전트의
Linux 사용자에 있습니다. 명령 하나가 그것을 아카이브 하나로 모읍니다.

```bash
./install-update-reinstall-debian.sh --backup
```

서비스가 실행 중인 상태에서(아무것도 멈추지 않습니다)
`/root/boa-backup-<date>.tar.gz`를 `root` 전용, 모드 0600으로 씁니다. 다른
곳에 쓰려면 경로를 넘기세요. `--backup /mnt/usb/boa.tar.gz`. 안에 들어 있는
것: 두 데이터베이스(write-ahead 로그에 아직 남아 있는 것도 빠뜨리지 않도록
SQLite 자체의 백업 API로 복사합니다), 공급자 키, 채널 비밀 정보, 세션 비밀
정보, 인증서, 홈·보호된 파일·Linux 사용자·crontab을 포함한 모든 에이전트, 이
서버에서 작성한 스킬과 도구, 그리고 비밀번호가 들어 있는 설치 로그. 들어 있지
않은 것: 코드, Python 환경, 브라우저, 그리고 이 기기 자체의 두 가지
선택(포트 모드와 브라우저 유무). 그래서 복원할 때 다른 기기의 선택을 가져오는
일은 없습니다.

직접 지정한 경로는 `root`가 소유하고 다른 사용자가 쓸 수 없는 폴더에 있어야 하며, 그 위의 모든 폴더도 마찬가지입니다. 예를 들어 `/root`나 root가 마운트한 디스크는 되지만 `/tmp`는 안 됩니다. 아카이브는 첫 바이트부터 비공개이고, 기존 파일 위나 링크를 통해 쓰이는 일이 없습니다.

**기기만큼 비공개로 보관하세요.** 모든 API 키, 모든 채널 토큰, 로그인
비밀번호가 들어 있습니다.

이 기기나 새 기기에 복원하려면:

```bash
./install-update-reinstall-debian.sh --install       # 새 기기에서만
./install-update-reinstall-debian.sh --restore /root/boa-backup-<date>.tar.gz
```

YES 입력을 요청하거나, `--yes`를 받습니다. 그다음 서비스를 멈추고, 에이전트
사용자를 같은 이름으로(비어 있으면 같은 id로) 다시 만들고, 데이터베이스, 키,
인증서, 에이전트, 스킬, 도구를 아카이브의 것으로 교체하고, crontab을
설치하고, 모든 것을 시작합니다. 백업의 이메일과 비밀번호로 로그인하세요. 둘
다 `/opt/boa/logs/install.log`에 `Credentials of the restored backup`이라는
제목 아래 덧붙여지며, 백업의 로그 전체는 그 옆에
`install.log.restored-<date>`로 보관됩니다.

이 기기에는 있었고 백업에는 없는 에이전트는 홈이 디스크에 남은 채
인터페이스에서 사라집니다. 에이전트 목록은 복원된 데이터베이스에 있기
때문입니다. Alpine에서는 같은 두 플래그를
`install-update-reinstall-alpine.sh`에 씁니다.

### 설치 제거

`root`로 실행합니다. `--purge`는 모든 BoA 서비스를 중지하고 모든 `boa-*` 유닛(Alpine에서는 OpenRC 서비스), `/opt/boa/`, `boa` 및 `agent-*` 계정과 crontab을 삭제합니다. 질문하거나 백업을 만들지 않습니다.

```bash
./install-update-reinstall-debian.sh --purge
./install-update-reinstall-debian.sh --uninstall
./install-update-reinstall-alpine.sh --purge
./install-update-reinstall-alpine.sh --uninstall
```

`--uninstall`은 먼저 권한 0700으로 `/root/boa-uninstall-<date>.<id>/`를 만듭니다. 이 폴더에는 이식 가능한 `backup.tar.gz`, 전체 `installation.tar.gz`(코드, 의존성, 모델, 로그 포함), `system.tar.gz`, 계정 기록과 crontab이 들어 있습니다. 파일 권한은 0600입니다. 삭제 전에 아카이브와 이식 가능한 복원 형식을 검증하며, 백업이 실패하면 삭제를 중단합니다.

다른 머신에서는 `--install`을 실행한 다음 `backup.tar.gz`로 `--restore`를 실행합니다. 나머지 파일은 복구를 위해 머신별 상태를 보관하며, 이식 가능한 가져오기는 대상의 코드와 포트 설정을 유지합니다. 두 제거 플래그 모두 `--yes` 없이 작동하고 기존 설치 스크립트 파일 이름을 유지합니다.

## 서비스

| 서비스 | 실행 사용자 | 하는 일 |
|---|---|---|
| `boa-proxy` | `boa` | HAProxy: 11443에서 TLS를 종료하고, 11080을 리디렉션하며, 웹 포트를 서비스합니다 |
| `boa-web` | `boa` | 웹 인터페이스와 API. 프록시 뒤의 Unix 소켓에서 동작합니다 |
| `boa-exec` | `root` | 사용자를 만들고, crontab을 설치하고, 에이전트 실행을 시작합니다 |
| `boa-samba` | `root` | SMB 사용자를 인증하고, 각 samba/ 폴더를 그 에이전트 사용자로 서비스합니다 |
| `boa-agent-api` | `boa` | 에이전트가 보드와 채널에 닿기 위해 쓰는 문 |
| `boa-buzzer` | `boa` | 보드를 지켜보다가 카드의 시각이 되면 에이전트를 깨웁니다 |
| `boa-embeddings` | `boa` | 문서 라이브러리의 로컬 벡터화 모델을 Unix 소켓으로 서비스합니다 |
| `boa-rag` | `boa` | 문서 라이브러리의 색인 대기열을 관리합니다 |
| `boa-channel-telegram.service` | `boa` | Telegram을 듣고 있어서, 휴대폰으로 에이전트에게 답할 수 있습니다 |
| `boa-channel-discord.service` | `boa` | Discord 채널에 대해 같은 일을 합니다 |
| `boa-channel-slack.service` | `boa` | Slack 채널에 대해 같은 일을 합니다 |
| `boa-channel-mattermost.service` | `boa` | Mattermost 채널에 대해 같은 일을 합니다 |
| `boa-channel-x.service` | `boa` | X 비공개 대화 |

```bash
systemctl status boa-proxy boa-web boa-exec boa-agent-api boa-buzzer \
                 boa-embeddings boa-rag \
                 boa-channel-telegram.service boa-channel-discord.service boa-channel-slack.service boa-channel-mattermost.service boa-channel-x.service boa-samba
journalctl -u boa-exec -f
```

Debian의 채널 유닛은 `boa-channel-<channel>.service`를 씁니다. `--update`로
업데이트하면 새 유닛을 켜기 전에 이전 채널 유닛을 멈추고 비활성화합니다.

Alpine에서도 같은 프로세스가 실행되며, 채널 서비스는 여전히 `boa-telegram`, `boa-discord`, `boa-slack`, `boa-mattermost`, `boa-x`입니다. 이들은 `supervise-daemon`이 감독하는 OpenRC 서비스이며,
각 서비스가 출력하는 내용은 `/opt/boa/logs/` 아래의 자기 파일로 가고, 매주
교체됩니다.

```bash
rc-status
rc-service boa-exec status
tail -f /opt/boa/logs/boa-exec.log
```

## 보안

공유 키는 공급자에 내장된 HTTPS 출처로 제한됩니다. 사용자 지정 게이트웨이에는 에이전트별 키가 필요합니다. 봇이나 대상이 바뀌면 대기 중인 Telegram 및 Discord 답변은 폐기되며 웹 대화에는 남습니다. 브라우저 도구는 WebSocket 대상을 검증하고 서비스 워커를 차단합니다.

신뢰하는 백업만 복원하세요. 검증은 설치 코드 경로와 에이전트 외 사용자의 crontab을 거부하며 매니페스트는 서명이 아닙니다. 에이전트 소유의 오래된 정의는 신뢰할 수 있는 사본에서 복구해야 합니다. 설치 프로그램은 `--commit`과 `--source-sha256`을 지원하며 코드 출처를 검증하려면 독립적으로 얻은 해시를 사용하세요.

이 설계는 에이전트가 언젠가는 당신이 의도하지 않은 일을 할 것이라고
가정합니다. 셸을 가진 언어 모델이기 때문입니다.

- **각 에이전트는 별도의 Linux 사용자이며**, 그 홈은 `0700`입니다.
  에이전트는 서로의 파일, 프롬프트, API 키를 읽을 수 없습니다.
- **`/opt/boa/agents/`는 `0711`이므로**, 어떤 에이전트도 다른 에이전트가
  존재하는지 목록조차 볼 수 없습니다.
- **어떤 에이전트도 결코 root로 실행되지 않습니다.** root로 실행되는 것은
  `boa-exec`뿐이며, 그것도 Unix 소켓을 통해 정해진 작업 목록만 받습니다. 그중에
  “이 명령을 실행하라”는 없습니다.
- **실행은 한도뿐 아니라 커널로도 제한됩니다.** 어떤 에이전트도 1024개가 넘는 프로세스와 스레드를 가질 수 없으므로 fork bomb은 그 수에서 멈춥니다. 각 실행은 2 GiB 메모리를 가진 자체 cgroup(Debian에서는 systemd scope, Alpine에서는 실행기가 준비하는 cgroup)에서 동작하며, 끝날 때 남겨 둔 것도 종료합니다. cron이 시작한 실행, 예약된 스크립트, 라이브러리 색인에도 같은 제한이 적용되고, 에이전트는 자기 cron 줄을 쓸 수 없습니다.
- **에이전트는 채널 인증 정보를 결코 보지 못합니다.** 봇 토큰은 메시지가
  아닙니다. 그 봇이 보낼 수 있는 무엇이든 보낼 수 있는 영구적인 권한입니다.
  에이전트는 에이전트 API에 보내 달라고 요청하고, 에이전트 API가 보냅니다.
- **에이전트는 자기 카드만 건드립니다.** [칸반 보드](#칸반-보드)를 보세요.
- **`web.fetch`는 사설 주소를 거부합니다.** 확인된 IP를 검사하고 리디렉션될
  때마다 다시 검사하므로, 악의적인 페이지를 읽는 에이전트가 당신의 내부
  네트워크를 호출하라는 지시를 받을 수 없습니다.
- **느린 서버가 실행을 붙잡을 수 없습니다.** `web.fetch`와 `rss.fetch`는 가져오기 전체로 센 `timeout_seconds`에서, 또는 그보다 먼저 오면 실행이 끝날 때 멈춥니다. 서버가 응답을 아무리 천천히 보내도 마찬가지입니다.
- **에이전트는 자신의 제한을 초기화할 수 없습니다.** BoA는 하루 실행 횟수를 에이전트의 기록이 아니라 자체 데이터베이스에서 세고, 에이전트의 실행을 한 번에 하나로 유지하는 잠금은 root의 것입니다. 에이전트의 홈에 있는 어떤 것도 둘 중 무엇도 되돌리지 못합니다.
- **로그는 root의 것입니다.** `/opt/boa/logs/`는 `root` 소유, 그룹 `boa`, 모드 0750입니다. 서비스는 그곳에서 자기 파일에 쓰며 `install.log`나 root가 쓰는 다른 파일을 바꿔치기할 수 없습니다.
- **공개 게시에는 여러분이 필요합니다.** `x.post`가 있는 에이전트는 요청만 합니다. 게시물은 수신자 계정에서 여러분이 그 코드에 DM으로 답할 때 나갑니다.
- **Alpine에서는 `boa-proxy`만 80과 443을 사용합니다.** `direct` 모드에서 `supervise-daemon`이 그 서비스에만 capability를 줍니다. 아무 사용자나 쓸 수 있던 haproxy 바이너리에는 더 이상 붙어 있지 않습니다.

LAN을 위한 것이며, 인터넷에 노출해서는 안 됩니다.

## 무언가 작동하지 않을 때

**`--ports direct`를 골랐더니 기기의 HAProxy가 사라졌습니다.** 사라진 것이
아니라 물러난 것입니다. 멈추고, Alpine에서는 모든 런레벨에서 빠지고,
Debian에서는 비활성화되고 마스킹되며, 그 `/etc/haproxy/haproxy.cfg`는 설치
프로그램이 쓴 것이면 삭제되고, 당신이 쓴 것이면
`haproxy.cfg.before-boa.<date>`로 보관됩니다. 이 모드에서는 애플리케이션이
직접 80과 443에 바인딩하며, 그 포트를 쥐고 있는 다른 무엇이든 있으면
애플리케이션이 아예 시작하지 못합니다. 켜진 채 남은 프록시는 다음 부팅 때
애플리케이션이 실행되기도 전에 그 포트를 차지할 것입니다. `haproxy` 패키지가
여전히 설치되어 있는 것은 일부러입니다. `boa-proxy`가 바로
`/usr/sbin/haproxy`이며, 이 모드에서 80과 443을 서비스하는 것이 그것입니다.

되돌리려면 설치 프로그램을 `--update --ports proxied`로 실행하세요. 유닛의
마스킹을 풀고, 기기의 설정을 다시 쓰고, 시작합니다. 예전 파일이 있었다면
여전히 `before-boa` 이름으로 그 옆에 있습니다.

**`boa-proxy`가 계속 재시작되고 11443에서 아무것도 듣고 있지 않습니다.**
`/opt/boa/logs/boa-proxy.log`를 읽으세요. `Cannot raise FD limit to 4131`이라고
되어 있다면, 이 기기의 파일 디스크립터 하드 한도가 프록시가 요청한 것보다
낮은 것입니다. 보통 작은 컨테이너입니다. 이 문제가 고쳐지기 전에 만든 설치는
`/opt/boa/config/haproxy.cfg`에 아직 `maxconn 2048`이 있습니다. 설치
프로그램을 `--update`로 실행하면 그 파일을 다시 쓰며, 그 자리에서 고치려면
다음과 같이 합니다.

```bash
sed -i 's/^  maxconn 2048$/  fd-hard-limit 4000/' /opt/boa/config/haproxy.cfg
rc-service boa-proxy restart        # Debian에서는 systemctl restart boa-proxy
```

그러면 HAProxy는 실제로 가질 수 있는 디스크립터를 기준으로 크기를 정하며,
하드 한도가 4096이면 약 1987개의 연결입니다. 이 프로그램에 필요한 것보다 훨씬
많습니다.

**설치 프로그램이 “Everything is in place but the application does not
answer”로 끝납니다.** 설치는 되어 있지만 페이지가 끝내 돌아오지 않은
것입니다. 로그에 이미 이유가 들어 있습니다.

```bash
sed -n '/Why it did not answer/,$p' /opt/boa/logs/install.log
```

그 블록은 그 순간 기기의 상태입니다. curl이 요청을 어떻게 처리했는지, 그
포트에서 무언가 듣고 있는지, 열 서비스 모두의 상태, 그리고 프록시와 웹
애플리케이션이 출력한 마지막 줄들. `000`은 HTTP 코드가 아닙니다. curl이 아무
코드도 받지 못했다는 뜻입니다. `nothing is listening on port 11443` 옆에서
스스로 `started`라고 하는 서비스는 몇 초마다 죽었다가 재시작되는
프로세스이며, 몇 줄 아래에 있는 그 서비스 자신의 로그가 이유를 말해 줍니다.

여기서 실패한 업데이트는 이미 이전 버전을 되돌려 놓고 그것을 실행하고
있습니다. 첫 설치에는 되돌아갈 것이 없으므로 모든 것을 그대로 둡니다.
블록이 지목하는 것을 고친 다음 설치 프로그램을 `--update`로 다시 실행하세요.

**설치 프로그램이 “systemd is not running”으로 멈춥니다.** systemd가 PID 1이
아닌 기기에 설치하기를 거부하는 것입니다. 설치하는 서비스가 모두 systemd
유닛이라 시작해 줄 주체가 없기 때문입니다. 일반적인 Debian이라면 괜찮습니다.
컨테이너는 systemd를 실행하도록 만든 것이 아니라면 안 됩니다.

```bash
apt-get install -y systemd systemd-sysv dbus dbus-user-session
```

그런 다음 `/sbin/init`을 명령으로 지정해 컨테이너를 다시 만드세요. 이미 실행
중인 컨테이너는 PID 1을 바꿀 수 없습니다. Alpine에서는 이 문제가 생기지
않습니다. 그 설치 프로그램은 기기에 OpenRC가 없으면 직접 추가합니다.

**지금 실행을 눌러도 아무 일도 일어나지 않습니다.** 사이드바 맨 아래의 점 두
개를 보세요. `executor`(실행기)가 빨간색이라면:

```bash
systemctl status boa-exec
journalctl -u boa-exec -n 50
```


**브라우저에 503이 나오는데 서비스는 모두 실행 중입니다.** 기기의 HAProxy가
백엔드를 다운으로 표시한 것입니다. 거의 언제나 그 백엔드의 `option
ssl-hello-chk` 때문입니다. 그 ClientHello는 TLS 1.2보다 오래된 것이고,
애플리케이션은 TLS 1.2를 요구합니다. 그 줄을 지우고 HAProxy를 다시 불러오세요.

**에이전트가 실행되는데 아무것도 하지 않습니다.** 기록 패널을 확인하세요.
그다음 손으로 실행해 지켜보세요.

```bash
runuser -u agent-001 -- /opt/boa/venv/bin/python3 \
  /opt/boa/webapp/backend/core/runner.py --agent-id 001
```

`--dry-run`을 더하면 모델을 호출하지 않고 무엇을 불러올지(공급자, 도구,
상한) 볼 수 있습니다.

**모델에 닿을 수 없다고 합니다.** 자체 운영 공급자라면 서버가 살아 있는지,
기본 URL이 맞는지 확인하세요. 클라우드 공급자라면 키 파일이 에이전트의 홈에
있고 그 에이전트의 소유인지 확인하세요.

**도구를 쓸 수 없다고 합니다.** 그 에이전트의 페이지에서 도구가 체크되어
있지 않은 것입니다. 프롬프트로 그것을 무시할 수는 없으며, 바로 그것이
핵심입니다.

**카드가 더 이상 나타나지 않습니다.** 그 에이전트의 칸반 체크박스가 해제되어
있거나, 사이드바 맨 아래의 `agent API`(에이전트 API)가 빨간색입니다.

```bash
systemctl status boa-agent-api
```

**에이전트가 한 모든 일을 보고 싶습니다.** 그 기록은 에이전트 자신의 홈에
있습니다.

```bash
cat /opt/boa/agents/001/runs.jsonl
```

한 줄에 JSON 객체 하나입니다. 언제 실행되었는지, 무엇을 썼는지, 끝났는지.
