## 1. 架构与设计决策

这部分无法从代码中推导出来，所以是值得一读的部分。

### 前提

这里的智能体，是一个在服务器上拥有 shell 的语言模型，由 cron 唤醒，无人看管。每一项结构性决策都源于认真对待这一点：模型迟早会做出意料之外的事，所以问题不在于如何阻止它，而在于事情发生时它能触及什么。

### 每个智能体一个 Linux 用户

智能体 `007` 就是系统用户 `agent-007`，它拥有 `/opt/boa/agents/007/`，权限模式为 `0700`。智能体之间的隔离由内核负责，而不是用 Python 写的沙箱。一个智能体读不到另一个智能体的系统提示词、运行日志或 API 密钥，因为文件系统不允许。

`/opt/boa/agents/` 本身是 `root:root 0711`：可以穿越，但不能列出。智能体无法枚举其他智能体，只能在自己猜测的路径上打开失败。

正因为这一决策，`bash.run` 不需要白名单。给 shell 设黑名单只是做做样子——任何能运行 `sh` 的东西都能运行名单上列出的任何东西——而用户账户是由内核强制执行的边界。

### 智能体不能改写自己的哪些东西

主目录归智能体自己所有，权限为 0700，这正是关键所在：它的记忆、它的运行日志、它的对话以及它写的任何脚本都放在那里。其中有三个文件不该由它来改，它们位于主目录之外的 `/opt/boa/agents-config/xxx/`，该目录是 `root:agent-xxx 0750`，其父目录是 `root:root 0711`。

| 文件 | 为什么它不归智能体管 |
|---|---|
| `info.json` | 它被授予了哪些工具，以及它可以花多少 |
| `system-prompt.md` | 对它应该做什么的定义 |
| `api-token` | 它向智能体 API 表明身份所用的凭据 |

让这一点成立的不是文件的属主，而是目录的属主。目录上的写权限决定了其中的文件能否被删除和替换，所以一个拥有该目录的智能体，无论文件归谁所有，都可以删除 `info.json` 再写入自己的版本。它可以进入这个目录并读取其中内容，但不能在其中创建、重命名或删除任何东西。

**这条规则对抽屉本身和抽屉里的东西同样适用**，这就是这些文件不再放在 `agents/xxx/config/` 中的原因。那个路径是主目录中的一个条目，主目录以 0700 归智能体所有，而重命名一个条目只需要父目录的写权限，别的什么都不需要——被重命名对象自身的权限模式根本不会被查看。所以智能体虽然无法编辑 `info.json`，却可以这样做：

    mv ~/config ~/config-old && mkdir ~/config && echo '...' > ~/config/info.json

然后程序就会从这个替代品中读取。把抽屉移出主目录，就让路径上的每一个目录都归 root 所有。这次迁移带来两个结果：

  - **不再回退到主目录。** 以前有过这种回退，目的是让更新时服务不至于在迁移运行之前就停止响应——而它本身就是一个绕过手段，因为只要把真正的文件藏起来，就能让程序改读智能体自己写的那份。现在守护进程在启动时也会执行迁移，安装脚本同样会做，所以已没有需要兜底的情况。
  - **删除智能体也会删除它的配置。** 配置已不在 `userdel --remove` 会一并删掉的主目录里，如果留下来，就会被交给下一个分配到该 id 的智能体。

`fOpenProtectedAgentFile` 是对同一问题的第二重回答：它以 `O_NOFOLLOW` 打开文件，并在已打开的文件上检查它是普通文件、属主为 root、且其他任何人都不可写。这样才能扛住更新时一次误操作的 chmod，或者从属主错误的备份中恢复。

这个问题是在修复之前、在一套真实安装上实测出来的：一个智能体把 `mail.read` 追加到了自己的 `info.json` 中，随后特权守护进程就报告该工具已被授予——也就是说，智能体可以给自己授予邮箱、频道的权限，或者提高自己的开销上限。它还可以把自己的提示词替换成“忽略你的所有规则”，从那以后的每次运行都会如此。

智能体之间的隔离不需要这些：`/opt/boa/agents/` 是 `root:root 0711`，每个主目录都是 0700，内核本来就会拒绝。所以即使某个工具有 bug，隔离依然成立。

### root 从主目录中读取什么

运行日志、记忆和对话是智能体自己的文件：由它自己的进程写入，位于它自己的 0700 主目录中，却由特权守护进程以 root 身份读取——而 root 指向什么就读什么。在这套机制出现之前对代码所做的实测：一个名为 `runs.jsonl` 的 FIFO 会让打开它的守护进程线程永远卡住，而由于智能体列表会读取每个智能体的运行日志，之后每一次请求该列表都会多泄漏一个线程；一个名为 `memory.md`、指向机器上任意文件的链接，会让 root 把那个文件的文本交给界面；而一个指向无尽内容的链接，会让 root 一直读到被杀掉为止。

因此这三者都通过 `fReadAgentOwnedFile` 读取，它是 `fOpenProtectedAgentFile` 的姊妹函数，专门处理确实属于智能体的文件：`O_NOFOLLOW` 在打开时拒绝链接，`O_NONBLOCK` 防止 FIFO 让打开操作一直等到有人写入，而各项检查都在已打开的描述符上进行——普通文件、属主为该智能体的用户——所以在检查与读取之间什么都无法被调包。它读取的量永远不超过一个上限，这个上限作用于实际读到的内容，而不仅仅依据 `fstat` 给出的结果，因为智能体可能在读取过程中继续追加：运行日志和对话为 32 MB，文件更大时从末尾读起，因为历史记录要显示的是最新的几行；记忆为 4 MiB，足以容纳其上限一百万个 UTF-8 字符。只有超出该读取预算的外部写入文件才会得到 `[truncated]`；`fWrite` 会在替换任何内容之前拒绝过大的内容。一个坏字节只损失一行，而不是整次读取。

被拒绝的情况会明说，而不是被悄悄吞掉：`read_run_journal`、`read_chat` 和 `read_memory` 会带着原因失败，这样运维人员就能知道那个主目录里有东西不是应用写的。唯一的例外是针对所有智能体的 `read_usage_summary`，侧边栏就是据此绘制的：在那里，一个无法读取的运行日志只会让该智能体失去它的统计总数，并在旁边注明原因，其他智能体的数据则不受影响。

### 命令行上传递什么

守护进程用 `Popen` 以智能体身份启动一次运行，而所有者输入的消息——或者到期卡片生成的提示词——过去曾是它的参数之一：`--chat-message <text>`、`--prompt <text>`。进程的命令行可以被机器上的每个用户通过 `/proc/<pid>/cmdline` 读取，而拥有 `bash.run` 的智能体就是机器上的一个用户。在 Debian 测试机上实测：以 `agent-001` 身份运行的 `ps` 显示出了所有者刚刚发给 `agent-000` 的消息，只要那次运行还活着就一直可见，而默认情况下一次运行最长可达五分钟。

所以文本改走子进程的标准输入，命令行上只带 `--chat-message-on-stdin` 或 `--prompt-on-stdin`。`fStartRunner` 是唯一启动运行器的地方：在任何进程存在之前，它就会拒绝长于 `cMaxStdinPayloadBytes` 的文本，因为这个上限低于管道的 64 KiB 缓冲区，而能放进缓冲区的写入永远不必等待子进程——这个守护进程不会等待运行器。写入发生时子进程已经退出（比如解释器在导入时失败），属于管道断开，而不是守护进程的故障。在另一端，运行器以同样的上限读取文本，拒绝空的对话消息，而不是去回答一个没人提出的问题，并且在拒绝时关闭为之启动的那一轮对话，这样对话就不会永远等下去。`--prompt` 和 `--chat-message` 仍然保留，用于从终端手动启动的运行。

### 一次运行能对机器做什么

`info.json` 中的开销上限——token 数、步数、秒数、每天的运行次数——由运行器强制执行，而运行器正是智能体在驱动的程序。当出问题的恰恰是这个程序本身时，能守住的是由内核强制执行的限制，分为两层。

运行器在做任何其他事情之前先降低自己的资源限制，即 `fApplyResourceLimits`，它从入口点调用，而不是从 `fMain` 调用——测试会在进程内调用 `fMain`，而在一个已有数千个线程在运行的开发者会话中降低 RLIMIT_NPROC，会让该会话无法再 fork。运行启动的每个进程都会继承这些限制：RLIMIT_NPROC 为 1024，按智能体的 uid 整体计数，所以来自 `bash.run` 的 fork 炸弹会停在这个数目上，而不是拖垮整台机器——线程也计入其中，这就是它没有设得更小的原因，一个浏览器就有几百个线程；不生成 core 文件；任何文件都不能超过 4 GiB。不设 RLIMIT_AS：Chromium 会以几十 GB 为单位预留地址空间，设了它就无法启动。这一层在 Debian 和 Alpine 上相同，而且由智能体自己的 crontab 启动的运行只有这一层。

在 systemd 为 PID 1 的系统上，守护进程会加上第二层：`fStartRunner` 把这次运行放进一个专属的临时 scope，即 `boa-agents.slice` 下的 `boa-agent-<id>-<random>.scope`，并设置 `TasksMax=1024` 和 `MemoryMax=2G`。`systemd-run --scope` 会 exec 成该命令，所以 pid 仍然是运行器的，`/proc` 仍然显示它的命令行；降权到智能体用户靠的是 `setpriv`，因为 systemd-run 必须以 root 身份运行才能创建 scope。在这样做之前的实测：一次运行是 `boa-exec.service` 的子进程，处于守护进程自己的 cgroup 中，一个失控的智能体耗尽了守护进程的 TasksMax，使它无法再 fork。scope 也负责结束一次运行遗留下来的东西：`bash.run` 向自己的进程组发信号，所以一个调用了 `setsid` 的命令，或者一个按时结束的命令留下的后台子进程，都会比这次运行活得更久；`fWatchRunner` 等待运行结束并停止它的 scope，这样无论运行启动的东西把自己挪到了哪里，都能被触及。一次被杀掉的运行——被内存上限杀掉，或被运维人员杀掉——在退出时什么都没写，所以由同一个线程在运行日志中记录结束，并在对话中关闭这一轮；自行退出的运行已经做完了这两件事，而这一轮的状态会被检查，而不是想当然。

### 服务商密钥存放在哪里

所有智能体共享的密钥位于 `/opt/boa/config/apikeys/<provider>.key`，归 `boa` 所有，目录为 `0700`，文件为 `0600`。

0750 和 0640 本来就能把智能体挡在外面——没有哪个智能体用户在 `boa` 组里——但那要依赖每个智能体的组列表在整个安装生命周期内始终为空，而只需一条 `usermod -aG` 就能让它不再成立。不给组任何权限的模式则不依赖于此。`api_keys.fWrite` 在每次写入时都设置这两种模式，而不仅仅是在创建时，所以从旧安装继承来的目录会在第一次保存密钥时被收紧。

这个目录在改名之前叫 `keys`：它读起来像是“本安装的密钥”，而且与每个智能体主目录内的 `keys/` 只差一个拼写错误，后者是另一回事，智能体*可以*读取它——那是它自己的密钥，放在那里是为了把它的费用记到另一个账户上。安装脚本在 `--update` 时把旧目录迁移过去，并且只在它变空之后才将其删除。

这些都无法阻止智能体持有它实际所用服务商的密钥：智能体 API 会把那一个交给它，它需要用它来发起调用，而拥有 `bash.run` 的智能体可以把它打印出来。它阻止的是智能体读取它不使用的那些服务商的密钥。

### 十个服务，两个以 root 启动

| 进程 | 用户 | 为什么存在 |
|---|---|---|
| `boa-proxy` | `boa` | HAProxy：终止 TLS，为两个端口提供服务 |
| `boa-web` | `boa` | 在 Unix 套接字上提供界面和 API |
| `boa-exec` | `root` | 创建用户并启动智能体的运行 |
| `boa-samba` | `root` | 验证 SMB 会话，然后以所属智能体的身份提供文件 |
| `boa-embeddings` | `boa` | 在 Unix 套接字上提供文档库的本地向量化模型 |
| `boa-rag` | `boa` | 调度文档库的索引队列 |
| `boa-agent-api` | `boa` | 保管智能体可以使用但不能读取的东西 |
| `boa-buzzer` | `boa` | 当智能体的某张卡片到期时唤醒它 |
| `boa-channel-telegram` | `boa` | 监听 Telegram，把收到的内容交给某个智能体 |
| `boa-channel-discord` | `boa` | 同上，用于 Discord 频道 |

Debian 上的频道单元是 `boa-channel-telegram.service` 和 `boa-channel-discord.service`；以后的频道单元遵循 `boa-channel-<channel>.service` 的格式。OpenRC 上仍保留 `boa-telegram` 和 `boa-discord`。`system_info.fServiceName` 为“操作系统”标签页和监听程序的状态报告解析这些名称。

`fInstallSystemdUnits` 会调用 `fRetireLegacyChannelUnits`，在删除每个旧频道单元并启用其替代单元之前，先将其停止并禁用。不存在旧单元时，重复更新也能正常进行。如果更新在安装新单元之前就失败了，`fStartServices` 可以在回滚时重新启动旧单元。

后四个服务以 `boa` 而不是 root 身份运行，这是有意为之：它们每一个都需要以某个智能体自己的用户身份做事——启动一次运行、写入 0700 的主目录——而它们每一个都请 `boa-exec` 代劳，而不是自己被授予这项特权。一个能从外部触及的服务（两个监听程序实际上就是如此），是最不应该持有这项特权的。

### 虚拟环境不可迁移

`python3 -m venv <path>` 会把 `<path>` 写进之后安装到其中的每个控制台脚本的 shebang、activate 脚本中的 `VIRTUAL_ENV`，以及 `pyvenv.cfg` 的 `command` 一行。环境在 `venv.new` 中构建，然后重命名为 `venv`，于是这三处指向的都是一个已经不存在的目录。

在真实的 Debian 13 和真实的 Alpine 3.24 上实测：两次安装都完成了，都打印了 "Installation finished"，却都让 `boa-web` 每五秒重启一次，报错如下

```
status=203/EXEC - Failed to execute /opt/boa/venv/bin/gunicorn:
No such file or directory
```

文件明明在那里。它的第一行指向 `/opt/boa/venv.new/bin/python3`，而这个文件并不存在。

`fBuildVirtualEnv` 本来就有针对这类故障的检查，而且检查通过了，因为它运行的是 `bin/python3`——一个指向系统解释器的符号链接，无论它碰巧位于何处都能应答。只有控制台脚本才把路径写死在里面。所以现在这项检查还会运行 `bin/gunicorn --version`，也就是服务单元所执行的那个文件，并且由 `fRepointVirtualEnv` 趁环境仍处于构建时的名称之下，改写全部三处记录的路径。改写结果会被验证，而不是想当然：如果将来某个 pip 以别的方式写控制台脚本，安装脚本就会停在那里。

### 失败的更新也会留下仍在运行的东西

三个阶段，顺序本身就是修复。

更新过去会先停止服务、删除 `webapp/`，然后才运行 pip。一旦 pip 失败——没有网络、索引服务器宕机、某个 wheel 无法构建——留下的就是一套服务已停止、代码也没了的安装：一台一分钟前还在正常工作的机器，需要有人发现并手动恢复。

| 阶段 | 发生什么 | 失败的代价 |
|---|---|---|
| 准备 | 提问、安装依赖、下载代码，就在正在运行的 virtualenv 旁边构建新的 virtualenv，并检查它能否导入 | 没有代价。旧版本仍在运行，未被触动 |
| 切换 | 停止，把 `webapp/` 移到 `webapp.previous`、`venv` 移到 `venv.previous`，把新的放到位，启动 | 可撤销：两个旧版本仍在磁盘上 |
| 验证 | `curl` 向应用请求登录页，在三十秒内请求十五次 | `fRollBack` 把两者都放回去并重新启动 |

那个 `curl` 只在 `proxied` 模式下发送 PROXY 协议。在 `direct` 模式下，绑定没有 `accept-proxy`，所以 PROXY 头会落进 TLS 握手中，请求根本得不到任何应答。它过去在两种模式下都会发送，导致每一次 `--install --ports direct` 都以 "did not answer" 告终，而那套安装其实正在正常提供页面；每一次 direct 模式下的 `--update` 也都会自行回滚。通过把两台测试机都切换到 `direct` 再切回来得到了确认：当这个标志与模式绑定后，两台机器先在 443 上、然后在 11443 上都返回了 200。有一个测试针对一个会记录自身参数的 `curl`，从两个安装脚本中分别运行 `fVerifyInstallation`，每种模式各一次，并检查该标志在一种模式下存在、在另一种模式下不存在。

当那个 `curl` 始终得不到应答时，`fExplainWhyItDoesNotAnswer` 会把那一刻机器的状况写进错误信息所指向的同一个日志：curl 自己怎么说——用 `-sS` 再问一次，以便区分连接被拒绝、握手失败和请求超时，因为 `000` 不是 HTTP 状态码，而是 curl 在说它从未得到过状态码——十个服务各自的状态、端口上到底有没有程序在监听，以及 `boa-proxy.log`、`boa-web.log` 和 gunicorn 的 `error.log` 的最后十五行。`fReportServiceStates` 是两个安装脚本之间不同的那一半：Alpine 上是 `rc-service ... status`，Debian 上是 `systemctl is-active` 加上 `boa-web` 和 `boa-proxy` 的 journal。

它之所以存在，是因为在一台全新的 Alpine 上首次安装时，结果停在了 "The application did not answer on port 11443 (last code: 000)"，而日志里关于此事别无他物——没说哪个服务挂了，没说端口是否被占用，gunicorn 打印的内容一行都没有。错误信息点名的那个唯一的文件，回答不了人们打开它想要回答的问题。该在其中找什么：一个自称已启动的服务，旁边却写着 "nothing is listening on port 11443"，说明有个进程在不断死掉又被重启，因为一个受监管的服务即使在启动的瞬间就死掉，也会被启动它的命令报告为已启动。有四个测试会真正运行这两个函数——分别针对一个拒绝连接的 `curl`、一个占用端口的 `ss` 和一个不占用端口的 `ss`，以及一个回答 "stopped" 并返回失败的 `rc-service` 和 `systemctl`。

`fRollBack` 在子 shell 中启动服务，而它旁边的 `|| true` 单靠自己是不够的：服务起不来时 `fStartServices` 会调用 `fDie`，`fDie` 会调用 `exit`，而无论旁边写了什么，`exit` 都会结束这个 shell。在真实的 Alpine 上实测：`boa-web` 反复崩溃重启时，`boa-proxy` 被 OpenRC 停掉了，回滚自己对它的启动在争夺服务锁时落败，安装脚本就死在了 `fRollBack` 内部。回滚其实已经成功——旧版本已经回来并且在应答——但运维人员看到的却是 "The boa-proxy service would not start"，对刚刚回滚了一次更新只字未提。在那个时刻，关于发生了什么的说明是运维人员仅有的东西。

旧版本由 `fFinishUpdate` 删除，而且只在新版本应答之后才删除。

`fRollBack` 过去只在一个地方运行：最后那次 `curl` 失败时。在 `fStopServices` 和那项检查之间，有十几个可能中途死掉的步骤——证书文件不见了、HAProxy 无法解析的代理配置、无法安装的单元——每一个都会让服务处于停止状态、新代码已经就位、`webapp.previous` 留在磁盘上，却没有人把它放回去。消息说出了失败的是什么，却对机器已经宕机只字未提。所以 `fDoUpdate` 在即将停止服务前设置 `vUpdateSwitched`，而 `fCleanup`——即 EXIT trap，无论子进程以何种方式结束都会运行——在发现该标志已设置且退出码不为零时执行回滚。离开切换阶段的两条路径会清除该标志：`fRollBack` 本身，这样显式路径就不会回滚两次；以及 `fFinishUpdate`，因为新版本一旦应答，就没有什么可回退的了。在两台测试机上把私钥藏起来实测："Missing certificate files"、"Putting the previous version back"，每个服务都起来了，登录页在旧代码上返回 200。有一个测试让每个安装脚本中真正的 `fCleanup`、`fRollBack` 和 `fFinishUpdate` 经历三种退出：切换之后、切换之前，以及完成之后。

`--install` 和 `--reinstall` 没有需要保留的旧版本，所以它们没有切换阶段，也没有回滚——但它们有验证阶段。它们过去以 `fWriteCredentialsFile` 结束，于是在两台真实机器上打印出了 "Installation finished"，而这两台机器的 Web 服务每五秒就重启一次：从来没有任何东西向应用问过一句话。现在它们会请求同一个登录页，请求不到时就如实说明并指出日志所在，因为机器上没有可以回退的东西。

`pip` 本身的版本是锁定的。不带版本号的 `--upgrade pip` 意味着同一份代码的两次更新可能解析出不同的结果，而锁定依赖项正是为了避免这一点。仍然没有锁定的是传递依赖——所以 `pip freeze` 的结果会被记录到环境中，下次更新时会打印出哪些发生了变化，这是任何人能发现这一点的唯一途径。

### 半途停下的安装

`fIsInstalled` 过去只要 `webapp/backend` 和 `boa` 用户存在，就认为机器已经安装——而这发生在虚拟环境、证书、数据库和管理员之前。一次在 pip 阶段因网络中断而死掉的安装，之后再运行 `--install` 会得到 "already installed"，运行 `--update` 则会因缺少的某样东西而死掉，只有 `--reinstall --yes` 能越过它，却没有任何东西把这一点告诉运维人员。

现在，完成的安装会留下 `/opt/boa/installed`，它由 `fMarkInstalled` 写入，而且只在 `fVerifyInstallation` 拿到页面之后才写：一套已经就位却不应答的安装不算完成，一次回滚了的更新也不算新版本。没有这个标记时，由完成的安装总会具备的五样东西来代替它——代码、用户、`venv/bin/gunicorn`、`db/boa.sqlite` 和 `certificates/privkey.pem`——所以标记出现之前的安装仍然算数，并会在下次更新时获得标记。`--install` 所做的其他一切本来就可以安全地做两次：用户只在缺失时才创建，环境在旧环境旁边构建，证书存在时会被保留，管理员会被删除并以新密码重新写入。所以只要再运行一次 `--install`，半途而废的安装就能完成，而 `--update` 发现这种安装时也正是这么说的。顺带一提，在 Debian 安装脚本中，`fGeneratePassword` 被移到了 `fInstallDependencies` 之后，原先的顺序是反过来的：`openssl` 在 Debian 上是 Priority: optional，于是在一个最小镜像上，生成密码所需的那个软件包还没安装，密码就先生成了。

### 安装脚本运行的一切都会进入它的日志

`fLog` 过去只把它自己的行写进 `install.log`，别的什么都不写。apt、pip、HAProxy 校验以及其他所有子进程都写到终端，所以失败的安装留下的日志里只有 "Installing the dependencies."，关于解释原因的 apt 错误一个字都没有——而那恰恰是人们打开这个文件想要找的细节。

`fStartCapturingOutput` 把这个 shell 自己的 stdout 和 stderr 重定向到一个 FIFO，由 `tee` 把内容复制到日志和终端。之所以用 FIFO，而不是 `exec > >(tee ...)`，是因为后者只有 bash 才支持，而 Alpine 启动时没有 bash；也不是在 `fMain` 外面套一条管道，因为那样会把它放进子 shell，破坏让 errexit 保持有效的 `fMain & wait` 安排。

由此产生两个后果，两个都必须处理：

`fLog` 既回显该行，又自己把它追加到日志中。一旦 stdout 变成了追加到同一个文件的 tee，第二次写入就成了重复：一次 90 行的安装产生了一个 185 行的日志，其中每一行都出现了两次。现在 `fLog` 只在捕获未运行时才写入文件。

`tee` 按 inode 保持日志处于打开状态。`--reinstall` 会删除整棵目录树（包括日志），再放回一份全新的副本——所以从那一刻起，`tee` 是在向一个没有名字的 inode 追加内容，而由于 `fLog` 已不再写入文件，丢失的将是重装的整个后半段，包括生成的密码。`fRestartCapturingOutput` 会把捕获重新指向现在存在的那个文件。

### 两个安装脚本，一个应用

`deploy/install-update-reinstall-debian.sh` 写入 systemd 单元，并且**要求 systemd 是正在运行的机器上的 PID 1**：以其他任何方式启动的 Debian 都不是目标，安装脚本会拒绝它，而不是安装到一台什么都启动不了的机器上。`deploy/install-update-reinstall-alpine.sh` 把来自 `deploy/openrc/` 的 OpenRC 服务写入 `/etc/init.d/`，并且事先什么都不需要：机器上没有 OpenRC 时，它会自己安装。两者安装的是同样的十个进程、`/opt/boa` 下同样的目录树、同样的用户模型；有一个测试会逐步比较两者，当其中一个多出另一个没有的步骤时就会失败。

它们不是用同一种语言写的，这是有意为之。Debian 的那个是 bash，和这里的其他一切一样。Alpine 的那个是 POSIX shell，使用 `#!/bin/sh`，因为全新的 Alpine 没有 bash：用 `#!/bin/bash` 的话，内核会去找一个并不存在的解释器，而

    curl -fsSL <raw-url> | bash -s -- --install

会在读取第一行之前就失败，而且偏偏是在最需要一行命令安装的机器上。作为 POSIX 脚本，它在 BusyBox ash、dash 和 bash 下都能运行，所以同一个文件既可以在光秃秃的 Alpine 上通过管道交给 `sh`，也可以在已经装有 bash 的机器上交给 `bash`。它仍然会安装 bash——每个智能体都会分配到一个 bash shell——只是它自己启动时不再需要 bash。代价是不能用数组、`[[ ]]`、`${var//x/y}` 和 `<(...)`；`local` 保留，因为这三种 shell 都支持它；`pipefail` 则先在子 shell 中试探，再进行设置，因为 dash 不支持它。有一个测试会拒绝上述每一种写法，因为一个不存在的 shell 特性，会在别人的机器上于安装时失败。

Alpine 需要而 Debian 不需要的东西，以及为什么每一样都不是可选的：

| | 原因 |
|---|---|
| `shadow` | 特权守护进程会调用 `useradd --home-dir --create-home --shell`。BusyBox 的 `adduser` 这些选项一个都没有，而无法创建智能体就意味着整个应用都无法工作 |
| `bash` | 分配给每个智能体的 shell，也是 `bash.run` 执行命令所经由的 shell。Alpine 默认不带它，这也是为什么 Alpine 安装脚本是本项目中唯一用 POSIX shell 而不是 bash 写成的文件：`#!/bin/bash` 会让 `curl ... \| sh` 在最需要它的机器上无法使用 |
| `dcron` | 总得有东西去读取守护进程写入的 crontab。这也是下文 `-d` 的由来 |
| `gcc`、`musl-dev`、`libffi-dev`、`python3-dev` | 有几个依赖项没有发布 musl wheel，要在安装过程中编译 |
| `libcap` | 在 `direct` 模式下对 haproxy 二进制文件执行 `setcap cap_net_bind_service`。systemd 通过 `AmbientCapabilities` 按服务授予这项能力；OpenRC 没有对应的机制 |

移植过程中有三处必须修改代码，每一处都是在安装时发现的：

- **用 `crontab -u <agent>` 代替降权到智能体身份。** Debian 的 `crontab` 是 setgid 的，任何用户都可以运行；Alpine 的 dcron 将其以 `4750 root:wheel` 发布，所以以智能体身份运行它会得到 `Permission denied`。要保留原来的做法，办法只有把每个智能体都放进 `wheel`——在大多数系统上这个组意味着 sudo——或者放宽系统中一个 setuid 二进制文件的权限。守护进程本身就是 root，可以改为直接指定用户。
- **删除 crontab 时用 `-r` 或 `-d`。** Vixie cron 用 `-r` 删除 crontab；dcron 用 `-d`，对 `-r` 则回以一条用法说明和退出码 2。只尝试 `-r` 会把已删除智能体的 crontab 留下来，而它仍然指向一个已不存在的用户的运行器。两种都会尝试，因为决定用哪个的是已安装的二进制文件，而不是发行版的名字。
- **`browser.conf` 中的 `executable=`。** Playwright 没有发布 musl 版本，所以在 Alpine 上这个包被完全排除在依赖项之外，也就没有浏览器。这一行由 `browser.fReadConfiguredExecutable` 读取，等到哪天有了能驱动系统 Chromium 的 Playwright，就在这里写上它的名字。

还有一处，是在 Alpine 测试机上查看 `/proc/<pid>/fd/2` 时发现的：除非另有指定，`supervise-daemon` 会把进程的 stdout 和 stderr 送往 `/dev/null`，而 Alpine 上没有其他东西收集它们——Debian 上的单元有 journald 来做这件事。没有一个服务往任何地方写过任何东西。现在每个 OpenRC 脚本都指定了 `output_log` 和 `error_log`，每个服务一个文件，位于 `/opt/boa/logs/` 下，在 `start_pre` 中以 `boa` 身份创建，这样无论谁往里写，logrotate 都能以 `boa` 身份轮转它。两个安装脚本中的 `fInstallLogRotation` 都会为这些文件以及 gunicorn 的两个文件写入 `/etc/logrotate.d/boa`：每周轮转，保留八份，使用 `copytruncate`，因为两个写入方都保持文件打开；并且永远不包括 `install.log`，它归 root 所有，里面存有密码。同一发现的另一半：“操作系统”标签页向 OpenRC 查询的是 `crond`，即 BusyBox 的 cron，而安装脚本运行的是代替它的 `dcron`，所以一台健康的 Alpine 会报告 cron 已停止。`fPickOpenRcCronService` 会查询两者中第一个拥有服务脚本的那个。

此外还有两处是安装脚本绕过而不是修复的，因为它们属于 Alpine 的 haproxy 包：它没有附带 `/etc/haproxy/errors/`，也没有供管理套接字使用的 `/run/haproxy`。当对应的文件或目录不存在时，这两行会从配置中删去，这在管理员确实创建了它们的机器上同样是正确的。最初尝试过创建 `/run/haproxy`，并在 `/etc/local.d/` 中放一个脚本，在每次启动时重新创建它：`local` 在启动的最后阶段才运行，所以等它出现时，haproxy 早已启动失败了。

还有一处属于 OpenRC 本身：它会缓存服务依赖树，并通过与 `/etc/init.d` 比较时间戳来决定是否重建。重装时，服务脚本与缓存在同一秒内被覆盖，所以它保留了旧的依赖树，这些服务都不在其中——它们在安装过程中能启动，因为 `rc-service start` 不需要依赖树；但重启之后就不会回来，因为 `openrc default` 需要它。`fInstallServices` 最后会无条件执行 `rc-update -u`。

### 每个安装脚本对机器有什么要求，又自己安装什么

Debian 安装脚本拒绝在 systemd 不是 PID 1 的地方运行（`fRequireSystemd`，在安装任何东西之前调用）。它设置的一切——十个单元、本机的 HAProxy、cron——都由 systemd 启动并保持运行，所以在这样的机器上，安装过去会完成、报告成功，却什么服务都不提供：`systemctl` 已安装，它回答 "System has not been booted with systemd as init system (PID 1). Can't operate."，而没有任何东西读取这个退出码。现在它打印的是修复方法：安装 `systemd systemd-sysv dbus`，以 `/sbin/init` 作为命令重新创建容器，再次运行安装脚本。它说的是“重新创建”而不是“重启”，因为正在运行的容器无法更换它的 PID 1。

Alpine 安装脚本在 OpenRC 上做了相反的决定，因为在那里缺失的部分是它可以补上的：`openrc` 会与其他软件包一起安装——容器镜像不带它，用 `setup-alpine` 安装的 Alpine 则带有它——随后 `fEnsureOpenRcUsable` 会创建 `/run/openrc/softlevel`，也就是 OpenRC 在拒绝操作一个并非由它引导的系统上的服务时所点名的那个文件。之后，十个服务就能在容器中启动。日志会说明它们不会自己回来，因为 `/run` 是 tmpfs，而 PID 1 不是 OpenRC。

两者并不矛盾：systemd 只能作为 PID 1 工作，而 OpenRC 不受此限。

### `if ! fMain` 会在整个安装过程中关闭 `set -e`

两个安装脚本最后都以子进程的方式启动 fMain：

    fMain "$@" &
    vMainPid=$!
    if ! wait "${vMainPid}"; then ...

而不是用 `if ! fMain "$@"`——虽然看起来应该这样写，它们过去也确实是这样写的。`if` 条件中的命令运行时 errexit 会被挂起，而这种挂起会被它调用的每个函数、以及这些函数再调用的每个函数继承——也就是整个安装过程。在一台没有 systemd 的机器上实测：连续八条命令失败，每一条都打印了错误，脚本却越过所有这些错误继续执行，最后以 "Installation finished" 结束。子进程会重新获得 errexit，因为挂起状态在 fork 之后不会保留。bash、dash 和 BusyBox ash 的行为都是如此，上面那句话的前后两半都成立，而无论是在函数内部 `set -e`，还是使用子 shell，都无法恢复它。

在子进程中运行 fMain 有两个后果：`trap fCleanup EXIT` 也要在 fMain 内部安装，因为子 shell 不会继承父进程的 EXIT trap，否则每次运行都会把下载到 `/tmp` 下的目录树留下来；另外，父进程在退出前会清除自己的 trap，这样 "Exited with code" 这一行就不会打印两次。

`fHasTty` 是同一类的修复：它打开 `/dev/tty` 再将其关闭，而不是测试 `[ -r /dev/tty ]`。在任何系统上，这个设备节点按权限模式都是可读的，所以在没有 pty 的 `ssh host ./installer` 下这项测试也能通过，紧接着的 `read` 却会以 ENXIO 失败——没有控制终端的进程根本打不开它。

### 自带的 haproxy.cfg 不是谁的心血

`fInstallMachineProxy` 在 `proxied` 模式下会替换 `/etc/haproxy/haproxy.cfg`，而对于不是它写的文件，它不会不经询问就去动——本机的代理可能还承载着其他站点。问题在于，它在一台全新机器上找到的那个文件，是 haproxy 包放在那里的，而这个包正是**这个安装脚本自己**在一分钟前于 `fInstallDependencies` 中安装的。

把那个示例文件当成别人的心血，正是让每一次普通的 `--install` 戛然而止的原因：没有 `--yes`，没有可以用来回答的终端，运行在已经构建好目录树、virtualenv 和证书之后，停在了 "Destructive operation with no terminal to confirm on"。在全部四台测试机上实测，Debian 和 Alpine 都一样，运行的正是 README 给出的那行命令。

`fMachineProxyIsPristine` 改为询问包管理器，而不是靠猜：

- Debian：将 dpkg 为该配置文件记录的 md5（`dpkg-query -W -f '${Conffiles}'`）与文件本身的 md5 进行比较。
- Alpine：将 apk 为该文件记录的哈希值（从 `/lib/apk/db/installed` 中读出，即 `R:haproxy.cfg` 下的 `Z:` 行）与该文件的 `openssl dgst` 结果进行比较。`Q1` 是 base64 编码的 sha1，`Q2` 是 sha256。

`apk audit --system` 看起来像是 Alpine 上的答案，其实不是：在 Alpine 3.24 上实测，对于一个被编辑过的 `/etc/haproxy/haproxy.cfg`，它**什么都不**报告。这项检查的第一个版本相信了它，结果会不经询问就替换掉别人的代理——而这恰恰是确认步骤要防止的那件事。此后已用软件包自带的文件、加了一行的文件以及本安装脚本写入的文件进行过测试。

原样未改意味着直接替换，只在日志中记一行，不提问。被编辑过则沿用原来的行为：在 `--update` 时不去动它，在安装或重装时先确认，并备份到 `.before-boa.<timestamp>`。

### 日志和密码放在同一个文件里

安装脚本写入 `/opt/boa/logs/install.log`，除此之外什么都不写：内容是它做了什么，并在末尾附上它生成的凭据。它过去会在 /root 中写两个文件——`app-web-install.log` 和 `app-web-credentials.txt`——而两个地方的两个文件，就是要找的两样东西。`fMigrateInstallFiles` 会先把旧文件中的内容复制到新文件中，再删除旧文件，因为其中的密码可能是任何人手上唯一的副本。

有三个细节支撑着这一切：

- 目录不存在时，`fLog` 会创建它。日志位于安装脚本正在构建的目录树中，所以首次安装时，写第一行的时候它还不存在，而 `--reinstall` 会在中途删除它。
- `fRemoveInstallation` 在执行 `rm -rf /opt/boa` 之前把日志复制到一旁，之后再放回去，这样重装就不会把它自己的记录也一并带走。
- 该文件为 `root:root 0600`，位于一个以 0750 归 `boa` 所有的目录中。`boa` 可以删除它——这就是拥有该目录的含义——却不能读取其中的密码；智能体不在 `boa` 组中，根本进不了这个目录。

登录页会在 `frontend/templates/login.html` 中写出这个路径，单独占一行，并用 `--colour-path` 着色。它不在那十五个翻译文件中：上面那句话会被翻译，而路径在哪里都一样，一个被折进句子中间的路径，就是一个会被人敲错的路径。

### 圆形应用标志

`frontend/static/img/boa.svg` 是一个蓝色的圆形标志，上面有三个半身的机器人智能体，身穿黑色西装、白衬衫，系深色领带。它们的头部有浅色金属面板、机械关节和带蓝色眼睛的深色面罩。风格略带插画感，织物纹理平滑，中间那个智能体没有口袋巾。它们的头部连接着可见的机器人脖颈；较大的中间智能体站在两侧两个较小的智能体前面。这幅带阴影的图稿是嵌入 SVG 中的 512px WebP，带有圆形裁剪，圆形之外是透明的。人物保持不透明，在各个主题下外观保持一致。这是 SVG 容器中的光栅图稿，而不是矢量路径。`favicon.svg` 包含同样的图稿。请保持这两个 SVG 文件同步。登录页、侧边栏和 favicon 的 URL 使用 `v=robot-agents` 来刷新旧标志的缓存副本。显示尺寸保持不变：登录页上为 30px，侧边栏中为 24px。

### 在有人另行指定之前，界面一律使用 en-US

`fGetLanguage` 从 `localStorage` 中读取所选语言，找不到时返回 `en-US`。它过去会先与 `navigator.languages` 协商，这意味着新安装的界面会使用第一个打开它的浏览器所用的语言——那是一台机器的语言，而不是一个决定。这个选择只需一次操作：在登录卡片的角落里和设置中都能修改，并且按浏览器分别记住。

同一个文件里曾有两个 bug，两者的表现都是“登录表单要切换两次语言才会变”：

- `fApplyTranslations` 只在加载的文件中有某个键时才写入字符串，而 `textContent` 已经被上一种语言覆盖了。所以切换到 en-US——它没有文件，`dTranslations` 是 `{}`——什么都不会改变；切换到一种缺少某个键的语言时，那个键会停留在之前的语言。现在，每个被翻译元素的原始字符串都会在它第一次被翻译时保存在一个 `WeakMap` 中，没有译文的键会恢复原始字符串。
- `fSetLanguage` 保存选择后，不带参数调用 `fLoadTranslations()`，而后者会从存储中把选择再读回来。在隐私窗口中，存储会抛出异常，读取返回的是之前的语言，于是页面重新加载了它本来就在显示的内容。现在它会把收到的语言直接传下去。

`fLoadTranslations` 带有一个序号，这样快速连续的两次切换就不会乱序落地，让页面停留在一种谁都没要求的语言上。它有三处错误，每一处都会向用户显示一种他们没有选择的语言：

- `lang` 属性是在最开头、在文件被获取之前设置的。于是 404 或解析错误会让上一种语言的字符串留在屏幕上，却挂着新语言的名字：`lang=fr-FR` 配上西班牙语文本。现在在拿到词典之前什么都不发布，而 `fPublish` 会把两者一起设置，因为故障恰恰就在于两者被分开设置。
- 序号是在 `await response.json()` 之前检查的。较早请求的响应体如果来得慢，会在较晚的请求完成之后才落地。现在每次 await 之后都会检查，因为序号可能在其中任何一次期间发生变化。
- 失败时什么都不说，让页面处于未知状态。现在它会回退到 en-US，并通过 `fOnLoadFailed` 报告。

### en-US.json 是源头，HTML 标记是兜底

加载器过去把 `en-US` 短路成一个空词典，理由是 HTML 标记中已经带有 en-US 文本。这话没错，但它让 `en-US.json` 成了五百个键的累赘：随应用发布，作为语言目录列出，由测试检查它与其他十三个文件是否一致，却没有任何东西读取它。修正其中的一个拼写错误在屏幕上毫无变化，而要发现这一点，唯一的办法就是亲自试一试。

现在它会像其他语言一样被获取。HTML 标记中的文本仍然是一直以来所描述的那个兜底：语言目录中没有的键，或者无法加载的语言目录，留下的仍然是一个可读的页面，而不是一片空白。改变的是两者中谁是源头。

### 五百个键不等于一个翻译好的界面

有四类可见字符串根本没有键，所以在全部十四种语言中都保持英文：

| 是什么 | 现在如何翻译 |
|---|---|
| 标签页标题 | `<title>` 上的 `data-i18n`，每个页面一个键 |
| API 自身的失败 | 传递的是 `code` 及其 `params`；由浏览器在 `fDescribeApiError` 中写出句子。`error` 留给来自外部的内容——服务商的原话、邮件服务器的拒绝——不应该为它们编造译文 |
| 模板描述 | 不在语言目录中：每个模板的 `agent.json` 带有十五种语言的描述，服务器挑选界面所要求的那一种（`agent_package.fPickDescription`） |
| 主题配色方案和描述 | `theme.scheme.<scheme>` 和 `theme.desc.<id>`，同样的约定。名称不翻译：主题是某个人的一套带名字的调色板，把 "Nord" 翻译出来不会帮任何人找到它 |

某个人为自己的安装编写的模板或主题，会保留它自己的文字，而不会消失。

登录页上的语言下拉菜单列出的是代码——`es-ES`、`en-US`——而不是语言名称。十五个用各自语言写的名称会让这个控件和卡片一样宽；代码只有 80px，而且在一串代码中，找自己语言的人最快能认出的就是它。完整名称保留在设置页面上，那里有足够的空间。

### 从右向左

希伯来语从右向左书写，而一个按从左向右排版、里面却有希伯来语的页面，是没有人能读的页面。四个决定让同一份样式表同时服务于两个方向：

**方向跟随语言。** `i18n.js` 中的 `fPublish` 会在设置 `lang` 的同一步里，依据 `lRightToLeftLanguages` 在 `<html>` 上设置 `dir`，所以两者绝不会不一致——这正是该函数为单独的 `lang` 而存在、要防止的那种故障。网格和 flex 行会自行跟随 `dir`，因此侧边栏以及所有按行排布的内容无需专门的规则就会镜像翻转。

**样式表说的是起始和末尾，而不是左和右。** 凡是与文本流向有关的外边距、内边距、边框、`inset` 和 `text-align`，都是逻辑属性（`margin-inline-start`、`inset-inline-end`、`text-align: start`）。`app.css` 中仅剩的那个物理 `left` 是智能体头像周围的圆环，它是几何图形，而不是文本。

**内容保持自己的方向。** 代码、路径和命令在每种语言中都是从左向右（`code, pre { direction: ltr; unicode-bidi: isolate }`），所以希伯来语句子里的路径不会被重新排序。一条聊天消息以及渲染后回答的每个段落，由它们自己的第一个字母决定方向（`unicode-bidi: plaintext`）：希伯来语页面上的英文回答从左向右阅读，英文页面上的希伯来语回答则从右向左。供人书写自由文本的文本框遵循同样的规则，空的文本框则跟随页面的方向，所以希伯来语下其中的提示文字从右向左阅读（若用 `dir="auto"`，空文本框连同提示文字都会从左向右排列）；crontab 和电子邮件地址带有 `dir="ltr"`。

**从左向右阅读的内容在句子中被隔离。** 双向算法会把中性字符归到与它相邻的某一侧，所以希伯来语句子末尾的路径，其斜杠和句号被周围的词拽走了：“/tmp/x/007/.”被显示成了“.tmp/x/007/ /”。在从右向左的语言中，`fPublish` 会让词典先经过 `fIsolateLeftToRightRuns`，它把每个 `{placeholder}` 以及每段含斜杠的文本，都包在 U+2068 FIRST STRONG ISOLATE ... U+2069 POP DIRECTIONAL ISOLATE 之间，这样调用方放进句子里的值就落在隔离之内。机器在“设置 → 操作系统”下报告的内容（`settings.js` 中的 `fLeftToRight`）、API 文档中的路由（`.endpoint-path`）、示例 crontab 行，以及标签页和列上的计数，也以同样的方式按从左向右隔离；没有它，内核版本就会被显示成“deb13-amd64 · x86_64+6.12.111”。

### 下载代码所用的分支

`cRepoBranch` 是 `main`，即仓库真正的分支。它以前是 `master`，之所以能用，只是因为 GitHub 在重命名后会重定向旧名称——这个重定向在真正的 `master` 分支出现的那天就会消失，而且对 `--repo-url file:///...` 也没有人来做重定向，而两个安装脚本正是这样测试的。

### 为什么应用自带 HAProxy

本机的 HAProxy 用 `send-proxy-v2` 转发到 11443 端口，所以 PROXY 头会在 TLS 握手**之前**到达。Gunicorn 在那里读不了它：它的 `proxy_protocol` 选项是在解析 HTTP 时解析这个头的，而这发生在 TLS 终止之后，所以这个头的字节会落进握手中，并以 `WRONG_VERSION_NUMBER` 破坏握手。这是在部署时发现的，而不是在测试时。

HAProxy 能在同一个绑定上同时接受两者——`accept-proxy ssl crt ...`——所以应用自带一个实例，它也是唯一监听端口的组件。Gunicorn 则绑定到一个 Unix 套接字，这意味着不存在任何不经过代理就能进入应用的途径，而真实的客户端地址会以 `X-Forwarded-For` 的形式保留下来——没有它，登录频率限制看到的所有人都是 127.0.0.1，也就不再是按地址限制了。

之所以选 HAProxy 而不是 nginx，是因为部署本来就依赖 HAProxy：已有技术能解决的问题，就不引入新技术。

本机的 HAProxy 不能在这个后端上使用 `option ssl-hello-chk`：这项检查的 ClientHello 早于 TLS 1.2，所以面对要求 TLS 1.2 的绑定时会失败，并把后端永远标记为宕机。症状是一个运行完全正常的服务返回 503，这一点值得了解，因为应用自己的日志里没有任何内容表明有问题。

而且这项检查必须敲 11080 的门，而不是 11443。针对 TLS 绑定的 TCP 检查会连接后不握手就挂断，而这个 HAProxy 把每一次都记录为 "SSL handshake failure"——在 Debian 测试机上实测，两天 64,075 行，每两秒一行，把任何真正的问题都淹没在 journal 里。最初尝试过 `check-ssl verify none`，结果只是把一行换成了另一行：检查的突然关闭会在握手尚未完成时到达，每次检查记录的要么是那个，要么是 `ECONNRESET`。对 11080 做同样的连接再关闭，就是一个会被 `option dontlognull` 挡在日志之外的空会话，两个端口属于同一个进程，journal 也安静了下来：三十秒内零行，而站点从外部访问时返回 200。

所以本机 HAProxy 上的后端完整写法是：

```
backend https-out
  mode tcp
  server srv-https-out 127.0.0.1:11443 check port 11080 send-proxy
```

`send-proxy` 负责携带客户端地址。`check-send-proxy` 是有意省略的：11080 不接受 PROXY 协议。面向运维人员的版本在 MANUAL.zh-CN.md 的“本机 HAProxy 应有的配置”一节中。

它没有固定 `maxconn`，这并非疏忽。`maxconn 2048` 会向内核要求 4131 个文件描述符，拿不到时 HAProxy 宁可退出也不启动：*Cannot raise FD limit to 4131, current limit is 1024 and hard limit is 4096*。这是在一台 BPI-R3 上、运行于 OpenWrt 之下的 Alpine LXC 中报告的，它的硬限制是 4096：`boa-proxy` 被重启了七十次，11443 上从来没有任何程序监听，首次安装停在了 "The application did not answer on port 11443 (last code: 000)"。两台测试机都是硬限制为 524288 的 Proxmox LXC，这就是两者都从未出现这个问题的原因，而且 `haproxy -c` 在每一台上都接受了这个文件——配置从来都没有错，是进程在启动时死掉了。没有 `maxconn` 时，HAProxy 会根据它实际能拿到的描述符数量来确定自身规模，这也正是它自己的消息所要求的，而 `fd-hard-limit 4000` 则在限制极大的地方为它的用量设定上限。用同一个二进制文件在三种硬限制下实测：4096 时 maxconn 为 1987，1024 时为 499，524288 时为 1987。有一个测试在 4096 的硬限制下用发布的文件启动真正的 haproxy，并要求它保持运行；再用旧的 `maxconn 2048` 启动它，并要求它死掉——一开始之所以漏掉这个问题，正是因为测试只读了文件。

真正需要 root 的事情有三件：创建系统用户、安装另一个用户的 crontab，以及以另一个用户的身份启动进程。其他的一切都不需要。所以 root 只存在于一个小小的守护进程中，它通过 Unix 套接字提供**一组封闭的动词**，而且有意没有任何表示“运行这条命令”的动词。攻击者即使触及那个套接字，也只能创建一个无特权的智能体，无法以 root 身份运行代码。

该套接字为 `0660 root:boa`，并且每次连接都会检查 `SO_PEERCRED`，这样无论将来某次更新之后文件模式碰巧变成什么，都只为 root 和 `boa` 提供服务。

### 修改必须来自本站自己的页面

会话 cookie 是 `SameSite=Lax`，这能防止来自另一个站点的请求携带它。但它挡不住同一站点上的另一个源：拥有 `bash.run` 的智能体可以在这台主机上、用自己的端口提供一个页面，而对话回答中指向它的链接只需点一下。那里的一个表单向 `/api/admin/agents/000/run` 发送 POST，就是一个同站请求，cookie 会随之发送，运行随即开始；而由于它是一个不带请求体的简单 POST，也不会有任何预检请求挡路。所以 `fRefuseChangesFromElsewhere`——API 蓝图上的一个 `before_request`——会对任何不是来自本站自己页面的 POST、PUT、PATCH 或 DELETE 回应 403：`Origin` 头必须精确指明这个主机和端口——`localhost` 和 `localhost:8080` 是两个源，而后者恰恰是智能体能够提供的页面——并且 `Sec-Fetch-Site` 头必须是 `same-origin`。两个头都没有的请求不是来自浏览器，而是来自脚本或测试，和以前一样交给登录来判断。GET 不受限制：它不改变任何东西，而来自别处的页面也读不到响应，因为没有允许它读取的 CORS 头。

### 智能体 API，以及它为什么存在

有两样东西属于 `boa`，绝不能被智能体读到：看板数据库（能直接写入它的智能体就能改写另一个智能体的历史）和频道凭据（机器人令牌不是一条消息——它是永久的发送权限）。

所以智能体通过 `boa-agent-api` 访问这两者，走的是第二个、每个智能体都能打开的 Unix 套接字。授权由两项相互独立的检查组成：

1. 出示的令牌与存储的某个智能体令牌的 SHA-256 相匹配。
2. `SO_PEERCRED` 表明调用进程属于*那个*智能体的用户。

单靠其中任何一项都会更弱：泄漏的令牌在错误的账户下毫无用处，而即使是正确的账户，没有令牌也毫无用处。

之所以用 Unix 套接字而不是 HTTPS，是因为同一台机器上两个进程之间使用 TLS 毫无益处，而自签名证书将意味着每个智能体都在禁用验证的情况下运行——这比没有 TLS 还糟，因为它看起来像是安全的。

### 状态存放在哪里，以及为什么要分开存放

| 状态 | 位置 | 为什么放在那里 |
|---|---|---|
| 智能体配置 | `agents/xxx/info.json` | 智能体必须以自己的身份读取它 |
| 智能体历史 | `agents/xxx/runs.jsonl` | 智能体唯一可以写入的地方 |
| 共享流程 | `skills/<Name>/SKILL.md`（root，0755） | 被授予它的每个智能体都能读取，没有谁能写入 |
| 智能体索引、登录、设置 | `db/boa.sqlite`（0700 `boa`） | Web 进程需要它 |
| 看板 | `kanban/kanban.sqlite`（0700 `boa`） | 有很多并发写入者 |

这里有意**没有 `runs` 或 `usage` 表**。智能体进程无法打开归 `boa` 所有的数据库，而授予它写权限会让任何智能体都能改写其他任何智能体的历史。取而代之，每个智能体都向自己的运行日志追加内容，Web 应用则通过 `boa-exec` 读取这些日志。附带的好处是，即使 Web 应用宕机，智能体仍会记录它做了什么。

看板使用 SQLite 而不是一个装满 JSON 文件的目录，因为多个智能体在同一个 cron 分钟内醒来是常态，而只有事务才能防止两次同时的添加相互覆盖。

### 备份里有什么

`--backup` 会把安装中所有不属于代码的东西写成一个归档，`--restore` 则用一个归档替换机器上现有的内容；两个安装脚本中都有这两者，函数一一对应。清单就是把上面那张表变成一行 `tar` 命令：两个数据库、密钥和频道、证书、每个智能体及其主目录和受保护文件、技能和工具。围绕它，有三件事是直接对 `/opt/boa` 执行 `tar` 会做错的：

- **数据库通过 SQLite 的备份 API 复制**，即 `fCopySqliteDatabase`，而不是通过 `cp`。两个数据库都运行在 WAL 模式下，所以复制 `.sqlite` 文件会漏掉仍在 `-wal` 文件中的内容，而在写入过程中复制的副本可能是残缺的。venv 中的 `python3` 带有这个模块；而 `sqlite3` 命令在两个发行版上都没有。同样的理由在恢复时反过来起作用：在读取恢复后的文件之前，会先删除旧的 `-wal` 和 `-shm` 文件，否则 SQLite 会把旧日志应用到它上面。
- **智能体用户按名称迁移。** `agents.txt` 记录每个智能体的用户、uid 和 gid，`fRestoreAgentUsers` 会创建缺失的用户，名称总是相同，id 在空闲时也保持相同。解包时，归档中的所有权按名称映射，所以新机器上 uid 不同的 `boa` 或 `agent-001` 仍然拥有自己的文件。crontab 存放在 cron 的 spool 中，而不在 `/opt/boa` 下，所以要用 `crontab -l` 读出，再用 `crontab -u` 放回。
- **有三个文件是有意排除的**：`config/ports.conf`、`config/browser.conf` 以及由它们生成的 `haproxy.cfg` 描述的是这台机器本身，恢复不能导入另一台机器的选择。安装日志以 `install.log.backup` 的名字随归档迁移，换个名字是为了让恢复永远不会覆盖此刻正在写入的日志；其中的凭据行会被追加到当前日志中，因为恢复之后用于登录的是备份中的凭据。

恢复是唯一一个会替换数据且无法撤销的操作，所以它像重装一样要求确认。测试会在真实的目录树上、分别在 bash 和 dash 下运行这两个函数：检查归档包含什么、排除什么，以恢复必须撤销的各种方式破坏目录树，然后逐个文件检查恢复结果。

### 技能在提示词中建立索引，按需获取

智能体的记忆会被完整加载到每一个系统提示词中，这对记忆来说是对的：它的字符上限可以按智能体配置（默认 8,000，允许 1,000–1,000,000），而且它是智能体唯一无法重新推算出来的东西。

技能不是这样。一个流程有一两页，一个智能体可以被授予好几个，而大多数运行一个都用不到——磁盘检查用不到证书流程。像加载记忆那样加载它们，就意味着每次运行的每次调用都要为所有技能付费，而 `info.json` 中的开销上限是以 token 计量的。

所以提示词中带的是一份索引——每个技能一行，写着它的名称和描述——正文则由判断自己需要它的智能体通过 `skill.read` 获取，只获取一次。五个技能每次运行大约花费 200 个 token，而不是 10000 个，而被读取的那个技能只计费一次，而不是每次调用都计费。

因此，头部中的描述才是承重的部分：智能体依据它做决定，而且无论技能是否被读取，每次运行都要为它付费。

### 技能和工具一样归 root 所有

工具归 root 所有，因为应用会把它作为代码导入。技能不会被任何东西执行，但它会被加在一个凌晨四点醒来、无人看管的智能体的推理前面，这让它和 `system-prompt.md` 一样敏感——而那个文件已经位于一个智能体可以读、不能写的目录中。

所以 Web 界面中没有技能编辑器，也没有用于写技能的特权动词。技能要通过 SSH 在服务器上编写。界面决定哪个智能体获得哪些技能，这和它对工具所做的事情一样。

这一决定的另一半是它们存放在哪里：`/opt/boa/skills/`，在 `webapp/` 之外，因为 `fDeploySourceCode` 会对 `webapp` 执行 `rm -rf`，而某人在这台服务器上写的流程，不是一次更新有权删除的东西。理由相同，在目录树中的位置也与 `/opt/boa/tools/` 相同。

应用本身不附带任何技能。没有 `backend/skills/`，安装脚本也不会往那个目录里复制任何东西：它们创建一个空的、归 root 所有、权限为 0755 的目录。技能是针对某一套安装的流程——这些主机、这个备份、这张证书——所以一个通用的技能将是一个没人遵循的流程，却要在每次运行的每个提示词中占用一行来声明这一点。全新安装时这个目录为空，说明这个功能在正常工作，而不是少了什么。


### `deploy/` 不会被部署

`/opt/boa/webapp/` 中只有 `backend/` 和 `frontend/`，别无他物。`deploy/` 目录——单元、两份 HAProxy 配置、智能体模板、服务商目录、`requirements.txt` 以及安装脚本本身——是安装脚本自己的材料，它从安装脚本刚刚下载到 `/tmp` 中的目录树读取，而这棵树在安装脚本退出时就会被丢弃。

这不只是为了整洁。从 `/opt/boa` 下的副本读取单元，意味着安装的是磁盘上碰巧存在的那个版本的单元；从下载的目录树读取，安装的则是正在部署的那个版本的单元，而这是唯一一对能够推理清楚的组合。每一次这样的读取都会先调用 `fRequireSourceCode`，所以如果某个步骤在下载之前运行，它会以一句说明失败，而不是从 `/deploy/...` 复制。

这也是 `gunicorn.conf.py` 放在 `backend/web/` 而不是 `deploy/` 中的原因：gunicorn 每次启动都会读取它，所以它必须是实际存在于服务器上的文件，而服务器上存在的目录，正是存放它所配置的代码的那个目录。

部署的内容为 `root:root`，目录 `00755`，文件 `0644`，由 `fSetCodeModes` 设置，且只由它设置。`webapp/` 下没有任何东西是按路径执行的——守护进程以 `venv/bin/python3 .../runner.py` 的方式运行运行器，它为每个智能体写入的 crontab 也是如此——所以那里没有任何文件需要执行位。在统一成一个函数之前，它们却都带着执行位：`fDeploySourceCode` 设置了 `0644`，而在更新时于其后运行的 `fCreateDirectoryTree` 随后又对同一棵树执行了 `chmod -R 00755`。

### Telegram 收到的是 HTML，失败时退回纯文字

模型写的是 markdown。原样显示的话，就是句子中间夹着星号的 `**25G free**`，在此之前手机上收到的正是这样的东西。

Telegram 只渲染一个很小的 HTML 子集——十四个标签，几乎没有像样的属性，其中也没有标题、列表或表格。所以 `telegram_html` 会翻译有对应标签的内容，并为没有对应标签的内容找一个可读的形式：标题变成单独一行的粗体，列表项加上项目符号，表格则变成一个经过填充对齐的 `<pre>` 块，这是在手机上让各列上下对齐的唯一办法。

其中有三点是承重的。

**转义放在第一位。** `&`、`<` 和 `>` 对 Telegram 来说是标记，所以一个报告 `grep <dev> && echo` 的智能体会产生一条 Telegram 以 400 回应的消息——也就是说，一条永远不会送达的消息。每一段文本在被任何东西包裹之前都要经过 `fEscape`。href 则经过 `fEscapeAttribute`，它还会转义双引号：一个包含双引号的 URL 会提前关闭属性，把自己剩下的部分变成没人写过的属性。

**被拒绝的消息会以纯文本重新发送。** 无论渲染器哪里弄错了，文字都比格式更有价值，所以遇到 400 时会去掉 `parse_mode` 重试，这一行就以无格式的形式发出。回退时会记录 Telegram 说了什么，因为一直悄无声息地降级的格式，是没人会去修的格式。

**Telegram 拒绝的回答会被丢弃，而它暂时收不下的回答会保留一小时。** `fSay` 返回三种结果而不是两种：已发送、未应答，以及被拒绝——除 429 之外的 4xx，即 `ChannelRejected`，这是 Telegram 在对这条消息说不，而且明天也会这么说：机器人被屏蔽了、对话没了、令牌被撤销了。`fDeliverAnswers` 过去在任何失败时都会保留该行，下一轮再试，而这一行存放在磁盘上，是为了让重启不会丢失回答，于是一个被屏蔽的机器人会让监听程序陷入一个永不结束的循环：轮询处于快速模式，每一轮都要通过 root 守护进程读取一次对话，并向 Telegram 发出最多两个请求，即使重启也照旧。现在，被拒绝的回答会立即被丢弃，并记一行说明；Telegram 在一次运行所获得的那一小时内仍未收下的回答也会被丢弃，理由与另一个分支放弃一次从未结束的运行相同。两者都不会丢失回答：它就在 Web 界面中该智能体的对话里，那是它最先被写入的地方。

这些模式与 `frontend/static/js/markdown.js` 使用的完全相同。两个渲染器对什么算 markdown 意见不一，就意味着同一个回答在显示它的两个地方读起来不一样，而两边都发送的意义恰恰在于它们是同一段对话。


### Discord 靠轮询，一条回答两千个字符

Discord 是人们回复智能体的第二个频道，负责接收的那一半是 `discord_listener`——`boa-channel-discord`，第七个服务。它与 Telegram 的那个有四点不同。

**它通过 REST 轮询。** `GET /channels/<id>/messages?after=<id>`，每五秒一次，智能体正在回答时每两秒一次。Gateway 是显而易见的替代方案，但没有采用：它是一个需要心跳和恢复协议的 WebSocket，还需要一个本项目没有的依赖，并且需要在开发者门户中打开 Message Content Intent——不打开的话，每条消息到达时 `content` 都是空的，而且没有任何东西说明原因。轮询也是向外连接的，这正是它能在没有任何端口转发的局域网中运行的原因，和 Telegram 的长轮询完全一样。代价是以秒计的延迟，以及每分钟十二个请求，而限额是每秒五十个。

**两千个字符，而不是四千。** `channels.cMaxMessageLength` 是 4096，这是 Telegram 的上限，而 Discord 对长于 2000 的 `content` 回应 400。一个长回答不是被截短后送达——它根本没有送达。`discord_markdown` 会在行与行之间把它切成最多四条消息，切口落在代码块内部时，会在前一条的末尾关闭该代码块，并在下一条的开头重新打开：否则，一半会以纯文本送达，另一半则成为一个永不结束的代码块，在 Discord 中会吞掉之后说的一切。每一部分都被记录为那个智能体的消息，因为人们会回复屏幕上出现的任何一条。

**没有按钮，命令用 `!`。** 按下按钮和斜杠命令都属于*交互*，而交互要通过 Gateway 或者一个 Discord 能访问到的 HTTPS 端点到达。轮询的频道两者都看不到。所以 `/agents` 变成了 `!agents`，一条普通消息，而智能体名单是一列要输入的名字，而不是一列按钮。`/agents` 同样被接受，因为配置过 Telegram 机器人的人会出于习惯输入它。

**智能体的回答不会提及任何人。** 这里发送的每条消息都带有 `allowed_mentions: {"parse": []}`，所以模型写的 `@everyone` 只是文本，而不是发给整个服务器的通知。`replied_user` 保持开启：回答应该送达提问的人。这是一条设在套接字层面而不是提示词中的规则，理由与邮件转发列表相同。

Discord 所缺少的，是 Telegram 对陌生人的沉默。没有可以比对的 `chat_id`：机器人要求指定一个频道并读取该频道，所以谁能和智能体说话，取决于谁能在那个频道里写字。私有频道才是与 `fIsFromTheConfiguredChat` 在代码中所强制执行的内容相符的配置——手册中也点明了这一点，因为这就是授权的全部。

这个频道之前的 webhook 仍然存在，也仍然能发送。webhook 无法读取、无法回复，也拿不回消息 id，所以在它上面开启 `listen` 会被拒绝，而不是提供出来：一个什么都不做的开关比没有开关更糟。

### 一套路由，两个监听程序

`agent_routing` 存放两个监听程序完全相同的行为：有哪些智能体、从 `@News Miner`、`/news_miner` 或 `@002` 中读出名称（最长匹配者胜出）、智能体说了什么来结束一轮对话，以及状态报告。协议则留在各自的监听程序中——长轮询不是 REST 轮询，内联键盘不是一列名字，回复在一个里是 `reply_to_message`，在另一个里是 `message_reference`。

它是在编写第二个监听程序时写成的，原因就是状态报告。那个回答若有两份副本，就会对“它在运行吗”给出两个答案，而它们首先会产生分歧的，就是一共有多少个服务。

发送不在其中。它作为 `fSay` 留在每个监听程序里，这样测试就可以替换其中一个监听程序的发送，而不动另一个。

### 一个浏览器，共享；一个配置文件，不共享

`web.fetch` 读取一个公开页面，仅此而已：没有会话、没有表单、没有按钮。浏览器是另一回事，它分为两部分：

| | 位置 | 归谁所有 |
|---|---|---|
| 浏览器 | `/opt/boa/playwright/` | root，0755，只有一份 |
| 配置文件 | `agents/xxx/browser/profile/` | 智能体，0700，每个智能体一份 |

二进制文件是共享的，因为它就是个二进制文件，没什么需要隔离的；每个智能体一份副本的话，每份 600 MB，更新也要做 N 次。配置文件不共享，因为它保存着 cookie：智能体 007 登录某个网站，绝不能让智能体 008 也处于登录状态。这种隔离由内核负责，靠的就是智能体其他所有东西所在的那个 0700 主目录——而这恰恰是一个托管式智能体产品在所有智能体共享一台机器和一套会话时无法提供的。

由此产生三项决策：

**浏览器在一次运行中的多次工具调用之间保持打开。** `browser.click` 作用于 `browser.open` 留在屏幕上的内容，而一次运行从第一次工具调用到最后一次都是同一个进程，所以一个模块级的句柄就是所需的全部状态。`atexit` 会关闭它；没有它的话，一个每小时运行的智能体每次运行都会留下一个 Chromium，到早上就把机器塞满了。

**Playwright 在函数内部导入，绝不在模块作用域导入。** 无论是否安装了浏览器，浏览器工具都会在界面中列出，而如果在顶部发生 ImportError，它们就会从列表中消失，而且哪里都没有解释。延迟导入的话，缺少浏览器就只是一句话，告诉你该运行哪条命令。

**无头模式，并且只访问公网地址。** 需要的是会话和 DOM，而不是一张窗口的图片，所以虚拟显示器只会是一个白白增加的活动部件。

“只访问公网地址”由安装在上下文（context）上的路由处理函数（`browser.fInstallNetworkPolicy`）强制执行，而不是由每个工具各自执行。在 `browser.open` 中检查 URL，每次运行只覆盖恰好一个地址：页面可以自由重定向，而智能体被要求阅读的页面也可以自由地包含指向 `127.0.0.1` 的链接、iframe、图片或表单——而 `browser.click` 根本没有任何检查。放在上下文上，它就覆盖了导航、重定向、点击、提交以及每一个子资源，而某人将来写的第六个浏览器工具，即使不知道它的存在也能得到它的保护。被拒绝的内容会在工具的回答中点名，否则被拦截的请求是看不见的：页面在没有它的情况下照样渲染，而智能体会把预算花在一次又一次的重试上。

主机名每次运行解析一次并被记住，这只是限制而不是消除了这样一个时间窗口：同一个名称在检查时解析为公网地址，在连接时却解析为私网地址。要彻底关闭这个窗口，需要把连接固定到经过检查的那个地址上，而 Chromium 并没有在这里开放这种能力。

和在任何浏览器中一样，会话 cookie 在这里也会在浏览器关闭时消失。保留下来的，是网站标记为要保留的那些。

### 服务商接受什么，与标准怎么说是两回事

有两个适配器发送了其服务商拒绝的东西，两种情况的结果相同：经由该服务商的每一次工具调用都失败了，在每个模型上都是如此，而测试套件什么都没发现，因为它测试的是各个部件，而不是完整的往返。

| 服务商 | 发送了什么 | 返回了什么 |
|---|---|---|
| Ollama | `kanban__list_cards` 被解码回了空 | 注册表拒绝了一个没有授予智能体的工具——而这个名字正是刚刚提供给它的那个 |
| Google | `"additionalProperties": false`，这是正确的 JSON Schema | `400 - Unknown name "additionalProperties" at 'tools[0].function_declarations[0].parameters'` |

Gemini 的 `function_declarations[].parameters` 只是 JSON Schema 的一个子集，对于不认识的东西会拒绝而不是忽略，所以 `fCleanSchemaForGoogle` 会通过一个白名单递归地过滤 schema。用白名单而不是黑名单，理由与这里每一个白名单相同：否则，某人将来往工具 schema 中添加的下一个键，无论有没有人记得把它加进待剥离清单，都会被 Gemini 拒绝。

两者都是通过运行完整的循环——提问、调用工具、回应那次调用——并使用真实的密钥对接真实的 API 发现的。`_/temp/probe-defaults.py` 就是这项检查，而它是唯一能发现这类 bug 的东西：schema 是合法的，名字是正确的，而服务商就是不接受。

### 每个服务商一个适配器文件

二十五个服务商，二十五个文件，尽管大多数说的是同一种方言。单一的“OpenAI 兼容”适配器看起来很整洁，直到其中某个服务商改了一个字段名，修复时就必须不破坏其他二十个。每个文件承载各自服务商的怪癖：DeepSeek 的会在运行器回放之前去掉 `reasoning_content`，llama.cpp 的会检测出不支持工具的对话模板，vLLM 的会把 404 变成它实际提供的模型列表，Cloudflare 的则用凭据拼出它的地址。

它们共享的是 `base.py`：一种以 chat/completions 为模板的中立消息格式，因为大多数服务商本来就使用这种格式，而 Anthropic 适配器会把它翻译成内容块。

它们还共享 `openai_dialect.py`，而它与共享适配器的区别正是关键所在。方言模块承载的是请求本身——POST、值得点名的 HTTP 错误、响应解析——这些都不是任何一个服务商的怪癖。怪癖留在各自的文件中，以模块会读取的类属性的形式声明：

| 属性 | 决定什么 |
|---|---|
| `cDisplayName` | 每条错误消息中的名称。"zai request failed" 不是任何人会去搜索的内容 |
| `cMaxTokensField` | `max_tokens` 还是 `max_completion_tokens`，取决于服务商采用了哪种写法 |
| `cToolChoiceMode` | `auto`、`any`，或者对拒绝该字段的服务商使用 `omit`。智能体需要的是 `auto`：被迫在每一轮都调用工具的模型永远无法结束一次运行 |
| `cChatCompletionsPath` | 基础 URL 之后的路径，用于少数不使用常规路径的服务商 |
| `cAssistantContentWhenEmpty` | 对于 schema 拒绝 null 的服务商，用什么来代替值为 null 的 `content` |

### 二十二个真实密钥改变了什么

这里的每个服务商都用真实的密钥调用过：问一个问题，给一个工具，然后把它发起的工具调用的结果交还给它。全部二十二个有密钥的服务商都完成了这个往返。有七件事只在第二步才显现出来——那一步是使用预设响应的测试永远到不了的——而每一件现在都是一行代码，旁边附有服务商自己的原话：

- **Perplexity 已经停用了那个端点。** `chat/completions` 回应 403 "Sonar is now the Agent API. Use /v1/responses instead of /v1/sonar"，所以那个适配器基于 Responses API 重写，而这个服务商也从单一模型变成了一个覆盖 48 个模型的路由服务。

- **错误消息中的密钥。** Gemini 过去以 `?key=...` 的方式调用，所以它返回的 503 会把整个密钥放进用户读到、运行日志保存的错误中。密钥已移到 `x-goog-api-key` 头中，而 `base.fRedactCredentials` 现在会从任何适配器产生的每个错误中清除 `key=`、`api_key=`、`access_token=` 和 `token=`，因为这种失败模式不应该依赖于某一个适配器记得处理。
- **Gemini 3 要求把它的思维签名交还回去。** 函数调用在返回时不带它所签发的签名的对话会被直接拒绝，所以每个 Gemini 智能体在用过一次工具之后立刻就会失败。`ToolCall.dProviderData` 负责把它带过去再带回来，对其他一切都是不透明的。
- **Cloudflare 拒绝值为 null 的 `content`。** 而当模型只用工具调用回答、没有写任何文字时，助手消息里装的恰恰就是 null。它会得到 `""`；对其他所有服务商，方言模块仍然发送 null，因为方言规定的就是 null。
- **写进回复里的推理。** MiniMax 在回答的文本本身中带有 `<think>...</think>`。它在方言模块中被剥离，而不是在某一个适配器中，因为这是模型的行为，所以同一个模型放在某个网关后面也会这样做——而且只在回复以该标签开头时才剥离，这样一个在写 HTML 相关内容的模型就能保留它的文字。
- **Together 会把通道名留在前面。** gpt-oss 按通道写入，Together 返回的是 "finalThe weather in Madrid"；提供同一模型的 Groq 和 Cerebras 则不会。在 `together.py` 中剥离，单个服务商的怪癖就应该放在那里。
- **四个服务商不肯提供的默认模型。** Fireworks 的 20b 需要它自己的部署，Together 的不是 serverless，Moonshot 停用了 kimi-k2.5，而 gemini-3.7-flash 回应 503 "experiencing high demand"。一个首次运行就失败的默认模型，比落后一个版本的更糟。

有五个适配器完全不使用它，因为它们的 API 不是那一种：Anthropic 的内容块、Google 的 `generateContent`、llama.cpp 的 `/completion`、Cohere 的 v2 chat——它接受相同的消息，但回答时文本放在块中，结束原因是它自己的大写形式，token 计数则嵌套在 `usage.tokens` 之下——以及 Perplexity，它彻底停用了 chat/completions，对其回应

    403 Sonar is now the Agent API. Use /v1/responses instead of /v1/sonar

所以那个适配器使用 Responses API：用一个 `input` 列表代替 `messages`，系统提示词作为 `instructions`，回复以输出项的形式到达——一个文本放在块中的 `message`，或者一个 `function_call`——而不是作为一个 choice。工具结果作为单独的一项 `function_call_output` 返回，并通过 `call_id` 进行匹配。

有两个名称会在其他任何东西看到之前先通过 `factory.dProviderAliases` 解析：`gemini` 是 Google 文档对该 API 的称呼，而 `google` 是从第一个版本起每个智能体的 `info.json` 中都写着的名字，所以两者都会到达同一个适配器，而且只有其中一个会被存储。

一个智能体可以设置为二十五个服务商中的哪一个，由 `fListProviders` 决定，而不是由浏览器决定：当一个服务商是自托管的、或者它的密钥已保存时，它就是 `selectable` 的。这是对哪些值得提供的过滤，而不是一条规则——密钥也可以存放在智能体自己的主目录中，Web 应用看不到那里，所以界面仍然会向智能体显示它当前已经设置的服务商。

同一个标志在界面中决定一件事：**基础 URL** 输入框，无论是主模型还是备用模型，在自托管服务商时显示，在云服务商时隐藏。`base.fInit` 本来就会回退到适配器的 `cDefaultBaseUrl`，所以对于云服务商来说，这个字段问的是一个在提问之前就已经有了答案的问题——而它能接受的、默认值给不出的唯一答案，就是一个错误的答案。它是被隐藏而不是被清空：在云服务商前面放了一个代理的安装，已经保存了那个地址，而隐藏一个输入框不是丢弃其中内容的理由。

`base.py` 对所有适配器隐藏的一件事是工具的名称。本项目把工具称为 `family.action`；而服务商会用 `^[a-zA-Z0-9_-]+$` 校验函数名，会因为那个点而拒绝整个请求，而且不提示是哪个字段出了错。在每个适配器中，`fToolNameToWire` 在发出时把点换成 `__`，`fToolNameFromWire` 在收到时再换回来，所以注册表、界面、`info.json` 和日志永远看不到编码后的形式。

### 开销上限，而不是信任

每次运行都会在四项开销上限中最先触及的那一项处停下：token 数、步数、秒数、每天的运行次数。它们之所以存在，是因为付费 API 上无人看管的循环就是一张空白账单，而在自托管模型上，则是一块永远回不来的 GPU。每个请求的 `max_tokens` 会减去这次运行已经花掉的量，所以一次运行不可能靠最后一次昂贵的调用超出预算。

有四件事决定了上限究竟是上限还是建议，而在修复之前，每一件都让上限只是一个建议：

  - **token 请求没有下限。** `max(512, remaining)` 在预算已经花光时仍然请求 512 个 token，所以一个只剩一个 token 的智能体仍然被允许写半页。
  - **每次调用得到的是剩余的时间**，而不是整次运行的超时。做法是在每次调用之前调整适配器自己的 `vTimeoutSeconds`，而不是给实现 `fSendMessages` 的二十六个适配器各加一个参数。
  - **截止时间在每个工具之前检查**，而不是每一步检查一次。过去，在截止时间前一刻到达的一批六个工具调用会全部执行，每一个都在一次已经结束的运行之上再加上自己的超时。
  - **单调时钟。** NTP 校正时间时 `time.time()` 会跳变，而一次“在未来”开始的运行永远不会到达它的超时。

仍然没有设限的是提示词。一次调用花费的是输入加输出，而这里只给输出设了上限，所以一段长对话会在输入上超支；要计算它，就意味着在每次调用之前都用各个服务商自己的分词器把对话过一遍。触及上限之后的收尾回答也有意超出预算，并在写它的地方注明了这一点。

### 一个智能体同一时间只运行一次

两把锁，因为调用者有两种。

守护进程为每个智能体持有一把 `threading.Lock`，覆盖“这个智能体是否在运行”和“启动进程”这两步。它在各自的线程上处理每个请求，所以两个带 `only_if_idle` 的 `run_now` 调用，就是同一个进程中两个之间毫无阻隔的线程——而扫描 /proc 看不到一个尚未 fork 出来的进程。实测：两次同时调用，两次运行。

运行器在 `<home>/run.lock` 上加 `flock`，并在整个进程生命周期内持有它。这把锁才是权威，因为 crontab 会直接启动运行器，从不经过守护进程。它不是权限边界——拥有 `bash.run` 的智能体想启动什么就能启动什么——它存在的目的是让应用本身不会把同一个智能体启动两次，在同一个浏览器配置文件和同一段对话上花掉两份预算。

### 从未启动的运行会说明这一点

特权守护进程启动运行器时，stdin、stdout 和 stderr 都指向 `/dev/null`。因此 `fLogLine` 写的一切都无处可去，而有两种故障过去完全只存在于这些输出中：

- 运行锁被占用，所以这次运行不会发生；
- 在 `fExecute` 写入 `run_started` 之前就有东西失败了——`info.json` 无法读取，或者服务商的 API 密钥尚未设置，后者的可能性要大得多。

在一套真实安装上实测：锁被占用时，`POST /agents/001/run` 回应 `202 {"started": true}`，而运行日志、`journalctl` 或任何文件中都没有出现任何内容。同样的故障在 cron 下却是可见的，因为 cron 会保留它所启动程序的输出——这就是这个问题存在了这么久的原因。这个漏洞只存在于界面所使用的那条路径上。

`fRecordRunRefused` 改为把它写进运行日志，作为一条状态为 `refused`、没有 `run_id` 的结束记录。这个形式的每一部分都是承重的：

| 部分 | 原因 |
|---|---|
| `kind: run_finished` | “历史”渲染的是结束记录。单独的类型需要界面去学习它，而一条没有任何东西渲染的条目等于没有条目 |
| `status: refused` | `failed_runs` 统计的是状态为 `failed` 的结束记录。智能体的任何部分都没有运行，所以智能体的任何部分都没有失败 |
| 没有 `run_started` | `runs` 和 `max_runs_per_day` 统计的是启动次数。被占用的锁不能为一次没有发生的运行吃掉当天的一次运行配额 |
| `run_id: ""` | 什么都没启动，所以没有可标识的运行 |

只在没有其他东西写入时才写。一旦 `fExecute` 拿到了运行 id，它就已经写入了 `run_started`，而它自己的异常处理函数会在重新抛出之前写入对应的 `run_finished`，所以 `fMain` 在为一次运行添加第二条结束记录之前会检查 `vRun.vRunId`。同样的检查也决定了由谁来关闭这一轮对话：`fExecute` 的处理函数在记录结束时关闭它，而 `fMain` 只为从未走到那一步的运行关闭它。在这样做之前，在 Debian 测试机上实测：每一次无法连接到其服务商的运行，都会用同一句话把问题回答两次。

### “历史”应当显示最新的运行，而过去并没有

`fReadEntries` 返回的运行日志是按从旧到新排列的——它自己的 docstring 里就这么写着——而 `fRenderRunHistory` 取的是它的 `.slice(0, cShownRuns)`。那是最旧的十次运行。一个运行过十次以上的智能体，其“历史”就再也不会变化了。

这是用真实的浏览器驱动真实的应用时发现的，而这也是唯一能发现它的方式：本项目中对 `dashboard.js` 的其他所有测试都只是读取文件并在其中查找某个字符串，而那个字符串确实在。在一套真实安装上用三种语言实测：一个最近一次运行刚因缺少 API 密钥而被拒绝的智能体，显示的却是四十分钟前的一次服务商故障，而那次拒绝根本没有出现。

`.slice(-cShownRuns).reverse()`：最后十次，最新的在最上面，这正是列表上方标题所说的。

列表上方的汇总表格也有它自己的两处错误，都是在同一张截图中发现的：它原样打印 `last_status`，所以西班牙语页面上显示 "Último estado: refused"；它还原样打印 `last_run_at`，所以一个光秃秃的 `2026-09-19T03:44:29Z` 就直接摆在一列经过整理的时间戳上方。现在两者都会经过下方各行早已使用的处理。

### 邮箱是任何人都能写入的那个输入

四个 `mail.*` 工具完全沿用频道的做法：智能体说出它想做什么，由智能体 API——它以 `boa` 身份运行并持有凭据——去做。一个能读到邮箱密码的智能体，拥有的就不是“收件箱的访问权限”；它拥有的是整个账户、其中的每一封邮件，而且永远如此，还能以账户所有者的身份发信。

邮件的不同之处在于输入传递的方向。读取邮箱的智能体，其指令有一部分就藏在它读到的邮件里，而这些邮件可以由世界上的任何人写。由此产生三项决策：

  - **转发只允许发往用户列出的地址**，而且这份列表在 `mailbox` 内部、在打开连接的那个进程中检查——绝不在提示词中检查。提示词里的规则只是建议；套接字上的规则才是规则。没有列表时，转发会被直接拒绝。
  - **读取不会把任何邮件标记为已读**（在只读 select 上使用 `BODY.PEEK[]`），所以智能体查看邮箱不会抹掉用户所依赖的未读计数。
  - **删除会移到废纸篓**，前提是账户有废纸篓。智能体按上个月写的规则删除的东西，人仍然能找到。“该账户没有废纸篓文件夹”和“无法读取文件夹列表”被区分开来，因为只有前者才可能以 expunge 告终：它们过去以同样的空字符串到达 `fDeleteMessage`，所以一行未能解析的 LIST 就会让每一次 `mail.delete` 都变成永久删除。

### 安装时只带一个智能体，却能提供很多

安装过程只创建一个智能体：编排者。其他一切都来自“+”，它提供三个起点：空白智能体、从智能体导出的 `.zip`，或者模板仓库中的模板。一套带着没人要求的智能体到来的安装，一开始就得先去关掉一些东西。

模板过去随本仓库一起发布，每个模板是 `backend/agents/examples/` 中的一个 Markdown 文件。现在它们存放在自己的仓库 [bunch-of-aigents-templates](https://github.com/nipegun/bunch-of-aigents-templates) 中，检出在本仓库旁边的 `../bunch-of-aigents-templates`：新模板无需更新应用就能到达每一套安装，而一套安装也可以在“设置 -> 智能体”中指向一个 fork 或它自己的仓库（`templates_repo_url`、`templates_repo_branch`，保存时由 `agent_templates.fValidateRepositoryUrl` 和 `fValidateBranch` 检查）。`agent_templates` 把整个仓库作为一个 `.tar.gz` 下载，也就是一个分支对外提供的那种形式——安装脚本下载应用时所用的正是这个地址——所以列出模板只需一个请求，不用 GitHub API，也没有频率限制。每个 Web 工作进程会把它缓存五分钟。一个具有相同 `archive/refs/heads/<branch>.tar.gz` 布局的 `file://` 地址，可以服务于一台无法访问外网的机器。

**所有会变成智能体的东西都使用同一种格式**（`agent_package`）：一个包含 `agent.json` 和 `system-prompt.md` 的文件夹，还可以选择包含 `memory.md`、`home/...` 以及 `rag/documents.json` 和 `rag/files/...`。模板文件夹就是只带前两样的这种软件包；导出的 `.zip` 是同样的布局，外加用户勾选的选项。所以安装模板和导入 `.zip` 是同一个函数 `agent_io.fInstallPackage`，任何能导出的东西都能作为模板发布。

一切都在智能体存在之前检查（`agent_package.fReadPackage`），因为半途失败的导入会留下一个没人要求的智能体：

- `agent.json` 只能包含 `lManifestKeys` 中的键，且 `format` 为 1。未知的键会被拒绝而不是被忽略：它要么是模板中的拼写错误，要么是来自更新版本、本版本会误读的软件包。
- 这种格式中没有任何地方可以放 `enabled`、密钥、令牌或频道凭据，也没有地方放智能体监听哪些频道。导入的智能体总是以关闭状态创建，服务商只以名称、模型和基础 URL 的形式迁移——`api_key_ref` 永远不会。
- 计划只能是五个 cron 字段，别无其他（`agents.fValidateSchedule`），并且会在 `exec_daemon.fVerbCreateAgent` 中再次检查。计划以 root 身份写在 crontab 行的开头；一个带有 " /bin/sh -c ..." 或换行符的计划就会成为一条命令。只靠 Web 进程检查是不够的：执行器才是边界。
- 工具只有在本机已安装时才会保留，被丢弃的会被列出（`missing_tools`），让用户在确认之前看到。技能以名称传递，执行器保留已安装的那些，和以前一样。
- `rag` 会经过 `rag_settings.fValidateSettings`，就像从 RAG 标签页写入时一样，而文档库中的文档必须符合软件包自己带来的文件和存储上限。
- 每个主目录路径都会经过 `agent_home.fValidatePath`：必须是相对路径，没有 `..`，并且绝不能是被排除的顶层名称（见下文）。
- `.zip`（`ZipSource`）出现以下情况时会被拒绝：某个成员名称向外越出、存在链接、存在加密成员、某个成员在超过 1 MiB 后膨胀比超过 200:1，或者总大小超过 8 GiB。仓库归档只保留普通文件；其中的链接会被跳过，而不是被跟随。

从模板创建时只指明模板，别无其他。由服务器下载并读取它：一个能够携带自己的工具和自己的计划的请求，会让浏览器把用户从未勾选过的权限交给智能体。对话框把空白智能体放在最前面，然后是 `.zip`，再然后是模板，模板的描述来自每个模板的 `agent.json`，使用界面的语言（`fPickDescription`：该语言，否则为 en-US）。

**一次导入分三个时刻**，因为一个文档库可能重达数百 MiB，而 HAProxy 会丢弃 300 秒内没有发送任何东西的请求：浏览器把 `.zip` 分块上传到 `/opt/boa/imports/<id>/`（`boa`，0700，由两个安装脚本创建，并列在 Web 单元的 `ReadWritePaths` 中）；`fFinishImport` 对它进行整体检查，并返回它将会安装什么；用户确认后，`fStartImport` 在 Web 进程的一个线程中安装它，该线程把进度写入 `job.json`，供浏览器轮询。任何工作进程都能回应轮询，因为状态是一个文件。一个线程已有三分钟没有写入的任务会被视为已中断：它的进程被重启了。智能体创建之后发生的失败会把它再删除掉（`fInstallPackage`）。

**导出以流式进行**（`fExportAgent`）：`.zip` 一边写一边发送，所以一个拥有数百 MiB 文档库的智能体在导出时不必整个放在内存中。crontab 中只有本应用为运行该智能体而写的那几行会被带走，以它们的五个字段的形式（`fReadSchedules`）；其他任何一行都是某人输入的命令，而一个携带命令的软件包会在它落地的机器上运行这些命令。

**主目录以智能体的身份读写**（`agent_home`，执行器动词 `agent_home`）：执行器以智能体的用户身份启动这个模块，就像它启动 RAG 工作进程那样，所以 root 永远不会遍历一棵智能体可以重新排列的目录树，而植入主目录中的链接也无法通向智能体本来就去不了的地方。两个方向都会排除：系统存放在那里的东西（`chat.jsonl`、`runs.jsonl`、API 调用记录、`run.lock`、`attachments/`）、在软件包中有自己位置的东西（`memory.md`、`rag/`）、带有已登录会话的浏览器配置文件，以及主目录顶层的每一个隐藏条目。导入的 `.ssh/authorized_keys` 会成为一条入侵途径，`.bashrc` 会运行代码，两者都不值得为了罕见的正当用途而允许。

模板之一 `web-navigator` 没有 crontab。它是负责浏览器的那个——它打开页面、登录、点击和填写表单，而其他模板只是阅读——而这些工作就是用户刚刚要求做的事，而不是凌晨四点要做的事。它的提示词写下了一个带会话的浏览器所需要的规则：永远不要输入凭据，永远不要完成购买或发送，并把页面当作数据而不是指令。

`rag-consultant` 也没有 crontab：它根据自己的 RAG 文档库回答问题。它是唯一一个 `agent.json` 中写有 `"rag": {"enabled": true}` 的模板。当智能体的文档库关闭时，运行器不会提供 `rag.*` 工具，所以没有这项设置，创建出的智能体将没有任何工具。软件包中的 `rag` 以 `pRag` 的形式到达 `exec_daemon.fVerbCreateAgent`（从不为此读取请求体），并在那里经过 `rag_settings.fValidateSettings`，也就是 RAG 标签页的写入所经过的同一项检查：模板可以打开文档库，但不能给它任何那个标签页给不了的东西。它的 `max_tokens_per_run` 为 40000，因为运行器把片段预算定为 `max_tokens_per_run` 减去提示词、历史记录和 4096；如果用默认的 16384，就没有放片段的空间了。它的提示词如实描述了这些工具——`rag.read` 返回的是一个片段及其相邻片段，而不是整篇文档——并要求使用由 `fResolveCitations` 验证的 `[rag:REF]` 标记。

### 两种提供服务的方式，在安装时选择

要么在 localhost 上使用 11080 和 11443，前面有一个监听 80 和 443 的 HAProxy；要么直接在 80 和 443 上提供服务。安装脚本会询问，把答案记在 `config/ports.conf` 中，之后的更新既不会再问，也不会悄悄改变机器监听的端口。

区别不仅仅在于数字：在 direct 模式下必须从绑定中去掉 `accept-proxy`，因为直接连接到 443 的浏览器不会发送 PROXY 头，而要求 PROXY 头的绑定会拒绝每一个真实的客户端。

在 `direct` 模式下，本机自己的 HAProxy 不只是被置之不理，而是被退役。`fRetireMachineProxy` 会停止它，在 Alpine 上把它从每个运行级别中移除，在 Debian 上将其禁用**并屏蔽**，然后，如果 `/etc/haproxy/haproxy.cfg` 是本安装脚本写的就删除它，如果是别人写的就将其移到 `haproxy.cfg.before-boa.<date>`。光停止它是不够的：一个仍处于启用状态的 HAProxy 会在下次启动时抢先占用 80 和 443，那时本应用还没运行；而在 systemd 下，一次软件包升级、另一个单元的 `Wants=` 或者一条普通的 `systemctl start`，都可能把一个已禁用的单元重新拉起来。被屏蔽的单元无法被任何东西启动，而没有 `/etc/haproxy/haproxy.cfg` 的 haproxy 也无从启动。在那之后仍然占用 80 或 443 的东西会在日志中点名，因为在这种模式下，没有这两个端口代理就无法启动，而半分钟之后才从 "the application did not answer" 中推断出来，是一种糟糕得多的发现方式。

有意不做的是卸载 haproxy 软件包。`boa-proxy` 就是 `/usr/sbin/haproxy`——它终止 TLS，并在 gunicorn 前面读取 PROXY 头，而在 `direct` 模式下，绑定 80 和 443 的正是它——所以清除这个软件包会让应用在任何一种模式下都没有任何东西在监听。被退役的是本机的 HAProxy *服务*，这是另一回事，只是碰巧使用同一个二进制文件。切换回 `proxied` 时会先取消屏蔽再启用该单元，否则回退的路会停在 "The machine's HAProxy would not start"，而原因是本安装脚本自己加上的屏蔽。

在两台测试机上用 `--update --ports direct` 实测：该单元在 Debian 上最终处于屏蔽状态，在 Alpine 上不属于任何运行级别，`/etc/haproxy` 中没有了配置，应用在 443 上返回 200，在 80 上返回 301。回退操作 `--update --ports proxied` 让它重新处于启用和活动状态，在 11443 和 443 上都返回 200。有七个测试会针对伪造的服务命令真正运行该函数，覆盖带标记和不带标记的配置以及两种模式，其中一个测试会在将来某个版本试图调用 `apk del haproxy` 或 `apt-get purge haproxy` 时失败。

### 确认消息显示在用户正在看的地方

`Settings saved`（“设置已保存”）过去写在内容栏的顶部。这在短面板上没问题，在长面板上却毫无用处：智能体“工具”标签页底部的“保存”按钮产生的消息，出现在它上方好几屏的地方，在浏览器正在绘制的范围之外，所以保存看起来像是什么都没做。

现在它是一个居中显示在内容栏上方的弹出消息，位于一个 `fixed` 图层上，该图层是内容栏的兄弟元素而不是子元素。`fixed` 正是关键：在内容栏内部居中会落在*文档*的中间，而对于长标签页，这就是同一个 bug，只是往下挪了几屏。该图层止于侧边栏，因为画在智能体列表上方的消息看起来会像是属于智能体列表的；它也不接收指针事件，所以消息显示期间，它后面的东西都照常工作。

它停留多久是这个浏览器的一项偏好设置（`boa.noticeSeconds`，设置 → 界面），与主题和语言放在一起，理由也相同：三秒对一个词绰绰有余，对一句话却不够，而一条消息属于哪一种，取决于谁在读它。错误是例外，完全忽略这个数字——错误会一直等待被关闭，因为它是用户回头再看屏幕时必须仍然在那里的唯一一种消息。

消息有三种颜色，而第三种之所以存在，是因为另外两种无法表达它。绿色是一次已经发生的保存，红色是一次失败，琥珀色是 **`No changes to save`**（“没有要保存的更改”）：按下了“保存”，而表单中的内容与已存储的内容完全相同。用绿色报告这一点比什么都不说更糟——在一次什么都没写入的保存之后显示“设置已保存”，恰恰是会让人察觉不到自己的修改从未生效的那句话——而红色则会在没有任何问题的地方声称失败。

每个会保存的表单都以同样的方式检查：把它*将要*发送的负载，以 JSON 形式与表单从服务器填充时、或上次保存后拍下的快照进行比较。智能体的设置在一个函数 `fCollectAgentPayload` 中构建这个负载，保存和拍快照都用它，因为同一个表单的两个读取者一旦彼此偏离，就会在其中一个从未看过的那个字段上报告“没有更改”。浏览器偏好设置面板本来就为“有未保存的更改”提示保存了这样的快照，它也能回答这个问题。

例外是**新的**智能体：它的表单装着模板自己的值，从未被保存过，所以按下“保存”会写入这些值并转到对话，而不是说没有什么可做的。

### 颜色表示状态，运动表示活动

智能体头像周围的圆环承载着两个不同的事实，并用两种不同的通道来绘制，这样哪一个都不需要去查。智能体是否打开，用一种不会动的颜色表示：绿色或红色。它此刻是否在工作，用运动表示：一段亮起的弧段沿着那个绿色圆环顺时针移动。为“忙碌”再加一种静态颜色，就成了一个需要学习的约定，而一个在转动的东西不用教就能看懂。

它被绘制成一个与边框完全重合的 SVG 圆角矩形，以虚线描边，并对虚线的偏移量做动画，这样**形状保持不动，只有光沿着它移动**。这就是使用 SVG 的全部原因：改为旋转一个圆环——锥形渐变、圆弧，任何放在 `transform: rotate` 下的东西——会把形状也一起转动，各个角就不再与下面的圆角正方形对齐。`pathLength="100"` 把轮廓归一化，所以样式表用周长的百分比来描述，头像或其圆角半径改变时，什么都不需要重新计算。

回答“谁在忙？”意味着要读取每个进程的命令行，而只有 root 能做到，所以这是特权守护进程上的一个动词。扫描一次 `/proc` 就能同时回答所有智能体的情况——而不是每个智能体调用一次——正是这一点让它足够廉价，侧边栏可以每五秒问一次。同一次扫描也支撑着 `only_if_idle`，所以 buzzer 和界面不会在某个智能体是否在工作这件事上意见不一。

### 到期的卡片会在对话中宣布

智能体的对话是该智能体被要求做的一切的记录，而不只是别人对它输入的内容的记录。所以当 buzzer 为一张到期的卡片启动一次运行时，这张卡片会作为单独的一轮写入智能体的 `chat.jsonl`，而运行的回答会关闭这一轮：打开对话，就能看到工作的到来、智能体对此做了什么，以及花费了多少。

有三项决策支撑着这一切。

**它在运行开始时写入，而不是在卡片创建时写入。** 一张安排在今晚、却在今天下午被删除的卡片从未运行过，而一段说它已被交付的对话，记录的就是一件没有发生的事。buzzer 只会看到仍然在看板上的卡片，所以在唤醒的那一刻写入，才能让这个宣布是真实的。

**文件存储的是卡片的字段，而不是一句话。** `role: "card"` 携带 id、标题、谁指派的，以及是否要求立即执行；消息的文本是卡片自己的指示。它们周围的每一个字都由界面以用户自己的语言写出——正是同一条规则，让一次被停止的运行记录 `ceiling: "tokens"`，而不是一句英文短语。

**“立即”和“在 13:45”必须区分开来，而等到智能体被唤醒时，两者都已成为过去。** 所以看板记录的是要求的是哪一种（`run_mode`），而不是事后根据时钟推算出来，而 `now` 这个词会以词的形式从浏览器传到 `kanban.fValidateRunAt`，在那个同时记录了它原本是什么的地方才变成时间戳。

写入是特权守护进程的工作，而不是 buzzer 的：`chat.jsonl` 位于归智能体所有的 0700 主目录中，而 buzzer 以 `boa` 身份运行。守护进程 fork，降权到智能体身份，写入宣布，然后才启动运行——如果主目录无法写入，运行照样启动。宣布是工作的记录，而不是工作本身。

反过来的失败并非无害，处理方式也正好相反：如果在这一轮打开**之后**进程无法启动，守护进程会在抛出异常之前把失败写进这一轮。其他任何东西都不会关闭它，而一个未关闭的轮次不只是让一张卡片得不到回答——它会让该智能体的输入框永久关闭。

接下来的运行既不是普通的定时运行，也不是一轮对话。它会把回答写回对话，因为问题在那里，但对话**不会**回放给它：它的提示词就是那张卡片，而回放十轮往来，就会让每次定时运行都为一段没人在进行的对话付费。在运行器中，这是两个独立的标志——`vWritesToChat` 和 `vIsChat`——而这一区分就是全部。由此推论，一次在询问模型任何东西之前就停止的运行（已关闭的智能体、每日上限），仍然必须关闭这一轮，否则界面会永远等待回答，输入框也会一直关闭。

### API 文档是本应用的一个页面

它根据本项目构建的 OpenAPI 规范渲染，而不是从 CDN 加载 Swagger UI，因为生产服务器是一台局域网中的机器，可能根本无法访问外网。由于它是我们自己的页面而不是外来的组件，由此产生两点。

它**跟随所选的语言**。规范本身保持英文——它是一个 API 的契约，其字段名、id 和错误字符串全都是 en-US，而一个翻译过的 `openapi.json` 描述的将是一个并不存在的 API。被翻译的是页面：`fAnnotateSpecForTranslation` 在渲染之前给每一段英文挂上一个 `data-i18n` 键，浏览器再像在其他每个页面上那样替换它。这样字符串就和其他所有字符串一起放在前端的 `.json` 文件中，而且对匿名读者也有效。这些键是从文本和路径派生出来的，而不是手写的，所以新的端点会自带它的键；没有译文的键保留英文，这正是 `fApplyTranslations` 对它不认识的键所做的处理。

它**填满分配给它的那一栏**，和其他每个页面一样。它过去保持 900px 的版心并居中，这对散文来说易读，对这个页面却很糟：页面大部分是参数表格和 JSON 块，它们被挤在宽屏的三分之一里，两侧是空白的边距。

### 图片附件需要显式的工具权限

`browser.screenshot` 保存一个文件；`image.send` 把它附加到当前回复上。后者需要单独授予，web-navigator 模板中包含了它。该工具把 PNG 快照到 `agents/<id>/attachments/<opaque-id>.png`，目录为 0700，文件为 0600。之后覆盖原始截图不会改变较早的回复。`ToolContext.lAttachments` 把这些引用带给 `AgentRun.fRecordChatAnswer`，或者带给它的失败报告/运行报告。

只有执行器会为 Web 进程读取这些私有文件。它的 `read_chat_attachment` 动词要求该引用存在于该智能体已记录的对话中，打开路径中的每一级目录时都不跟随链接，并检查图片是归该智能体所有的普通文件。它以 1 MiB 的分块读取 PNG；即使是 50 MiB 的附件，base64 回复也保持在现有的 RPC 上限以下。经过身份验证的 HTTP 端点以 `private, no-store` 流式传输这些字节。前端根据 ID 构建本地图片 URL，绝不使用模型提供的 URL。

Telegram 对符合条件的图片使用 [sendPhoto](https://core.telegram.org/bots/api#sendphoto)，对很高或很大的截图使用 [sendDocument](https://core.telegram.org/bots/api#senddocument)，发送的是原始 PNG。私有文件以 multipart 数据上传；不需要公开 URL，也不需要让智能体访问机器人凭据。`telegram_deliveries` 为每个待处理的轮次记录已确认送达的文本和图片部分。重试时从缺失的部分继续，删除待处理的那一行会清除这些检查点。永久性失败会报告给用户。两个收件箱都会把 SQLite 的 UTC 时间戳与 Unix 时间进行比较；把它们当作本地时间来解释，曾导致最近的投递在夏令时期间过期。

### 没有构建步骤

前端是 Jinja2 模板、纯 CSS 和纯 JavaScript。生产目标是一台自托管的 Debian 或 Alpine 机器；一个改样式表都需要 Node 工具链的部署，是一个会慢慢腐朽的部署。出于同样的理由，`/api/doc/` 渲染它自己的 OpenAPI 规范，而不是从 CDN 加载 Swagger UI：局域网服务器可能无法访问外网，而离开外网就会失败的文档，恰恰会在有人调试时失败。

### 音频转写

启动 OpenRC 服务时，安装脚本会在 `rc-service` 命令上关闭文件描述符 3 和 4。它们是安装脚本保存下来的 SSH stdout/stderr 管道：曾观察到 `supervise-daemon` 在安装脚本成功退出之后仍然持有它们。普通输出仍会记录到 `install.log` 中。

`audio_transcription` 在 `settings.audio_transcription` 中保存一份经过校验的 JSON 配置。OpenAI、Groq、Mistral 和 Together 使用 multipart；Hugging Face 和 Cloudflare 接收二进制 WAV。它们复用 `api_keys`，不会把密钥返回给浏览器。FFmpeg 对容器格式、协议、大小、时长和运行时间加以限制。音频被切成每段 120 秒（对 Hugging Face 和 Cloudflare 的原始端点是 30 秒，以免依赖长音频生成选项）；whisper.cpp 和解码都以 `boa` 身份运行，不经过 shell，也不会自动切换到另一个服务商。

`audio_inbox` 把目标、设置和转写文本持久化到 SQLite 中。`boa-channel-telegram` 中一个受进程锁保护的后台线程会在重启后恢复它的队列。预留的轮次 ID 让执行器在检查智能体是否忙碌之前，就能确认一次重复提交。把任务标记为已提交和插入 `telegram_pending` 在同一个事务中完成。私有音频存放在 `/opt/boa/audio/`（0700，属于 boa），播放时既要求已登录，也要求有匹配的聊天引用；清空已完成的聊天轮次时，它会被删除。

两个安装脚本都会先校验源码归档的 SHA-256，再编译 whisper.cpp v1.9.4，并下载 `base`。`whisper_models.json` 包含全部 30 个官方模型的名称、大小和哈希值。只有 root 执行器会通过 `install_whisper_model` 下载模型；任意 URL 和路径都会被拒绝。下载到一半的文件只有在哈希校验通过之后才会可见。`whisper/` 归 root 所有；`boa` 只能读取它。更新会保留模型和音频；备份包含音频，但不包含模型权重。缺少 Python 解释器时，会在检查最低版本之前连同依赖一起安装。

### 原始服务商请求与智能体工作区

`AgentRun.fSendRecordedRequest` 会在该次调用期间给所选服务商挂上一个记录器，备用模型的调用和收尾调用也包括在内。基于 Requests 的适配器使用 `BaseProvider.fPostJson`，它会在发送之前记录完全相同的序列化 JSON 请求体。OpenAI 和 Anthropic 的 SDK 客户端使用请求钩子，捕获已经准备好的请求体，包括 SDK 添加的字段和每一次重试。记录器从不保存认证头，也从不根据聊天历史重建请求。

`api_calls` 在 `agents/<id>/api-calls.jsonl` 中写入一份索引，并为每个请求写入一个完整的 `api-call-<id>.json` 请求体，权限为 0600，位于智能体的私有主目录中。保留策略会删除最近 100 个之外的整条请求。执行器只读取属于该智能体的普通文件，拒绝符号链接和 FIFO。请求体通过执行器的套接字以有大小上限的分块传输；经过认证的 HTTP 路由在 `body` 下以流的形式传回它们原始的 JSON 文本。浏览器按词法单元进行格式化，不解析数字，因此大整数和字符串转义都能原样保留。

受保护的 `info.json` 保存 `interface.show_api_calls`，默认为 false。它只控制可见性；无论该标签页显示还是隐藏，请求都会被记录。`dashboard.js` 把对话类标签页和设置类标签页分开，并且在加载智能体时总是选中“聊天”。只有“API Calls”打开时它才轮询请求元数据，展开详情时才加载完整的请求体。设置区的标题用 ID 标识智能体；“立即运行”属于工作区，删除操作在“常规”中有自己的面板。

输入框固定在状态栏正上方，只有 `#vChatLog` 会滚动。在桌面宽度下，显示聊天时 `app.css` 让 `.app` 恰好占满一个视口的高度（`.app:has(#vChatPanel:not([hidden]))`），并通过一个 flex 列把这个高度一路传给 `.chat`，因此页面本身不会滚动，表单也就不会被滚出视野。在 820 px 及以下，页面重新作为一个整体滚动，`.chat` 的高度是一个视口减去 `--status-bar-live-height`，而 `api.js:fTrackStatusBarHeight` 借助 `ResizeObserver` 让这个值始终等于状态栏的实际高度——在手机上状态栏会折成好几行，用固定的估计值时，文本框就被压在了它下面。输入框下方没有提示行：`fSetComposerEnabled` 把提示写成占位文本的第二行（Enter 键的作用，或者智能体正在工作），`fFitChatInputToPlaceholder` 在一个不可见的副本上测量这段占位文本，并设置文本框的 `min-height`，使它永远不会被截断。每当占位文本或输入框的宽度变化时（`fTrackChatInputWidth`），它都会运行。高度通过 CSSOM 设置，从不通过 `style` 属性，因为 CSP 会把后者丢掉。

### 每个智能体的 Samba 共享

`agents.dDefaultSambaSettings` 定义了默认值：开启共享、可读写、可浏览、需要认证访问，文件/目录权限为 0600/0700。密码初始为未设置。`info.json.samba` 是受保护的配置；密码只存在于 Samba 仅 root 可读的 passdb 中。它通过 stdin 传给 `smbpasswd`，从不经过 argv、模型、返回的 API 对象或 `info.json`。

`boa-samba` 在 TCP 445 上运行一个隔离的 smbd，配置和原生状态位于归 root 所有的 `/opt/boa/samba/`，运行时文件位于 `/run/boa-samba/`。它没有 homes 服务。共享名由 `fGetAgentSystemUser` 派生；共享路径始终是 `<agent home>/samba`。认证使用该账户，文件操作使用该智能体的 uid。访客访问需要对每个智能体单独显式设置。安装脚本拒绝接管与本项目无关的 Samba 安装，并且只在 BoA 自己的安装中停用发行版的默认实例。

执行器在创建/索引智能体之后创建该文件夹，并在删除用户之前移除共享和账户。两个安装脚本都会在安装/更新/恢复之后，让现有智能体的共享与配置保持一致。一个排他文件锁让更改依次进行；`testparm` 先校验，然后才原子地替换配置。`smbcontrol` 重新加载配置，并且只关闭发生变化的那个共享的连接。停用智能体的共享与智能体的运行开关相互独立。

创建文件夹时使用带 `O_NOFOLLOW` 的目录描述符，并检查所有权。Samba 拒绝共享内部的链接，一个以 root 身份运行的 preexec 守卫会在每次连接时再次检查共享的根目录。该守卫以 `-I` 运行受信任的 Python 代码，因此智能体的工作目录无法提供被导入的模块。

备份通过常规的智能体主目录归档包含共享文件，通过受保护的 info 文件包含设置。`tdbbackup` 在原生密码数据库运行期间为它创建快照；备份还会保留服务器 SID。恢复要求 smbd 处于停止状态，会先校验一个临时数据库，然后整体替换，而不是与当前凭据合并。通过旧的 smbpasswd 格式导出时，某些原生账户 RID 会被拒绝，因此不采用这种方式。`fVerifyInstallation` 读取保存下来的 Web 端口模式，因此恢复时校验的是实际的 HTTPS 端口，包括没有显式 `--ports` 参数的 direct 模式。

参考：[Samba 共享选项](https://www.samba.org/samba/docs/current/man-html/smb.conf.5)、[TDB 备份工具](https://www.samba.org/samba/docs/3.6/man-html/tdbbackup.8.html)。

### 本地文档检索

该标签页在所有语言中都叫 `RAG`，HTML 和 JavaScript 中的后备文本也一样。

`rag_store` 负责每个智能体的编目（SQLite WAL、FTS5、文档、修订版和上传偏移量）。原始文件名只是元数据；磁盘上的文件名使用生成的标识符。`rag_extract` 读取 PDF/EPUB/TXT/Markdown，并调用本地的 Poppler 和 Tesseract 进行 OCR。它保留页码/章节位置，并在解析之前检查 EPUB 解压后的大小。`rag_embeddings` 只使用 `AF_UNIX`，固定连接 `/run/boa-embeddings/engine.sock`：没有主机名、没有代理，也没有云端回退。

文档可编辑的 **文档信息**，按表单显示的顺序（即 `rag_store.lMetadataKeys`，`fAction` 也以它为准进行校验）依次为：出版年份、标题、副标题、作者、版本、语言和标签。文档列表中，如果有副标题，会显示在标题正下方。年份以文本形式保存（为空，或最多四位数字），这样“未知”就不会和某个数字混为一谈。`rag_store.fMigrate` 会添加 `rag_store.lAddedColumns` 中列出的列，也就是编目已经存在之后才引入的那些列（目前是 `year` 和 `subtitle`）：`CREATE TABLE IF NOT EXISTS` 从不修改已存在的表，而旧的文档库和恢复的备份都带着旧的表结构。`rag_search.fSource` 给每个片段都附上副标题、年份、作者、版本和语言，因此模型无需额外调用 `rag.list`，就能区分标题相同的文档、为引文标注日期和出处，并权衡两个说法不一致的版本。引用链接和文档库搜索只保留标题和位置：它们指明的是一个位置，副标题只会让链接变长。

`rag_models.json` 是向量化模型的清单：每个模型都记录了固定的 URL 和 SHA-256、维度、上下文长度、池化方式、查询前缀和片段前缀，以及为它测得的两个相似度（`min_support` 用于经验证模式，`min_similarity` 用于搜索下限）。随附两个模型：EmbeddingGemma 300M Q8（`default`；768 维，均值池化）和 Qwen3-Embedding 0.6B Q8（1024 维，末 token 池化，每个查询前加一条英文指令，片段前不加任何内容）。正在使用的模型是运行时设置（`/opt/boa/rag-runtime/settings.json`，由 root 写入，每个智能体都可以读取）中的 `model`，通过 `rag_settings.fSelectedModel` 和 `rag_embeddings.fModel` 读取。`rag_runtime` 负责安装权重——安装脚本安装所选的模型，执行器按请求安装其他任何模型（`install_rag_model`，在一个线程中一次只下载一个，进度写在 `rag-runtime/status/<id>.json` 中）——文件只有在大小和 SHA-256 都匹配之后才会得到它的正式名称。它以模型的池化方式启动 llama.cpp v0.5.0，并把模型 ID 作为 `--alias`。网络访问只属于安装阶段。运行时使用模型自己的分词器和检索前缀，并拒绝超长的输入。SQLite 保存文本和向量；USearch 保存增量的 HNSW 代。发布一个修订版会原子地切换编目中的可见性和索引名称。

引擎只有一个，所以模型是为整台机器选择的，由 root 执行器完成切换（`rag_exec.fRuntime`）：它拒绝不在磁盘上的权重，保存这一选择，把仍在使用旧模型推荐值的每个智能体的 `min_similarity` 改为新模型的推荐值（`fFollowModelSimilarity`；有人特意选定的值保持不变），然后重启 `boa-embeddings`。任何向量都不会仅凭设置文件就被信任。`rag_embeddings.fEmbed` 在向量化之前会先询问引擎它提供的是哪个模型（`/v1/models`，即别名），如果不是预期的模型，或者向量的维数不对，就抛出 `EngineUnavailable`；索引任务会传入它开始时所用的模型，因此中途换模型会让任务停下，而不是在同一个修订版中混入两个向量空间。每个文档都会记录其已发布修订版背后那个模型的指纹（`documents.model`）。`rag_worker.fWork` 在下一轮处理时发现文档库的模型不是所选的模型（`fFollowNewModel`）：它丢弃未完成修订版的分块，把每个用其他模型索引的文档重新排入队列，并丢弃旧索引。已发布的修订版保持不变。在轮到它之前，文档只能通过 FTS5 找到：`fSearch` 只用当前模型的文档构建向量排名——通过新索引，或者在新索引还不存在时逐一比较它们保存的向量——并附加一条 `notice`，说明有多少个文档在等待。引擎重启期间，搜索也由同样的关键词回退来应答。`rag_verify` 在比较的两侧固定使用同一个模型，并从该模型取得阈值。

`boa-rag` 以 boa 身份运行，并请求现有的执行器启动固定的工作进程命令。`rag_exec` 在任何文档或 SQLite 操作之前都会先降权到对应的 UID/GID；root 从不解析书籍，也从不打开智能体的编目。工作进程使用操作系统锁、资源限制和持久化状态。上传 RPC 以 256 KiB 为一块，下载以 1 MiB 为一块；整本书从不作为一条消息穿过执行器协议。工作进程会让前一个修订版保持可搜索，并在中断后从已完成的分块继续。设置保存在受保护的智能体配置中。

引擎不可用不是文档错误。套接字出错，或者引擎在加载模型期间回答 503 时，`rag_embeddings` 会抛出 `EngineUnavailable`（一种 `ValueError`）；其他任何拒绝仍然是普通的 `ValueError`。`fIndexDocument` 单独捕获这种不可用：文档带着**同一个**修订版回到 `queued`，保留所有已经向量化的分块，并显示原因，直到任务再次运行。旧的做法——标记为 `error` 并删除该修订版的分块——会让一本大书在每次 `--update` 时都损失几个小时的工作，因为安装脚本会在由 `boa-exec` 启动的工作进程仍在运行时停止 `boa-embeddings`。`fWork` 在开始处理每个排队的文档之前都会探测引擎（`fIsAvailable`），遇到不可用就结束这一批；否则调度器每 5 秒一轮，每一轮都会对整个文档做提取或 OCR，结果只是在第一个分块处停下。

`rag_search` 结合 FTS5 排名和语义排名；带筛选的搜索只在选定的子集上计算。运行器在回答调用之前先检索，并且只在启用 RAG 时才授予三个只读的 RAG 工具。来源的数量受配置的文本预算和保守的运行 token 估算限制。引用标记只解析为本次运行中实际返回过的来源。回答服务商可以是远程的：仅在本地处理的要求只适用于向量化。

三种回答模式的区别在于**运行器**强制执行什么，而不只是提示词怎么说。`mixed` 允许模型补充通用知识。在 `documental` 和 `verified`（`runner.lRagModesThatSearch`）中，模型必须自己调用 `rag.search`：没有调用就给出的最终回答，会被 `fCheckRagAnswer` 退回一次（`cRagSearchFirstPrompt`）。运行器自己的搜索逐字使用用户的最后一条消息，而在对话中（“那第二版呢？”），这样的搜索什么也找不到，模型在看得到整段对话的情况下写出的查询却能找到。出于同样的原因，空搜索不再在询问模型之前就结束 documental 模式的运行；保证被移到了最后：`fFinishRagAnswer` 会把一次完全没有检索到任何片段的运行的回答替换为一句固定的话。不使用 `tool_choice` 来强制搜索：29 个适配器中，有的发送 `auto`，Cohere 什么也不发送，Mistral 使用 `any`，所以只有运行器才能对每个服务商强制这一点。

`verified` 额外加入 `rag_verify`。回答被切分为若干单元——段落，以及各自单独成为一个单元的列表项；围栏代码块附在它前面的段落上，并与之一起比较（单看一个示例的引导语几乎说明不了什么，忠实的示例曾因此被删掉）；标题、以“:”结尾的短标签和分隔线不受检查。一个单元需要带有一个 `[rag:REF]`，指向本次运行中检索到的片段之一，而且除非它只是一个单纯的引用，否则还必须与其中某个片段足够接近：把该单元作为查询进行向量化，与作为文档进行向量化的片段比较，用的是与搜索相同的距离，阈值为模型的 `min_support`（EmbeddingGemma 为 0.36，Qwen3-Embedding 为 0.44）。第一次未通过的回答会连同未通过的单元被退回一次（`fBuildCorrectionPrompt`）；之后这些单元会被删除，并由一行本地化的文字说明删除了多少个。如果没有剩下任何有依据的内容，就给出那句固定的话；无法连接引擎时，则扣下回答（失败即关闭）。这些固定的话（`rag_verify.dFixedTexts`）使用系统提示词要求回答所用的语言，通过它在 `dAnswerLanguageLines` 中的那一行来识别，否则使用英语。这项检查的局限经过测量，并写在检查代码旁边。在 138 个忠实段落和 2,652 条指向其他话题片段的引用上，两个模型都没有任何阈值能把两者分开；当前使用的阈值会删掉约 6% 的忠实段落（主要是简短的列表项和一行的总结），并放过不到 1% 的那些错误引用。指向同一话题片段的引用大约有四分之一的概率能通过，而与其片段相矛盾的段落得分和忠实段落差不多：这项检查能抓住的，是引用了讲别的事情的片段，以及完全没有来源的段落。

备份在归 root 所有的暂存父目录下创建快照，让以智能体身份运行的子进程执行 SQLite 备份，并硬链接它选定的不可变文件，然后把该快照归档。这样可以让 WAL 和 HNSW 代保持一致，也避免 root 遍历一棵智能体可以偷梁换柱的快照树。恢复会取消未完成的上传，并把中断的索引重新排队。索引指纹仍然可用于重建。

## 4. 主要流程

### 文档检索

安装脚本在解压快照之前，会先清除被恢复智能体的旧 RAG 目录树，因此陈旧的 SQLite WAL 文件和向量代不会在恢复之后残留下来。恢复运行时设置时，不会替换已经安装的模型权重。工作进程每一轮最多处理八个文档，或者最多花 90 秒开始处理新文档；未完成的任务会持久保存。文档库的响应会显示从收件箱导入失败的情况。本地 OCR 会安装 Liberation 字体，供没有嵌入字体的 PDF 使用。向量化引擎的构建会禁用预构建 Web UI 的下载。

上传：`rag_api → exec_client.fRag → rag_exec → rag_worker`，以智能体身份执行。索引：`boa-rag → exec_daemon → rag_worker.fWork → rag_embeddings.fIsAvailable → extraction → local embeddings → publication`。索引期间引擎不可用：`rag_embeddings.fRequest → EngineUnavailable → fIndexDocument → state queued, chunks kept → fWork ends the batch → next pass resumes at the first missing chunk`。模型下载：`settings_rag.js → POST /api/admin/rag/models/<id>/install → exec_client.fInstallRagModel → exec_daemon.fVerbInstallRagModel → rag_runtime.fStartModelDownload → thread fInstallModel → status file ← GET /api/admin/rag (fDescribe) polled every 2 s`。更换模型：`settings_rag.js (fConfirmModelChange) → PUT /api/admin/rag → rag_exec.fRuntime → fIsModelInstalled → fSaveRuntimeSettings → fFollowModelSimilarity → restart boa-embeddings → [each library] rag_worker.fWork → fFollowNewModel → fIsAvailable waits for the new alias → fIndexDocument(pModel) → fBuildIndex/fPublish (documents.model)`；与此同时 `fSearch → FTS5 only for the waiting documents → notice`。回答：`AgentRun.fExecute → rag_search.fSearch → bounded passages → configured provider → verified citation links`。documental 和 verified 模式的回答：`model answers → fCheckRagAnswer (no rag.search yet → cRagSearchFirstPrompt, once) → rag.search → model answers → [verified] rag_verify.fVerify → unbacked units → fBuildCorrectionPrompt, once → model answers → fFinishRagAnswer (no passages → fixed sentence; verified → units removed + count, engine down → withheld) → fResolveCitations`。

### 保存记忆及其上限

`dashboard.js:fSaveAgent` 按 Unicode 码位计数，并把 `memory` 与 `info.limits.max_memory_characters` 一起提交。`api.fCheckMemoryUpdate` 在任何写入之前，对照拟设定的上限（或者读取已保存的上限）进行校验，因此提高上限和保存更长的文本可以在同一个请求中完成。拒绝时，它返回已翻译的 `memoryTooLong` 或 `memoryLimitInvalid` 错误。接着，`fVerbWriteAgentInfo` 持久化该上限，`fVerbWriteMemory` 在降权之前进行校验。`memory.fWrite` 再次检查受保护的设置，并在不截断的情况下原子地替换文件。`memory.append` 和 `memory.replace` 使用同样的检查；超过上限的 75% 时开始出现警告。表单会保留粘贴进来的超长文本，以便继续编辑。

传输预算足以支撑这个上限的最大值：每个执行器请求 6 MiB，由客户端在连接之前检查；每个响应 8 MiB；每次读取记忆文件 4 MiB；每个 HTTP 请求体 16 MiB，对会转义 Unicode 增补字符的 JSON 客户端也够用。这些是传输上限，而不是模型上下文的上限。

### 机器人对陌生人什么都不显示

机器人的用户名是公开的：任何找到它的人都能和它打开一个对话。所以 `fIsFromTheConfiguredChat` 会把 Telegram 附在每条消息上的 `chat.id`（发送者无法伪造）与配置的那个进行比较，`fHandleMessage` 会在分派任何命令、选择任何智能体之前，丢弃不匹配的消息。`fHandleCallback` 对按钮点击也做同样的处理。不会回复任何内容：回复就等于向正在试探的人确认这个机器人还活着。也不会记录任何内容。以前丢弃时会连同来源对话的 ID 一起记入日志，而那是别人的数据，这意味着这套安装会悄悄积累一份谁发现了这个机器人的名单。剩下的，就是一条从未存在过的消息。

代价是真实存在的，值得说清楚：配置错误的 `chat_id` 现在看起来和陌生人一模一样，所有者自己的消息会悄无声息地消失。每次启动时，配置的 ID 都会写入日志——`Registered 3 command(s) for chat <id> only`——这就是要拿来对照的号码。来自*已配置*对话、却没有到达任何智能体的消息仍然会被记录，因为在那里发送者就是所有者，否则“我给它发了消息，什么也没发生”就和“消息根本没到”无法区分。

这个过滤器不涉及、也无法涉及的，是对话内部的*谁*：如果 `chat_id` 指向一个群组，那么这个群组的每个成员都能与智能体对话。

命令列表写在哪里，也由同样的道理决定。`setMyCommands` 接受一个作用域，而 `default` 和 `all_private_chats` 对 Telegram 的每个用户都会生效——所以写在那里的列表就是展示给陌生人看的菜单，里面还有“Server status”，等于宣告这背后有一台值得去捅一捅的机器。他们永远无法运行其中任何命令，但锁着的门上挂的牌子仍然是块牌子。`fSetTelegramCommands` 只把列表写到已配置对话的作用域中，并在每次刷新时**删除**两个公开作用域中的列表：旧版本代码写下的列表会一直留在 Telegram 那边，直到有什么东西把它删掉。`fHideTelegramPublicProfile` 清空另外两个公开字符串 `setMyDescription` 和 `setMyShortDescription`，空对话中“What can this bot do?”下方显示的就是它们。

仍然可见的是机器人的名称、头像和“开始”按钮，Telegram 会在每个与机器人的空对话中画出这个按钮，任何 API 都无法移除。按下它会发送 `/start`，而它会像来自其他对话的任何消息一样被丢弃。

### 为什么菜单里放的是工具而不是智能体

Telegram 会在命令菜单的每一项旁边画出 `/name`——这个字符串就是菜单项本身，点击它时输入框里填入的就是它，任何 API 都无法隐藏它。所以由智能体组成的菜单永远不可能是别人想看的那种智能体列表，而且它会随着名册一起变长，却丝毫说明不了这个机器人是干什么用的。

菜单里放的是机器人能做的三件事。有哪些智能体是一个问题，`/agents` 用内联按钮来回答它，按钮上只写 `os-watcher`，别的什么都没有，因为按钮上的文字由机器人决定。

其余的都由此而来：

- **选中的智能体会一直保持选中。** 点击按钮或点名一个智能体就会选中它；所有未指明对象的消息都会发给它，直到选中另一个为止。每一行都点名智能体，一次还好，到第四条消息就让人厌烦了。它保存在 `settings` 中，而不是内存里，因为服务在每次更新时都会重启。
- **回复仍然优先。** 它没有歧义，而且正是拿着手机的人会做的事。除此之外没有任何东西会改变选择，所以一个智能体永远不会仅仅因为恰好是最后一个说话的，就接手一段对话。
- **已删除的智能体不再被选中。** `fReadSelectedAgent` 在返回时会检查名册：谁也联系不上，总好过联系上接手了它 ID 的那个智能体。
- **机器人说安装所设定的语言。** 首先看 `agent_language`，也就是智能体回答所用的同一个设置——机器人说的话和智能体的话出现在同一段对话中。

## 6. 影响分析

修改这些地方会弄坏什么。

| 组件 | 修改它会影响 |
|---|---|
| `paths.fNormalizeAgentId` | **系统中的每一条路径。** 它是用户输入和文件系统路径之间唯一的校验。削弱它，任何智能体 ID 都会变成路径穿越 |
| `paths.py` 中的常量 | 全部四个服务、安装脚本和 systemd 单元。修改 `/opt/boa` 就意味着要重新安装 |
| `deploy/haproxy/boa.cfg` | 每一个请求。`accept-proxy` 必须与本机 HAProxy 发送的内容一致：如果那个后端上有 `send-proxy-v2`，它就是必需的；如果没有，bind 会拒绝每一个连接 |
| `backend/web/gunicorn.conf.py` 的 bind | 必须保持为 Unix 套接字。再次给 gunicorn 一个端口和一张证书，就会重新引入 PROXY 头部先于 TLS 到达的故障 |
| `exec_protocol.lKnownVerbs` | 特权接口面。添加一个动词，就是给 Web 进程多了一种向 root 请求某件事的途径。每一次添加都需要和第一次一样严格的审查 |
| `exec_daemon.fRunPrivilegedCommand` | 每一个特权命令。它从不使用 shell；在那里引入 `shell=True`，就会让每个智能体名称都成为注入点 |
| `agent_api.fAuthenticate` | 智能体对看板和频道的每一个请求。两项检查都必须保留 |
| `db.cAppSchema` / `cKanbanSchema` | 现有的安装。没有迁移系统：表结构使用 `IF NOT EXISTS`，所以**新的列需要显式的迁移代码**，而不是修改表结构 |
| `agent_scripts.cMinimumMinuteStep` | 智能体可以多频繁地为自己安排运行。在一个粗心的时间表和一个前面挂着 cron 行的死循环之间，它是唯一的屏障 |
| `paths.lProtectedAgentFiles` | 哪些文件会移进归 root 所有的那个“抽屉”。安装脚本的迁移和创建智能体的守护进程都读取它，因此两者对于是哪些文件不会有分歧 |
| `agents.fBuildAgentInfo` | 只影响新智能体。现有的 `info.json` 文件不受影响，所以新字段需要一条读取默认值的路径 |
| `exec_daemon.fVerbWriteAgentInfo` | **`info.json` 中每个能在保存后留存的字段。** 它逐个键重建文件，所以它没有列出的字段，就是有人第一次按下“保存”时界面会悄悄丢掉的字段。列表通过 `fReadNameList` 读取，它能区分不存在的键（“别动它”）和空列表（“全部去掉”）：如果用 `or` 读取，取消勾选最后一个工具反而会恢复之前的列表 |
| `skills.fSelectInstalledSkills` | 什么会进入提示词，以及 `skill.read` 会打开什么。索引和工具都经过它的过滤，所以从服务器上删除的技能不会再被提及，而不是先被许诺、然后失败 |
| `providers.base` 的中立结构 | 每个适配器和运行器 |
| `tool_registry` 接口 | `/opt/boa/tools/` 中的每个工具，包括用户自己编写的 |
| `telegram_listener.fIsFromTheConfiguredChat` | 谁可以和你的智能体对话。机器人的用户名是公开的，所以这项检查就是全部的授权：削弱它，任何找到这个机器人的人都能在你的服务器上启动运行 |
| `channels.fSendMessage` 的签名 | 每个调用者，以及那两个接受两个参数的发送函数。`pReplyToMessageId` 会传给 Telegram 和 Discord，它们正是人可以通过其回复的两个频道 |
| `discord_markdown.cMaxDiscordLength` | 智能体的回答究竟能不能送达。Discord 会拒绝超过 2000 个字符的 `content`，而它的做法就是拒绝，不是截断 |
| `agent_routing.fMatchNamedAgent` | 一条消息会到达谁，在**两个**监听程序中都是如此。正是最长匹配让 `@News` 和 `@News Miner` 成为两个智能体 |
| `agent_routing.fBuildStatusReport` | 两边的 /status 回答什么。只有一份报告，所以两者对有多少个服务不会有分歧 |
| `discord_listener.fIsFromTheConfiguredChannel` | 智能体监听哪个频道。与 Telegram 不同，这里没有第二道关于谁在说话的检查：凡是能在那个频道里写消息的人，都能启动运行 |
| `kanban.lStates` | 看板、API、前端，以及每个智能体的提示词 |
| `run_journal` 的条目结构 | 写入方（运行器）和读取方（守护进程、Web）。旧的行会留在日志中：读取方必须容忍缺失的字段 |
| `samba` | 智能体的生命周期、特权 API、SMB 客户端，以及两个安装脚本的备份/恢复。保持文件夹守卫、名称/路径的派生和密码处理完好无损 |
| 守护进程从智能体主目录中读取的文件（`runs.jsonl`、`chat.jsonl`、`memory.md`） | 只能通过 `paths.fReadAgentOwnedFile` 读取。守护进程从主目录中读取的新文件也必须经过它，否则 root 会去读智能体指给它的任何东西——一个永远不应答的 FIFO，一个指向机器上任意文件的链接 |
| 备份包含的内容（`fDoBackup` 中的 `tar` 那一行） | `/opt/boa/` 下属于安装而不属于代码的新状态必须加到那里，否则在新机器上恢复时就会丢失 |
| 一次运行的内核限制（`runner.cMaxProcesses`、`exec_daemon.cRunTasksMax`、`cRunMemoryMax`） | 需要超过 1024 个任务或 2 GiB 的工具必须调高它们；一个浏览器本身就有几百个线程 |
| 作为路径的 `runner.py` | 每一次计划运行。cron 按路径启动它，几乎不带任何环境，所以运行器会把它自己的根目录放进 sys.path：没有这一步，`import backend` 会失败，回溯信息会进入 cron 的邮件，而在局域网机器上，那封邮件哪儿也去不了 |
| `runner.dAnswerLanguageLines` | 添加到系统提示词中、告诉智能体用哪种语言回答的那一行。它用**那种语言本身**写成，并声明自己优先于提示词自身的规则——实测表明，放在规则旁边的偏好会输 |
| `agent_api.fFilterCardsForAgent` | 智能体可以知道哪些东西存在。对看板的每一次读取都经过它，编排者是唯一的例外。如果改为在工具中过滤，就等于把一条安全规则放进了一段模型可以被说服放弃的描述中 |
| 聊天气泡位于哪一侧 | 谁在说话。卡片是智能体被要求去做的事，所以它和用户的消息一起放在右侧；计划运行的报告是智能体在说话，所以留在左侧 |
| `chat.lToolsWorthReporting` | 哪些工具让一次计划运行值得放进聊天。其余的都留在日志中：否则每小时运行一次的智能体每天会发二十四条“没什么可报告的”消息 |
| `chat.lAskingRoles` | 哪些角色会等待回答。一个会打开轮次却没有列出的角色，会在智能体工作时让输入框保持打开；一个列出了却从不关闭的角色，会让输入框永远关闭 |
| `kanban.cRunNow` | 浏览器、智能体和 API 发送的那个词，用来代替时间戳。在 `fValidateRunAt` 之外的任何地方把它转换成时间，都会丢失 `run_mode`，也就丢掉了“现在”和一个选定时刻之间的区别 |
| `chat.cReplayedTurns` | 每条聊天消息的开销。每个被回放的轮次在下一条消息时都要再付一次费，所以调高它会让长对话越来越贵 |
| `TestThemes` 中的 `lTextColours` | 对比度测试会测量哪些颜色。用作文字颜色却没有列进这个列表的颜色，就是没有任何东西检查的颜色 |
| 任何模板中的 `style=` 属性 | 没有任何作用：`style-src` 是 `'self'`，没有 `unsafe-inline`，所以浏览器会把它丢掉。有一个测试会在出现这种属性时失败 |
| `app.css` 中的 `.notice-layer` | 应用中每一条确认和每一条错误出现的位置。`position: fixed` 起着关键作用：`absolute` 会在文档中居中，而不是在屏幕上居中，而这正是这个图层要修复的 bug |
| `app.css` 中的 `.app:has(#vChatPanel…)` 链和 `--status-bar-live-height` | 聊天的文本框能否保持在状态栏上方。这个 flex 列中如果有一个块没有 `min-height: 0`，或者 `.chat` 的高度不再减去状态栏的实时高度，页面就会重新滚动，输入框就会跑到状态栏下面 |
| `agents.fValidateSchedule` | 来自 `.zip` 或模板的时间表，能否在一个以 root 写入的 crontab 中变成命令。放宽它（一个空格、一个 `#`、一个换行），就会把一次导入变成代码执行 |
| `agent_home.sExcludedTopNames` / `fIsExcluded` | 导出可能泄露什么，导入可能植入什么：浏览器会话、`.ssh`、聊天记录。去掉一个名称，就会让它在两个方向上都畅通无阻 |
| `agent_package.lManifestKeys` / `cFormatVersion` | 每个导出的 `.zip`，以及每个仓库中的每个模板。新的键需要这个版本才能读取；含义改变则需要新的格式编号 |
| `rag_models.json` 中的 `min_support` | 对该模型而言，经验证回答中的哪些段落能保留下来。调高它，忠实的段落开始被删掉；调低它，指向无关片段的引用会被放过。两个模型的每个取值会删掉什么、放过什么，都写在 `rag_verify.py` 中检查代码旁边的表格里：改动某个值之前，先在真实文档上重新测量，并更新那张表格 |
| `rag_models.json` 中某个模型的 `sha256` 或 `dimensions` | 用它索引的每个文档库。新的指纹就是新的向量空间：每个文档库都会在下一轮处理时重新索引全部文档（`fFollowNewModel`），对大文档库来说要花上几个小时 |
| `rag_embeddings.fCheckServedModel` / `rag_runtime.fServe` 中的 `--alias` | 向量能否来自其文档库所记录模型之外的模型。没有它们，一个跨越模型更换的任务就会在同一个修订版中保存两个模型的向量 |
| `runner.lRagModesThatSearch` / `fFinishRagAnswer` | documental 或 verified 模式的运行，能否交付出自模型自身权重的文本。从列表中去掉一个模式，或者去掉“没有片段”的检查，就会重新出现背后没有任何检索的回答 |
| `rag_search.fSource` | 模型得知的关于一个片段的一切，以及引用链接指向的地方：预先检索的提示词块、`rag.search`、`rag.read` 和 `fResolveCitations` 都使用它。给它添加字段时，还需要在为它提供数据的三个 `SELECT` 中加上对应的列 |
| `rag_embeddings.EngineUnavailable` | 索引失败时是保留还是丢弃已完成的工作。对引擎不可用抛出普通的 `ValueError`，会让文档变成 `error` 并删除其已向量化的分块；对永久性的拒绝抛出 `EngineUnavailable`，则会让文档永远停留在队列中 |
| `rag_store.cSchema` | 只影响修改之后创建的编目。每个现有智能体的文档库和每个恢复的备份都保留旧表：新的列还需要在 `rag_store.lAddedColumns` 中加上对应条目，由 `fMigrate` 来应用 |
| `frontend/static/i18n/en-US.json` | 添加一个键，就意味着要把它添加到其他十四个文件中，否则该字符串会回退为英文。缺少键、丢失 `{placeholder}`、翻译了路径或工具名称时，`TestTranslations` 都会失败 |

### 新的工具

在 `/opt/boa/tools/` 中创建一个 `.py` 文件，声明：

```python
cToolName = "namespace.verb"
cToolDescription = "What the model is told it does."
dToolSchema = {"type": "object", "properties": {...}, "required": [...]}

def fRunTool(pArguments, pContext):
  return "text the model sees"
```

它以发起调用的智能体身份运行。如果它需要智能体无法访问的东西，就改为在智能体 API 中添加一个动词，并通过 `agent_api_client` 调用它。

该文件必须归 root 所有：应用会把它当作代码导入。

### 新的技能

在 `/opt/boa/skills/` 中创建一个目录，并在其中放一个 `SKILL.md`：

```markdown
---
name: BackupVerification
description: One line. This is what every run pays for.
---

The procedure, at whatever length it needs.
```

无需注册，也无需重启：`fListSkills` 会读取该目录，因此下次加载页面时它就会出现在界面中。在某个智能体上勾选它，再给该智能体 `skill.read`，下一次运行时它就在提示词中了。

目录中的其他任何东西都会随技能一起提供。这些内容所有人都可读，所以技能可以说“运行此目录中的 `verify.sh`”，而智能体也确实能运行。

名称就是目录名：字母、数字和短横线，以字母开头。头部中的 `name:` 是人在列表中看到的名称；目录名则是智能体请求时使用的名称。

### 新的特权操作

在每个参数到达路径或命令行之前都对其进行校验，并让动词保持专一。一个通用到可以复用的动词，通常也通用到可以被滥用。

### 新的语言

`tests/test_web.py` 中的 `TestTranslations` 会在以下情况下失败：缺少键、多出键、空字符串、丢失 `{placeholder}`、翻译了路径或工具名称、文件未排序、某个选择器没有提供该语言、缺少提示词中的那一行，以及缺少 Telegram 块。六种非拉丁文字的语言还会检查是否真的用它们自己的文字书写，因为一个以俄语命名、内容却全是英文字符串的文件能通过其他所有检查。`tests/test_tools.py` 中的 `TestExampleAgents` 会在某种语言缺少 README、CODE 或 MANUAL，或者某个 README 没有链接到其他每种语言的 README 时失败；`tests/test_web.py` 中的 `TestTheCodeDocumentsPointAtRealLines` 会在某个 CODE 的 `file.py:line` 引用与英文版不同时失败。
