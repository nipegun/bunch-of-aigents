## できること

- **エージェントは Linux ユーザーです。** Web 画面でエージェントを1つ作ると、システム上に `agent-007` が作られ、ほかのどのエージェントも読めないホームディレクトリを持ちます。それが隔離の仕組みです。Python で書かれたサンドボックスではなく、カーネルによる隔離です。
- **エージェントは自分のスケジュールで動きます。** それぞれが専用の crontab を持ち、その所有も実行もエージェント自身のユーザーが行います。エージェントは起きて、仕事をして、終了します。
- **エージェントと話せます。** エージェントをクリックするとチャットが開きます。何かを頼むと、エージェントはツールを使い、終わったら答えます。会話は記憶されます。
- **会話は人ごとではなく、エージェントごとに1つです。** 期限が来たカードは実行の開始とともにその同じチャットに投稿され、回答はその下に表示されます。そのため、エージェントのチャットには、あなたやほかのエージェントから頼まれたことのすべてと、それに対してエージェントが何をしたかが残ります。
- **カンバンボードを共有します。** エージェントはカードを追加し、動かし、互いの作業を見ます。あなたはログを読む代わりに `/kanban/` で様子を見守ります。
- **クラウドでも自前ホストでも、どんなモデルでも。** 25 のプロバイダーが最初から用意されています。Anthropic、OpenAI、Google、DeepSeek、Mistral、Qwen、xAI など、その前段に立つルーターである OpenRouter、Groq、Together、Vercel など、そして自分のハードウェアで動かす Ollama、llama.cpp、vLLM です。エージェントはそれぞれ自分のモデルを選び、そのモデルが落ちているときのための予備も持てます。
- **本当に止まる支出の上限。** トークン数、ステップ数、秒数、1日あたりの実行回数を、エージェントごとに決められます。そうしなければ、有料 API の上で無人で動くエージェントは白紙の請求書です。
- **設定できるメモリ。** 各エージェントのメモリ上限は、その設定で 1,000 から 1,000,000 文字の範囲で選べます（既定は 8,000）。上限を超える書き込みは、テキストを切り詰めたり保存済みのメモリを置き換えたりせずに拒否されます。
- **エージェントごとの文書ライブラリ。** PDF、EPUB、TXT、Markdown の本をアップロードできます。テキスト抽出、OCR、ベクトル化はローカルで行われ、エージェントは関連する抜粋を取り出して出典を示します。設定は **RAG** で行います。ベクトル化モデルは既定で EmbeddingGemma 300M です。プロセッサーとメモリに余裕のあるマシンなら、**設定 → RAG** で Qwen3-Embedding 0.6B に切り替えられます。
- **持ち運べるエージェント。** エージェントの **エクスポート** タブは、そのエージェントを `.zip` としてダウンロードします。メモリ、モデル、ライブラリ、ホームのファイルを含めることもできますが、鍵は決して含みません。そして **+** で、ここにも別のインストールにもインポートできます。既製のエージェントは[テンプレート リポジトリ](https://github.com/nipegun/bunch-of-aigents-templates)から入手できます。
- **拡張できるツール。** ツールはそれぞれ `/opt/boa/tools/` 内の1つの `.py` ファイルです。新しいものを置くと **設定 → ツール** に現れ、「自動化」や「ブラウザー」といったサブタブに分類されます。
- **共有できるスキル。** `/opt/boa/skills/` に一度書いた手順は、好きなだけ多くのエージェントに与えられます。エージェントが自力で学んだことはそのエージェント自身のメモリの中で消えていきますが、スキルはそうではありません。
- **エージェントごとのブラウザーと、それぞれのセッション。** エージェントはサイトにログインし、フォームに記入し、クリックできます。ページを読むだけではありません。その cookie はエージェント自身の 0700 のホームに置かれるので、あるエージェントのログインがすべてのエージェントのログインになることはありません。
- **Telegram や Discord から返事できます。** /agents でエージェントを選ぶか、エージェントから届いたメッセージに返信すると、書いた内容がそのエージェントに届いて実行が始まり、答えがスマートフォンに返ってきます。やり取りの全体は、双方の発言とも Web 画面のそのエージェントの会話にも残るので、1つの画面ですべてを見られることに変わりはありません。
- **Telegram の音声。** **設定 → 音声** では、ローカルの whisper.cpp か、保存済みの API キーを使う OpenAI、Groq、Mistral、Together AI、Hugging Face、Cloudflare を選べます。30 のネイティブモデルがすべて選択肢にあり、必要に応じてダウンロードされます。音声での返信はテキストとして元のエージェントに届き、Web チャットに表示されます。音声を再生することもできます（任意）。
- **エージェントごとの共有フォルダー。** 各エージェントの `samba/` フォルダーは、その Linux ユーザー名を共有名とする SMB 共有なので、Windows、Linux、macOS からファイルを置けます。
- **15 の言語。** ドイツ語、英語（英国と米国）、スペイン語（スペインとアルゼンチン）、フランス語、ヘブライ語、ヒンディー語、イタリア語、日本語、韓国語、ポルトガル語（ブラジルとポルトガル）、ロシア語、簡体字中国語に対応しています。対象は画面、エージェントにどの言語で答えるかを伝える1行、そして2つのボットの発言です。

1人の利用者が自分の LAN で動かすために作られています。

## 動作環境

対応するシステムは2つです。どちらでも、init は細かな話ではなく要件の一部です。

- **systemd が PID 1 の Debian。** 10のサービスは systemd ユニットです。ほかの init で起動する Debian にはそれらを起動するものがないため、インストーラーはマシンに手を付ける前に `systemctl is-system-running` を確認し、systemd がなければ拒否します。そのようなマシンで試さないでください。答えは変わりません。
- **OpenRC の Alpine。** 10のサービスは `supervise-daemon` で監視される OpenRC スクリプトです。事前に何かをインストールしておく必要はありません。マシンに `openrc` がなければ、インストーラーが自分で追加します。

Debian では `systemctl is-system-running` で確認してください。応答（`running`、`degraded`、`starting`）が返ってくる必要があり、「System has not been booted with systemd as init system (PID 1)」と表示されてはいけません。コンテナの場合は `systemd systemd-sysv dbus` をインストールし、コマンドを `/sbin/init` にする必要があります。

init システムのほかに、次のものが必要です。

- `root` でのアクセス。どちらのインストーラーも `sudo` を使わず、必要ともしません。
- アプリケーションとその Python 環境のための、約 500 MB のディスク容量。
- `haproxy`（インストーラーがインストールします）。TLS を終端するのはこれです。マシンの HAProxy が送る PROXY ヘッダーは TLS ハンドシェイクより前に届き、その位置でそれを読めるのはプロキシだけだからです。
- 話し相手となるモデル。クラウドプロバイダーの API キーか、到達できるどこかで動いている Ollama、llama.cpp、vLLM のいずれかです。

インストーラーはさらに **whisper.cpp v1.9.4** を `/opt/boa/whisper/` にビルドし、FFmpeg をインストールし、多言語対応の `base` モデル（追加で約 142 MiB）をダウンロードします。コンパイル、システムの依存パッケージ、ブラウザーには、さらにディスク容量が必要です。Python インタープリターがない場合は、バージョンを確認する前にインストールされます。

このマニュアルのそれ以外の内容は、どちらでも同じです。

## Alpine を使う場合

このマニュアルで `systemctl` や `journalctl` が出てくるコマンドは、すべて Debian 用です。Alpine でもアプリケーションは同じで、変わるのは init システムとログの行き先です。

| Debian の場合 | Alpine の場合 |
|---|---|
| `systemctl status boa-web` | `rc-service boa-web status`、10すべてなら `rc-status` |
| `systemctl restart boa-web` | `rc-service boa-web restart` |
| `journalctl -u boa-web -f` | `tail -f /opt/boa/logs/boa-web.log` |
| `install-update-reinstall-debian.sh` | `install-update-reinstall-alpine.sh` |

Alpine には機能が1つ欠けており、今後も戻ってきません。ブラウザーがないのです。Playwright が musl 向けのビルドを公開していないためです。ブラウザーのツールは一覧に残り、エージェントが呼び出すとその旨を伝えます。

## インストール

インストーラーはディストリビューションごとに1つあり、どちらも同じフラグを受け付けます。`root` で実行してください。

### Debian の場合

> **マシンで systemd が動いている必要があります。** まず `systemctl is-system-running` を実行してください。「System has not been booted with systemd as init system (PID 1). Can't operate.」と表示されたら、そこで止めてください。これがインストールするサービスはすべて systemd ユニットなので、それらを起動するものがありません。インストーラーが拒否するのはそのためで、何も提供しないインストールを残すようなことはしません。

```bash
curl -fsSL https://raw.githubusercontent.com/nipegun/bunch-of-aigents/main/deploy/install-update-reinstall-debian.sh \
  | bash -s -- --install --email you@example.com
```

`curl` がインストールされていない場合は（最小構成の Debian には `curl` も `wget` もないことがよくあります）、先にインストールしてください。そうしないと、上の行は `curl: command not found` と表示して止まります。

```bash
apt-get update && apt-get install -y curl
```

あるいは、インストーラーを先にダウンロードし、実行する前に読んでください。そのほうがよい習慣です。

```bash
wget https://raw.githubusercontent.com/nipegun/bunch-of-aigents/main/deploy/install-update-reinstall-debian.sh
less install-update-reinstall-debian.sh
chmod +x install-update-reinstall-debian.sh
./install-update-reinstall-debian.sh --install --email you@example.com
```

### Alpine Linux の場合

フラグは同じで、スクリプトが違います。systemd ユニットの代わりに OpenRC サービスを書き込みます。`wget` を使って `sh` にパイプする1行で実行します。インストールしたばかりの Alpine には `curl` も bash もなく、`wget` と `sh` はどちらも BusyBox のものだからです。

```bash
wget -qO- https://raw.githubusercontent.com/nipegun/bunch-of-aigents/main/deploy/install-update-reinstall-alpine.sh \
  | sh -s -- --install --email you@example.com
```

`curl` があるマシンでは、`wget -qO-` の代わりに `curl -fsSL` を使ってもかまいません。ただしその場合は、その行に注意してください。`curl: not found` が `sh` にパイプされると、エラーを表示したうえで、何もインストールしないまま **成功** するからです。

インストーラーが bash ではなく POSIX シェルで書かれているのは、`wget` と同じ理由です。インストールしたばかりの Alpine には、`| bash -s --` が渡す先の bash がありません。インストーラーは途中で bash をインストールするので（どのエージェントにも bash シェルが与えられます）、すでに bash があるマシンでは `| bash -s --` でも同じように動きます。

あるいは、先にダウンロードし、実行する前に読んでください。

```bash
wget https://raw.githubusercontent.com/nipegun/bunch-of-aigents/main/deploy/install-update-reinstall-alpine.sh
less install-update-reinstall-alpine.sh
chmod +x install-update-reinstall-alpine.sh
./install-update-reinstall-alpine.sh --install --email you@example.com
```

動き始めてから違う点が2つあります。どちらも設計上の判断ではなく、システムの事情によるものです。

- **ブラウザーがありません。** Playwright は musl 向けのビルドを公開しておらず、Alpine もパッケージを用意していないため、エージェントが `browser.open` などを呼び出すと、その旨を伝えます。`web.fetch` と `rss.fetch` はどこでも同じように動きます。
- **`systemctl status` の代わりに `rc-status`** を、`systemctl restart boa-web` の代わりに `rc-service boa-web restart` を使います。[Alpine を使う場合](#alpine-を使う場合)を参照してください。

Alpine では、サービスがインストーラーの SSH 出力を手放すので、インストーラーは終了するとセッションの制御を返します。

### インストーラーが行うこと

1. `boa` システムユーザーと、`/opt/boa/` 以下のツリーを作成します。
2. Python の依存パッケージを `/opt/boa/venv/` にインストールします。
3. 自己署名の TLS 証明書を生成します。ただし、自分の `fullchain.pem` と `privkey.pem` を `/opt/boa/certificates/` に置いてある場合は生成しません。
4. アプリケーションを、80 と 443 の HAProxy の背後の 11080/11443 で提供するか、80 と 443 で直接提供するかを尋ねます。`--ports proxied|direct` を渡せば、あらかじめ答えておけます。答えは記録されるので、`--update` が再び尋ねることも、黙って変えることもありません。`direct` を選ぶと、マシン自身の HAProxy は退役します。停止され、すべてのランレベルから外されるかマスクされ、その `/etc/haproxy/haproxy.cfg` は、このインストーラーが書いたものなら削除され、ほかの誰かが書いたものなら `haproxy.cfg.before-boa.<date>` として残されます。こうして、次回の起動時に 80 と 443 を奪うものがなくなります。haproxy パッケージ自体は残ります。アプリケーション自身のプロキシがそのバイナリだからです。
5. エージェントを1つ作成します。オーケストレーターの `manager` です。それ以外はすべて、**+** を押したときに選ぶ、空のエージェント、エージェントからエクスポートした `.zip`、または[テンプレート リポジトリ](https://github.com/nipegun/bunch-of-aigents-templates)のテンプレート（`web-navigator`、`os-watcher`、`mail-watcher` など）です。最初に提示される選択肢は空のエージェントです。
6. [サービス](#サービス)に挙げたサービスをインストールして起動します。Debian では systemd ユニット、Alpine では `supervise-daemon` で監視される OpenRC サービスです。
7. 行った内容とログインパスワードを `/opt/boa/logs/install.log`（root、モード 0600）に書き込みます。
8. 完了したと伝える前に、アプリケーションにログインページを要求します。ページが返ってこなければその旨を伝え、その時点のマシンの様子（curl がリクエストをどう扱ったか、そのポートで何かが待ち受けているか、サービスの状態、サービスが最後に出力した数行）を同じログに書き込み、成功を報告する代わりにそのログを示します。`--update` の場合は、その前に以前のバージョンを元に戻します。

### パスワードの場所

指定したメールアドレスが唯一のログイン ID です。パスワードは自動で生成されます。次のコマンドで読めます。

```bash
cat /opt/boa/logs/install.log
```

この1つのファイルが両方を兼ねています。インストールの完全なログと、そこで生成された認証情報です。ログインページにこのファイルの名前が表示されるので、どこにあるかを覚えておく必要はありません。

## 更新と再インストール

```bash
./install-update-reinstall-debian.sh --update      # エージェントとデータを残す
./install-update-reinstall-debian.sh --reinstall   # 先にすべてを削除する
```

Alpine では、もう一方のスクリプトで同じ2つのフラグを使います。

```bash
./install-update-reinstall-alpine.sh --update
./install-update-reinstall-alpine.sh --reinstall
```

`--reinstall` は、すべてのエージェント、ホームディレクトリ、crontab、そしてカンバンボードを削除します。`--yes` を渡さない限り、確認を求めます。

途中で止まったインストール（ダウンロードの失敗やネットワークの切断など）は、もう一度 `--install` を実行すれば完了します。止まったところから再開します。`--update` は、そういうインストールを見つけるとその旨を伝えます。

残りの2つのフラグ `--backup` と `--restore` については、[バックアップと復元](#バックアップと復元)で説明します。

## アプリケーションを開く

既定の `proxied` モードでは、アプリケーション自身の HAProxy が `127.0.0.1:11443`（HTTPS）と `127.0.0.1:11080`（HTTP、リダイレクトします）で待ち受けます。これらのポートにはサーバーの外からは届きません。LAN に向けて提供するのはマシン自身の HAProxy で、実際のクライアントのアドレスが失われないよう、`send-proxy-v2` 付きで 11443 に転送します。`direct` モードでは、アプリケーション自身が 80 と 443 で待ち受け、前段には何もありません。

準備ができたら、次を開きます。

```
https://your-server/
```

`/opt/boa/certificates/` に自分の証明書を置いていなければ、証明書は自己署名なので、ブラウザーが一度警告を出します。

### マシンの HAProxy に必要な設定

このアプリケーションを指すバックエンドには、2つのものが必要です。

```
backend https-out
  mode tcp
  server srv-https-out 127.0.0.1:11443 check port 11080 send-proxy
```

- **`send-proxy`**。実際のクライアントのアドレスがアプリケーションに届くようにするためです。これがないと、すべてのリクエストが 127.0.0.1 から来たように見え、ログインの試行回数の制限がアドレスごとに働かなくなります。
- **`check port 11080`**。ヘルスチェックが TLS のポートではなく、平文の HTTP ポートを叩くようにするためです。TLS ポートへの TCP チェックは、接続してからハンドシェイクなしに切断するので、アプリケーション自身の HAProxy はそのたびに SSL ハンドシェイクの失敗としてログに記録します。2秒ごとに1行、いつまでもです。2つのポートは同じ1つのプロセスのものなので、片方が応答すれば、もう片方もあるということです。`check-send-proxy` は追加しないでください。11080 は PROXY プロトコルを受け付けません。
- **`option ssl-hello-chk` は使いません。** その ClientHello は TLS 1.2 より古いため、TLS 1.2 を要求するバックエンド（このアプリケーションも、最近の Apache や nginx もそうです）はチェックに失敗し、いつまでもダウンと判定されます。症状は、完璧に動いているサービスからの 503 です。普通の `check` だけで、ポートが応答することはすでに確認できます。

## ログイン

`https://your-server/` を開き、インストーラーに指定したメールアドレスと、インストーラーが生成したパスワードでログインします。パスワードが手元にない場合は、次のようにします。

```bash
cat /opt/boa/logs/install.log
```

このファイルはインストールの全ログで、末尾に認証情報があります。ログインページにこのファイルの名前が表示されているのは、まさにこういうときのためです。

**ログアウト** を押すと、画面の中央に確認が表示されます。確認するとセッションが終了します。ログインしたままにするには、**キャンセル** を選ぶか Escape キーを押します。

アカウントは1つだけです。そのパスワードは **設定 → アカウント** で変更します。変更するときは現在のパスワードも求められます。それがあることで、ブラウザーが開いたままなのを見つけた誰かではなく、あなた自身による変更になります。また、ほかのすべての端末にあるほかのすべてのセッションも、即座に終了します。ほかの誰かがパスワードを知っていると思ったときに変更する意味は、まさにそこにあります。

更新後に初めてアプリケーションを開くと、もう一度ログインを求められます。更新前のセッションには、いつ発行されたかの記録がありません。「分からない」ときは、尋ねることで答えます。

同じアドレスから10回失敗すると、ログインは15分間閉ざされます。正しいパスワードでも入れません。

## 初回の手順

1. メールアドレスと生成されたパスワードでログインします。
2. エージェントがクラウドプロバイダーを使うなら、先に **設定 → APIキー** でその鍵を保存してください。プロバイダーの一覧には、鍵のあるクラウドプロバイダーしか表示されません（[APIキー](#apiキー)を参照）。
3. サイドバーの **+** を押して、最初のエージェントを作成します。
4. プロバイダーとモデルを選びます。同じマシン上の Ollama なら、既定値がすでに正しい設定です。このエージェントだけを別のアカウントに請求させたいなら、専用の鍵を与えてください（[エージェントにモデルを与える](#エージェントにモデルを与える)を参照）。
5. システムプロンプトを書きます。何のためのエージェントか、そして「完了」とは何を意味するかです。
6. 必要なツールを与えます。まずはカンバンのツールから始めましょう。
7. **今すぐ実行** を押して、ボードを見守ります。
8. 思いどおりに動くようになったら、スケジュールを与えます。

## 画面構成

円形の青いロゴには、明るい色のフェイスパネル、暗いバイザー、青い目を持つ3体のロボットのエージェントが描かれています。黒いスーツに白いシャツ、暗い色のネクタイ姿です。腰から上が描かれ、中央のエージェントがひと回り大きくなっています。ロゴはログインページ、サイドバー、ブラウザーのタブに表示されます。

左のサイドバーには、エージェントの一覧が表示されます。それぞれ ID、名前、実行回数、使ったトークン数が表示されます。どの枠も同じ高さなので、長い名前は省略記号で切られます。全体を読むにはマウスを重ねてください。ID を囲む四角は、エージェントがオンのときは緑の輪で、オフのときは赤の輪で囲まれます。

**エージェントが作業中のときは、光る部分がその緑の輪を時計回りに回ります。** これは、そのエージェントがいままさに実行中であることを示します。何をしているかではなく、何かをしているということだけです。チャットでメッセージを送るか **今すぐ実行** を押すとすぐに回り始め、実行が終わると止まります。実行のきっかけが、あなたでも、スケジュールでも、期限が来たカードでも同じです。輪の状態は数秒ごとに確認されるので、少し遅れることがあります。

サイドバーの下部にある2つの点は、バックグラウンドサービスが動いているかどうかを示します。どちらかが赤なら、エージェントは動きません。[うまく動かないとき](#うまく動かないとき)を参照してください。

**+** ボタンでエージェントを作成します。

## 最初からいるエージェント

インストールで作られるエージェントは、ちょうど1つです。

**`manager`（agent-000）** はほかのエージェントを取りまとめます。目標をカードに分解し、それを割り振ります。最初からオンになっています。

あえてそれだけにしています。誰も頼んでいないエージェントを抱えて届くインストールは、まずオフにするものがある状態から始まってしまいます。それ以外はすべて、**+** を押したときに提示される、テンプレート リポジトリの **テンプレート** か、誰かがエクスポートした `.zip` です。

## 新しいエージェントの作成元

**+** を押すと、どこから始めるかを尋ねられます。

| 選択肢 | 内容 |
|---|---|
| **空のエージェント** | プロンプトもツールもスケジュールもなし。自分で書きます。 |
| **.zip ファイルからインポート** | その **エクスポート** タブから書き出したエージェント（このインストールでも別のインストールでも）。 |
| **GitHub のテンプレートからインポート** | テンプレート リポジトリのエージェントを一覧から選びます。 |

**空のエージェント** が一覧の先頭にあるのは、それがいつでも正しい唯一の答えで、ほかの選択肢はすべてそこへの近道だからです。

### GitHub のテンプレート

テンプレートは専用のリポジトリ [bunch-of-aigents-templates](https://github.com/nipegun/bunch-of-aigents-templates) に、1つにつき1フォルダーで置かれています。そのため、新しいテンプレートはインストールを更新しなくても手元に届きます。**GitHub のテンプレートからインポート** を選ぶと、サーバーはそのリポジトリをダウンロードし（1つの `.tar.gz` で、5分間保持されます）、そこにあるエージェントをアルファベット順に一覧表示します。それぞれに、あなたの言語での説明、付属するツールの種類、起きる頻度、ライブラリを有効にするかどうかが示されます。このインストールにないツールは除かれ、一覧にその旨が表示されます。確認に通らないテンプレートは提示されず、いくつ除かれたかが1行で示されます。

現在リポジトリにあるテンプレートは次のとおりです。

| テンプレート | 内容 |
|---|---|
| **backup-watcher** | バックアップが実行されたか、新しいか、怪しいほど小さくないかを確認します。 |
| **cert-watcher** | TLS 証明書の期限切れが近づくと、まだ時間があるうちに警告します。 |
| **disk-cleaner** | 何がディスクを埋めているかを見つけ、何を消せそうかを伝えます。提案するだけで、削除はしません。 |
| **kanban-watcher** | 平日の毎朝ボードを読み、短い要約を1つ書きます。 |
| **log-watcher** | 指定したログを読み、新しいことや新たに頻発していることを報告します。 |
| **mail-watcher** | メールボックスを見張り、届いたものを、プロンプトに書いた規則に従って処理します。 |
| **news-watcher** | プロンプトに挙げた RSS フィードを読み、規則に合うものを報告します。 |
| **os-watcher** | このマシンを見張ります。ディスク、メモリ、スワップ、負荷、そしてサービスが動いているかどうかです。 |
| **rag-consultant** | RAG ライブラリの文書をもとに質問に答え、主張ごとにその根拠となる箇所を引用します。文書に書かれていないことは、そう伝えます。 |
| **site-watcher** | 指定したサイトが応答するか、すばやく応答するか、以前と同じ内容を表示しているかを確認します。 |
| **web-navigator** | 自分のブラウザーを操作して、サイト上で頼まれたことを行います。検索、ログイン、フォームへの記入、クリックによる移動を行い、見つけたものを報告します。 |

`web-navigator` と `rag-consultant` にはスケジュールがありません。頼まれたときに働き、その依頼がそのまま作業内容になります。`web-navigator` は、ブラウザーが何のためにインストールされているかを示すエージェントでもあります。ほかのエージェントがページを読むのに対して、これはログインし、クリックし、フォームに記入します。パスワードを入力すること、何かを購入すること、送信ボタンを押すことはしません。その手前まで進んで止まり、どのボタンを押せば作業が終わるかを伝えます。

`rag-consultant` は自分の文書ライブラリをもとに答えます。ライブラリが有効な状態で届く唯一のテンプレートで、ライブラリがオフのあいだはそのツールが与えられません。役に立つようにするには、その **RAG** タブで文書をアップロードし（[ローカル文書ライブラリ](#ローカル文書ライブラリrag)を参照）、モデルを選んでください。回答の各記述には、その出典となる文書のページへのリンクが付きます。文書に書かれていないことは、穴を埋める代わりにそう伝えます。トークンの上限（1回あたり 40,000）がほかより高いのは、読んだ抜粋がその上限に数えられるからです。

どのテンプレートも、選ぶ前に、付属するツールの種類と起きる頻度を示します。テンプレートはプロンプトであると同時に、権限の集まりでもあります。「メールボックスを見張る」という説明だけでは、メールを削除できる状態で届くことは分かりません。

どのテンプレートも **オフで、モデルなし** の状態で届きます。選ぶと、そのプロンプト、ツール、推奨のスケジュールが手に入り、あとはあなたがプロバイダーを選んでオンにするのを待ちます。

テンプレートは出発点です。プロンプトも、ツールも、スケジュールも、すべて変えてかまいません。いくつかのテンプレートは、午前3時に失敗する代わりに、役に立つ前に何を記入してほしいかを自分のプロンプトの中で伝えます。

**設定 → エージェント** で、一覧をどのリポジトリとブランチから取得するかを指定します。既定はプロジェクト自身のリポジトリですが、フォークや、同じ構成を持つ自分のリポジトリでもかまいません。GitHub に接続できないマシンでは、`archive/refs/heads/<branch>.tar.gz` を置いた `file://` パスを使えます。インストーラーが受け付けるのと同じ構成です。リポジトリに接続できないときは、どのアドレスで失敗したかが一覧に表示されます。`.zip` のインポートはそのまま使えます。

### .zip のインポート

1. `.zip` を選びます。分割してアップロードされ、進捗がパーセントで表示されるので、数百 MiB のライブラリでも届きます。
2. サーバーは何よりも先に、パッケージ全体を確認します。エージェントのホームの外を指すパス、`.ssh` や `.bashrc` のような隠しファイル、チャットや実行履歴、コマンドを含むスケジュールは、1つも含まれていてはいけません。問題があれば何が問題かが示され、何も作成されません。
3. 何が持ち込まれるかが表示されます。説明、ツール（とこのインストールにないもの）、スケジュール、そしてメモリ、ホーム用のファイル、ライブラリ文書、モデルを含むかどうかです。確認し、名前を付けます。
4. バックグラウンドでインストールされ、進捗が画面に表示されます。ライブラリ文書は1つずつアップロードされ、ここで改めてインデックス化されます。途中で何かが失敗すると、エージェントは中途半端にインストールされたまま残されるのではなく、削除されます。

インポートしたエージェントも **オフ** の状態で届きます。プロバイダーが指定されている場合、その鍵はこのインストールで設定する必要があります。鍵が `.zip` に入って移動することはありません。

そもそも尋ねられたくなければ、**設定 → インターフェース** の **新しいエージェントの作成元を尋ねる** をオフにしてください。すると **+** は空のエージェントに直接進みます。

### どのエージェントも root を持たない

1つもありません。オーケストレーターも含めてです。それが隔離モデルのすべてであり、`os-watcher` のようなエージェントに何ができるかを決めるので、はっきりさせておく価値があります。

- **見るのに権限は要りません。** `df`、`free`、`uptime`、`nproc`、`systemctl is-active` は、どれも一般ユーザーで動きます。エージェントは、ディスクがいっぱいになるずっと前に、埋まりつつあることに気づけます。
- **直すにはたいてい権限が要り、エージェントはそれを持っていません。** プロンプトは、試して失敗する代わりに、何を実行するかを正確に伝えるよう指示しています。「root が必要: journalctl --vacuum-size=200M で約 1.2G 空きます」と書かれたカードは、失敗した試みよりも価値があります。

何かを自動で直したいなら、そのコマンドを root 自身の crontab に入れてください。エージェントが自分の判断で root としてファイルを削除するなど、午前3時に誰も望まない機能です。

## 最初のエージェントを作る

**+** を押し、空のエージェント、`.zip`、テンプレートのいずれかを選んで、名前を付けます。これでサーバー上に次のものが作られます。

- Linux ユーザー `agent-001`
- そのホーム `/opt/boa/agents/001/`（モード 0700）
- その中の `info.json`、`system-prompt.md`、API トークン

ID は空いている最小の番号です。`000` はオーケストレーター用に予約されています。

新しいエージェントは、カンバンのツールだけを持ち、控えめな上限で始まります。スケジュールがないので、スケジュールを与えるか **今すぐ実行** を押すまでは何もしません。

## エージェントと話す

サイドバーでエージェントをクリックすると、そのチャットが開きます。してほしいことを入力して Enter を押します。Shift+Enter で改行します。

入力欄は、ページ下部のステータスバーのすぐ上に固定されています。スクロールするのはその上の会話だけなので、入力欄が隠れることはなく、たどり着くために下へスクロールする必要もありません。空のあいだは、Enter がどう動くか（またはエージェントがまだ作業中であること）を灰色の文字で示します。幅の狭いスマートフォンでは、その案内が切れないように1〜2行分高くなります。

メッセージ1つが1回の実行です。エージェントはツールを使って作業し、終わったら答えます。数分かかることがあるので、作業中は入力欄が無効になり、回答は届いた時点で表示されます。各回答には、かかったコストがトークン数とステップ数で表示されます。

回答は Markdown として表示されます（見出し、表、リスト、引用、コードブロック）。モデルはそういう書き方をするからです。あなた自身のメッセージは、入力したとおりに表示されます。リンクになるのは http か https を指すものだけで、それ以外は元のテキストのままです。

会話は記憶されます。メッセージのたびに直近10往復がモデルに再送されるので、エージェントは何の話をしていたかを分かっています。そのため、長いスレッドは短いスレッドよりも1メッセージあたりのコストが高くなります。**会話を消去** でやり直せます。

エージェントと話しても、1日あたりの実行回数の上限には数えられ **ません**。その上限は無人のスケジュールを止めるためのもので、あなたの入力を止めるためのものではないからです。1回あたりのトークン数、ステップ数、時間の上限は適用されます。

各エージェントは専用の会話を持ち、それは自分のホームディレクトリに保存されます。あなたがあるエージェントに言ったことを、ほかのエージェントが読むことはできません。

会話は、あなたが入力したものだけではありません。エージェントのカードの期限が来ると、実行が始まった瞬間にそのカードが同じチャットに投稿され、実行の回答はその下に表示されます。そのため、エージェントを開けば、あなたやほかのエージェントから頼まれたことのすべてと、それに対して何をしたかが分かります。[カードが実行されるとき](#カードが実行されるとき)を参照してください。

### API Calls

エージェントの名前は「チャット」タブと「API Calls」タブの上に表示されます。既定で表示されるのは **チャット** だけです。もう一方のタブを表示するには、エージェントのレンチを開き、**インターフェース** を選んで **API Calls タブを表示** をオンにし、**保存** を押します。この選択は、このエージェント用としてサーバーに保存されます。API Calls を有効にしていても、エージェントを開いたり再読み込みしたりすると、常にチャットから始まります。

**API Calls** には、実際に送信された JSON が表示されます。そのリクエストで送られた、エージェントの完全なプロンプト、会話、ツール定義、ツールの結果も含まれます。最新のリクエストは展開されています。ほかの呼び出しを調べるには、それを展開してください。エージェントの実行中は新しい呼び出しが現れます。失敗したリクエスト、SDK の再試行、予備モデルへの呼び出しも含まれます。インデントと色分けによって、チャットとして描画したり大きな数値の識別子を丸めたりせずに、JSON を読みやすく表示します。

最新の100件の完全なリクエストは、会話とは別に保存されます。チャットを消去しても消えません。記録はこのバージョンから始まり、それ以前のリクエストを再現することはできません。認証ヘッダーは記録されません。

## エージェントの設定

見出しには、選択したエージェントの ID とともに **エージェント 001 の設定** と表示されます。**今すぐ実行** は、チャットと API Calls がある作業領域にだけ表示されます。エージェントを削除するには、**一般 → エージェントを削除** を開き、ダイアログでその名前を入力して確認します。削除は「識別情報」の下にある独立したセクションです。


エージェントをクリックすると開くのはチャットです。それ以外のすべて（モデル、ツール、上限、システムプロンプト、スケジュール）は、サイドバーのエージェントの枠の右にある **レンチ** の奥にあります。

## エージェントのエクスポート

エージェントの設定の最後のタブ **エクスポート** は、そのエージェントを `.zip` としてダウンロードします。この `.zip` は、このインストールでも別のインストールでも、**+ → .zip ファイルからインポート** でインストールできます。設定、システムプロンプト、スケジュールは常に含まれます。次の4つはチェックしたときだけ含まれ、各チェックボックスには何が加わるかが事前に表示されます。

| オプション | 加わるもの |
|---|---|
| **メモリー** | その `memory.md` と、それが何文字あるか |
| **プロバイダーとモデル** | どのプロバイダーとモデルを使うか。鍵は決して含みません |
| **ライブラリ文書** | ライブラリの原本と、その情報（タイトル、年など）。インポート先で改めてインデックス化されます |
| **ホーム フォルダーのファイル** | スクリプト、`samba` フォルダー、そのほかホームに置いているもの。共有したくないものが含まれている可能性があるので、ダウンロード前にファイルの一覧が表示されます |

何をチェックしても含まれないものがあります。API キー、エージェント自身のトークン、チャンネルの認証情報、チャット、実行履歴、ブラウザーのセッション、ホームの隠しファイルです。crontab からは、エージェントを起動するスケジュールだけが移り、誰かがそこに入力したほかのコマンドは移りません。コマンドを運ぶ `.zip` は、インポート先のマシンでそれを実行してしまうからです。

## Samba 共有フォルダー

各エージェントのホームには `samba/` フォルダーがあり、その Linux ユーザー名で自動的に公開されます。たとえば、共有 **agent-001** が指すのは `/opt/boa/agents/001/samba/` だけです。「一般」でエージェントの名前を変えても、共有名は変わりません。ホームのそれ以外の部分や、保護された設定は公開されません。

1. エージェントの **レンチ → Samba** を開きます。
2. 8文字以上の **新しい Samba パスワード** を入力し、権限を選んで **保存** を押します。
3. タブに表示される Windows アドレスまたは SMB アドレス（Windows では `\\server\agent-001`、Linux と macOS では `smb://server/agent-001`）を開き、表示されたユーザー名とそのパスワードでログインします。

共有は、有効で、サーバーの共有一覧に表示され、読み書きができ、ゲストアクセスがオフの状態で始まります。初めて認証付きで接続する前に、このタブでパスワードを設定してください。その後の保存でパスワード欄が空なら、既存のパスワードが維持されます。Samba の認証情報は Linux のログイン認証情報とは別のもので、設定してもエージェントの Linux アカウントが使えるようになるわけではありません。

| 設定 | 効果 |
|---|---|
| このフォルダーを共有 | ファイルを削除せずに、この共有をオンまたはオフにします |
| 認証 | 既定はエージェントのユーザー名とパスワード。ゲストアクセスは明示的に選んだときだけ |
| アクセス権 | SMB 経由での読み取り専用または読み書き。エージェントは自分のローカルファイルを引き続き扱えます |
| 表示と説明 | サーバーの共有一覧に表示するかどうかと、その説明 |
| 新しいファイル／フォルダーの権限 | 8進数の Unix モード。初期値は `0600` / `0700`。既存のファイルはモードを保ちます |

共有名とパスは固定です。フォルダーは、その Linux 上の所有者だけのものであり続けます。アクセス設定を変えて保存すると、この共有の既存の接続が閉じられ、クライアントは新しい権限で接続し直します。ほかのエージェントの共有はそのまま動き続けます。パスワードそのものが API から返されることも、`info.json` に保存されることもありません。

`--update` は、`agent-000` を含む既存のエージェントに Samba フォルダーと共有を追加します。エージェントを削除すると、そのホームとともに共有と Samba アカウントも削除されます。`--backup` / `--restore` は、共有データ、設定、Samba パスワード、アカウントの識別情報を保持します。復元では、保存された Web ポートのモードを確認します。443 で直接提供しているインストールも対象です。

Samba は Web のプロキシとは無関係に TCP **445** を使います。Docker では、このポートを明示的に公開する必要があります。BoA は専用の `boa-samba` サービスを動かし、その設定とパスワードデータベースは `/opt/boa/samba/` 以下に置かれます。ほかの Samba サーバーの設定を上書きしたり乗っ取ったりすることはなく、インストーラーは自分が管理していない既存の Samba インストールを引き継ぐことを拒否します。

モデルの欄には、そのプロバイダーが提供するモデルが候補として表示され、入力に合わせて絞り込まれます。ただし普通のテキスト欄なので、今朝リリースされたばかりのモデルもそのまま入力できます。候補は `/opt/boa/config/providers/<provider>.json` から来ており、サーバー上で編集できます。変更したファイルが更新で上書きされることはありません。

自前ホストのプロバイダーは、同じマシンで動いているなら、ほかに何も要りません。

**ベースURL** は `ollama`、`llamacpp`、`vllm` のときだけ表示され、自分のサーバーが待ち受けている場所を指定します。既定値はこのマシンの通常のポートで、モデルがアプリケーションと同じマシンで動いているならそれで正しい設定です。クラウドプロバイダーを選ぶと、この欄は消えます。そのアドレスは固定で、このインストールはすでにそれを知っており、そこに欄があってもできるのは、入力ミスで動いているエージェントを壊すことだけだからです。予備モデルも同じように動作します。

クラウドプロバイダーの場合、いちばん簡単なのは「設定」の **APIキー** タブです。そこに設定した鍵は、そのプロバイダーを使うすべてのエージェントが使います。このエージェントにだけ別の鍵を与えるには、root でそのエージェント自身のホームに書き込みます。

```bash
mkdir -p /opt/boa/agents/001/keys
echo "sk-..." > /opt/boa/agents/001/keys/anthropic.key
chown -R agent-001:agent-001 /opt/boa/agents/001/keys
chmod 700 /opt/boa/agents/001/keys
chmod 600 /opt/boa/agents/001/keys/anthropic.key
```

ファイル名はプロバイダー名です。各エージェントは自分の鍵しか読まないので、あるエージェントがほかのエージェントの予算を使うことはできません。

### APIキー

「設定」には **APIキー** タブがあります。クラウドプロバイダーごとに1つの鍵を置き、それを使うすべてのエージェントで共有します。自前ホストのプロバイダーは鍵が要らないので、一覧にありません。

鍵は `/opt/boa/config/apikeys/<provider>.key` に保存されます。ディレクトリは `0700`、ファイルは `0600` で、どちらも Web ユーザーの所有なので、どのエージェントもそのどれも読めません。ほかのプロバイダーの鍵も、自分の鍵もです。エージェントが実行されるとき、エージェント API はそのエージェントに **そのエージェントが設定されているプロバイダーの鍵だけ** を渡します。Ollama を使うエージェントが Anthropic の鍵を求めることはできません。

このディレクトリの名前が変わる前に作られたインストールでは、鍵は `/opt/boa/config/keys/` にあります。`--update` がそれを移し、古いディレクトリを削除します。

これが何を守り、何を守らないかは、はっきりさせておく価値があります。有料プロバイダーを正当に使うエージェントは、実行中はその鍵を持っています。呼び出しに必要だからで、`bash.run` を持つエージェントならそれを表示できてしまいます。共有の保管場所が防ぐのは、あるエージェントが自分の使わないプロバイダーの鍵を集めることです。また、すべての鍵をエージェントのホームディレクトリの外に置くので、うっかり残ったバックアップ1つですべての鍵が一度に漏れることもありません。

1つのエージェントを別のアカウントに請求させるには、そのエージェント自身のホームの `keys/<provider>.key` に鍵を置きます。その鍵が共有の鍵より優先されます。

## システムプロンプトの書き方

システムプロンプトは、そのエージェントそのものです。エージェントのホームに `system-prompt.md` として保存され、画面で編集します。

うまくいくのは次のことです。

- **エージェントが何のためにあるかを書きます。** 1〜2文で。
- **「完了」が何を意味するかを書きます。** 完了の定義がないエージェントは、早すぎるところで止まるか、いつまでも止まりません。
- **行き詰まったときにどうするかを書きます。** これがないと、モデルは障害を回避する方法をでっち上げます。「できないなら、ボードにそう書いて止まること」で十分です。
- **最初にボードを読むよう指示します。** それが、実行と実行のあいだにエージェントが持てる唯一の記憶です。

うまくいかないのは、ツールを使うなと指示することです。ツールを使ってほしくないなら、そのツールを与えないでください。プロンプトは提案にすぎませんが、ツールの一覧は強制されます。

## エージェントが覚えていること

各エージェントのホームディレクトリには `memory.md` があり、ある実行から次の実行へ持ち越せるのはこのファイルだけです。残す価値のあることを学ぶと `memory.append` で書き込み、`memory.replace` で整理します。

ファイル全体が実行のたびに最初に読み込まれます。それが役に立つ理由であり、コストがかかる理由でもあります。モデルを呼び出すたびに、すべての文字に料金がかかるのです。**エージェントの設定 → メモリ → メモリ上限（文字数）** で、1,000 から 1,000,000 文字の上限を選びます。既定は 8,000 で、既存のエージェントも同じです。メモリが上限の75%を超えると、エージェントは整理するよう求められます。

カウンターには、空白と改行を含む現在の文字数と、選んだ上限が表示されます。上限を上げることと、より大きなメモリを貼り付けることを、1回の保存で同時に行えます。テキストが選んだ上限を超えていると、その設定のリクエストは何も保存されません。テキストを短くするか、上限を上げてください。以前のメモリはそのまま残ります。新しい書き込みが `[truncated]` を付け加えることはありません。以前に切り捨てられたテキストは、元の文章からもう一度貼り付ける必要があります。メモリ全体は、プロンプト、会話、ツールと合わせて、選んだモデルのコンテキストに収まる必要があることに変わりはありません。

残すとよいのは、どこに何があるか、あるコマンドが結局どういうものだったか、あなたの好みです。やったことの日記ではありません。それはボードの役目です。

エージェントの設定の **メモリ** で、自分で読んだり直したりできます。エージェントが間違った事実をもとに動き続けているなら、手で直す価値があります。

## ローカル文書ライブラリ（RAG）

各エージェントは `/opt/boa/agents/<id>/rag/` 以下に専用のライブラリを持ちます。対応するのは PDF、EPUB、UTF-8 の TXT、Markdown のファイルです。インストーラーは、ローカルのベクトル化モデル（別のモデルを選んでいない限り EmbeddingGemma 300M Q8、約 318 MiB。[ベクトル化モデルの選び方](#ベクトル化モデルの選び方)を参照）と、その llama.cpp エンジン、OCR を用意します。テキスト抽出、OCR、文書のベクトル化、質問のベクトル化は、このサーバーで行われます。取り出された抜粋は、エージェントが回答用に選んだプロバイダーに送られます。クラウドプロバイダーを設定していれば、そこにも送られます。外部のベクトル化エンドポイントは使えません。インストール、更新、文書の取り込み、OCR、バックアップと復元は、再起動後のサービスの起動も含めて、Debian 13 と Alpine 3.24 で確認済みです。

1. **設定 → RAG** を開き、ローカルエンジンの準備ができていることを確認します。
2. エージェントの **RAG** タブを開き、検索を有効にしてエージェントを保存します。**rag-consultant** テンプレートは、検索が有効な状態で届きます。
3. ファイルを選んで **文書をアップロード** をクリックします。大きなファイルは分割して送られます。あるいは、完全なファイルを `rag/inbox/` にコピーして **rag/inbox のファイルを取り込む** をクリックします。取り込まれた原本は、管理された文書の保管場所に移されます。
4. **準備完了** になるのを待ちます。抽出とベクトル化はバックグラウンドで行われ、準備のできたほかの文書は検索できる状態のままです。ページには進捗とエラーが表示されます。
5. **ライブラリを検索** で質問を試すか、普段のチャットでエージェントに尋ねます。引用は、出典の PDF のページか、元の EPUB／文書にリンクします。

`rag/inbox/` からの取り込みのエラーは、文書一覧の上に表示されます。失敗した原本は、修正できるように inbox に残ります。インデックス化は上限のあるバッチ単位で処理されるので、小さな文書が、本を1冊処理するたびにスケジューラーの一巡を待たされることはありません。

**文書情報** の欄では、出版年、タイトル、サブタイトル、著者、バージョン、言語、タグを、この順に編集します。年は任意で、4桁まで入力できます。サブタイトルがある場合は、文書一覧のタイトルのすぐ下に表示されます。サブタイトル、年、著者、バージョン、言語は、エージェントが取り出すすべての抜粋に付いていくので、エージェントは同じタイトルの文書を見分け、引用したものに日付と出典を添え、内容の食い違う版を区別できます。ファイルを置き換えても、新しいファイルのインデックス化が終わるまでは、以前の文書が検索できる状態で残ります。文書のインデックス化中にローカルのベクトル化エンジンが止まると（更新や再起動など）、その文書は「Local embeddings are unavailable」というメッセージとともに **待機中** に戻り、エンジンが再び応答するようになると、止まったところから続きを行います。再インデックスする必要はありません。「再索引」は文書を作り直し、「キャンセル」は保留中の処理を止め、「削除」は今後の検索からその文書を外します。言語とバージョンのフィルターは、入力したメタデータを使います。EPUB の引用は、でっち上げたページ番号ではなく、章を示します。スキャンした PDF には、サーバーに OCR の言語がインストールされている必要があります。既定では英語とスペイン語がインストールされています（`eng+spa`）。対応していないファイルや暗号化されたファイルは、空のインデックスを作って成功したことにするのではなく、エラーを報告します。

**回答モード** は、エージェントが文書の外にどこまで踏み出してよいかを決めます。一覧の下の1行に、選んだモードが何をするかが表示されます。

- **文書と一般知識**: エージェントは両方を使えますが、区別して扱います。
- **文書による根拠を必須にする**: エージェントは、回答する前に自分でライブラリを検索しなければなりません。検索せずに出した回答は、一度だけ差し戻されます。その実行で抜粋が1つも取り出されなかった場合は、モデルが書いた内容の代わりに、「The document library does not contain enough information to answer this question」（文書ライブラリには、この質問に答えるのに十分な情報がありません）という決まった文が返ります。
- **文書のみ（検証あり）**: 前のモードに加えて、回答のすべての段落とすべてのリスト項目が、その実行で取り出した抜粋を引用していなければなりません。段落は1つずつ確認されます。引用がない、取り出されていない抜粋を引用している、あるいは引用した抜粋と意味がかけ離れている（ローカルのベクトル化エンジンで測定します）場合、回答はそれらの段落の一覧とともに一度だけ差し戻されます。その後も裏付けのないものは削除され、最後の1行に、いくつの段落が削除されたかが示されます。裏付けのあるものが何も残らなければ、決まった文が返ります。確認のためにエンジンに接続できない場合、回答は確認されないまま表示されるのではなく、差し止められます。

検証ありのモードにもできないことがあります。引用した段落が、その抜粋とまったく同じことを言っていると証明することです。私たちの測定では、抜粋と矛盾する段落や、同じ話題について何かを付け加えた段落も、忠実な段落と同じような点数になります。この確認で見つけられるのは、別の話題についての抜粋を引用した段落と、出典がまったくない段落です。また、どちらの方向にも正確ではありません。私たちのテストでは、忠実な段落の100件中約6件を削除し（その多くは、比較材料の少ない短いリスト項目や1行の要約でした）、別の話題の抜粋への引用を100件中1件未満ですが通しました。コード例は、それを紹介する文と一緒に判定されます。正確さが重要なときは、引用された抜粋を確認してください。決まった文は **設定 → エージェント → エージェントが答える言語** で選んだ言語で書かれ、何も選んでいなければ英語になります。引用は、取り出された出典の識別子からのみ解決されます。

エージェントごとの既定値は、1ファイルあたり 128 MiB、原本の文書で合計 2,048 MiB、200,000 個の断片、8件の結果、1回の実行あたり最大 16,000 文字の取得テキストです。控えめなバイト数の予算によって、プロンプトや履歴と並べて収まる量も制限されます。**最小類似度** は、使っているベクトル化モデルで測定した値（EmbeddingGemma なら 0.20、Qwen3-Embedding なら 0.35）から始まり、欄の下の1行にそれがどちらかが表示されます。これは確率ではなく検索のスコアで、モデルごとに尺度が違います。意味による検索結果が広すぎる場合は値を上げてください。文字どおりの一致も結果に加わります。API では、さらに断片の割り当て量と、断片のトークンサイズも設定できます。

全体の設定では、ベクトル化のスレッド数、同時に実行する索引処理の数、既定の OCR 言語を管理します。**同時に実行する索引処理** は、いくつのエージェントのライブラリを同時にインデックス化するかです（エージェントごとに1つの処理で、その文書は1つずつ順番に処理されます）。各処理は最大 4GB の RAM を使うことがあり、ラベルにもそう書かれています。1つのエージェントのライブラリが速くなるわけではありません。ベクトル化エンジンは一度に1つのリクエストにしか応えないからです。ベクトル化を速くしたいなら、代わりに **ベクトル化のCPUスレッド数** を上げてください。モデルは共有で、ライブラリと権限はエージェントごとです。処理は再起動後に再開され、完了した文書と、中断された処理の再利用できる断片は保持されます。再インデックスに失敗しても、最後に公開されたバージョンが残ります。ダウンロードが必要なのはモデルのインストールだけで、通常の検索はインターネットなしで動きます。ローカルエンジンが使えないときはそう報告され、外部のベクトル化サービスで代用されることは決してありません。

`boa-embeddings` は Unix ソケット経由でモデルを提供し、`boa-rag` はキューを管理します。どちらにも systemd と OpenRC のユニットがあり、システムの設定に表示されます。バックアップには、文書の原本、メタデータ、整合性の取れた SQLite／ベクトルインデックスのスナップショットが含まれます。実行時の設定も含まれ、それとともに選んだベクトル化モデルも記録されます。モデルのバイナリとダウンロードした重みは含まれません。復元では、選んだモデルがマシンになければダウンロードし、そのダウンロードが失敗した場合はその旨を伝えて処理を続けます。その後、**設定 → RAG** でモデルをダウンロードするか、別のモデルを選べます。復元したバックアップでは、進行中だったアップロードはキャンセルされます。インデックス化済みのライブラリは、通常の更新では失われません。

### ベクトル化モデルの選び方

ベクトル化モデルは、すべての抜粋とすべての質問を、ライブラリの検索に使う数値に変換します。**設定 → RAG → ベクトル化モデル** には2つの選択肢があり、すべてのエージェントが同じモデルを使います。

| | EmbeddingGemma 300M (Q8) | Qwen3-Embedding 0.6B (Q8) |
|---|---|---|
| ダウンロード | 318 MiB | 610 MiB |
| 実行中のエンジンのメモリ | 約 600 MB | 約 1.1 GB |
| インデックス化の時間（同じプロセッサー） | 1× | 約 4× |
| ライセンス | Gemma Terms of Use | Apache 2.0 |

EmbeddingGemma が既定で、どんなマシンにも向いています。Qwen3-Embedding は、プロセッサーとメモリに余裕のあるマシン向けです。テスト用ライブラリのスペイン語の Python の本では、本についての質問（0.51〜0.79）と無関係な質問（最大 0.21）の差を、EmbeddingGemma（0.35〜0.67 対 0.17）よりも大きく保ちました。抜粋を言い換えた段落と、別のことについての段落の差も同様です。2プロセッサーのテストマシンでは、断片1つあたり、EmbeddingGemma の 0.5 秒に対して 2.2 秒かかりました。

変更するには、次のようにします。

1. 一覧でモデルを選びます。その下に、サイズ、メモリ、速度、ライセンス、そしてダウンロード済みかどうかが表示されます。
2. ダウンロードされていなければ、**モデルをダウンロード** をクリックし、バーが終わるのを待ちます。ダウンロードしたものは、使う前に公開されている SHA-256 と照合されます。
3. **保存** をクリックして確認します。エンジンが新しいモデルで再起動します。上部の1行に数秒間「エンジンがこのモデルを読み込んでいます」と表示され、その後 **準備完了** になります。

変更すると、次のことが起こります。

- すべてのエージェントのすべての文書が、新しくアップロードしたときと同じように、索引処理1つにつきライブラリ1つずつ、改めてインデックス化されます。大きなライブラリでは数時間かかります。
- 順番が来るまで、文書はライブラリに残り、意味ではなく質問の語句によって見つかります。そのあいだの検索では、いくつの文書が待っているかがエージェントに伝えられるので、抜粋が見つからなくても、ライブラリがその質問を扱っていないとは受け取られません。
- 古いモデルの推奨値のままだったすべてのエージェントの **最小類似度** は、新しいモデルの推奨値に変わります。別の値を設定していたエージェントは、その値を保ちます。
- 検証ありのモードは、使っているモデルで段落と抜粋を比較し、そのモデル用に測定したしきい値（EmbeddingGemma なら 0.36、Qwen3-Embedding なら 0.44）と照らし合わせます。

以前のモデルの重みはディスクに残るので、元に戻すのにダウンロードは要りません。ただし、もう一方のモデルでインデックス化されたすべての文書が、改めてインデックス化されます。

## ツールの選び方

**ツール** で、このエージェントが使ってよいものにチェックを入れます。チェックしていないツールはモデルに示されず、求められてもサーバーが拒否します。この確認はプロンプトではなくサーバー側で行われます。

最初から付属しているツールは次のとおりです。

| ツール | エージェントにできること |
|---|---|
| `bash.run` | 自分の非特権ユーザーとしてシェルコマンドを実行する |
| `kanban.add_card` | 共有ボードにタスクを載せる |
| `kanban.assign_card` | 自分のカードの1つを別のエージェントに渡す |
| `kanban.move_card` | 自分のカードの1つを列から列へ動かす |
| `kanban.delete_card` | 自分のカードの1つを削除する |
| `kanban.list_cards` | ボードを読む。自分のカード、**manager** ならすべてのカード |
| `channel.write` | 設定済みのチャンネルにメッセージを送る |
| `web.fetch` | 公開の Web ページを読む |
| `rss.fetch` | RSS や Atom のフィードを項目の一覧として読む |
| `memory.append` | 未来の自分のために何かを書き留める |
| `memory.replace` | 覚えていることを整理する |
| `skill.read` | 与えられた手順書を読む |
| `script.write` | 自分の `scripts/` ディレクトリにスクリプトを書く |
| `script.list` | 自分が書いたスクリプトを一覧にする |
| `script.delete` | 自分のスクリプトの1つを、それを実行していた cron の行とともに削除する |
| `cron.add` | 自分のスクリプトの1つを、自分の crontab で定期実行する |
| `cron.list` | 自分の crontab を読む |
| `cron.remove` | 自分のスクリプトの1つの定期実行をやめる |
| `mail.read` | 設定済みのメールボックスのメッセージを読む |
| `mail.move` | メッセージを同じアカウントの別のフォルダーに仕分ける |
| `mail.delete` | メッセージをアカウントのごみ箱に送る |
| `mail.forward` | 許可したアドレスにメッセージを転送する |
| `rag.search` | 自分の文書ライブラリを検索する |
| `rag.read` | 検索で返された断片を読む |
| `rag.list` | ライブラリ内の文書を一覧にする |
| `browser.open` | cookie を保ちながら、自分のブラウザーでページを開く |
| `browser.read` | 開いているページ、またはそのリンクを読む |
| `browser.click` | ページ上のリンクやボタンをクリックする |
| `browser.type` | 欄に入力する。送信も可能 |
| `browser.screenshot` | ページの画像をあなたのために保存する |
| `image.send` | PNG を Web チャットに添付し、会話が Telegram で始まった場合は Telegram の返信にも添付する。画像は Web メッセージのテキスト領域いっぱいに表示される |

ツールの種類ごとに専用の枠があり、このエージェントがその種類のツールをいくつ持っているかが表示されます。「このエージェントはメールボックスを読んでよいか」は1つの判断であり、1つの枠として描かれます。エージェントのカンバンボードをオンにするスイッチは、**カンバン** の枠の下端、それが管理するツールの下にあります。

- **`bash.run`** — そのエージェントのユーザーとしてのシェルコマンド。root はなく、手に入れることもできません。エージェントにマシン上で実際にやる仕事があるときに与えてください。
- **`kanban.*`** — 共有ボード。見えるようにしたいものには、少なくとも `list_cards` と `add_card` を与えてください。
- **`channel.write`** — あなたへのメッセージ。**チャンネル** タブでチャンネルにもチェックを入れてください。
- **`web.fetch`** — 公開のページだけ。プライベートアドレスとループバックアドレスは拒否されます。
- **`rss.fetch`** — RSS や Atom のフィードを、XML 文書ではなく項目の一覧として読みます。同じフィードを `web.fetch` で取得するよりずっと安く、エージェントが解析する手間も省けます。どちらも **インターネット** の下にあります。
- **`script.*` と `cron.*`** — **自動化** の下にあります。エージェントは自分の `scripts/` ディレクトリにスクリプトを書き、自分の crontab で予定に入れます。考える必要のない繰り返しの作業のためです。スクリプトは単独で動き、トークンを消費せず、エージェントは次の実行でその結果を読みます。予定に入れられるのは自分のスクリプトだけで、5分より短い間隔にはできず、自分を起こす行には決して触れられません。

エージェントは自分のホームの中ではかなりのことができますが、その外では何もできません。ほかのエージェントが存在することさえ分からず、ましてやそのプロンプトを読むことはできません。エージェントのディレクトリは通り抜けられても一覧はできず、各ホームはそれぞれの Linux ユーザー専用なので、拒否しているのは Python のチェックではなくカーネルです。

また、**自分が何者であるか** を書き換えることもできません。与えられたツール、支出の上限、システムプロンプト、API トークンは、ホームの中にある root 所有の引き出しに入っています。エージェントはそれらを読めますが、変えられません。変えるのはあなたで、エージェントではありません。自分について編集してよい唯一のものは、メモリです。
- **`mail.*`** — **設定 → メール** で設定したメールボックス。下記を参照してください。
- **`skill.read`** — **スキル** パネルでチェックした手順書。両方が必要です。ここのツールと、そこにある少なくとも1つのスキルです。

### メールツール

メールツールは4つあり、**設定 → メール** で IMAP のメールボックスを設定しておく必要があります。エージェントがそのパスワードを見ることはありません。エージェントは何をしてほしいかを伝え、認証情報を持つエージェント API がそれを実行します。

| ツール | 内容 |
|---|---|
| `mail.read` | メッセージを読みます。**何も既読にしない** ので、あなた自身の未読数の意味は変わりません。 |
| `mail.move` | メッセージを同じアカウントの別のフォルダーに仕分けます。フォルダーは存在している必要があります。 |
| `mail.delete` | ごみ箱があるアカウントなら、メッセージをそこへ送ります。 |
| `mail.forward` | メッセージを転送します。転送先は **あなたが挙げたアドレスだけ** です。 |

重要なのは最後の1つです。受信箱は、世界中の誰もが書き込めるエージェントへの唯一の入力です。そのため `mail.forward` は、転送のたびに毎回、サーバーがあなたの一覧と照合します。照合するのはエージェントでも、プロンプトに書かれた何かでもありません。一覧が空なら、転送は一律に拒否されます。

見張るだけのエージェントには `mail.read` だけを与えてください。仕分けをさせるなら `mail.move` を加え、`mail.delete` と `mail.forward` は与える前によく考えてください。

下部にある **カンバン** のチェックボックスは、このエージェントのボードを完全にオフにします。チェックを外すと、カンバンのツールを一切受け取らず、カードの追加もやめます。仕事がボードに載るべきでないエージェントには、このスイッチを使ってください。

## エージェントにスキルを与える

スキルとは、書かれた手順です。ここで、ある仕事をどう進めるかを、順を追って記したものです。アプリケーションには1つも付属していません。スキルは「この」マシン、つまりこれらのホスト、このバックアップ、この証明書についてのものなので、汎用のスキルは誰も従わない手順になってしまうからです。自分のスキルは、サーバー上で root として書きます。

```bash
mkdir -p /opt/boa/skills/BackupVerification
nano /opt/boa/skills/BackupVerification/SKILL.md
chown -R root:root /opt/boa/skills
chmod 00755 /opt/boa/skills/BackupVerification
chmod 0644 /opt/boa/skills/BackupVerification/SKILL.md
```

ファイルは、2本の `---` の線のあいだに名前と1行の説明を書くところから始まり、残りが手順です。

```markdown
---
name: BackupVerification
description: How to check that last night's backups actually ran.
---

1. Read /var/log/backup.log ...
```

すると、`/opt/boa/skills/` 以下の各ディレクトリが、エージェントの **スキル** パネルにチェックボックスとして表示されます。1つにチェックを入れ、**ツール** でエージェントに `skill.read` ツールを与えて、**保存** を押します。次の実行から、エージェントはその手順があることを知り、その仕事が来たときに読めるようになります。

### システムプロンプトがあるのに、なぜスキルが要るのか

理由は3つあり、肝心なのは3つ目です。

- **プロンプトはエージェントが何のためにあるかを、スキルは仕事をどう進めるかを表します。** 6つのエージェントが1つの手順を共有でき、6つの写しがそれぞれ別々に古くなっていくことはありません。
- **スキルは必要なだけ長くできます。** システムプロンプトは、どの実行のどの呼び出しでも料金がかかるので、短く保つ必要があります。スキルの料金は、それを読む実行が一度払うだけです。
- **エージェントが自力で学んだことは、そのエージェントとともに消えます。** そのメモリは、ほかのどのエージェントも開けないホームの中にあります。次のエージェントにも知っておいてほしいことを置く場所が、スキルです。

### スキルの書き方

画面にはスキル用のエディターがありません。わざとです。スキルの内容は、誰も見ていない午前4時に動くエージェントの推論にそのまま入り込むので、ツールと同じく root のものです。スキルはサーバー上で書きます。

```bash
mkdir -p /opt/boa/skills/DatabaseBackup
nano /opt/boa/skills/DatabaseBackup/SKILL.md
```

ファイルは2行のヘッダーで始まり、その後に必要なことを何でも書きます。

```markdown
---
name: DatabaseBackup
description: How the nightly dump is taken and where it goes.
---

# Database backup

1. Dump with `mysqldump --single-transaction`, never with the table lock.
2. Write it to /srv/backups/, never to /tmp.
...
```

いちばん重要なのは `description` の行です。どの実行でも料金がかかるのはこの部分だけで、エージェントが残りを読むかどうかを決めるときの判断材料もこれです。「How the nightly dump is taken and where it goes」（夜間のダンプをどう取り、どこに置くか）なら、いつ当てはまるかが伝わりますが、「Database stuff」（データベース関係）では伝わりません。

エージェントのページを再読み込みすると、スキルが一覧に表示されます。

更新が `/opt/boa/skills/` に触れることはありません。そこに書いたものは、あなたのものであり続けます。Web 画面が決めるのはどのエージェントにどのスキルを与えるかで、スキルを編集することはありません。

### スキルは独自のファイルを持てる

ディレクトリ内のほかのものも、スキルと一緒に扱われます。

```
/opt/boa/skills/DatabaseBackup/
  SKILL.md
  dump.sh
  exclude-tables.txt
```

エージェントはそれらを読んだり実行したりできるので、手順には40行のシェルを書き連ねる代わりに「このディレクトリの `dump.sh` を実行する」と書けます。どんなファイルがどこにあるかは、`skill.read` がエージェントに伝えます。

### コスト

プロンプトに入るのは、各スキルの名前と説明だけです。1つにつき約2行です。本文は、必要だと判断したエージェントが、そのときにだけ、`skill.read` で一度取得します。エージェントに5つのスキルを与えても、1回の実行あたりのコストは1万トークンではなく数百トークンです。だからこそ、請求額を気にせずに5つ与えられます。

### エージェントが使っているスキルを削除した場合

何も壊れず、できないことを約束したままのエージェントも残りません。

- そのスキルは、それを持っていたすべてのエージェントの次の実行で、**プロンプトから消えます**。エージェントが、読めない手順について知らされることはありません。
- **スキル パネルから消える** ので、誰も再びチェックを入れられません。
- 名前は、何かがそれを書き換えるまで **エージェントの `info.json` に残る** ので、ディレクトリを戻せば、ほかに何もしなくてもスキルが元に戻ります。
- それでもエージェントがそのスキルを求めた場合（以前の実行から名前を覚えていることがあります）、そのスキルは一覧にあるがもうインストールされていないと伝えられ、その内容を推測しないよう指示されます。

1つ知っておいてください。**スキルがない状態でそのエージェントの「保存」を押すと、スキルは一覧から完全に外れます。** 画面は存在するスキルしか保存しないからで、それによって、削除されたスキルがいつまでも残り続けることを防いでいます。エージェントを保存する前にディレクトリを戻すか、保存した後でスキルにもう一度チェックを入れてください。

## エージェントにブラウザーを与える

`web.fetch` は公開のページを読むだけで、それ以外は何もしません。ログインも、フォームも、ボタンもなしです。エージェントがサイトを読むのではなく *使う* 必要があるなら、ブラウザーが必要です。

ブラウザーは最初からインストールされます。インストーラーが一度だけ尋ね、既定の答えは「はい」です。約 600 MB の Chromium なので、ディスクに余裕のないマシンでは断ることができ、後からどちらにも変更できます。

```bash
./install-update-reinstall-debian.sh --update --browser no    # 入れない
./install-update-reinstall-debian.sh --update --browser yes   # 再び入れる
```

答えは、ポートと同じく記録されます。その後、エージェントの **ツール** パネルでブラウザーのツールにチェックを入れます。

Alpine にはどれも当てはまりません。Playwright が musl 向けのビルドを公開していないため、Alpine にはブラウザーがまったくないからです。ツールは一覧に残り、エージェントが呼び出すとその旨を伝えます。

| ツール | エージェントにできること |
|---|---|
| `browser.open` | ページを開く。cookie は保持される |
| `browser.read` | 開いているページをもう一度読む。その一部だけ、またはリンクだけも可能 |
| `browser.click` | 見えている文字かセレクターで指定して、リンクやボタンをクリックする |
| `browser.type` | 欄に入力する。Enter を押すことも可能 |
| `browser.screenshot` | 自分のダウンロードディレクトリに PNG を保存する |
| `image.send` | Web チャットと Telegram の返信に PNG を添付する |


`browser.screenshot` はサーバー上に PNG を保存します。それをチャットに表示するには、エージェントがそのパスを指定して `image.send` を呼び出します。**エージェントの設定 → ツール → 画像** で **image.send** を許可し、保存してください。**web-navigator** から作成した新しいエージェントには、すでに含まれています。既存のエージェントは、現在の許可をそのまま保ちます。

画像は、縦横比と高さ全体を保ったまま、Web チャットのメッセージのテキスト領域いっぱいに表示されます。元のサイズで開くこともできます。会話が Telegram で始まった場合は、Telegram にも送られます。縦長のキャプチャや大きなキャプチャは、PNG ドキュメントとして届けられます。アップロードが失敗した場合は、すでに届いたテキストや画像を繰り返さずに、欠けた部分だけを再試行します。

受け付けるのは、そのエージェントのホーム内にある PNG ファイルだけで、1つあたり 50 MiB まで、1回の返信につき16個までです。添付ファイルは非公開のままで、見るにはログイン中のセッションが必要です。既存のスクリーンショットは、保存されたパスで `image.send` を使うようエージェントに頼めば送れます。

### セッションはエージェントごとに別

ブラウザー本体は `/opt/boa/playwright/` にある1つだけで、root の所有、ほかの全員には読み取り専用です。共有され **ない** のはプロファイルです。

```
/opt/boa/agents/001/browser/profile/     agent-001, 0700
/opt/boa/agents/002/browser/profile/     agent-002, 0700
```

サイトにログインしたエージェントは、cookie が自分のディスクにあるので、**次の実行でも** ログインしたままです。そして、ほかのエージェントはログインしていません。そのディレクトリは 0700 で、そのエージェントの Linux ユーザーのものだからです。拒否するのはカーネルで、間違いうる Python のチェックはありません。この分離こそ、すべてのエージェントが1台のマシンを共有するホスティング型の製品には提供できないものです。

どのブラウザーとも同じく、ここでもセッション cookie はブラウザーを閉じると消えます。サイトが残すよう指定したものは残ります。

### できないこと

- **プライベートアドレスは開きません。** `browser.open` は、`web.fetch` とまったく同じく、`192.168.*`、`127.*` などを拒否します。悪意のあるページを読んだばかりのエージェントが、言いくるめられてあなたのルーターを開くようなことがあってはなりません。そうした用途には、単なる取得よりも、セッションを持つブラウザーのほうがはるかに適した道具になってしまいます。
- **画面はありません。** ヘッドレスです。エージェントが見たものをあなたが見る方法が `browser.screenshot` で、エージェント自身はその画像を見られません。
- **ツールなしでは何もできません。** ほかのすべてと同じく、エージェントに与えていないツールは呼び出せないツールで、その確認はサーバー側で行われます。

ブラウザーが一度もインストールされていない場合でも、ツールは一覧に表示され、実行すべきコマンドを答えます。消えることも、黙って失敗することもありません。

## 支出の上限

上限はエージェントごとに4つあり、どの実行も、最初に到達した上限で止まります。

| 上限 | 既定値 | 何から守るか |
|---|---|---|
| 1回あたりのトークン数 | 16384 | 1回の高くつく会話 |
| 1回あたりのステップ数 | 25 | ツールを永遠に呼び続けるループ |
| 1回あたりの秒数 | 300 | 固まってしまった実行 |
| 1日あたりの実行回数 | 48 | 張り切りすぎた cron の行 |

これは心配しすぎではありません。上限もなく誰も見ていない状態で、有料 API を使って毎時起きるエージェントは、あなたが眠っているあいだに膨らんでいく請求書です。

エージェントが実際にどれだけ使うかを **履歴** パネルで確認してから、上限を引き上げてください。

### 予備モデル

**LLM** には、1つ目の下に2つ目のプロバイダーとモデルがあります。これは主モデルが **失敗した** とき（鍵がない、応答がない、存在しないモデルなど）にだけ使われます。実行は、そこまでの経過を再送したうえで、同じステップから予備モデルで続けるので、すでに済んだ作業が無駄になりません。

予備は **1回の実行につき一度** 試されます。予備も失敗すれば、実行は失敗します。両方を交互にいつまでも試していては、障害のあいだに上限を使い果たし、それでも何の成果も残らないからです。予備への切り替えはエージェントの履歴に記録されます。黙って別のモデルで答え、別のアカウントに請求する実行は、そのことを伝えなければならないからです。

予備のプロバイダーを **なし** のままにするのが既定で、その場合は失敗すると実行が終わります。

予備に **同じプロバイダー** を選ぶと、モデル欄には同じモデルではなく、そのプロバイダーのカタログにある *別の* モデルが入ります。同じプロバイダーで同じモデルでは、主モデルが答えられなかったことには答えられません。毎回まったく同じ理由で失敗するだけです。それでも同じ組み合わせに入力し直すと、欄の下の1行にその旨が表示されます。あなたのエージェントなので、拒否ではなく警告です。


実行がトークンやステップの上限で止まると、エージェントはもう一度だけ、ツールなしで、専用の小さな予算で、言いかけていた回答を求められます。そのため、予算のすべてを事実集めに使った実行が「これからシステムを確認します」で終わることはありません。その回答は途中で切れているかもしれないので、チャットでは回答の下にその旨が表示されます。時間の上限にはこうした呼び出しはありません。その実行はすでに遅れているからです。

この締めくくりの呼び出しは会話全体を再送するので、ツールを多用する長い実行では安くありません。12000 トークンの上限で止まった実行が、最終的に 24901 トークンに達したという測定結果があります。つまり、トークンの上限は作業のための予算であって、実行全体の厳密な最大値ではありません。上限に達しない限り、この方法で何かが消費されることはありません。

### さらにカーネルが課す制限

4つの上限は、実行そのものが課します。さらに2つの制限をカーネルが課すので、おかしくなったのが実行そのものであっても効き続けます。どのエージェントも、同時に 1024 を超えるプロセスとスレッドを持てません。そのため、際限なく fork するコマンドは、マシン全体ではなくそこで止まります。また Debian では、各実行が 2 GiB のメモリを持つ専用の systemd スコープの中で動きます。このスコープは、実行が終わるときに、その実行がバックグラウンドに残したものもすべて終了させます。メモリ制限によって強制終了された実行は、ほかの失敗と同じく、「履歴」では失敗として、チャットではエラーとして報告されます。ブラウザーだけで数百のスレッドになるので、数値をこれより小さくはしていません。

## エージェントのスケジュール設定

**Cron** で、エージェントの crontab を書きます。これはエージェント専用の crontab で、所有も実行もエージェント自身の Linux ユーザーが行います。そのユーザーとして `crontab -e` を実行した場合とまったく同じです。

1時間ごと：

```
0 * * * * /opt/boa/venv/bin/python3 /opt/boa/webapp/backend/core/runner.py --agent-id 001
```

平日の毎朝 08:00：

```
0 8 * * 1-5 /opt/boa/venv/bin/python3 /opt/boa/webapp/backend/core/runner.py --agent-id 001
```

画面には編集中のエージェント用の正確な行が表示されるので、それをコピーしてタイミングだけを変えれば済みます。

スケジュールを削除するには空にします。スケジュールを残したままエージェントに無視させるには、**オン** のチェックを外します。

時間帯によって料金が変わる有料プロバイダーを使うなら（DeepSeek はピーク時間帯に数倍の料金を請求します）、その選択はここで行います。

## カンバンボード

このページには2つのタブがあります。3つの列からなる **ボード** と、フォームである **カードを作成** です。どちらが開いているかは URL に含まれるので、再読み込みしても、戻るボタンを押しても、そのまま保たれます。カードを保存するとボードに戻ります。

列は **未着手**、**作業中**、**完了** の3つです。

ボードは、エージェントが互いに仕事を残しておくために使い、あなたが実際に何が起きたかを見るために使うものです。どのカードにも履歴があります。誰が作り、誰が動かしたか、いつ、なぜかです。

カードにはタイトルと **やること** の欄があります。タイトルはカードの名前で、欄には指示を書きます。エージェントはその両方を読みます。欄が空のカードを割り当てられたエージェントは推測するしかありません。渡されたカードに対してエージェントが何もしない、よくある理由がこれです。

もう1つの理由は、エージェントがボードをまったく見られないことです。エージェントがボードを読む方法は `kanban.list_cards` を呼ぶことだけで（ボードがプロンプトに入れられることはありません）、このツールを持たないエージェントは、カードがあることを知りようがありません。そのようなエージェントを選ぶと、**割り当て先** にその旨が表示されます。これは警告であって阻止ではありません。カードは作成されますし、エージェントの **ツール** タブでそのツールにチェックを入れるだけで解決します。

ボード上のカードには、誰が作ったか、誰が担当しているか、いつ作られたか、タイトルの最初の2行、やることの最初の3行、そして **いつ実行されるか** が表示されます。切り詰められたタイトルや本文の全体は、ツールチップで読めます。

読む価値があるのは最後の行です。時刻のないカードは遅れているわけではありません。そのために誰かが起こされることはなく、担当のエージェントが次の予定実行でそれを見つけます。カードを手で動かすには **移動先** を使います。このボードにはドラッグ操作はありません。

あなたはどのカードでも追加、移動、削除できます。**エージェントが見て変更できるのは自分のカードだけです**。エージェントが作ったカード、またはそのエージェントに割り当てられたカードが、そのエージェントのカードです。

これは好みの問題ではなく、壁です。エージェントは、ほかのエージェントの仕事が存在することさえ一切知ることができません。タイトルも、件数も、そこに何かがあることもです。自分のものでないカードを動かすよう頼まれたエージェントは、そのような自分のカードはないと告げられます。存在しないカードについても同じ文が返ります。2つを区別するような拒否の仕方では、ID を1つずつ試してボードに何があるかを問い合わせる手段になってしまうからです。

例外はオーケストレーターの **manager**（エージェント 000）です。仕事を割り振り、その後を追うのが役目なので、ボード全体を読みます。調整がほかの誰でもなくこのエージェントの仕事なのは、そのためです。

破壊的な操作の確認には **既定のボタンがありません**。フォーカスがダイアログそのものにある状態で開くので、Enter を押してもどちらも実行されず、どちらにするかをはっきり選ぶ必要があります。Escape でキャンセルします。実行するには赤いボタンをクリックします。

何も壊さない通常の確認は、確認ボタンにフォーカスがあり、枠で囲まれた状態で開きます。そこでは Enter が「はい」を意味します。

カードを削除しても、それが存在したことと誰が削除したかを記録した行が残るので、エージェントが自分のしていたことの証拠を消すことはできません。

## 設定

設定はタブに分かれており、タブは URL に含まれるので、再読み込みやブックマークで元の場所に戻れます。

| タブ | 内容 |
|---|---|
| **オペレーティングシステム** | このマシンが何であるか、メモリとディスクの残り、4つのサービスが動いているかどうか（動いていれば緑、いなければ赤）。`os-watcher` と同じやり方で、権限なしに読み取ります |
| **アカウント** | 唯一のメールアドレスとパスワード。パスワードの変更には現在のパスワードが必要です |
| **メール** | SMTP。何かをメールであなたに届ける必要があるときのためのものです |
| **チャンネル** | Discord、Mattermost、Telegram、X をアルファベット順に。それぞれ専用の枠と「保存」ボタンがあります |
| **音声** | 文字起こしエンジン、プロバイダー、モデルのダウンロード、言語、Telegram の音声の保存 |
| **ツール** | インストール済みのツール。「自動化」や「ブラウザー」といったサブタブに分類されています |
| **エージェント** | すべてのエージェントに一度に効く設定と、テンプレートを取得するリポジトリとブランチ。サーバーに保存されます。cron が始めた実行には、設定を読み取るブラウザーがないからです |
| **チャット** | メッセージ欄のふるまい。Enter で送信するかどうか、各回答にかかった費用を表示するかどうか |
| **カンバン** | 各列に表示するカードの数と、最近削除したカードを一覧に表示するかどうか |
| **インターフェース** | テーマ、言語、ポップアップメッセージの表示時間、そして **+** が新しいエージェントの作成元を尋ねるかどうか |

**オペレーティングシステム** では、サービスの状態が **このマシン** の2列目にそろえて表示されます。

チャット、カンバン、インターフェースの設定は、サーバーではなくブラウザーに保存されます。これらはこの端末でのあなたの使い方を表すもので、スマートフォンとデスクトップで違っていても当然だからです。

### 音声文字起こし

Alpine では、インストールと更新が終わると SSH セッションの制御が戻ります。サービスは OpenRC が動かし続けます。

**設定 → 音声** を開きます。これらの設定はサーバーに保存され、Telegram で受け取ったボイスメッセージと音声ファイルに適用されます。

1. **ローカル · whisper.cpp** か **プロバイダー API** を選びます。文字起こしは最初は無効になっています。
2. ローカルで認識する場合は、モデルを選び、必要なら **モデルをダウンロード** をクリックします。インストーラーは `base` を用意します。選択欄には、英語専用の `.en` 版や量子化版を含む公式モデル30種すべてと、`/opt/boa/whisper/models/` に手動でインストールした `ggml-*.bin` モデルが表示されます。サイズとインストール状態も表示されます。大きなモデルほど多くのメモリと CPU 時間が必要です。
3. API を使う場合は、先に **APIキー** でその鍵を保存してください。OpenAI、Groq、Mistral、Together AI、Hugging Face、Cloudflare は、鍵を保存すると表示されます。候補から選ぶか、そのプロバイダーの別の文字起こしモデルの識別子を入力します。Cloudflare は対応している2つの Whisper 版を提示し、`account-id:api-token` 形式の認証情報を使います。
4. 言語（`auto`、または `en` のようなコード）、最大の長さ、再生用に音声を保存するかどうかを選び、**保存** をクリックします。試すには、エージェントの Telegram メッセージにボイスメッセージで返信します。先に `/agents` でエージェントを選んでおくこともできます。

初期の上限は 600 秒で、30 から 3600 の範囲で設定できます。受け取るファイルは 20 MiB を超えられません。処理はバックグラウンドで行われ、そのキューは更新後も残ります。作業中のエージェントには、手が空いたときに保存済みのテキストが届きます。録音の中でエージェントの名前を口にしても、宛先は変わりません。

Web チャットには文字起こしが表示され、保存が有効ならプレーヤーも表示されます。再生用の Ogg のコピーは、ログインしなければ見られない場所に保存されます。保存を無効にすると、新しいメッセージではテキストだけが残ります。チャットを消去すると、完了した処理の保存済み音声も削除されます。バックアップにはその音声が含まれます。ダウンロードしたモデルは更新後も残りますが、バックアップには含まれません。別のマシンに復元した後は、足りない追加モデルを「音声」からダウンロードしてください。

ローカルでの認識は、音声をあなたのサーバーで処理します。API での認識は音声を選んだプロバイダーに送るので、エージェントのモデル利用とは別に料金がかかることがあります。ローカルで失敗しても、自動的にクラウドプロバイダーに切り替わることはありません。Whisper は翻訳ではなく文字起こしをします。`.en` モデルは英語しか理解しません。音声の受け付けは Telegram 経由です。Web チャットは結果を表示するだけで、録音ボタンは追加しません。

既存のインストールでは、ディストリビューションのインストーラーを root で `--update` 付きで実行してください。FFmpeg、whisper.cpp、base モデルが `/opt/boa/whisper/` 以下にインストールされます。文字起こしは、設定するまで無効のままです。

## ポップアップメッセージ

何かを保存すると、見ているパネルの中央に確認が表示され、ひとりでに消えます。わざと目に入る位置に出しています。以前は、長いタブの下部にある「保存」ボタンを押すと、ページのいちばん上、見ている場所から何画面も上に1行が表示されていたので、保存しても何も起きなかったように見えたのです。

**設定 → インターフェース → ポップアップを表示し続ける秒数** で、表示時間を1〜30秒の範囲で設定します。既定は3秒です。`Settings saved` を読むには十分な長さで、これから入力しようとしていた欄の上に居座らない程度の短さです。

エラーメッセージはこの数値を無視します。`×` か Escape で閉じるまで残ります。エラーは、画面に目を戻したときにまだ表示されていなければならない唯一のメッセージだからです。

色は、3つのうちどれが起きたかを示します。

| 色 | 意味 |
|---|---|
| 緑 | 保存されました |
| 黄色 | **保存する変更はありません**。「保存」を押したものの、フォームで何も変わっていなかった |
| 赤 | 失敗しました。何が悪かったかを示し、閉じられるまで待ちます |

黄色のメッセージは、「保存」を押せるすべての場所で使われます。**設定**（アカウント、メールサーバー、API キー、チャンネル、ブラウザー側の設定）と、エージェント自身の設定です。「保存」を2回押すと、2回目には、行われなかった保存を報告する代わりにそう伝えます。作ったばかりのエージェントは例外です。そのフォームはテンプレートの値を保持していて一度も保存されていないので、「保存」でそれが書き込まれ、そのエージェントのチャットに移動します。

## テーマ

**設定 → インターフェース** で配色を選びます。

| テーマ | 内容 |
|---|---|
| **Day** | やわらかいグレーと明るめのカード。明るい部屋向け |
| **Night** | ダークなパレット。暗い部屋向け |
| **Day High Contrast** | 白い背景、ほぼ黒の文字、はっきりした境界。ここではアクセントカラーで塗りつぶされるものはありません。サイドバーのエージェントの枠は輪郭線だけになり、あなた自身のメッセージは青ではなく、やわらげたインク色で塗られます |
| **Night High Contrast** | ほぼ黒の背景、明るい文字、はっきりした境界。選択したエージェントはグレーで塗られ、選択したタブは下の線とつながった閉じた輪郭線になります。あなた自身のメッセージには、やや暗くした白が使われます |

一度も選んだことのないブラウザーでは、Day と Night のうちオペレーティングシステムに合うほうで始まり、誰かが選ぶまでそれに従います。選んだ後は、言語と同じくこのブラウザーに保存されるので、スマートフォンとデスクトップで合わせる必要はありません。

テーマは、サーバーの `frontend/themes/` にある1つの CSS ファイルで、`--colour-*` 変数を定義し直します。そこにファイルを置けばテーマが増えます。コードの中に、更新すべき一覧があるわけではありません。名前と説明は、ファイル冒頭のコメントから取られます。

```css
/*
name: Midnight
scheme: dark
description: What it looks like, in one line.
*/

:root {
  color-scheme: dark;
  --colour-page: #101014;
  /* ... every --colour-* app.css defines ... */
}
```

すべてを定義してください。テーマが定義しなかった変数は app.css の値のままになります。明るいテーマなら、ダークなパレットの色が1つだけ真ん中に取り残されることになります。

付属のテーマはすべて、文字に使うすべての色で 4.5:1 のコントラストを満たし、2つのハイコントラストテーマは 7:1（WCAG AAA）を満たします。どれかがこれを満たさなくなると失敗するテストがあり、各テーマは名前が掲げる基準で判定されます。手で追加したテーマはこの対象外ですが、同じ問いは当てはまります。誰にも読めない赤で停止と表示されたサービスは、誰にも気づかれないサービスです。

## カードが実行されるとき

カードを割り当てることが、エージェントに仕事を与える方法です。それを実行に変えるのが **buzzer** というサービスです。

    数秒ごとに:
      担当者がいて、時刻が過ぎていて、まだ呼び出していないカード
        -> そのエージェントを起動する（すでに実行中でなければ）
        -> 呼び出したことをカードに記録する

カード追加フォームの **いつ** で時刻を決めます。

| 選択肢 | 何が起きるか |
|---|---|
| **すぐに** | カードを保存した時点でエージェントが起こされます。これが既定です。カードを割り当てることは、仕事を頼むことだからです |
| **エージェントが起きたとき** | カードはボードで待ちます。誰も起こされず、エージェントは自分の次の実行でそれを見つけます |
| **指定した時刻に予約** | UTC の時刻。その時刻にエージェントが起こされます |

すでに作業中のエージェントが中断されることはありません。カードは順番を保ったまま次の巡回で再び試されるので、作業中のエージェントに予定された実行は、実行されないのではなく数秒遅れて始まります。また、1つのエージェントが同時に2つの実行を持つことはありません。カードが呼び出されるのは一度だけです。もう一度実行するには、時刻を設定し直してください。

### カードはエージェントのチャットに表示される

実行が始まると、エージェントのチャットにそのカードを示すメッセージが届きます。

    カードで作業が割り当てられました:

    カードID: 1284
    タイトル: 証明書を更新する
    内容:「--update を付けてインストーラーを実行し、報告する」
    実行予定: すぐに

別のエージェントがカードを渡した場合は、最初の行に誰からかが示されます。*manager があなたに新しいカードを割り当てました* のようにです。すぐにではなく時刻を指定して予定されたカードなら、最後の行には代わりにその時刻が表示されます。`a2026m03d31@13:45` のように UTC で、ボードがそのカードに表示するのと同じ時刻です。

メッセージが書かれるのは **実行が始まったとき** で、それより前ではありません。今夜に予定して今日の午後に削除したカードは、チャットに何も残しません。何も実行されなかったからです。

エージェントは、ほかのメッセージと同じようにその下に回答し、実行にかかったコストも表示されます。エージェントが何もしていないのにそこに1行が表示される場合が3つあり、それぞれどれに当たるかが示されます。エージェントがオフだった、その日の実行回数をすでに使い切っていた、実行をまったく開始できなかった、の3つです。どれも黙って終わることはありません。知らされたのに無視されたカードは、動いていないエージェントとまったく同じに見えるからです。

この実行がしないことが1つあります。会話を読むことです。指示はカードです。以前にチャットで言ったことが再送されるのは、あなた自身がメッセージを送ったときだけです。そうしないと、予定されたすべての実行が、誰もしていない会話の料金を請求されることになります。

**manager** に渡されたカードは扱いが違います。manager は、誰がその仕事をすべきかを決め、`kanban.assign_card` でカードを渡すよう指示されます。カードは ID、指示、履歴を保ったまま持ち主が変わり、受け取ったエージェントはそのために起こされます。これは委任であって、同じ仕事のための2枚目のカードではありません。

## チャンネル

**設定 → チャンネル** で、エージェントが書き込める先を設定します。

| チャンネル | 必要なもの |
|---|---|
| Discord | 双方向でやり取りするなら `bot_token` と `channel_id`、送信だけなら Webhook URL |
| Mattermost | 受信 Webhook の URL |
| Telegram | BotFather から得る `bot_token` と、`chat_id` |
| X | `bearer_token` |

設定済みのチャンネルには、保存済みの API キーと同じ緑色で **設定済み** と表示されます。設定のないチャンネルは、中立の表示のままです。

認証情報は、**どのエージェントも読めない** ように保存されます。エージェントはサーバーに送信を頼み、サーバーがトークンを読んで送信します。メッセージには、サーバーが付けたエージェントの名前が先頭に付いて届くので、どのエージェントもほかのエージェントになりすますことはできません。

そのうえで、各エージェントの **チャンネル** タブで、使ってよいチャンネルにチェックを入れます。`channel.write` とチャンネルそのものの両方が必要です。

### Telegram からエージェントに返事する

Telegram と Discord は、逆方向にも使える2つのチャンネルです。その設定で **Telegram からエージェントに返事できるようにする** にチェックを入れて保存すれば、返事を書けるようになります。

ボットのメニューには3つの機能があり、`/` ボタンで表示されるのはそれらです。

| コマンド | 内容 |
|---|---|
| `/agents` | エージェントをボタンで一覧表示します。1つをタップすると、そのエージェントと話し始めます |
| `/status` | サービス、ボード、そしてすべてのエージェントとそのモデル、ツール、スキル |
| `/help` | この3つと、エージェントに話しかけるほかの2つの方法 |

### ほかの誰にも見えない

ボットのユーザー名は公開されています。見つけた人なら誰でも開けます。そのため、メニューは **あなたのチャットにだけ** 設定されます。ほかの誰かが同じボットを開いても、空のチャットが見えるだけです。`/` の下にコマンドはなく、説明もなく、押せるのは「開始」ボタンだけです。このボタンは Telegram がすべてのボットに表示するもので、どの API でも消せません。

押しても何も起きません。受信側はすべてのメッセージの `chat_id` を設定にあるものと比べ、一致しないものは、コマンドが実行される前、エージェントが選ばれる前に捨てます。

**そして、何も記録されません。** 返事もなく、ログに1行もなく、誰かが書いたという記録すらありません。あなたのものではないチャットの ID は他人のデータであり、それを残せば、あなたのインストールが、誰がボットを見つけたかの一覧を黙って作っていくことになるからです。

その代償として、`chat_id` の設定を間違えると、あなた自身が見知らぬ人とまったく同じに見えます。あなた自身のメッセージが黙って捨てられるのです。設定されている ID は起動のたびにログに書かれるので、それと比べてください。

```bash
journalctl -u boa-channel-telegram.service | grep "Registered"
```

Debian では、チャンネルのユニットは `boa-channel-<channel>.service` という名前です。インストーラーを `--update` 付きで実行すれば、古いユニット名が自動的に移行されます。Alpine では、OpenRC の名前 `boa-telegram` と `boa-discord` のままです。

このフィルターは人ごとではなく **チャット** ごとです。設定した `chat_id` がグループなら、そのグループのメンバー全員があなたのエージェントと話せます。

### 話す相手を選ぶ

`/agents` をタップし、エージェントをタップすると、こう答えます。

```
Agente os-watcher:

Envíame tus instrucciones...
```

それ以降は、別のエージェントを選ぶまで、**書いたことはすべてそのエージェントに届きます**。誰の名前も出さずに4つの質問を続けて尋ねられます。それがコマンドラインではなく会話である理由です。

宛先が決まる方法は3つあり、次の順で適用されます。

1. **エージェントの発言への返信** は、ほかに何が選ばれていても、そのエージェントに届きます。そのメッセージに返信し（スワイプするか、長押しまたは右クリックで「返信」を選びます）、書いて送信します。
2. **名前を挙げる**（`@os-watcher check the disk`）と、そのエージェントに届き、*さらに* そのエージェントが選ばれた状態になります。`@001` でも使えますし、空白を含む名前でもかまいません。`@News Miner what is new` は1つのエージェントであって、2つの単語ではありません。
3. **どちらでもない** ものは、最後に選んだエージェントに届きます。

ほかに選択を変えるものはないので、たまたま最後に発言したからといって、エージェントがあなたの会話を引き継ぐことはありません。削除したエージェントは、すべてを受け取り続けるのではなく、選択が解除されます。

まだ誰も選んでいないうちは、誰の名前もないメッセージにはエージェントの一覧が返ってくるので、説明なしに何かが消えてしまうことはありません。

### 返ってくるもの

エージェントは Telegram で、あなたが書いたものへの返信として、最初の行に自分の名前を付けて答えます。

```
os-watcher:
25G free of 28G on /, unchanged since yesterday.
```

**そして、やり取りの全体が Web 画面のそのエージェントのチャットに残ります。** あなたの質問とその回答で、あなたが送ったものの時刻の横には `(via Telegram)` と表示されます。それぞれがどの端末で入力されたものであっても、エージェントが頼まれたことと言ったことのすべてを、1つの画面で見られることに変わりはありません。

知っておくべきことが2つあります。

- **作業中のエージェントはそう伝えます。** すでに何かに答えている最中なら、キューに入れられる代わりに、少ししてからやり直すよう伝えられます。キューに入れると、エージェントが遅れをとっていることが見えなくなってしまうからです。
- **聞き取るのはあなたのチャットだけです。** ボットのユーザー名は公開されており、見つけた人なら誰でも書き込めます。ほかのチャットからのメッセージは返事なしに捨てられるので、誰があなたのエージェントと話せるかを決めるのは、設定した `chat_id` です。これを間違えると、何も起きません。

これは Webhook ではなくロングポーリングです。サーバーのほうから Telegram に接続するので、これを動かすためにインターネットに向けて何かを開放する必要はありません。

Telegram が回答を受け付けない場合（ボットをブロックした、チャット ID が変わった、トークンが無効になったなど）、その回答の Telegram への送信はすぐに取りやめられます。Telegram に1時間接続できない場合も同様です。それでも失われることはありません。その回答を含む会話の全体が、Web 画面のエージェントのチャットに残っています。

### エージェントのメッセージの見た目

モデルは Markdown で書き、Telegram は HTML のごく一部しか表示しないので、送り出すときに両者を変換します。届くのはアスタリスクだらけの文ではなく、書式の付いた文です。

| エージェントが書くもの | スマートフォンでの見え方 |
|---|---|
| `**25G free**` | **25G free** |
| `` `df -h` `` | 等幅フォントの `df -h` |
| `# Disk report` | 太字の1行 |
| `- item` | • item |
| 表 | 列をそろえた等幅のブロック |
| ```` ```bash ```` | コードブロック |
| `[text](https://…)` | リンク |

Telegram には独自の見出しもリストも表もありません。そのため、この3つは消えてしまう代わりに、いちばん近い読みやすい形になります。

Telegram が書式を拒否した場合は、**メッセージは失われずに、プレーンテキストとして送り直されます**。どちらにしても文面は届きます。何が起きたかはサーバーのログに残るので、書式のバグは黙っていつまでも品質を落とし続けるのではなく、表に出てきます。

ボットが自分で言うこと（エージェントの一覧、「まだ別のことに答えています」、`/status`）はすべて、**設定 → エージェント** で設定した言語、つまりエージェントが答えるのと同じ言語になります。

## Discord からエージェントに返事する

Discord も、自分専用のボットを使って Telegram と同じように動きます。設定は一度だけ、5分ほどです。

### ボットを作る

1. <https://discord.com/developers/applications> を開き、**New Application** を押します。名前は何でもかまいません。
2. サイドバーの **Bot** を開き、**Reset Token** を押して、表示されたものをコピーします。それが `bot_token` で、表示されるのは一度だけです。
3. **OAuth2 → URL Generator** で **bot** にチェックを入れ、その下の **View Channels**、**Send Messages**、**Read Message History** にチェックを入れます。生成された URL を開き、ボットを自分のサーバーに追加します。
4. Discord アプリ本体で **設定 → 詳細設定 → 開発者モード** をオンにし、エージェントを置きたいチャンネルを右クリックして **チャンネルIDをコピー** を選びます。それが `channel_id` です。

ほかには何も要りません。特に、Message Content Intent は必要 **ありません**。そのスイッチは Gateway 用のもので、このアプリケーションは通常の API でチャンネルを読みます。

### 有効にする

**設定 → チャンネル → Discord** でトークンとチャンネル ID を入力し、**Discord からエージェントに返事できるようにする** にチェックを入れて保存します。数秒以内に、どのボットがどこで待ち受けているかがログに表示されます。

```bash
journalctl -u boa-channel-discord.service | grep "Listening"      # Debian
tail /opt/boa/logs/boa-discord.log                # Alpine
```

有効にする前に書かれたメッセージには答えません。最初の巡回でチャンネルの現在位置を記録し、そこから始めるからです。

### エージェントと話す

| コマンド | 内容 |
|---|---|
| `!agents` | エージェントの一覧と、それぞれに話しかけるために入力するものを表示します |
| `!status` | サービス、ボード、そしてすべてのエージェントとそのモデル、ツール、スキル |
| `!help` | この3つと、エージェントに話しかけるほかの方法 |

指が `/agents` と打ってしまうなら、それでも動きます。ここにはボタンもスラッシュコマンドのメニューもありません。どちらも *インタラクション* で、Discord はそれを、このインストールがあえて開かない接続でしか届けないからです。

宛先を決める3つの方法は、すでにご存じのものです。

1. **エージェントの発言への返信** は、ほかに何が選ばれていても、そのエージェントに届きます。そのメッセージを右クリックして「返信」を選ぶか、スマートフォンならスワイプします。
2. **名前を挙げる**（`@os-watcher check the disk`）と、そのエージェントに届き、*さらに* そのエージェントが選ばれた状態になります。`!os-watcher`、`@001`、`@News Miner what is new` のどれでも使えます。
3. **どちらでもない** ものは、最後に選んだエージェントに届きます。

### 返ってくるもの

回答はあなたの質問への返信として届き、最初の行にはエージェントの名前が太字で表示されます。そして、**やり取りの全体が Web 画面のそのエージェントのチャットに残り**、あなたが送ったものの時刻の横には `(via Discord)` と表示されます。

長い回答は、途中で切られた1通ではなく、複数のメッセージに分かれて届きます。Discord は 2000 文字を超えるものを拒否するので、回答は行の区切りで分割され、最大4通になります。どれに返信しても、同じエージェントに届きます。4通分を超える場合、最後のメッセージは `…` で終わります。全文は、それが書かれた Web 画面にあります。

### 誰がエージェントと話せるか

**そのチャンネルに書き込めるすべての人です。** これが Telegram との唯一の本当の違いで、少し時間をとって考える価値があります。Telegram では、ボットがすべてのメッセージのチャット ID を比べ、一致しないものを捨てるので、あなたのボットを見つけた見知らぬ人は何も得られません。Discord では、ボットは1つのチャンネルを読み、そこに投稿できる人なら誰でも、あなたのサーバーで実行を始められます。

ですから、エージェントは **プライベートチャンネル** に置いてください。あなただけ、またはあなたと信頼できる人たちだけが見られるチャンネルです。ボットには、ほかのものへのアクセスは一切必要ありません。

### 通知だけが欲しい場合

トークンを空のままにして、代わりに **Webhook URL** を設定します。**チャンネルの編集 → 連携サービス → ウェブフック → 新しいウェブフック → ウェブフックURLをコピー** です。これでエージェントはチャンネルに書き込めますが、それだけです。待ち受けにはボットが必要なので、Webhook の場合、スイッチは何もしないまま受け付けられるのではなく、拒否されます。

## オーケストレーター

**manager** と呼ばれる `agent-000` は、インストール時に作られる唯一のエージェントです。削除できないこと以外は、あらゆる点で普通のエージェントです。

想定している使い方はこうです。manager にはカンバンのツールと、目標をカードに分解し、ID でほかのエージェントに割り当てるよう指示するプロンプトを与えます。ほかのエージェントには `bash.run` と必要なものすべて、そして自分に割り当てられたカードに取り組むよう指示するプロンプトを与えます。

これがうまくいくのは、manager のカードに「完了」の意味が書かれている場合だけです。書かれていないカードはただの願いごとで、それを受け取ったエージェントが自分で判断することになります。

## ツールタブ

**設定 → ツール** には、サーバーにインストールされているものが表示されます。ツールの種類ごとにサブタブ（自動化、ブラウザー、チャンネル、メール、画像、インターネット、カンバン、メモリ、オペレーティングシステム、RAG、スキル）があり、それぞれに含まれるツールの数が示されます。各ツールには、引数とその意味を示した専用の枠があります。開いているタブは URL に含まれる（`/settings/?tab=tools&family=mail`）ので、再読み込みやブックマークでもそのまま保たれます。古い `/tools/` へのリンクはここにリダイレクトされ、選択した種類も保たれます。

種類が誰にも名付けられていないツール（誰かが `/opt/boa/tools/` に置いた `.py`）は **その他** に入り、その種類は自分の枠に書かれます。画面に至るまで、れっきとしたツールであることに変わりはありません。専用のタブを持てないだけです。そうしないと、使い捨てのスクリプトが増えるたびにタブの列が伸びてしまうからです。

どのエージェントがどのツールを使えるかは、ここではなく、各エージェント自身の **ツール** タブで設定します。

## APIドキュメント

サイドバーの **APIドキュメント** には、`/api/` 以下のすべてのエンドポイントが、領域ごとに、パラメーターと応答の内容とともに一覧表示されます。このインストール自身の OpenAPI 記述から生成されるので、コードとずれることはありません。上部にリンクのある `openapi.json` は、同じ内容を、クライアントジェネレーターに渡せるファイルにしたものです。

画面のほかの部分と同じく、**設定 → インターフェース** で選んだ言語で表示されます。仕様そのものは英語のままです。このプロジェクトでは、フィールド名、ID、エラー文字列はどこでも英語であり、翻訳した `openapi.json` は存在しない API を記述することになってしまうからです。

リクエスト本文は、エディターと同じように色分けされた JSON で表示されます。フィールド名は1つの色、値は別の色で、波かっこやカンマは足場にすぎないので薄く表示されます。色は選んだテーマに従い、ブロックをコピーしても正しい JSON が得られます。

このページはログインしなくても、サイドバーなしの単独のページとして読めます。記述しているのは API の形であって、あなたのデータではないからです。

## エージェントが考える必要のない作業

繰り返しの機械的な作業もあります。証明書を確認する、ログをローテートする、数値を集める、といったものです。そのためにエージェントを起こすと、シェルスクリプトならただで出せる結論のために、毎回トークンを消費します。

そこで、エージェントは自分でスクリプトを書き、それを予定に入れられます。**自動化** のツールを与えれば、次のことができます。

1. `script.write` — 自分の `scripts/` ディレクトリにシェルスクリプトを置く。
2. `cron.add` — 自分の crontab で、それを定期的に実行する。
3. 次の実行で結果を読み、それが何を意味するかを判断する。

スクリプトはそのエージェントの Linux ユーザーとして、エージェントと同じ権限で動き、**トークンは一切かかりません**。モデルの呼び出しではなく、シェルスクリプトだからです。トークンがかかるのは、後でエージェントがその出力を読み、どうするかを判断するときです。

してはいけないことは次のとおりです。

- 自分のスクリプト以外を予定に入れること。crontab に書かれた自由形式のコマンドは、後から誰も検証できません。
- 5分より短い間隔で実行すること。毎分のジョブはスケジュールとは言えません。
- 自分を起こす行に触れること。その行はあなたのもので、エージェントの **Cron** タブにあります。

あなたには両方が見えます。ホームにあるスクリプトと、Cron タブであなた自身の行と並んで表示される、それを実行する行です。

## 実行の報告の行き先

チャットから始めた実行は、そこであなたに答えます。期限が来たカードで始まった実行も、同じ場所で答えます。エージェント **自身の crontab** で始まった実行には、特に答える場所がありません。誰も何も尋ねていないからです。そこで、次のようになります。

- **常に「履歴」に残ります。** **最近の実行** の下に、各実行が言ったことが、そのコストとともに表示されます。エージェントが何をしていたのか気になったら、ここを見てください。
- **あなたの手を止める価値があるときは、チャットにも残ります。** 実行が終わらなかった場合や、あなたの目に見えるもの（カード、チャンネルのメッセージ、メールボックス）を変えた場合です。様子を見ただけの実行は「履歴」にだけ残ります。そうしないと、毎時の crontab を持つエージェントは、1日に24回も「報告することはありません」というメッセージを会話に投稿することになります。

それらのメッセージの上には、誰も頼んでいないものであることが示されます。また、モデルに再送されることはないので、次にあなたがメッセージを送るときのコストにもなりません。

**開始されなかった実行も「履歴」に残り**、「開始されず」と表示されます。API キーがまだ設定されていないエージェントで、あるいはエージェントがすでに実行中のときに **今すぐ実行** を押すと、「履歴」の行で、そのどちらだったかが分かります。以前は、画面には実行が始まったと表示されるだけで、ほかには何も現れませんでした。理由が、誰も読まない場所に書かれていたからです。開始されなかった実行は、エージェントのその日の実行回数には数えられず、エージェントの失敗としても数えられません。何も実行されていないからです。

## ステータスバー

すべてのページの下部にあり、サイドバーの下も含めてウィンドウの幅いっぱいに伸びる帯は、インストール全体についての情報を示します。

- **エグゼキューター** と **エージェントAPI**。動いていれば緑です。どちらかが赤なら、エージェントは動かず、画面のほかの場所はそれを教えてくれません。
- **エージェント**: 存在するもののうち、いくつがオンになっているか。
- **ボード**: 各列のカードの数。
- **本日のトークン**: UTC の午前0時以降に、すべてのエージェントで使った量と、それにかかった実行回数。エージェントがループに陥ったことを、請求書より先に示してくれる数字です。

帯の右端にある GitHub のマークと **nipegun** という名前をクリックすると、プロジェクトのリポジトリ <https://github.com/nipegun/bunch-of-aigents> が新しいタブで開きます。ログインしているアカウントは表示されません。インストールにはアカウントが1つしかないので、表示しても、すでに知っていること以上は何も伝わらないからです。

## エージェントが答える言語

各エージェントのプロンプトを自分がふだん考える言語で書けば、エージェントはその言語で答えます。これでチャットはまかなえます。しかし、エージェント自身の crontab で始まった実行はまかなえません。誰もどの言語でも話しかけておらず、付属のプロンプトは英語だからです。そのため、スペイン語で使っているインストールが、予定された報告を英語で受け取っていました。

**設定 → エージェント → エージェントが答える言語** は、それをすべてのエージェントについて一度に解決します。各エージェントのシステムプロンプトに、指定した言語で書かれた1行を加え、プロンプトが言語について何と言っていても、それより優先すると伝えます。既定のままにしておけば何も変わらず、各エージェントは自分のプロンプトの言語で答えます。

この設定はサーバーに保存されます。ブラウザー側の設定である画面の言語とは違います。cron に起こされた実行にはブラウザーがないからです。

## 自分の言語でプロンプトを書く

システムプロンプトは、自分がふだん考える言語で書いてください。システムのどこも英語に縛られてはいません。プロンプト、メモリ、チャット、カードのタイトル、サービス間のメッセージは、すべて最初から最後まで UTF-8 で、アクセント記号なども含めてそのまま扱われます。

新しいエージェントが受け取る既定のプロンプトは英語で、その最後の規則は、プロンプトが書かれている言語で答えるようエージェントに指示しています。全体を自分の言語で書き直せば、その規則も一緒に書き換わります。エージェントは、最初に持っていたプロンプトではなく、今持っているプロンプトに従います。

プロンプトは、決まった桁で折り返さず、行をまるごと保存します。テキスト欄は読みやすいように画面上で折り返しますが、ファイルに改行を入れることはありません。1文の規則は1行のままで、編集するときに段落を折り返し直す必要はありません。

## バックアップと復元

このインストールをあなたのものにしているすべては、`/opt/boa/` 以下と、エージェントの Linux ユーザーの中にあります。1つのコマンドで、それを1つのアーカイブにまとめます。

```bash
./install-update-reinstall-debian.sh --backup
```

サービスを動かしたまま（何も止まりません）、`root` だけが読めるモード 0600 の `/root/boa-backup-<date>.tar.gz` を書き出します。別の場所に書き出すには、パスを渡します（`--backup /mnt/usb/boa.tar.gz`）。中に含まれるのは、両方のデータベース（ログ先行書き込みにまだ残っているものも漏れないよう、SQLite 自身のバックアップ API でコピーします）、プロバイダーの鍵、チャンネルの秘密情報、セッションの秘密鍵、証明書、すべてのエージェントとそのホーム、保護されたファイル、Linux ユーザー、crontab、このサーバーで書かれたスキルとツール、そしてパスワードが記載されているインストールログです。含まれないのは、コード、Python 環境、ブラウザー、そしてこのマシン自身の2つの選択（ポートのモードとブラウザーの有無）です。そのため、復元で別のマシンの選択が持ち込まれることはありません。

**マシンと同じくらい厳重に保管してください。** すべての API キー、すべてのチャンネルのトークン、そしてログインパスワードが入っています。

このマシンでも新しいマシンでも、復元は次のように行います。

```bash
./install-update-reinstall-debian.sh --install       # 新しいマシンの場合のみ
./install-update-reinstall-debian.sh --restore /root/boa-backup-<date>.tar.gz
```

YES の入力を求めます。`--yes` を渡してもかまいません。その後、サービスを止め、エージェントのユーザーを同じ名前で（空いていれば同じ ID で）作り直し、データベース、鍵、証明書、エージェント、スキル、ツールをアーカイブのものに置き換え、crontab をインストールして、すべてを起動します。バックアップのメールアドレスとパスワードでログインしてください。どちらも `/opt/boa/logs/install.log` の `Credentials of the restored backup` という見出しの下に追記され、バックアップのログ全体は、その隣に `install.log.restored-<date>` として残されます。

このマシンにはあってバックアップにはないエージェントは、ホームがディスクに残ったまま、画面から消えます。エージェントの一覧は、復元されたデータベースにあるからです。Alpine では、`install-update-reinstall-alpine.sh` で同じ2つのフラグを使います。

## サービス

| サービス | 実行ユーザー | 内容 |
|---|---|---|
| `boa-proxy` | `boa` | HAProxy。11443 で TLS を終端し、11080 をリダイレクトし、Web のポートを提供します |
| `boa-web` | `boa` | Web 画面と API。プロキシの背後の Unix ソケットで動きます |
| `boa-exec` | `root` | ユーザーを作成し、crontab をインストールし、エージェントの実行を開始します |
| `boa-samba` | `root` | SMB ユーザーを認証し、各 samba/ フォルダーをそのエージェントのユーザーとして提供します |
| `boa-agent-api` | `boa` | エージェントがボードやチャンネルにアクセスするための入り口 |
| `boa-buzzer` | `boa` | ボードを見張り、カードの期限が来たらエージェントを起こします |
| `boa-embeddings` | `boa` | 文書ライブラリのローカルのベクトル化モデルを、Unix ソケットで提供します |
| `boa-rag` | `boa` | 文書ライブラリのインデックス化のキューを管理します |
| `boa-channel-telegram.service` | `boa` | Telegram で待ち受け、スマートフォンからエージェントに返事できるようにします |
| `boa-channel-discord.service` | `boa` | Discord のチャンネルについて同じことをします |

```bash
systemctl status boa-proxy boa-web boa-exec boa-agent-api boa-buzzer \
                 boa-embeddings boa-rag \
                 boa-channel-telegram.service boa-channel-discord.service boa-samba
journalctl -u boa-exec -f
```

Debian のチャンネルのユニットは `boa-channel-<channel>.service` という名前です。`--update` で更新すると、新しいユニットを有効にする前に、古いチャンネルのユニットを停止して無効にします。

Alpine でも同じプロセスが動きます。チャンネルのサービスは `boa-telegram` と `boa-discord` のままです。これらは `supervise-daemon` で監視される OpenRC サービスで、それぞれの出力は `/opt/boa/logs/` 以下の専用ファイルに書かれ、毎週ローテートされます。

```bash
rc-status
rc-service boa-exec status
tail -f /opt/boa/logs/boa-exec.log
```

## セキュリティ

この設計は、エージェントがいずれ意図しないことをすると想定しています。シェルを持った言語モデルだからです。

- **各エージェントは別々の Linux ユーザー** で、そのホームは `0700` です。エージェントは互いのファイル、プロンプト、API キーを読めません。
- **`/opt/boa/agents/` は `0711`** なので、どのエージェントも、ほかにどんなエージェントが存在するかを一覧することさえできません。
- **root で動くエージェントは決してありません。** root で動くのは `boa-exec` だけで、それも Unix ソケット経由で決められた操作の一覧しか受け付けません。その中に「このコマンドを実行せよ」はありません。
- **実行を制限するのは上限だけでなく、カーネルでもあります。** どのエージェントも 1024 を超えるプロセスとスレッドを持てないので、fork 爆弾はその数で止まります。Debian では、各実行が 2 GiB のメモリを持つ専用の systemd スコープの中で動き、実行が終わるときに、その実行が動かしたまま残したものもすべて終了させます。
- **エージェントがチャンネルの認証情報を見ることはありません。** ボットのトークンはメッセージではありません。そのボットが送れるものなら何でも送れる、永続的な権限です。エージェントはエージェント API に送信を頼み、エージェント API が送信します。
- **エージェントは自分のカードにしか触れません。** [カンバンボード](#カンバンボード)を参照してください。
- **`web.fetch` はプライベートアドレスを拒否します。** 名前解決後の IP を確認し、リダイレクトのたびに確認し直すので、悪意のあるページを読んだエージェントが、内部ネットワークを呼び出すよう指示されることはありません。

LAN での利用を想定しており、インターネットに公開すべきではありません。

## うまく動かないとき

**`--ports direct` を選んだら、マシンの HAProxy が消えました。** 消えたのではなく、退役したのです。停止され、Alpine ではすべてのランレベルから外され、Debian では無効化されてマスクされ、その `/etc/haproxy/haproxy.cfg` は、インストーラーが書いたものなら削除され、あなたが書いたものなら `haproxy.cfg.before-boa.<date>` として残されています。このモードでは、アプリケーション自身が 80 と 443 にバインドするので、ほかの何かがそれらのポートを使っていると、アプリケーションはまったく起動できません。有効のまま残したプロキシがあれば、次回の起動時に、アプリケーションが動く前にそれらのポートを奪ってしまいます。`haproxy` パッケージがインストールされたままなのは意図的です。`boa-proxy` は `/usr/sbin/haproxy` であり、このモードで 80 と 443 を提供しているのはそれだからです。

元に戻すには、インストーラーを `--update --ports proxied` 付きで実行します。ユニットのマスクを解除し、マシンの設定を書き直して起動します。古いファイルがあった場合は、`before-boa` の名前でその隣に残っています。

**`boa-proxy` が再起動を繰り返し、11443 で何も待ち受けていません。** `/opt/boa/logs/boa-proxy.log` を読んでください。`Cannot raise FD limit to 4131` と書かれていれば、このマシンのファイルディスクリプターのハードリミットが、プロキシが求めた値より低いということです。たいていは小さなコンテナです。これが修正される前に作られたインストールでは、`/opt/boa/config/haproxy.cfg` にまだ `maxconn 2048` があります。インストーラーを `--update` 付きで実行するとファイルが書き直されます。その場で直すには、次のようにします。

```bash
sed -i 's/^  maxconn 2048$/  fd-hard-limit 4000/' /opt/boa/config/haproxy.cfg
rc-service boa-proxy restart        # Debian では systemctl restart boa-proxy
```

すると HAProxy は、実際に持てるディスクリプターの数から自分の規模を決めます。ハードリミットが 4096 なら約 1987 接続で、このアプリケーションが必要とする量をはるかに上回ります。

**インストーラーが「Everything is in place but the application does not answer」で終わります。** インストールは済んでいますが、ページが一度も返ってきませんでした。理由はすでにログに書かれています。

```bash
sed -n '/Why it did not answer/,$p' /opt/boa/logs/install.log
```

そのブロックは、その時点のマシンの様子です。curl がリクエストをどう扱ったか、そのポートで何かが待ち受けているか、10のサービスすべての状態、そしてプロキシと Web アプリケーションが最後に出力した数行です。`000` は HTTP コードではありません。curl が何のコードも受け取らなかったという意味です。`nothing is listening on port 11443` の横で自分を `started` と称しているサービスは、数秒ごとに異常終了しては再起動されているプロセスで、その理由は数行下にある、そのサービス自身のログに書かれています。

ここで失敗した更新は、すでに以前のバージョンを元に戻して動かしています。初回のインストールには戻る先がないので、すべてをそのまま残します。ブロックに挙げられた問題を直してから、インストーラーをもう一度 `--update` 付きで実行してください。

**インストーラーが「systemd is not running」で止まります。** systemd が PID 1 ではないマシンへのインストールを拒否しているのです。インストーラーが書き込むサービスはすべて systemd ユニットで、それらを起動するものがないからです。普通の Debian なら問題ありません。コンテナは、systemd を動かすように作られたものでなければ問題になります。

```bash
apt-get install -y systemd systemd-sysv dbus dbus-user-session
```

そのうえで、コマンドを `/sbin/init` にしてコンテナを作り直します。すでに動いているコンテナは PID 1 を変えられないからです。Alpine ではこの問題は起きません。Alpine のインストーラーは、マシンに OpenRC がなければ自分で追加します。

**「今すぐ実行」を押しても何も起きません。** サイドバーの下部にある2つの点を見てください。`executor` が赤なら、次のようにします。

```bash
systemctl status boa-exec
journalctl -u boa-exec -n 50
```


**ブラウザーに 503 が表示され、サービスはすべて動いています。** マシンの HAProxy がバックエンドをダウンと判定しています。ほとんどの場合、そのバックエンドにある `option ssl-hello-chk` が原因です。その ClientHello は TLS 1.2 より古く、アプリケーションは TLS 1.2 を要求するからです。その行を削除し、HAProxy を再読み込みしてください。

**エージェントは実行されるのに何もしません。** その「履歴」パネルを確認してください。そのうえで、手動で実行して様子を見ます。

```bash
runuser -u agent-001 -- /opt/boa/venv/bin/python3 \
  /opt/boa/webapp/backend/core/runner.py --agent-id 001
```

`--dry-run` を付けると、モデルを呼び出さずに、何を読み込むか（プロバイダー、ツール、上限）を確認できます。

**モデルに接続できないと言います。** 自前ホストのプロバイダーなら、サーバーが動いていて、ベースURL が正しいことを確認してください。クラウドのプロバイダーなら、鍵のファイルがエージェントのホームにあり、そのエージェントの所有になっていることを確認してください。

**ツールが使えないと言います。** そのエージェントのページで、そのツールにチェックが入っていません。プロンプトでそれを覆すことはできません。それこそが狙いです。

**カードが表示されなくなりました。** そのエージェントのカンバンのチェックボックスが外れているか、サイドバーの下部で `agent API` が赤になっています。

```bash
systemctl status boa-agent-api
```

**エージェントがしたことをすべて見たい。** 記録はエージェント自身のホームにあります。

```bash
cat /opt/boa/agents/001/runs.jsonl
```

1行に1つの JSON オブジェクトで、いつ実行したか、何を消費したか、最後まで終わったかが記録されています。
