## 1. アーキテクチャと設計判断

ここはコードから導き出せない部分であり、だからこそ読む価値のある部分だ。

### 前提

ここでいうエージェントとは、サーバー上でシェルを持ち、cron に起こされ、誰にも見張られていない言語モデルである。構造上の判断はすべて、このことを真剣に受け止めるところから導かれている。モデルはいずれ意図しないことをする。だから問題は、それをどう防ぐかではなく、それが起きたときに何に手が届くかである。

### 1エージェントにつき1つの Linux ユーザー

エージェント `007` はシステムユーザー `agent-007` であり、モード `0700` の `/opt/boa/agents/007/` を所有する。エージェント間の隔離はカーネルが担うものであり、Python で書かれたサンドボックスではない。エージェントがほかのエージェントのシステムプロンプト、ジャーナル、APIキーを読めないのは、ファイルシステムがそう定めているからだ。

`/opt/boa/agents/` 自体は `root:root 0711` である。通り抜けはできるが、一覧表示はできない。エージェントはほかのエージェントを列挙できず、推測したパスを開こうとして失敗するだけだ。

`bash.run` に許可リストが要らないのは、この判断があるからだ。シェルに対するブロックリストは見せかけにすぎない（`sh` を実行できるものなら、リストに挙がっているものは何でも実行できる）。一方、ユーザーアカウントはカーネルが強制する境界である。

### エージェントが自分自身について書き換えてはならないもの

ホームはエージェント自身のもので、0700 であり、そこが肝心な点だ。メモリ、ジャーナル、会話、そしてエージェントが書くスクリプトはすべてそこにある。しかし 3つのファイルはエージェントが変えてよいものではなく、ホームの外、`/opt/boa/agents-config/xxx/` に置かれている。このディレクトリは `root:agent-xxx 0750` で、その親は `root:root 0711` である。

| ファイル | エージェントのものではない理由 |
|---|---|
| `info.json` | どのツールを許可されているか、いくらまで使ってよいか |
| `system-prompt.md` | 何をすべきかの定義 |
| `api-token` | エージェントAPIに対して自分を名乗るためのもの |

これを成り立たせているのはファイルの所有者ではなく、ディレクトリの所有者である。ディレクトリ内のファイルを削除して置き換えられるかどうかを決めるのは、そのディレクトリの書き込み権限だ。したがって、ディレクトリを所有するエージェントであれば、ファイルの所有者が誰であっても `info.json` を削除して自分で書いたものに置き換えられてしまう。エージェントはこのディレクトリに入って中を読むことはできるが、その中で何かを作成、名前変更、削除することはできない。

**そしてこの規則は、中身と同じく引き出しそのものにも当てはまる**。これらのファイルがもう `agents/xxx/config/` に置かれていないのはそのためだ。あのパスはホームの中のエントリであり、ホームは 0700 でエージェントのものだ。そしてエントリの名前を変えるのに必要なのは親ディレクトリの書き込み権限だけで、名前を変えられる対象自体のモードは一切参照されない。そのためエージェントは、`info.json` を編集することはできなくても、次のことはできた。

    mv ~/config ~/config-old && mkdir ~/config && echo '...' > ~/config/info.json

そうすれば、差し替えたほうが読まれる。引き出しをホームの外へ移すと、そこへ至る途中のディレクトリはすべて root の管理下に入る。この移動から 2つのことが導かれる。

  - **ホームへのフォールバックはもうない。** 以前はあった。更新によって、マイグレーションが走る前にサービスが応答しなくなることがないようにするためだ。しかし、それ自体が抜け道だった。本物のファイルを隠すだけで、代わりにエージェント自身が書いたファイルが読まれたからである。今はインストーラーだけでなくデーモンも起動時にマイグレーションを行うので、補うべきものはもう何も残っていない。
  - **エージェントを削除すると、その設定も削除される。** 設定はもはや `userdel --remove` が消し去るホームの中にはなく、残しておけば、次にその ID を与えられたエージェントに引き渡されてしまう。

`fOpenProtectedAgentFile` は同じ問いに対する 2つ目の答えだ。`O_NOFOLLOW` 付きで開き、開いたファイルそのものについて、通常ファイルであること、root が所有していること、ほかの誰も書き込めないことを確認する。更新中の誤った chmod や、所有者を誤ったバックアップからの復元があっても持ちこたえるのはこれである。

これは修正前に、実際のインストール環境で計測した。エージェントが自分の `info.json` に `mail.read` を追記すると、特権デーモンはそのツールを許可済みとして報告した。つまりエージェントは、自分にメールボックスやチャンネルを許可したり、自分の上限を引き上げたりできた。自分のプロンプトを「ルールをすべて無視せよ」に置き換えることもでき、そうなればそれ以降のすべての実行でそのままになっていたはずだ。

エージェント間の隔離にはこのどれも必要ない。`/opt/boa/agents/` は `root:root 0711` で、各ホームは 0700 なので、カーネルがすでに拒否する。ツールにバグがあっても隔離が保たれるのはそのためだ。

### root がホームから読み出すもの

ジャーナル、メモリ、チャットはエージェント自身のファイルである。エージェント自身のプロセスが自身の 0700 のホームの中に書き、それを特権デーモンが root として読む。そして root は、指し示されたものを何でも読んでしまう。この仕組みができる前のコードで計測したところ、次のことが起きた。`runs.jsonl` という名前の FIFO は、それを開いたデーモンのスレッドを永久に捕まえたままにした。エージェント一覧はすべてのエージェントのジャーナルを読むので、その一覧へのその後のリクエストのたびに、スレッドが 1つずつ漏れた。マシン上の任意のファイルを指す `memory.md` という名前のリンクがあると、root がそのファイルの内容を画面に渡した。そして終わりのないものへのリンクがあると、root は強制終了されるまで読み続けた。

そこで 3つとも `fReadAgentOwnedFile` を通して読む。これは、まさにエージェントのものであるファイルのための、`fOpenProtectedAgentFile` の兄弟にあたる関数だ。`O_NOFOLLOW` は開く時点でリンクを拒否し、`O_NONBLOCK` は誰かが書き込むまで FIFO が open を止めておくのを防ぐ。確認（通常ファイルであること、エージェントのユーザーが所有していること）は開いたディスクリプタに対して行うので、確認と読み込みの間に何かをすり替えることはできない。読み込む量には上限があり、それを超えて読むことはない。この上限は `fstat` が示した値だけでなく、実際に読んだ量に対して適用される。読んでいる最中にもエージェントは追記できるからだ。ジャーナルとチャットは 32 MB で、ファイルがそれより大きいときは末尾から読む。履歴が表示するのは最新の行だからである。メモリは 4 MiB で、その最大値である UTF-8 の 100万文字に十分な大きさだ。`[truncated]` が付くのは、外部で書かれてこの読み込み枠を超えたファイルだけである。`fWrite` は大きすぎる内容を、何かを置き換える前に拒否する。不正なバイトがあっても失うのはその 1行であり、読み込み全体ではない。

拒否したことは握りつぶさずに伝える。`read_run_journal`、`read_chat`、`read_memory` は理由を付けて失敗するので、運用者はそのホームの中に、アプリケーションが書いたものではない何かがあると知ることができる。唯一の例外は、サイドバーの描画に使う全エージェント分の `read_usage_summary` だ。そこでは、読めないジャーナルが 1つあっても、失われるのはそのエージェントの合計値だけで（理由はその横に表示される）、ほかのエージェントの合計値は失われない。

### コマンドラインに載るもの

デーモンは `Popen` を使い、エージェントとして実行を開始する。以前は、オーナーが入力したメッセージ（あるいは期限の来たカードが組み立てるプロンプト）が、その引数の 1つになっていた。`--chat-message <text>` や `--prompt <text>` である。プロセスのコマンドラインは `/proc/<pid>/cmdline` を通じてマシンのすべてのユーザーが読める。そして `bash.run` を持つエージェントは、マシンのユーザーである。Debian のテストマシンで計測したところ、`agent-001` として実行した `ps` に、オーナーが `agent-000` に送ったばかりのメッセージが表示された。表示はその実行が続く間ずっと続き、その長さは既定で最長 5分である。

そこでテキストは子プロセスの標準入力に流し込み、コマンドラインには `--chat-message-on-stdin` か `--prompt-on-stdin` だけを載せる。ランナーを起動するのは `fStartRunner` ただ 1か所だ。この関数は、プロセスが存在する前に、`cMaxStdinPayloadBytes` より長いテキストを拒否する。この上限はパイプの 64 KiB のバッファより小さく、バッファに収まる書き込みは子プロセスを待つことがないからだ。このデーモンはランナーを待たない。書き込みの時点で子プロセスがすでにいない場合（インタープリターが import で失敗した場合など）、それはパイプの切断であり、デーモンの失敗ではない。反対側では、ランナーが同じ上限でテキストを読み、誰も尋ねていない質問に答えるのではなく空のチャットメッセージを拒否し、拒否するときには自分が起動された目的のターンを閉じる。そうすれば会話がいつまでも待たされることはない。`--prompt` と `--chat-message` は、端末から手で開始する実行のために残してある。

### 実行がマシンに対してしてよいこと

`info.json` にある上限（トークン、ステップ、秒数、1日あたりの実行回数）はランナーが強制する。そしてランナーは、エージェントが動かしているプログラムだ。そのプログラム自体がおかしくなったときにも効くものは、カーネルが 2層で強制する。

ランナーはほかの何よりも先に、自分のリソース制限を下げる（`fApplyResourceLimits`）。これはエントリーポイントから行い、`fMain` からではない。テストは `fMain` をプロセス内で呼び出すので、すでに何千ものスレッドが動いている開発者のセッション内で RLIMIT_NPROC を下げると、そのセッションが fork できなくなるからだ。実行が開始するすべてのプロセスはこの制限を継承する。RLIMIT_NPROC は 1024 で、エージェントの uid 全体に対して数えられる。そのため `bash.run` からの fork 爆弾は、マシンではなくこの数で止まる。スレッドも数に入るので、これより小さくはしていない。ブラウザー 1つで数百のスレッドになるからだ。コアファイルは作られず、4 GiB を超えるファイルも作れない。RLIMIT_AS は設定しない。Chromium は数十 GB 単位でアドレス空間を予約するので、起動しなくなってしまう。この層は Debian でも Alpine でも同じであり、エージェント自身の crontab が開始した実行にあるのはこの層だけだ。

systemd が PID 1 である環境では、デーモンが 2つ目の層を加える。`fStartRunner` は実行を、その実行専用の一時的なスコープ、つまり `boa-agents.slice` の下の `boa-agent-<id>-<random>.scope` に入れ、`TasksMax=1024` と `MemoryMax=2G` を設定する。`systemd-run --scope` はコマンドへ exec するので、pid はランナーのままであり、`/proc` にはそのコマンドラインが表示され続ける。エージェントへの権限降格を行うのは `setpriv` だ。スコープを作るには systemd-run が root でなければならないからである。こうなる前に計測したところ、実行は `boa-exec.service` の子プロセスとしてデーモン自身の cgroup の中にあり、暴走したエージェントがデーモンの TasksMax を使い果たして、デーモンが fork できなくなった。スコープは、実行が後に残したものを終わらせる役目も担う。`bash.run` は自分のプロセスグループにシグナルを送るので、`setsid` を呼んだコマンドや、時間内に終わったコマンドのバックグラウンドの子プロセスは、実行より長く生き残っていた。`fWatchRunner` は実行を待ってからそのスコープを停止する。スコープを止めれば、実行が開始したものすべてに、それがどこへ移動していても届く。（メモリ制限や運用者によって）強制終了された実行は、終わり際に何も書かない。そのため同じスレッドがジャーナルに終了を記録し、チャットのターンを閉じる。自分で終了した実行はすでに両方を済ませており、ターンについては済んだと仮定せずに確認する。

### プロバイダーの鍵の置き場所

すべてのエージェントが共有する鍵は `/opt/boa/config/apikeys/<provider>.key` にあり、所有者は `boa`、ディレクトリは `0700`、ファイルは `0600` である。

0750 と 0640 でも、エージェントを締め出すには足りる（`boa` グループに入っているエージェントユーザーはいない）。しかしそれは、インストールが続く限りすべてのエージェントのグループ一覧が空のままであることに依存しており、`usermod -aG` 1回でその前提は崩れる。グループに何も与えないモードなら、その前提に依存しない。`api_keys.fWrite` は作成時だけでなく書き込みのたびに両方のモードを設定するので、古いインストールから引き継いだディレクトリも、最初に鍵が保存された時点で閉じられる。

このディレクトリは、名前を変えるまで `keys` と呼ばれていた。「このインストールの鍵」と読めてしまううえに、各エージェントのホームにあるエージェントごとの `keys/` とはタイプミス 1つ分しか離れていなかった。後者は別物で、エージェントが読むことの*できる*もの、つまり別のアカウントに請求させるためにそこに置かれた、エージェント自身の鍵である。インストーラーは `--update` のときに古いディレクトリの中身を移し、空になってから初めてそれを削除する。

こうしたことはどれも、エージェントが実際に使っているプロバイダーの鍵を持つことを止めはしない。エージェントAPIがその鍵を渡し、エージェントは呼び出しにそれを必要とし、`bash.run` を持つエージェントならそれを表示できる。止めるのは、エージェントが使っていないプロバイダーの鍵を読むことである。

### 10のサービスと、そのうち root で起動する 2つ

| プロセス | ユーザー | 存在する理由 |
|---|---|---|
| `boa-proxy` | `boa` | HAProxy。TLS を終端し、両方のポートで応答する |
| `boa-web` | `boa` | 画面と API を Unix ソケットで提供する |
| `boa-exec` | `root` | ユーザーを作成し、エージェントの実行を開始する |
| `boa-samba` | `root` | SMB セッションを認証し、その後は所有者のエージェントとしてファイルを提供する |
| `boa-embeddings` | `boa` | 文書ライブラリのローカルのベクトル化モデルを、Unix ソケットで提供する |
| `boa-rag` | `boa` | 文書ライブラリのインデックス化のキューを管理する |
| `boa-agent-api` | `boa` | エージェントが使ってよいが読んではならないものを保持する |
| `boa-buzzer` | `boa` | エージェントのカードの期限が来たら、そのエージェントを起こす |
| `boa-channel-telegram` | `boa` | Telegram を待ち受け、届いたものをエージェントに渡す |
| `boa-channel-discord` | `boa` | 同じことを Discord のチャンネルに対して行う |

Debian でのチャンネルのユニットは `boa-channel-telegram.service` と `boa-channel-discord.service` であり、今後のチャンネルのユニットも `boa-channel-<channel>.service` に従う。OpenRC では `boa-telegram` と `boa-discord` のままである。`system_info.fServiceName` が、システムのタブとリスナーの状態報告の両方のために、これらの名前を解決する。

`fInstallSystemdUnits` は `fRetireLegacyChannelUnits` を呼び出し、古いチャンネルのユニットをそれぞれ停止して無効化してから削除し、その後で置き換え先を有効にする。古いユニットが存在しなくても、更新を繰り返して問題ない。新しいユニットをインストールする前に更新が失敗した場合は、ロールバック中に `fStartServices` が古いユニットを再起動できる。

最後の 4つが root ではなく `boa` なのは意図的である。どれも何かをエージェント自身のユーザーとして行う必要がある（実行の開始や、0700 のホームへの書き込みなど）。そしてどれも、その権限を与えられるのではなく、`boa-exec` に頼んでそれを行ってもらう。外部から到達できるサービス（2つのリスナーは事実上そうである）は、その権限を持つべきでない最たるものだ。

### 仮想環境は移動できない

`python3 -m venv <path>` は、後からその中にインストールされるすべてのコンソールスクリプトのシバン、activate スクリプトの `VIRTUAL_ENV`、そして `pyvenv.cfg` の `command` 行に `<path>` を書き込む。環境は `venv.new` に構築されてから `venv` へ名前を変えられるので、この 3つはいずれも、もう存在しないディレクトリを指すことになる。

実際の Debian 13 と実際の Alpine 3.24 で計測したところ、どちらのインストールも完了し、どちらも「Installation finished」と表示した。そしてどちらも、`boa-web` が次のメッセージとともに 5秒ごとに再起動を繰り返す状態になっていた。

```
status=203/EXEC - Failed to execute /opt/boa/venv/bin/gunicorn:
No such file or directory
```

ファイルはそこにあった。その 1行目が `/opt/boa/venv.new/bin/python3` を指しており、そちらが存在しなかったのだ。

`fBuildVirtualEnv` には、まさにこの種の失敗を調べる確認があり、それは通っていた。確認が `bin/python3` を実行していたからだ。これはシステムのインタープリターへのシンボリックリンクであり、どこに置かれていても応答する。パスが焼き込まれているのはコンソールスクリプトだけである。そこで確認は、サービスユニットが実行するファイルである `bin/gunicorn --version` も実行するようになり、`fRepointVirtualEnv` が、環境がまだ構築用の名前にあるうちに、記録された 3つのパスをすべて書き換える。書き換えは、済んだと仮定せずに検証する。将来の pip がコンソールスクリプトを別のやり方で書くようになれば、インストーラーはそこで止まる。

### 失敗した更新でも、何かは動いたまま残る

3つの段階があり、その順序こそが修正である。

以前の更新は、サービスを停止し、`webapp/` を削除し、それから初めて pip を実行していた。pip が失敗すると（ネットワークがない、インデックスが落ちている、wheel がビルドできない）、サービスが止まりコードが消えたインストールが残った。1分前まで動いていたマシンが、誰かが気づいて手で復旧するのを待つことになったのである。

| 段階 | 何が起きるか | 失敗したときに失うもの |
|---|---|---|
| 準備 | 質問をし、依存関係をインストールし、コードをダウンロードし、新しい virtualenv を動いているものの隣に構築して、import できることを確認する | 何もない。古いバージョンは動いたままで、手つかずである |
| 切り替え | 停止し、`webapp/` を `webapp.previous` に、`venv` を `venv.previous` に移し、新しいものを配置して起動する | 元に戻せる。以前のバージョンは両方ともディスクに残っている |
| 検証 | `curl` がアプリケーションにログインページを要求する。30秒の間に 15回行う | `fRollBack` が両方を元に戻し、再び起動する |

その `curl` が PROXY プロトコルを送るのは `proxied` モードのときだけである。`direct` モードでは bind に `accept-proxy` がないので、PROXY ヘッダーは TLS ハンドシェイクに紛れ込み、リクエストにはまったく応答が返らない。以前は両方のモードで送っていたため、`--install --ports direct` はどれも、ページを提供しているインストールなのに「did not answer」で終わり、direct での `--update` はどれも自らロールバックしていた。両方のテストマシンを `direct` に切り替えて戻すことで確認した。フラグをモードに結びつけると、どちらも 443 で、その後 11443 で 200 を返した。あるテストは、引数を記録する `curl` に対して両方のインストーラーの `fVerifyInstallation` をモードごとに 1回ずつ実行し、一方ではフラグがあり、もう一方ではないことを確認する。

その `curl` に応答が返らないとき、`fExplainWhyItDoesNotAnswer` はその時点のマシンの状態を、エラーが指し示すのと同じログに書き込む。書き込むのは、curl 自身が言うこと（`-sS` を付けてもう一度尋ねる。接続の拒否、ハンドシェイクの失敗、リクエストのタイムアウトを区別するためだ。`000` は HTTP コードではなく、curl がコードを受け取れなかったと言っているのである）、10のサービスそれぞれの状態、そもそもそのポートで何かが待ち受けているかどうか、そして `boa-proxy.log`、`boa-web.log`、gunicorn の `error.log` の最後の 15行である。`fReportServiceStates` が 2つのインストーラーで異なる部分で、Alpine では `rc-service ... status`、Debian では `systemctl is-active` に加えて `boa-web` と `boa-proxy` のジャーナルを使う。

これがあるのは、まっさらな Alpine への最初のインストールが「The application did not answer on port 11443 (last code: 000)」で終わり、ログにはそれ以外何も残っていなかったからだ。どのサービスが落ちていたのかも、ポートが使われていたのかも、gunicorn が何を出力したのかも 1行もなかった。エラーが名指しする唯一のファイルが、それを開く目的である問いに答えられなかったのである。そこで何を探すべきか。「nothing is listening on port 11443」の隣で、自分は起動済みだと言っているサービスは、落ちては再起動されているプロセスである。監視下のサービスは、起動した瞬間に落ちても、起動したコマンドからは起動済みとして報告されるからだ。4つのテストが両方の関数を実際に実行する。相手は、接続を拒否する `curl`、ポートを使っている `ss` と使っていない `ss`、そして「stopped」と答えて失敗を返す `rc-service` と `systemctl` である。

`fRollBack` はサービスをサブシェルの中で起動するが、その横の `|| true` だけでは足りない。サービスが立ち上がらないと `fStartServices` は `fDie` を呼び、`fDie` は `exit` を呼び、`exit` は横に何が書かれていてもシェルを終わらせる。実際の Alpine で計測したところ、`boa-web` が再起動を繰り返している間に OpenRC が `boa-proxy` を落とし、ロールバック自身による起動はサービスロックの競合に負け、インストーラーは `fRollBack` の中で終了した。ロールバックそのものは成功していた（以前のバージョンが戻って応答していた）。それなのに運用者に伝えられたのは「The boa-proxy service would not start」であり、更新がロールバックされたばかりだということには一言も触れていなかった。その時点で運用者の手元にあるのは、何が起きたかの説明だけなのである。

以前のバージョンは `fFinishUpdate` が削除する。それも、新しいバージョンが応答した後に限られる。

以前は `fRollBack` が実行されるのは 1か所だけだった。最後の `curl` が失敗したときである。`fStopServices` とその確認の間には、失敗しうる手順が十数個ある（証明書ファイルがなくなっている、HAProxy が解析できないプロキシ設定、インストールできないユニットなど）。そしてそのどれもが、サービスを止め、新しいコードを配置し、`webapp.previous` をディスクに残したまま、誰も元に戻さない状態にしていた。メッセージは何が失敗したかを挙げるだけで、マシンが止まっていることには何も触れなかった。そこで `fDoUpdate` はサービスを止める直前に `vUpdateSwitched` を立て、`fCleanup`（EXIT のトラップで、子プロセスがどのように終わっても実行される）は、そのフラグが立っていて終了コードが 0 でないとわかると、ロールバックする。切り替えから抜ける 2つの道筋がフラグを下ろす。1つは `fRollBack` 自身で、明示的な経路が 2回ロールバックしないようにするため。もう 1つは `fFinishUpdate` で、新しいバージョンが応答したら、もう戻るべきものはないからだ。秘密鍵を隠して両方のテストマシンで計測したところ、「Missing certificate files」、「Putting the previous version back」と表示され、すべてのサービスが起動し、ログインページは以前のコードで 200 を返した。あるテストは、各インストーラーの本物の `fCleanup`、`fRollBack`、`fFinishUpdate` を 3通りの終了で実行する。切り替えの後、切り替えの前、そして完了の後である。

`--install` と `--reinstall` には保持すべき以前のバージョンがないので、切り替えもロールバックもない。しかし検証は行う。以前は `fWriteCredentialsFile` で終わっており、実際の 2台のマシンで、Web サービスが 5秒ごとに再起動を繰り返しているのに「Installation finished」と表示された。アプリケーションに何かを尋ねたものが一度もなかったのである。今は同じログインページを要求し、それが返ってこなければそう伝えてログを名指しする。マシン上には戻るべきものが何もないからだ。

`pip` 自体もバージョンを固定している。バージョンなしの `--upgrade pip` では、同じコードの 2回の更新が異なる解決結果になりうる。それを防ぐために requirements を固定したのである。まだ固定されていないのは推移的な依存関係だ。そこで `pip freeze` を環境に記録し、次の更新で何が変わったかを表示する。誰かがそれに気づくには、それしか方法がない。

### 途中で止まったインストール

`fIsInstalled` は、`webapp/backend` と `boa` ユーザーが存在した時点で、そのマシンをインストール済みとみなしていた。それは仮想環境、証明書、データベース、管理者よりも前の段階である。ネットワークが切れて pip で止まったインストールは、その後 `--install` からは「already installed」と言われ、`--update` では欠けている何かのところで止まり、`--reinstall --yes` だけがそれを乗り越えられた。そしてそのことを運用者に伝えるものは何もなかった。

完了したインストールは今では `/opt/boa/installed` を残す。これは `fVerifyInstallation` がページを受け取った後にだけ `fMarkInstalled` が書く。配置済みでも応答しないインストールは完了しておらず、ロールバックした更新は新しいバージョンではないからだ。マーカーがない場合は、完了したインストールなら必ず持っている 5つのもの（コードとユーザー、`venv/bin/gunicorn`、`db/boa.sqlite`、`certificates/privkey.pem`）がその代わりになる。そのため、マーカーができる前のインストールもインストール済みとみなされ、次の更新でマーカーを受け取る。`--install` が行うほかのことはすべて、すでに 2回行っても安全である。ユーザーはなければ作成され、環境は古いものの隣に構築され、証明書はあればそのまま保持され、管理者は削除されてから新しいパスワードで書き直される。そのため、途中までのインストールは `--install` をもう一度実行すれば完了し、`--update` はそうしたインストールを見つけると、まさにそう伝える。ついでに、Debian のインストーラーでは `fGeneratePassword` を `fInstallDependencies` の後に移した。以前はその逆だった。Debian では `openssl` は Priority: optional であり、最小構成のイメージでは、パスワードを生成するパッケージがインストールされる前にパスワードを生成していたのである。

### インストーラーが実行するものはすべてログに届く

`fLog` は自分の行を `install.log` に書くだけで、ほかには何も書いていなかった。apt、pip、HAProxy の検証、その他のすべてのサブプロセスは端末に書いていたので、失敗したインストールのログには「Installing the dependencies.」とあるだけで、その理由を説明する apt のエラーは一言も残っていなかった。誰かがそのファイルを開くのは、まさにその詳細を探すためなのに、である。

`fStartCapturingOutput` は、このシェル自身の stdout と stderr を FIFO にリダイレクトし、`tee` がそれをログと端末にコピーする。FIFO を使い、`exec > >(tee ...)` は使わない。これは bash 専用であり、Alpine は bash なしで起動するからだ。また `fMain` を囲むパイプラインも使わない。それでは `fMain` がサブシェルの中に入ってしまい、errexit を生かしておくための `fMain & wait` の仕組みが台無しになるからだ。

結果として 2つのことが起き、どちらにも対処が必要だった。

`fLog` は行を echo し、さらに自分でログに追記していた。stdout がその同じファイルに追記する tee になると、2回目の書き込みは重複になる。90行のインストールが、すべての行が 2回ずつ入った 185行のログを生み出した。今の `fLog` は、キャプチャが動いていない間だけファイルに書く。

`tee` はログを inode で開いたまま保持する。`--reinstall` はログも含めてツリー全体を削除し、新しいコピーを配置し直す。そのため、その瞬間から `tee` は名前のない inode に追記していることになり、`fLog` がもうファイルに書かない以上、再インストールの後半すべて（生成されたパスワードも含む）がそこに消えてしまう。`fRestartCapturingOutput` は、キャプチャの向き先を、その時点で存在するファイルに付け替える。

### 2つのインストーラー、1つのアプリケーション

`deploy/install-update-reinstall-debian.sh` は systemd のユニットを書き込むので、**動いているマシンの PID 1 が systemd である必要がある**。それ以外で起動した Debian は対象外であり、インストーラーは何も起動しないマシンにインストールするのではなく、それを拒否する。`deploy/install-update-reinstall-alpine.sh` は `deploy/openrc/` から OpenRC のサービスを `/etc/init.d/` に書き込み、事前には何も必要としない。マシンに OpenRC がなければ、自分でインストールする。どちらも同じ 10のプロセス、`/opt/boa` の下の同じツリー、同じユーザーモデルをインストールする。あるテストが 2つを 1手順ずつ比較し、一方にだけ手順が増えると失敗する。

2つは同じ言語で書かれておらず、それは意図的である。Debian 用はここにあるほかのすべてと同じく bash だ。Alpine 用は `#!/bin/sh` の POSIX シェルである。まっさらな Alpine には bash がないからだ。`#!/bin/bash` にすると、カーネルは存在しないインタープリターを探すことになり、

    curl -fsSL <raw-url> | bash -s -- --install

は 1行も読まないうちに失敗する。それも、1行インストールを最も必要とするマシンで、である。POSIX であれば BusyBox ash でも dash でも bash でも同じように動くので、同じファイルを、素の Alpine では `sh` に、すでに bash がある Alpine では `bash` にパイプで渡して使える。それでもインストーラーは bash をインストールする（どのエージェントにも bash シェルが与えられる）。ただ、起動するのに bash を必要としなくなっただけだ。その代わりに失うのは、配列、`[[ ]]`、`${var//x/y}`、`<(...)` である。`local` は残している。3つのシェルすべてにあるからだ。`pipefail` は設定する前にサブシェルで使えるかを確かめる。dash にはないからである。あるテストはこれらの構文をそれぞれ拒否する。存在しないシェルの機能は、インストールのときに誰かほかの人のマシンで失敗するからだ。

Alpine には必要で Debian には必要ないもの、そしてそれぞれが省けない理由は次のとおりである。

| | 理由 |
|---|---|
| `shadow` | 特権デーモンは `useradd --home-dir --create-home --shell` を呼ぶ。BusyBox の `adduser` にはそのどのオプションもなく、エージェントを作成できなければアプリケーション全体が動かない |
| `bash` | すべてのエージェントに与えられるシェルであり、`bash.run` はこれを通して実行される。Alpine には最初から入っていない。Alpine のインストーラーが、このプロジェクトで唯一 bash ではなく POSIX シェルで書かれたファイルであるのもそのためだ。`#!/bin/bash` にすると、それを最も必要とするマシンで `curl ... \| sh` ができなくなる |
| `dcron` | デーモンが書く crontab を、何かが読まなければならない。下の `-d` の理由でもある |
| `gcc`、`musl-dev`、`libffi-dev`、`python3-dev` | いくつかの依存パッケージは musl 用の wheel を公開しておらず、インストール中にコンパイルされる |
| `libcap` | `direct` モードで haproxy のバイナリに `setcap cap_net_bind_service` を行うため。systemd はこれをサービスごとに `AmbientCapabilities` で与えていたが、OpenRC には相当するものがない |

移植でコードを変えなければならなかったことが 3つあり、どれもインストールしてみて見つかった。

- **エージェントに権限を落とすのではなく、`crontab -u <agent>` を使う。** Debian の `crontab` は setgid で、どのユーザーでも実行できる。Alpine の dcron はそれを `4750 root:wheel` で配布しているので、エージェントが実行すると `Permission denied` になる。以前の形を保つには、すべてのエージェントを `wheel`（たいていのシステムで sudo を意味するグループ）に入れるか、システムの setuid バイナリの制限を緩めるしかなかった。デーモンは root なので、代わりにユーザーを指定できる。
- **削除するときは `-r` か `-d`。** Vixie cron は `-r` で crontab を削除する。dcron は `-d` で削除し、`-r` には使い方のメッセージと終了コード 2 で応じる。`-r` だけを試していたので、削除したエージェントの crontab が、もう存在しないユーザーのランナーを指したまま残っていた。両方を試す。決め手になるのはディストリビューションの名前ではなく、インストールされているバイナリだからだ。
- **`browser.conf` の `executable=`。** Playwright は musl 用のビルドを公開していないので、Alpine ではパッケージを requirements から完全に外しており、ブラウザーはない。この行は `browser.fReadConfiguredExecutable` が読むもので、システムの Chromium を操作できる Playwright が登場した日に、その Chromium を指定する場所である。

もう 1つ、Alpine のテストマシンで `/proc/<pid>/fd/2` を見て見つかったことがある。`supervise-daemon` は、特に指定しなければプロセスの stdout と stderr を `/dev/null` に送り、Alpine にはそれを集めるものがほかに何もない。Debian のユニットには、そのために journald がある。すべてのサービスが、どこにも何も書いていなかった。今では各 OpenRC スクリプトが `output_log` と `error_log` を指定する。`/opt/boa/logs/` の下にサービスごとに 1ファイルで、`start_pre` で `boa` として作成する。そうすれば、誰が書き込んでも logrotate が `boa` としてローテーションできる。両方のインストーラーにある `fInstallLogRotation` は、それらのファイルと gunicorn の 2つのファイルのために `/etc/logrotate.d/boa` を書く。週 1回、8世代保持、`copytruncate`（どちらの書き手もファイルを開いたままにするため）で、`install.log` は決して対象にしない。それは root のもので、パスワードを含むからだ。同じ発見のもう半分はこうである。システムのタブは OpenRC に BusyBox の cron である `crond` について尋ねていたが、インストーラーはその代わりに `dcron` を動かしているので、正常な Alpine で cron が停止していると報告されていた。`fPickOpenRcCronService` は、2つのうちサービススクリプトがあるほうの最初のものについて尋ねる。

そしてインストーラーが修正するのではなく回避しているものが 2つある。Alpine の haproxy パッケージに属する問題だからだ。このパッケージには `/etc/haproxy/errors/` がなく、管理ソケット用の `/run/haproxy` もない。どちらの行も、そのファイルやディレクトリが存在しなければ設定から外す。これは管理者が実際にそれらを作成したマシンでも正しい動作である。最初は、`/run/haproxy` を作成し、起動のたびにそれを作り直すスクリプトを `/etc/local.d/` に置く方法を試した。しかし `local` は起動の最後に実行されるので、それが現れたときには haproxy はもう起動に失敗していた。

さらにもう 1つは OpenRC 自体に属する。OpenRC はサービスの依存関係ツリーをキャッシュし、`/etc/init.d` とタイムスタンプを比べて再構築するかどうかを決める。再インストールでは、サービススクリプトがキャッシュと同じ 1秒のうちに上書きされるので、OpenRC は古いツリーを使い続け、サービスはそこから漏れる。サービスはインストール中には起動する。`rc-service start` はツリーを必要としないからだ。そして再起動後には戻ってこない。`openrc default` はツリーを必要とするからだ。`fInstallServices` は無条件の `rc-update -u` で終わる。

### 各インストーラーがマシンに求めるものと、自分でインストールするもの

Debian のインストーラーは、systemd が PID 1 でない環境では実行を拒否する（`fRequireSystemd`。何かをインストールするより前に呼ばれる）。このインストーラーが用意するものは、10のユニット、マシンの HAProxy、cron と、どれも systemd が起動して動かし続けるものだ。そのため、そうしたマシンでは以前、インストールが完了し、成功を報告し、何も提供しない状態になっていた。`systemctl` はインストールされ、「System has not been booted with systemd as init system (PID 1). Can't operate.」と答え、その終了コードを読むものは何もなかった。今表示されるのは、それを直す方法である。`systemd systemd-sysv dbus` をインストールし、`/sbin/init` をコマンドにしてコンテナを作り直し、インストーラーをもう一度実行する。「再起動」ではなく「作り直す」と言うのは、動いているコンテナは PID 1 を変えられないからだ。

Alpine のインストーラーは OpenRC について逆の判断をする。そこで欠けている部品は、インストーラー自身が用意できるものだからだ。`openrc` はほかのパッケージと一緒にインストールされ（コンテナイメージには入っておらず、`setup-alpine` でインストールした Alpine には入っている）、続いて `fEnsureOpenRcUsable` が `/run/openrc/softlevel` を作成する。これは、自分が起動したのではないシステムでサービスに触れることを OpenRC が拒否するときに、OpenRC 自身が名前を挙げるファイルである。そうすれば、10のサービスはコンテナの中で起動する。ログには、サービスが自動では戻ってこないと書かれる。`/run` は tmpfs であり、PID 1 は OpenRC ではないからだ。

2つは矛盾していない。systemd は PID 1 以外では動かせないが、OpenRC は動かせるのである。

### `if ! fMain` はインストール全体で `set -e` を無効にする

どちらのインストーラーも、fMain を子プロセスとして起動して終わる。

    fMain "$@" &
    vMainPid=$!
    if ! wait "${vMainPid}"; then ...

`if ! fMain "$@"` で終わるのではない。見た目はそう読めるし、以前はそうなっていた。`if` の条件にあるコマンドは errexit が停止された状態で実行され、その停止は、そのコマンドが呼ぶすべての関数と、さらにそれらが呼ぶすべての関数に引き継がれる。それはつまりインストール全体である。systemd のないマシンで計測したところ、8つのコマンドが続けて失敗し、それぞれがエラーを表示したが、スクリプトはそのすべてを通り過ぎて「Installation finished」で終わった。子プロセスでは errexit が戻る。停止は fork を越えて生き残らないからだ。bash、dash、BusyBox ash はどれも、この文の前半と後半のどちらについても同じように振る舞い、関数の中での `set -e` もサブシェルも、それを取り戻すことはできない。

fMain を子プロセスで実行することの帰結は 2つある。1つは、`trap fCleanup EXIT` を fMain の中でもインストールすること。サブシェルは親の EXIT トラップを引き継がないので、そうしなければ `/tmp` の下にダウンロードしたツリーが毎回残ってしまう。もう 1つは、親が終了する前に自分のトラップを解除すること。そうしないと「Exited with code」の行が 2回表示される。

`fHasTty` も同じ系統の修正である。`[ -r /dev/tty ]` を調べるのではなく、`/dev/tty` を開いてまた閉じる。デバイスノードはどのシステムでもモード上は読めるので、pty のない `ssh host ./installer` でもあの判定は通り、続く `read` が ENXIO で終了していた。制御端末のないプロセスは、そもそもそれを開けないのである。

### 標準の haproxy.cfg は誰かの作品ではない

`fInstallMachineProxy` は `proxied` モードのとき `/etc/haproxy/haproxy.cfg` を置き換える。そして自分が書いたのではないファイルには、先に尋ねずに手を触れない。マシンのプロキシがほかのサイトも扱っているかもしれないからだ。落とし穴は、まっさらなマシンで見つかるそのファイルが haproxy パッケージによって置かれたものであり、そのパッケージは **このインストーラー自身が** 1分前に `fInstallDependencies` でインストールしたものだということである。

その見本を誰かの作品として扱ったことが、素の `--install` をすべてそこで止めていた原因だった。`--yes` もなく、答えるための端末もなく、実行はツリー、virtualenv、証明書をすでに構築した後で「Destructive operation with no terminal to confirm on」で終わった。Debian でも Alpine でも、4台のテストマシンすべてで、README に書かれているとおりの行を実行して計測した。

`fMachineProxyIsPristine` は推測する代わりにパッケージマネージャーに尋ねる。

- Debian: dpkg がその conffile について記録した md5（`dpkg-query -W -f '${Conffiles}'`）を、ファイル自体の md5 と比べる。
- Alpine: apk がそのファイルについて記録したハッシュを `/lib/apk/db/installed`（`R:haproxy.cfg` の下の `Z:` 行）から読み、ファイルの `openssl dgst` と比べる。`Q1` は base64 の sha1、`Q2` は sha256 である。

`apk audit --system` は Alpine での答えのように見えるが、そうではない。Alpine 3.24 で計測したところ、編集した `/etc/haproxy/haproxy.cfg` について **何も** 報告しなかった。この確認の最初のバージョンはそれを信じており、誰かのプロキシを尋ねずに置き換えていたはずだ。それこそ、確認の仕組みが防ぐために存在する唯一のことである。その後、パッケージのファイル、それに 1行加えたもの、このインストーラーが書くファイルでテストした。

手つかずなら、ログに 1行残して質問なしに置き換える。編集されていれば以前どおりの動作になる。`--update` では手を触れず、インストールや再インストールでは確認したうえで `.before-boa.<timestamp>` にバックアップする。

### ログとパスワードのための 1つのファイル

インストーラーが書くのは `/opt/boa/logs/install.log` だけである。何を行ったか、そしてその末尾に、生成した認証情報を書く。以前は /root に `app-web-install.log` と `app-web-credentials.txt` の 2つのファイルを書いていた。2か所にある 2つのファイルは、探すものが 2つあるということだ。`fMigrateInstallFiles` は古いファイルの中身を新しいファイルにコピーしてから、古いファイルを削除する。そこにあるパスワードが、誰かが持っている唯一の写しかもしれないからだ。

3つの細部がこれを支えている。

- `fLog` はディレクトリがなければ作成する。ログはインストーラーが構築しているツリーの中にあるので、最初のインストールでは最初の行を書く時点でまだ存在せず、`--reinstall` は途中でそれを削除する。
- `fRemoveInstallation` は `rm -rf /opt/boa` の前にログを脇へコピーし、後で元に戻す。そうすれば、再インストールが自分自身の記録まで持ち去ることはない。
- ファイルは、`boa` が 0750 で所有するディレクトリの中にある `root:root 0600` である。`boa` はそれを unlink できる（ディレクトリを所有するとはそういうことだ）が、中のパスワードは読めない。エージェントは `boa` グループに入っていないので、そのディレクトリにそもそも入れない。

ログインページは、`frontend/templates/login.html` で、そのパスを独立した 1行に `--colour-path` の色で表示する。パスは 15 の翻訳ファイルには入っていない。その上の文は翻訳されるが、パスはどこでも同じであり、文の途中で折り返されたパスは、誰かが打ち間違えるパスになるからだ。

### 円形のアプリケーションロゴ

`frontend/static/img/boa.svg` は青い円形のマークで、黒いスーツに白いシャツ、濃い色のネクタイを着けた 3体のロボットエージェントが腰から上で描かれている。頭部には明るい金属のパネル、機械の関節、青い目の濃い色のバイザーがある。スタイルはややイラスト風で、布地の質感はなめらかであり、中央のエージェントにポケットチーフはない。頭部は目に見えるロボットの首につながっており、大きい中央のエージェントが、小さい左右の 2体の前に立っている。陰影のあるこの絵は SVG に埋め込まれた 512px の WebP で、円形のクリップがかかり、円の外は透明である。人物は不透明のままで、どのテーマでも同じ見た目を保つ。これは SVG の器に入ったラスター画像であり、ベクターのパスではない。`favicon.svg` にも同じ絵が入っている。2つの SVG ファイルは同期させておくこと。ログイン、サイドバー、favicon の URL は、以前のマークのキャッシュされたコピーを更新させるために `v=robot-agents` を使う。表示サイズは引き続き、ログインページで 30px、サイドバーで 24px である。

### 画面は、誰かが別の言語を選ぶまで en-US で表示される

`fGetLanguage` は `localStorage` から選択を読み、何もなければ `en-US` を返す。以前は先に `navigator.languages` とネゴシエートしていたので、新しいインストールは、最初にそれを開いたブラウザーの言語で表示されていた。それはマシンの言語であって、判断ではない。選択はコントロール 1つで変えられ、ログインカードの隅と「設定」にあり、ブラウザーごとに記憶される。

同じファイルに 2つのバグがあり、どちらも「ログインフォームの言語が 2回変えないと変わらない」として現れていた。

- `fApplyTranslations` は、読み込んだファイルにそのキーがあるときだけ文字列を書いており、`textContent` はすでに前の言語で上書きされていた。そのため en-US（ファイルがなく、`dTranslations` は `{}`）に切り替えても何も変わらず、キーが 1つ欠けている言語に切り替えると、そのキーは前の言語のまま残った。今は、翻訳される各要素の元の文字列を、最初に翻訳する時点で `WeakMap` に保存しておき、翻訳のないキーではそれを元に戻す。
- `fSetLanguage` は選択を保存してから、引数なしで `fLoadTranslations()` を呼んでいた。この関数はストレージから選択を読み直す。プライベートウィンドウではストレージへの保存が例外を投げ、読み出しは前の言語を返し、ページはすでに表示していたものを読み込み直していた。今は渡された言語をそのまま渡す。

`fLoadTranslations` はシーケンス番号を持っている。続けざまに 2回変更しても順序が入れ替わって届き、誰も頼んでいない言語のページが残ることがないようにするためだ。そこには間違っていた点が 3つあり、どれも利用者が選んでいない言語を表示させていた。

- `lang` 属性を、ファイルを取得する前の冒頭で設定していた。そのため 404 や解析エラーがあると、新しい言語の名前の下に前の言語の文字列が画面に残った。`lang=fr-FR` なのにスペイン語のテキスト、という具合である。今は辞書が手に入るまで何も公開せず、`fPublish` が 2つを一緒に設定する。失敗とはまさに、その 2つがばらばらに設定されることだからだ。
- シーケンスを `await response.json()` の前に確認していた。前のリクエストの本文の到着が遅いと、後のリクエストが終わった後にそれが届いていた。今はすべての await の後で確認する。シーケンスはそのどれをまたいでも進みうるからだ。
- 失敗しても何も言わず、ページを不明な状態のままにしていた。今は en-US に戻り、`fOnLoadFailed` で報告する。

### en-US.json が原本であり、マークアップは代替である

ローダーは、マークアップがすでに en-US のテキストを持っていることを理由に、`en-US` を空の辞書へと短絡させていた。それは事実だが、そのせいで `en-US.json` は 500 のキーからなる無用の荷物になっていた。配布され、カタログとして一覧され、テストではほかの 13 と揃っているか確認されていたのに、何からも読まれていなかったのである。その中のタイプミスを直しても画面は何も変わらず、それを知るには試してみるしかなかった。

今はほかの言語と同じように取得する。マークアップのテキストは、もともと説明されていたとおりの代替として残る。カタログにないキーや、読み込めないカタログがあっても、空白だらけのページではなく読めるページが残る。変わったのは、2つのうちどちらが原本かという点である。

### 500 のキーがあっても、画面が翻訳されているとは限らない

目に見える文字列のうち 4種類はキーをまったく持っていなかったので、14 の言語すべてで英語のままだった。

| 対象 | 今の翻訳方法 |
|---|---|
| タブのタイトル | `<title>` に `data-i18n`。ページごとに 1つのキー |
| API 自身の失敗 | `code` とその `params` を送り、ブラウザーが `fDescribeApiError` で文を組み立てる。`error` は外部から来たもの（プロバイダーの言葉やメールサーバーの拒否）のために残す。そうしたものに翻訳をでっち上げるべきではない |
| テンプレートの説明 | カタログには入れない。各テンプレートの `agent.json` が 15 の言語で説明を持っており、サーバーが画面の求める言語のものを選ぶ（`agent_package.fPickDescription`） |
| テーマの配色と説明 | `theme.scheme.<scheme>` と `theme.desc.<id>`。取り決めは同じ。名前は翻訳しない。テーマは名前の付いた誰かのパレットであり、「Nord」を翻訳しても誰もそれを見つけやすくならない |

誰かが自分のインストールのために書いたテンプレートやテーマは、消えてしまうのではなく、自分の言葉を保つ。

ログインページの言語ドロップダウンは、言語名ではなくコード（`es-ES`、`en-US`）を一覧にする。それぞれの言語で書かれた 15 の名前を並べると、コントロールがカードと同じ幅になってしまった。コードなら 80px で済み、自分の言語を探す人がコードの一覧から最も早く見つけられるのもそれである。完全な名前は、余裕のある設定ページに残る。

### 右から左へ

ヘブライ語は右から左へ書かれる。ヘブライ語が入ったページを左から右へレイアウトしたら、誰にも読めないページになる。1つのスタイルシートで両方向をまかなうために、4つの決定をした。

**方向は言語とともに運ばれる。** `i18n.js` の `fPublish` は、`lang` と同じ段階で `<html>` の `dir` を `lRightToLeftLanguages` から設定する。そのため両者は食い違いようがない。この関数がもともと `lang` だけについて防ぐために存在する失敗である。グリッドとフレックスの行は `dir` に自然に従うので、サイドバーも、横に並べたものすべても、専用のルールなしで反転する。

**スタイルシートは、左と右ではなく、開始と終了で書く。** テキストの流れに関わるマージン、パディング、ボーダー、`inset`、`text-align` は、すべて論理プロパティ（`margin-inline-start`、`inset-inline-end`、`text-align: start`）である。`app.css` に残っている物理的な `left` は、エージェントのアバターの周りのリングだけで、これはテキストではなく図形である。

**内容は自分自身の方向を保つ。** コード、パス、コマンドは、どの言語でも左から右である（`code, pre { direction: ltr; unicode-bidi: isolate }`）。そのため、ヘブライ語の文の中にあるパスは並べ替えられない。チャットのメッセージと、描画された回答の各段落は、最初の文字から自分の方向を取る（`unicode-bidi: plaintext`）。ヘブライ語のページ上の英語の回答は左から右に、英語のページ上のヘブライ語の回答は右から左に読める。自由なテキストを書くテキストボックスも同じ規則に従い、空のボックスはページの方向に従うので、ヘブライ語ではヒントの文も右から左に読める（`dir="auto"` では、空のボックスはヒントも含めて左から右に配置されてしまう）。crontab とメールアドレスは `dir="ltr"` を持つ。

**左から右に読むものは、文の中で隔離される。** 双方向アルゴリズムは、中立文字が接している側のどちらかに寄せてしまう。そのため、ヘブライ語の文の末尾にあるパスは、スラッシュとピリオドを周りの単語に取られてしまっていた。"/tmp/x/007/." が ".tmp/x/007/ /" と表示されたのである。右から左へ書く言語では、`fPublish` が辞書を `fIsolateLeftToRightRuns` に通す。これは、すべての `{placeholder}` と、スラッシュを含むすべての連続部分を、U+2068 FIRST STRONG ISOLATE ... U+2069 POP DIRECTIONAL ISOLATE で囲むので、呼び出し側が文に入れた値は隔離の内側に収まる。「設定 → オペレーティングシステム」にマシンが報告する内容（`settings.js` の `fLeftToRight`）、API ドキュメントのルート（`.endpoint-path`）、crontab の例の行、タブや列に付く件数も、同じように左から右へ隔離される。これがないと、カーネルのバージョンが "deb13-amd64 · x86_64+6.12.111" と表示されていた。

### コードをダウンロードするブランチ

`cRepoBranch` は、リポジトリの本当のブランチである `main` だ。以前は `master` だった。それが動いていたのは、名前を変更した後も GitHub が古い名前をリダイレクトしてくれるからにすぎない。そのリダイレクトは、本物の `master` ブランチができた日に消え、`--repo-url file:///...` に対しては誰もリダイレクトしない。そして両方のインストーラーはその方法でテストされている。

### アプリケーションが独自の HAProxy を同梱する理由

マシンの HAProxy は `send-proxy-v2` で 11443 番ポートに転送するので、PROXY ヘッダーは TLS ハンドシェイクの **前に** 届く。Gunicorn はそこではそれを読めない。その `proxy_protocol` オプションは HTTP を解析する中でそのヘッダーを解析し、それは TLS が終端された後に行われる。そのため、ヘッダーのバイトがハンドシェイクに紛れ込み、`WRONG_VERSION_NUMBER` でハンドシェイクを壊してしまう。これはテストではなく、デプロイして見つかった。

HAProxy は 1つの bind で両方を受け付けられる（`accept-proxy ssl crt ...`）。そこでアプリケーションは独自のインスタンスを持ち込み、それがポートで待ち受ける唯一のコンポーネントでもある。Gunicorn は代わりに Unix ソケットに bind する。つまり、プロキシを通らずにアプリケーションに入る道はなく、本当のクライアントのアドレスは `X-Forwarded-For` として残る。これがなければ、ログインのレート制限には全員が 127.0.0.1 に見え、アドレスごとの制限ではなくなってしまう。

nginx ではなく HAProxy なのは、デプロイがすでに HAProxy に依存しているからだ。既存の技術で解決できる問題に、新しい技術は持ち込まない。

マシンの HAProxy は、このバックエンドに `option ssl-hello-chk` を使ってはならない。そのチェックの ClientHello は TLS 1.2 より古いので、TLS 1.2 を要求する bind に対しては失敗し、バックエンドを永久にダウンと判定してしまう。症状は、完全に正常に動いているサービスからの 503 である。アプリケーション自身のログには何もおかしいと書かれないので、知っておく価値がある。

そしてチェックは 11443 ではなく 11080 を叩かなければならない。TLS の bind に対する TCP チェックは、接続してハンドシェイクせずに切断し、この HAProxy はその 1つ 1つを「SSL handshake failure」として記録していた。Debian のテストマシンで計測したところ、2日で 64,075行、2秒に 1行で、ジャーナルにある本当の情報を埋もれさせていた。最初に `check-ssl verify none` を試したが、ある行が別の行に替わっただけだった。チェックの唐突な切断がハンドシェイクの完了途中に届き、どのチェックもそれか `ECONNRESET` を記録した。11080 に対してなら、同じ接続して切断する動作は空のセッションであり、`option dontlognull` がログから除外する。2つのポートは 1つのプロセスのものであり、ジャーナルは静かになった。サイトが外部から 200 を返している状態で、30秒間に 0行だった。

したがって、マシンの HAProxy のバックエンドは、全体で次のとおりである。

```
backend https-out
  mode tcp
  server srv-https-out 127.0.0.1:11443 check port 11080 send-proxy
```

`send-proxy` がクライアントのアドレスを運ぶ。`check-send-proxy` は意図的に外している。11080 は PROXY プロトコルを受け付けないからだ。これの運用者向けの説明は MANUAL.ja-JP.md の「マシンの HAProxy に必要な設定」にある。

`maxconn` を固定しないのは見落としではない。`maxconn 2048` はカーネルに 4131 のファイルディスクリプタを要求し、HAProxy はそれがなければ起動せずに終了する。*Cannot raise FD limit to 4131, current limit is 1024 and hard limit is 4096* というメッセージである。BPI-R3 上の OpenWrt で動く Alpine の LXC から報告されたもので、そのハードリミットは 4096 だった。`boa-proxy` は 70回も再起動され、11443 では何も待ち受けず、最初のインストールは「The application did not answer on port 11443 (last code: 000)」で終わった。両方のテストマシンはハードリミットが 524288 の Proxmox の LXC なので、どちらでもこれは一度も現れず、`haproxy -c` もそのどれでもファイルを受け入れていた。設定が不正だったことは一度もなく、プロセスが起動時に終了していたのである。`maxconn` がなければ、HAProxy は実際に持てるディスクリプタの数から自分の規模を決める。これは HAProxy 自身のメッセージが求めていることであり、制限が非常に大きい環境では `fd-hard-limit 4000` が取得する量に上限をかける。1つのバイナリを 3つのハードリミットで計測した。4096 では maxconn が 1987、1024 では 499、524288 では 1987 になる。あるテストは、配布するファイルで本物の haproxy をハードリミット 4096 の下で起動して動き続けることを求め、さらに古い `maxconn 2048` で起動し直して終了することを求める。ファイルを読むだけのテストだったことが、そもそもこれを見逃した原因である。

本当に root を必要とすることは 3つある。システムユーザーの作成、別のユーザーの crontab のインストール、別のユーザーとしてのプロセスの起動である。それ以外は必要としない。そこで root は、Unix ソケット越しに **閉じた動詞の語彙** を持つ 1つの小さなデーモンの中にだけ存在し、「このコマンドを実行せよ」を意味する動詞は意図的に用意していない。そのソケットに到達した攻撃者は、特権のないエージェントを作成することはできるが、root としてコードを実行することはできない。

ソケットは `0660 root:boa` であり、接続のたびに `SO_PEERCRED` を確認する。将来の更新の後でファイルのモードがどうなっていても、応答するのは root と `boa` だけになるようにするためだ。

### 変更はこのサイト自身のページから来なければならない

セッション cookie は `SameSite=Lax` であり、別のサイトからのリクエストがそれを運ぶことはない。しかし同じサイトの別のオリジンは締め出さない。`bash.run` を持つエージェントは、まさにこのホームの自分のポートでページを提供でき、チャットの返答にそこへのリンクがあれば、ワンクリックで開かれてしまう。そこにあるフォームが `/api/admin/agents/000/run` に POST すれば、それは同じサイトのリクエストであり、cookie が運ばれ、実行が始まる。本文のない単純な POST なので、プリフライトがそれを阻むこともない。そこで、API の blueprint の `before_request` である `fRefuseChangesFromElsewhere` が、このサイト自身のページから来たのではない POST、PUT、PATCH、DELETE に 403 で応える。`Origin` ヘッダーは、このホストとポートを正確に示していなければならず（`localhost` と `localhost:8080` は 2つの別のオリジンであり、後者はまさにエージェントが提供できるページだ）、`Sec-Fetch-Site` ヘッダーは `same-origin` でなければならない。どちらもないリクエストはブラウザーのものではなく、スクリプトかテストのものなので、以前どおりログインの判断に任せる。GET には関門を設けない。何も変更しないうえ、ほかから来たページは応答を読めない。それを許す CORS ヘッダーがないからだ。

### エージェントAPIと、そもそもそれが存在する理由

`boa` のものであり、エージェントに読まれてはならないものが 2つある。カンバンのデータベース（それに直接書き込めるエージェントは、ほかのエージェントの履歴を書き換えられてしまう）と、チャンネルの認証情報（ボットのトークンはメッセージではなく、送信する恒久的な権限である）だ。

そこでエージェントは、どのエージェントも開ける 2つ目の Unix ソケット越しに、`boa-agent-api` を通してその両方に到達する。認可は 2つの独立した確認からなる。

1. 提示されたトークンが、いずれかのエージェントのトークンについて保存された SHA-256 と一致すること。
2. `SO_PEERCRED` によれば、呼び出したプロセスが*その*エージェントのユーザーに属していること。

どちらか一方だけでは弱くなる。漏れたトークンも違うアカウントからでは役に立たず、正しいアカウントであってもトークンがなければ役に立たない。

HTTPS ではなく Unix ソケットなのは、1台のマシン上の 2つのプロセスの間で TLS を使っても得るものがないからだ。自己署名証明書を使えば、すべてのエージェントが検証を無効にして動くことになる。それは TLS がないよりも悪い。セキュリティがあるように見えてしまうからである。

### 状態の置き場所と、それを分けている理由

| 状態 | 場所 | そこにある理由 |
|---|---|---|
| エージェントの設定 | `agents/xxx/info.json` | エージェントが自分自身としてそれを読まなければならない |
| エージェントの履歴 | `agents/xxx/runs.jsonl` | エージェントが書き込める唯一の場所 |
| 共有の手順 | `skills/<Name>/SKILL.md`（root、0755） | 与えられたすべてのエージェントが読み、どのエージェントも書かない |
| エージェントの索引、ログイン、設定 | `db/boa.sqlite`（0700 `boa`） | Web プロセスがそれを必要とする |
| ボード | `kanban/kanban.sqlite`（0700 `boa`） | 同時に書き込むものが多い |

**`runs` や `usage` のテーブルは意図的に存在しない**。エージェントのプロセスは `boa` が所有するデータベースを開けず、そこへの書き込み権限を与えれば、どのエージェントもほかのエージェントの履歴を書き換えられてしまう。その代わり、各エージェントは自分のジャーナルに追記し、Web アプリケーションは `boa-exec` を通してそれを読む。副次的な利点は、Web アプリケーションが落ちていても、エージェントは自分が行ったことを記録し続けられることだ。

ボードが JSON ファイルのディレクトリではなく SQLite なのは、複数のエージェントが cron の同じ 1分に起きるのが普通のことであり、同時に行われた 2つの追加が互いを上書きしないようにできるのはトランザクションだけだからだ。

### バックアップに含まれるもの

`--backup` は、インストールを構成するもののうちコード以外のすべてを 1つのアーカイブに書き、`--restore` はマシンにあるものをそのアーカイブで置き換える。どちらも両方のインストーラーに、関数単位で同じものがある。一覧は上の表を `tar` の 1行にしたものだ。2つのデータベース、鍵とチャンネル、証明書、ホームと保護されたファイルを含むすべてのエージェント、スキル、ツールである。その周りに、`/opt/boa` を `tar` するだけでは間違えてしまうことが 3つある。

- **データベースは `cp` ではなく SQLite のバックアップ API を通す**（`fCopySqliteDatabase`）。どちらも WAL モードで動いているので、`.sqlite` ファイルのコピーには `-wal` ファイルにまだあるものが含まれず、書き込みの途中で取ったコピーは壊れているかもしれない。venv の `python3` にはそのモジュールがあり、`sqlite3` コマンドはどちらのディストリビューションにもない。同じ理由は復元のときには逆向きに働く。復元したファイルを読む前に古い `-wal` と `-shm` のファイルを削除する。そうしなければ、SQLite が古いログをそれに適用してしまう。
- **エージェントのユーザーは名前で運ぶ。** `agents.txt` に各エージェントのユーザー、uid、gid を記録し、`fRestoreAgentUsers` は欠けているユーザーを、名前は常に同じに、ID は空いていれば同じにして作成する。アーカイブ内の所有権は展開時に名前で対応づけられるので、新しいマシンで `boa` や `agent-001` の uid が違っていても、自分のファイルを所有し続ける。crontab は `/opt/boa` の下ではなく cron のスプールにあるので、`crontab -l` で読み出し、`crontab -u` で戻す。
- **3つのファイルは意図的に外す。** `config/ports.conf`、`config/browser.conf`、そしてそれらから生成される `haproxy.cfg` は「この」マシンを記述するものであり、復元で別のマシンの選択を持ち込んではならない。インストールのログは `install.log.backup` として運ぶ。名前を変えているのは、復元がその時点で書かれているログを上書きすることが決してないようにするためだ。その認証情報の行は現在のログに追記する。復元後のログインはバックアップのものだからである。

復元は、データを置き換え、元に戻せない唯一の操作なので、再インストールと同じように確認を求める。テストは両方の関数を本物のツリーに対して bash と dash で実行する。アーカイブについては何が含まれ何が外されているかを確認し、ツリーは復元が元に戻さなければならないあらゆるやり方で壊し、復元はファイルごとに確認する。

### スキルはプロンプトに索引として載り、必要なときに取得される

エージェントのメモリは、毎回のシステムプロンプトに丸ごと読み込まれる。そしてメモリにとってはそれが正しい。その文字数の上限はエージェントごとに設定でき（既定は 8,000、1,000～1,000,000 まで可能）、エージェントがもう一度調べ直せない唯一のものだからだ。

スキルはそうではない。手順は 1、2ページあり、エージェントには複数を与えることができ、たいていの実行はそのどれも必要としない。ディスクの点検に証明書の手順は要らない。メモリと同じように読み込めば、すべての実行のすべての呼び出しで、そのすべての分を払うことになる。そして `info.json` の上限はトークンで測られる。

そこでプロンプトには索引（スキルごとに 1行で、名前と説明）を載せ、本文は、それが必要だと判断したエージェントが `skill.read` で 1回取得する。5つのスキルの費用は、実行あたり 10000 トークンではなく約 200 トークンになり、読まれたスキルの分は呼び出しのたびではなく 1回だけ課金される。

したがって、ヘッダーにある説明こそが要となる部分である。エージェントはそれをもとに判断し、スキルが読まれるかどうかにかかわらず、すべての実行がその分を払うからだ。

### スキルはツールと同じく root のもの

ツールが root の所有なのは、アプリケーションがそれをコードとして import するからだ。スキルは何からも実行されないが、朝の 4時に誰にも見られずに起きるエージェントの推論の前に置かれる。そのため、スキルは `system-prompt.md` とまったく同じくらい慎重に扱うべきものであり、そのファイルはすでに、エージェントが読めても書けないディレクトリに置かれている。

だから Web の画面にスキルのエディターはなく、スキルを書くための特権動詞もない。スキルはサーバー上で SSH を使って書く。画面が決めるのはどのエージェントがどのスキルを受け取るかであり、それはツールについて行っていることと同じだ。

その判断のもう半分は置き場所である。`/opt/boa/skills/` は `webapp/` の外にある。`fDeploySourceCode` は `webapp` に対して `rm -rf` を行い、誰かがこのサーバーで書いた手順は、更新が削除してよいものではないからだ。`/opt/boa/tools/` と同じ理由で、ツリーの同じ位置にある。

アプリケーションはスキルを 1つも同梱しない。`backend/skills/` はなく、インストーラーはそのディレクトリに何もコピーしない。空で、root が所有する 0755 のディレクトリを作るだけである。スキルは「1つの」インストールのための手順（これらのホスト、このバックアップ、この証明書）なので、汎用的なスキルは誰も従わない手順になり、それを伝えるためにすべての実行のすべてのプロンプトで 1行を占めることになる。新規インストールでディレクトリが空なのは、機能が正しく働いているということであり、部品が欠けているのではない。


### `deploy/` はデプロイされない

`/opt/boa/webapp/` にあるのは `backend/` と `frontend/` だけである。`deploy/` ディレクトリ（ユニット、2つの HAProxy の設定、エージェントのテンプレート、プロバイダーのカタログ、`requirements.txt`、そしてインストーラー自体）はインストーラー自身の材料であり、インストーラーが `/tmp` にダウンロードしたばかりのツリーから読む。そのツリーはインストーラーが終了するときに捨てられる。

これは単に整理整頓のためではない。`/opt/boa` の下のコピーからユニットを読めば、たまたまディスクにあったバージョンのユニットをインストールすることになっていた。ダウンロードしたツリーから読めば、デプロイしているバージョンのユニットがインストールされる。筋道を立てて考えられるのは、その組み合わせだけである。そうした読み込みはどれも先に `fRequireSourceCode` を呼ぶので、ダウンロードより前に実行される手順があっても、`/deploy/...` からコピーするのではなく、説明の文を出して失敗する。

`gunicorn.conf.py` が `deploy/` ではなく `backend/web/` にあるのもそのためである。gunicorn は起動のたびにそれを読むので、実際にサーバー上にあるファイルでなければならず、サーバー上にあるディレクトリとは、それが設定するコードを収めたディレクトリなのだ。

デプロイされるものは `root:root` で、ディレクトリは `00755`、ファイルは `0644` であり、それを設定するのは `fSetCodeModes` だけである。`webapp/` の下にあるものはパスで実行されることがない。デーモンはランナーを `venv/bin/python3 .../runner.py` として実行し、各エージェントのために書く crontab も同様である。そのため、そこにあるファイルに実行ビットは要らない。それでも、これが 1つの関数になるまでは実行ビットが付いていた。`fDeploySourceCode` が `0644` を設定し、更新時にその後で実行される `fCreateDirectoryTree` が同じツリーに `chmod -R 00755` を行っていたからだ。

### Telegram には HTML を送り、だめなら言葉だけを送る

モデルは Markdown を書く。そのまま表示すれば、文の途中にアスタリスクの付いた `**25G free**` になる。これまでスマートフォンに届いていたのはそれだった。

Telegram が描画するのは HTML の小さなサブセット（14 のタグ、属性と呼べるほどのものはなく、見出しもリストも表もない）である。そこで `telegram_html` は、対応するタグがあるものは変換し、ないものには読みやすい形を見つける。見出しは独立した行の太字に、リストの項目には行頭記号を付け、表は空白で揃えた `<pre>` ブロックにする。スマートフォンで列を縦に揃えておく方法はそれしかない。

そのうち 2つの点が要である。

**エスケープが最初に来る。** `&`、`<`、`>` は Telegram にとってマークアップなので、`grep <dev> && echo` と報告するエージェントは、Telegram が 400 で応えるメッセージを作ってしまう。つまり、決して届かないメッセージである。すべてのテキストは、何かで囲まれる前に `fEscape` を通る。href は `fEscapeAttribute` を通り、これはダブルクォートもエスケープする。ダブルクォートを含む URL は属性を閉じてしまい、URL の残りを誰も書いていない属性に変えてしまうからだ。

**拒否されたメッセージはプレーンテキストで送り直す。** 描画で何を間違えたにせよ、言葉は書式より価値がある。そこで 400 は `parse_mode` なしで再試行し、その行は書式なしで送られる。フォールバックは Telegram が言ったことをログに残す。黙って劣化し続ける書式は、誰も直さない書式だからだ。

**Telegram が拒否した返答は捨て、受け取れない返答は 1時間保持する。** `fSay` が返すのは 2つではなく 3つである。送信済み、応答なし、そして拒否（429 以外の 4xx、`ChannelRejected`）だ。拒否とは、Telegram がこのメッセージにノーと言い、明日もそうだということである。ボットがブロックされた、チャットがなくなった、トークンが取り消された、といった場合だ。`fDeliverAnswers` は以前、どんな失敗でもその行を保持して次の周回で再試行しており、その行は再起動で返答を失わないようにディスクにある。そのため、ブロックされたボットはリスナーを終わりのないループに変えていた。高速モードのポーリング、root デーモン経由のチャットの読み込み、そして周回ごとに最大 2回の Telegram へのリクエストが、再起動をまたいで続いたのである。拒否された返答は、そう伝える行を残してただちに捨てる。実行に与えられる 1時間のうちに Telegram が受け取らなかった返答も捨てる。もう一方の分岐が、終わらなかった実行をあきらめるのと同じ理由である。どちらも返答を失うわけではない。返答は Web の画面のエージェントの会話にあり、最初にそこへ書かれているからだ。

パターンは `frontend/static/js/markdown.js` が使うものと同じである。何を Markdown とみなすかについて 2つのレンダラーの意見が分かれれば、1つの返答が、表示される 2つの場所で違って読めることになる。両方に送る意味は、それが同じ会話だということにある。


### Discord はポーリングし、返答は 2,000 文字

Discord は、人がエージェントに返事をするための 2つ目のチャンネルであり、受信を担う半分は `discord_listener`、つまり 7番目のサービスである `boa-channel-discord` だ。Telegram のものとは 4つの点で異なる。

**REST でポーリングする。** `GET /channels/<id>/messages?after=<id>` を 5秒ごとに、エージェントが返答の途中であれば 2秒ごとに行う。Gateway が当然の代替案だが、採用しなかった。それはハートビート、再開プロトコル、そしてこのプロジェクトにはない依存関係を必要とする WebSocket であり、さらに開発者ポータルで Message Content Intent をオンにする必要がある。オンにしなければ、すべてのメッセージが `content` が空の状態で届き、その理由は何も示されない。ポーリングは外向きに接続するので、Telegram のロングポーリングとまったく同じく、何もポートフォワードせずに LAN 上で動かせる。その代償は秒単位の遅延と、1秒あたり 50 という制限に対して 1分あたり 12 のリクエストである。

**4,000 文字ではなく 2,000 文字。** `channels.cMaxMessageLength` は Telegram の上限である 4096 だが、Discord は 2000 より長い `content` に 400 で応える。長い返答は短くなって届いたのではなく、届かなかったのである。`discord_markdown` は返答を行の間で最大 4つのメッセージに分割し、分割位置がコードブロックの中に入った場合は、前のメッセージの末尾でそのブロックを閉じ、次のメッセージの先頭で開き直す。そうしなければ、一方はプレーンテキストとして、もう一方は終わらないブロックとして届き、Discord ではそれ以降に言われたことがすべてそのブロックに飲み込まれてしまう。どの部分もそのエージェントのものとして記録する。人は、自分の画面に表示されている部分に返信するからだ。

**ボタンはなく、コマンドには `!` を使う。** ボタンを押すこともスラッシュコマンドも、どちらも*インタラクション*であり、インタラクションは Gateway か、Discord が到達できる HTTPS エンドポイントを通して届く。ポーリングするチャンネルにはどちらも見えない。そこで `/agents` は普通のメッセージである `!agents` になり、エージェントの一覧はボタンの列ではなく、入力するための名前の一覧になる。`/agents` も受け付ける。Telegram のボットを設定した人は、癖でそれを入力するからだ。

**エージェントの返答は誰にもメンションしない。** これが送るすべてのメッセージは `allowed_mentions: {"parse": []}` を伴うので、モデルが書いた `@everyone` は、サーバー全体への通知ではなくテキストになる。`replied_user` はオンのままである。返答は、尋ねた人には届くべきだからだ。これはプロンプトではなくソケットでの規則である。メール転送の宛先一覧がそうであるのと同じ理由による。

Discord にないのは、Telegram の見知らぬ相手に対する沈黙である。比べるべき `chat_id` がない。ボットは 1つのチャンネルを指定されてそのチャンネルを読むので、エージェントと話せるのは、そのチャンネルに書き込める人である。プライベートチャンネルが、`fIsFromTheConfiguredChat` がコードで強制していることに合う設定であり、マニュアルでもそれを挙げている。それが認可のすべてだからだ。

このチャンネルに以前からあった Webhook は今もあり、今も送信する。Webhook は読めず、返信できず、メッセージ ID も返ってこないので、Webhook での `listen` は提供せずに拒否する。何もしないスイッチは、スイッチがないより悪い。

### 1つのルーティングと 2つのリスナー

`agent_routing` には、両方のリスナーがまったく同じように行うことがまとめてある。どのエージェントが存在するか、`@News Miner`、`/news_miner`、`@002` から名前を読み取ること（最も長く一致したものが勝つ）、エージェントがターンを閉じるために言ったこと、そして状態報告である。プロトコルはそれぞれのリスナーに残っている。ロングポーリングは REST のポーリングではなく、インラインキーボードは名前の一覧ではなく、返信は一方では `reply_to_message`、もう一方では `message_reference` である。

これは 2つ目のリスナーと同時に書かれ、その理由は状態報告にある。その答えのコピーが 2つあれば、「動いているか」への答えが 2つになり、両者がまず食い違うのはサービスがいくつあるかという点だろう。

送信はそこに入っていない。各リスナーに `fSay` として残っている。そのおかげで、テストは一方のリスナーの `fSay` を差し替え、もう一方には手を付けずにおける。

### ブラウザーは 1つで共有し、プロファイルは共有しない

`web.fetch` は公開ページを読んでそこで止まる。セッションもフォームもボタンもない。ブラウザーはそれとは別物で、2つに分かれる。

| | 場所 | 所有者 |
|---|---|---|
| ブラウザー | `/opt/boa/playwright/` | root、0755、1つのコピー |
| プロファイル | `agents/xxx/browser/profile/` | エージェント、0700、エージェントごとに 1つ |

バイナリを共有するのは、それがバイナリであり、隔離すべきものが何もないからだ。エージェントごとにコピーすれば、それぞれ 600 MB になり、更新も N 回行うことになる。プロファイルは共有しない。cookie を保持しているからだ。エージェント 007 が何かにログインしたからといって、エージェント 008 がログインした状態になってはならない。その分離はカーネルによるもので、エージェントのほかのすべてがある 0700 のホームと同じである。そしてそれこそ、すべてのエージェントが 1台のマシンと 1組のセッションを共有するホスティング型のエージェント製品には提供できないものだ。

3つの判断がそこから導かれる。

**ブラウザーは、1回の実行の中ではツール呼び出しをまたいで開いたままにする。** `browser.click` は `browser.open` が画面に残したものに対して働き、実行は最初のツール呼び出しから最後まで 1つのプロセスなので、必要な状態はモジュールレベルのハンドル 1つで足りる。`atexit` がそれを閉じる。そうしなければ、1時間ごとに動くエージェントは実行のたびに Chromium を残し、朝までにマシンをいっぱいにしてしまう。

**Playwright は関数の中で import し、決してモジュールのスコープでは import しない。** ブラウザーのツールは、ブラウザーがインストールされているかどうかにかかわらず画面に一覧表示され、冒頭で ImportError が起きると、どこにも説明のないまま、その一覧からツールが消えてしまう。遅れて import すれば、ブラウザーがないことは、どのコマンドを実行すべきかを伝える文になる。

**ヘッドレスで、公開アドレスのみ。** 必要なのはセッションと DOM であり、ウィンドウの画像ではない。そのため、仮想ディスプレイは何の役にも立たない可動部品になるだけだ。

「公開アドレスのみ」は、各ツールではなく、コンテキストにインストールしたルートハンドラー（`browser.fInstallNetworkPolicy`）が強制する。`browser.open` で URL を確認しても、実行ごとにちょうど 1つのアドレスしか対象にならなかった。ページはリダイレクトしてかまわないし、エージェントが読むように言われたページには `127.0.0.1` を指すリンク、iframe、画像、フォームがあってかまわない。そして `browser.click` には確認がまったくなかった。コンテキストに置けば、ナビゲーション、リダイレクト、クリック、送信、そしてすべてのサブリソースを対象にでき、誰かが書く 6つ目のブラウザーツールも、その存在を知らないまま恩恵を受ける。拒否したものはツールの応答で名前を挙げる。そうしなければブロックされたリクエストは目に見えないからだ。ページはそれなしで描画され、エージェントは再試行に予算を費やしてしまう。

ホスト名は実行ごとに 1回だけ解決して記憶する。これにより、ある名前が確認のときには公開アドレスに、接続のときにはプライベートアドレスに解決されうる隙は、なくなるわけではないが限定される。その隙を閉じるには、確認したアドレスに接続を固定する必要があり、Chromium はここからそれを行う手段を公開していない。

セッション cookie は、ほかのどのブラウザーとも同じく、このブラウザーでも閉じたときに消える。残るのは、サイトが残すように指定したものである。

### プロバイダーが受け付けるものは、標準が言うものとは違う

2つのアダプターが、プロバイダーの拒否するものを送っていた。どちらの場合も結果は同じだった。そのプロバイダーを通したすべてのツール呼び出しが、どのモデルでも失敗した。そしてテストスイートは何も気づかなかった。スイートが試していたのは部品であって、往復全体ではなかったからだ。

| プロバイダー | 送ったもの | 返ってきたもの |
|---|---|---|
| Ollama | 何もないところまでデコードし直された `kanban__list_cards` | レジストリが、エージェントに許可されていないツールとして拒否した。それは直前に提示されたばかりの名前だった |
| Google | `"additionalProperties": false`。正しい JSON Schema である | `400 - Unknown name "additionalProperties" at 'tools[0].function_declarations[0].parameters'` |

Gemini の `function_declarations[].parameters` は JSON Schema のサブセットであり、知らないものを無視するのではなく拒否する。そこで `fCleanSchemaForGoogle` が、許可リストを使ってスキーマを再帰的にフィルターする。拒否リストではなく許可リストなのは、ここにある許可リストがすべてそうである理由と同じだ。そうしなければ、誰かがツールのスキーマに次に追加するキーは、取り除くものの一覧にそれを加えることを誰かが覚えていたかどうかにかかわらず、Gemini に拒否されてしまう。

どちらも、サイクル全体（尋ねる、ツールを呼ぶ、その呼び出しに答える）を本物の API に本物の鍵で実行して見つかった。`_/temp/probe-defaults.py` がその確認であり、この種のバグを見つけられるのはそれだけである。正しいスキーマ、正しい名前、そしてそれを受け付けないプロバイダー、という種類のバグだ。

### プロバイダーごとに 1つのアダプターファイル

25 のプロバイダーに 25 のファイルがある。大半が同じ方言を話すにもかかわらず、である。単一の「OpenAI 互換」アダプターは、それらのプロバイダーのどれかがフィールド名を変えるまではすっきりして見えるが、そうなれば、ほかの 20 を壊さずに修正しなければならない。各ファイルは自分のプロバイダーの癖を持っている。DeepSeek はランナーが再送する前に `reasoning_content` を落とし、llama.cpp はツールに対応していないチャットテンプレートを検出し、vLLM は 404 を自分が実際に提供しているモデルの一覧に変え、Cloudflare は認証情報から自分のアドレスを組み立てる。

共有しているのは `base.py` である。これは chat/completions を手本にした中立的なメッセージの形で、それを手本にしたのは、大半のプロバイダーがすでにその形を話しているからだ。Anthropic のアダプターはそれをコンテンツブロックに変換する。

`openai_dialect.py` も共有しており、それと共有アダプターとの違いこそが肝心な点だ。方言モジュールが持つのはリクエストそのもの（POST、名前を挙げる価値のある HTTP エラー、応答の解析）であり、それはどのプロバイダーの癖でもない。癖はそれぞれのファイルに残り、モジュールが読むクラス属性として宣言される。

| 属性 | 何を決めるか |
|---|---|
| `cDisplayName` | すべてのエラーメッセージに出る名前。「zai request failed」では、誰もそれで検索しようとは思わない |
| `cMaxTokensField` | プロバイダーがどちらの綴りに従ったかによって、`max_tokens` か `max_completion_tokens` |
| `cToolChoiceMode` | `auto`、`any`、またはそのフィールドを拒否するプロバイダーのための `omit`。エージェントに必要なのは `auto` である。毎ターン、ツールを呼ぶことを強制されたモデルは、実行を決して終えられない |
| `cChatCompletionsPath` | ベース URL の後のパス。通常のものを使わない少数のプロバイダーのため |
| `cAssistantContentWhenEmpty` | スキーマが null を拒否するプロバイダーのために、null の `content` の代わりに送るもの |

### 22 の本物の鍵が変えたこと

ここにあるどのプロバイダーも、本物の鍵で呼び出し、質問をし、ツールを与え、そしてプロバイダー自身が行ったツール呼び出しへの答えを渡した。鍵を持つ 22 のプロバイダーはすべて、その往復を完了する。7つのことは 2段階目（決まった応答を返すテストでは決して到達しない段階）でしか現れなかった。そしてそのそれぞれが今では、プロバイダー自身の言葉を横に添えた 1行のコードになっている。

- **Perplexity はエンドポイントを廃止していた。** `chat/completions` は 403「Sonar is now the Agent API. Use /v1/responses instead of /v1/sonar」で応える。そこでそのアダプターは Responses API に対して書き直され、プロバイダーは 1つのモデルから、48 のモデルを振り分けるルーターに変わった。

- **エラーメッセージの中の鍵。** Gemini は `?key=...` として呼び出されていたので、そこからの 503 は、利用者が読むエラーとジャーナルが保存するエラーに鍵を丸ごと入れていた。鍵は `x-goog-api-key` ヘッダーに移し、さらに `base.fRedactCredentials` が、どのアダプターが生成するどのエラーからも `key=`、`api_key=`、`access_token=`、`token=` を取り除くようになった。この種の失敗が、1つのアダプターが覚えているかどうかに左右されてはならないからだ。
- **Gemini 3 は思考の署名を返してほしがる。** 発行した署名を付けずに関数呼び出しが返ってくる会話は、即座に拒否される。そのため、どの Gemini のエージェントも、ツールを使った瞬間に失敗していた。`ToolCall.dProviderData` がそれを行きも帰りも運び、ほかのすべてにとっては中身の見えないものとして扱う。
- **Cloudflare は null の `content` を拒否する。** それはまさに、モデルが言葉なしにツール呼び出しで答えたときのアシスタントメッセージの中身である。Cloudflare には `""` を送る。方言モジュールはほかのすべてには null を送り続ける。方言が定めているのは null だからだ。
- **返信の中に書かれた推論。** MiniMax はテキスト自体の中に `<think>...</think>` を入れて答える。これは 1つのアダプターではなく方言モジュールで取り除く。そうするのはモデルなので、ゲートウェイの向こうにある同じモデルもそうするからだ。そして取り除くのは返信がそのタグで始まるときだけである。そうすれば、HTML について書くモデルの言葉は残る。
- **Together はチャンネル名を先頭に残す。** gpt-oss はチャンネルで書き、Together は「finalThe weather in Madrid」を返す。同じモデルを提供している Groq と Cerebras はそうしない。1つのプロバイダーの癖が属する場所である `together.py` で取り除く。
- **プロバイダーが提供しようとしない 4つの既定モデル。** Fireworks の 20b は専用のデプロイを必要とし、Together のものはサーバーレスではなく、Moonshot は kimi-k2.5 を廃止し、gemini-3.7-flash は 503「experiencing high demand」で応える。最初の実行で失敗する既定値は、1バージョン古い既定値よりも悪い。

5つのアダプターはそれをまったく使わない。その API がそれではないからだ。Anthropic のコンテンツブロック、Google の `generateContent`、llama.cpp の `/completion`、Cohere の v2 chat（同じメッセージを受け取るが、ブロックに入ったテキスト、独自の大文字の終了理由、`usage.tokens` の下に入れ子になったトークン数で答える）、そして Perplexity である。Perplexity は chat/completions を完全に廃止し、それに次のように答える。

    403 Sonar is now the Agent API. Use /v1/responses instead of /v1/sonar

そのため、そのアダプターは Responses API を話す。`messages` の代わりに 1つの `input` リストを使い、システムプロンプトは `instructions` として送り、返信は choice としてではなく、出力項目（ブロックに入ったテキストを持つ `message`、または `function_call`）として届く。ツールの結果は独立した項目 `function_call_output` として返し、`call_id` で対応づける。

2つの名前は、ほかの何かがそれを見る前に `factory.dProviderAliases` で解決される。`gemini` は Google のドキュメントがその API を呼ぶ名前であり、`google` は最初のバージョンからすべてのエージェントの `info.json` に書かれてきた名前である。そこで両方が同じアダプターに届き、保存されるのは常にそのうちの一方だけである。

25 のうちどれをエージェントに設定できるかは、ブラウザーではなく `fListProviders` が決める。プロバイダーは、自前ホストであるか、その鍵が保存されていれば `selectable` になる。これは提示する価値のあるものを絞り込むフィルターであって、規則ではない。鍵はエージェント自身のホームにも置け、そこは Web アプリケーションからは見えない。そのため画面は、エージェントにすでに設定されているプロバイダーを引き続き表示する。

その同じフラグが、画面のあることを 1つ決める。主モデルと予備モデルの両方にある **ベースURL** の欄は、自前ホストのプロバイダーでは表示され、クラウドのプロバイダーでは隠される。`base.fInit` はすでにアダプターの `cDefaultBaseUrl` にフォールバックするので、クラウドのプロバイダーでは、この欄は尋ねる前に答えの出ている質問をしていた。そして既定値が与えない答えで、この欄が受け取れるのは間違った答えだけだった。欄は隠すが、中身は空にしない。クラウドのプロバイダーの前にプロキシを置くインストールではそのアドレスが保存されており、欄を隠すことは、中にあるものを捨てる理由にはならない。

`base.py` がそのすべてから隠していることが 1つある。ツールの名前である。このプロジェクトはツールを `family.action` と呼ぶ。プロバイダーは関数の名前を `^[a-zA-Z0-9_-]+$` で検証し、ドットがあるとリクエスト全体を拒否し、どのフィールドが間違っていたかの手がかりも示さない。`fToolNameToWire` は送り出すときにドットを `__` に置き換え、`fToolNameFromWire` は受け取るときに元に戻す。これはすべてのアダプターで行われるので、レジストリ、画面、`info.json`、ログがエンコードされた形を目にすることはない。

### 信頼ではなく上限

どの実行も、4つの上限（トークン、ステップ、秒数、1日あたりの実行回数）のうち最初に到達したもので止まる。上限があるのは、有料 API の上で誰も見ていないループは白紙の請求書であり、自前ホストのモデルでは二度と戻ってこない GPU だからだ。各リクエストの `max_tokens` は、その実行がすでに使った分だけ小さくなるので、実行が最後の高価な 1回の呼び出しで予算を超えることはない。

上限とただの目安との違いを生むものが 4つあり、どれも修正されるまでは目安のほうだった。

  - **トークン要求に下限を設けない。** `max(512, remaining)` は予算を使い切っていても 512 トークンを要求していたので、残り 1トークンのエージェントでも、まだ半ページ分を許されていた。
  - **各呼び出しには、実行全体のタイムアウトではなく「残っている」時間を与える。** 今は `fSendMessages` を実装する 26 のアダプターに引数を追加するのではなく、アダプター自身の `vTimeoutSeconds` を呼び出しのたびに調整する。
  - **期限は、ステップごとに 1回ではなく、ツールごとにその前に確認する。** 以前は、期限の直前に届いた 6つのツール呼び出しの一括処理がすべて実行され、すでに終わっているはずの実行の上に、それぞれのタイムアウトが積み重なっていた。
  - **単調増加する時計。** `time.time()` は NTP が時刻を補正すると動き、「未来」に始まった実行は、そもそもタイムアウトに達しない。

まだ制限されていないのはプロンプトである。呼び出しは入力と出力の両方を消費するが、ここで上限をかけているのは出力だけなので、長い会話は入力の段階で超過する。それを数えるには、呼び出しのたびに各プロバイダー独自のトークナイザーを会話に対して実行しなければならない。上限に達した後の締めくくりの返答も、意図的に予算を超えており、それが書かれている場所にそう明記してある。

### 1つのエージェントの実行は一度に 1つ

ロックは 2つある。呼び出し元が 2種類あるからだ。

デーモンは、「このエージェントは実行中か」と「プロセスを起動する」の間、エージェントごとに `threading.Lock` を保持する。デーモンはすべてのリクエストをそれぞれのスレッドで処理するので、`only_if_idle` 付きの 2つの `run_now` 呼び出しは、1つのプロセスの 2つのスレッドであり、その間には何もなかった。そして /proc を走査しても、まだ fork されていないプロセスは見えない。計測結果は、2つの同時呼び出しで 2つの実行だった。

ランナーは `<home>/run.lock` に `flock` をかけ、プロセスが続く間それを保持する。こちらが決定権を持つ。crontab はランナーを直接起動し、デーモンを決して経由しないからだ。これは権限の境界ではない（`bash.run` を持つエージェントは何でも好きなものを起動できる）。これが存在するのは、「アプリケーション」が同じエージェントを 2回起動し、1つのブラウザープロファイルと 1つの会話に 2つの予算を費やすことがないようにするためである。

### 始まらなかった実行は、そう伝える

特権デーモンは、stdin、stdout、stderr を `/dev/null` にしてランナーを起動する。そのため `fLogLine` が書くものはすべてどこにも届かず、以前は 2つの失敗が完全にその出力の中だけにあった。

- 実行ロックが保持されていたので、この実行は行われない。
- `fExecute` が `run_started` を書く前に何かが失敗した。読めない `info.json`、あるいは APIキーが設定されていないプロバイダーである。2つのうち、後者のほうがはるかに起こりやすい。

実際のインストールで計測したところ、ロックが保持された状態で `POST /agents/001/run` は `202 {"started": true}` と答え、ジャーナルにも `journalctl` にも、どのファイルにも何も現れなかった。cron の下での同じ失敗は目に見えていた。cron は自分が起動したものの出力を保持するからだ。この問題がこれほど長く残っていたのはそのためである。穴があったのは、画面が使う経路だけだった。

今は `fRecordRunRefused` が、それを代わりにジャーナルに書く。状態が `refused` で `run_id` のない終了としてである。その形のどの部分にも意味がある。

| 部分 | 理由 |
|---|---|
| `kind: run_finished` | 「履歴」は終了を描画する。独自の種類にすれば画面がそれを覚える必要があり、何も描画しない項目は、項目がないのと同じである |
| `status: refused` | `failed_runs` は状態が `failed` の終了を数える。エージェントの何も実行されていないので、エージェントの何も失敗していない |
| `run_started` なし | `runs` と `max_runs_per_day` は開始を数える。保持されたロックが、行われなかった実行のためにその日の実行回数を 1つ食いつぶしてはならない |
| `run_id: ""` | 何も始まっていないので、識別すべき実行がない |

これは、ほかの何もそれを書かなかったときにだけ書く。`fExecute` が実行 ID を持った時点で、すでに `run_started` は書かれており、`fExecute` 自身のハンドラーが例外を再送出する前に対応する `run_finished` を書く。そのため `fMain` は、1つの実行に 2つ目の終了を加える前に `vRun.vRunId` を確認する。同じ確認が、誰がチャットのターンを閉じるかも決める。`fExecute` のハンドラーは終了を記録するときにターンを閉じ、`fMain` はそこまで到達しなかった実行の場合にだけターンを閉じる。こうなる前に Debian のテストマシンで計測したところ、プロバイダーに到達できなかった実行はどれも、同じ文で質問に 2回答えていた。

### 履歴には最新のものが表示される（以前はそうではなかった）

`fReadEntries` はジャーナルを古い順に返し（自身の docstring にそう書いてある）、`fRenderRunHistory` はそこから `.slice(0, cShownRuns)` を取っていた。それは最も「古い」10 の実行である。10 を超える実行を経たエージェントの「履歴」は、二度と変わらなかった。

本物のブラウザーで本物のアプリケーションを操作して見つかった。見つけるにはそれしか方法がなかった。このプロジェクトにある `dashboard.js` のほかのテストはどれもファイルを読んでその中の文字列を探すだけで、その文字列はそこにあったからだ。実際のインストールで 3つの言語で計測したところ、直近の実行が APIキーがないために拒否されたばかりのエージェントが、40分前のプロバイダーの失敗を表示しており、拒否のほうはまったく現れなかった。

`.slice(-cShownRuns).reverse()`。最後の 10 件を、最新のものを一番上にして表示する。一覧の上の見出しが言っているのはそういうことだ。

その一覧の上にある要約の表には、独自の欠陥が 2つあり、どちらも同じスクリーンショットで見つかった。`last_status` をそのまま表示していたので、スペイン語のページには「Último estado: refused」とあり、`last_run_at` をそのまま表示していたので、整形済みのタイムスタンプの一覧の真上に、生の `2026-09-19T03:44:29Z` が置かれていた。今はどちらも、その下の行がすでに使っていた処理を通している。

### メールボックスは、誰でも書き込める唯一の入力である

4つの `mail.*` ツールは、チャンネルとまったく同じやり方に従う。エージェントは何をしてほしいかを指定し、エージェントAPI（`boa` として動き、認証情報を保持している）がそれを行う。メールボックスのパスワードを読めるエージェントは、「受信箱へのアクセス」を持つのではない。アカウントそのもの、その中のすべてのメッセージを永久に持ち、さらに所有者として送信する能力まで持つことになる。

メールで異なるのは、入力が伝わる方向である。メールボックスを読むエージェントとは、その指示の一部が、世界中の誰でも書けるメッセージの中に入って届くエージェントのことだ。そこから 3つの判断が導かれる。

  - **転送は、利用者が一覧に挙げたアドレスにだけ許可する**。その一覧は、プロンプトの中ではなく `mailbox` の中、接続を開くプロセスの中で確認する。プロンプトの中の規則は助言にすぎず、ソケットでの規則こそが規則である。一覧がなければ、転送はきっぱり拒否する。
  - **読んでも何も既読にしない**（読み取り専用の select に対する `BODY.PEEK[]`）。そうすれば、メールボックスを見るエージェントが、人が頼りにしていた未読数を奪うことはない。
  - **削除は、アカウントにごみ箱があればごみ箱への移動になる**。先月書かれた規則に従ってエージェントが削除したものを、人があとから見つけられる。「このアカウントにはごみ箱フォルダーがない」と「フォルダーの一覧を読めなかった」は区別する。expunge で終わってよいのは前者だけだからだ。以前は両方とも同じ空文字列として `fDeleteMessage` に届いていたので、解析できなかった LIST の行が 1つあるだけで、すべての `mail.delete` が完全な削除になっていた。

### 同梱するエージェントは 1つ、提示するエージェントは多数

インストールで作成されるエージェントはちょうど 1つ、オーケストレーターだけである。ほかはすべて「+」から作る。「+」は 3つの出発点を提示する。空のエージェント、エージェントからエクスポートした `.zip`、そしてテンプレートリポジトリのテンプレートである。誰も頼んでいないエージェントを抱えて届くインストールは、まずオフにすべきものを抱えて始まるインストールである。

テンプレートは以前、このリポジトリの中に、`backend/agents/examples/` にテンプレートごとに 1つの Markdown ファイルとして同梱されていた。今は独自のリポジトリ [bunch-of-aigents-templates](https://github.com/nipegun/bunch-of-aigents-templates) にあり、このリポジトリの隣に `../bunch-of-aigents-templates` としてチェックアウトされている。そのため、新しいテンプレートはアプリケーションの更新なしにすべてのインストールに届き、インストールの向き先を、「設定」→「エージェント」でフォークや独自のリポジトリに変えることもできる（`templates_repo_url`、`templates_repo_branch`。保存時に `agent_templates.fValidateRepositoryUrl` と `fValidateBranch` が確認する）。`agent_templates` はリポジトリ全体を、ブランチの提供形式である 1つの `.tar.gz` としてダウンロードする（インストーラーがアプリケーションをダウンロードするのと同じアドレスである）。そのため、テンプレートの一覧取得は 1回のリクエストで済み、GitHub API もレート制限もない。これは Web のワーカーごとに 5分間キャッシュされる。同じ `archive/refs/heads/<branch>.tar.gz` の構成を持つ `file://` のアドレスなら、外部に出る手段のないマシンにも対応できる。

**エージェントになるものはすべて 1つの形式**（`agent_package`）である。`agent.json` と `system-prompt.md` を持ち、任意で `memory.md`、`home/...`、そして `rag/files/...` 付きの `rag/documents.json` を持つフォルダーだ。テンプレートのフォルダーは、最初の 2つだけを持つそうしたパッケージであり、エクスポートした `.zip` は、利用者がチェックした任意項目を含む同じ構成である。したがって、テンプレートのインストールと `.zip` のインポートは同じ関数 `agent_io.fInstallPackage` であり、エクスポートできるものはすべてテンプレートとして公開できる。

エージェントが存在する前に、すべてを確認する（`agent_package.fReadPackage`）。途中で失敗したインポートは、誰も頼んでいないエージェントを残してしまうからだ。

- `agent.json` が持てるのは `lManifestKeys` のキーだけで、`format` は 1 である。未知のキーは無視するのではなく拒否する。それはテンプレートのタイプミスか、このバージョンが読み違えてしまう新しいバージョンのパッケージだからだ。
- この形式には、`enabled`、鍵、トークン、チャンネルの認証情報、エージェントがどのチャンネルを待ち受けるかを入れる場所がない。インポートしたエージェントは常にオフの状態で作成され、プロバイダーは名前、モデル、ベース URL だけが運ばれる。`api_key_ref` は決して運ばれない。
- スケジュールは cron の 5つのフィールドであり、それ以外は認めない（`agents.fValidateSchedule`）。そして `exec_daemon.fVerbCreateAgent` で「もう一度」確認する。スケジュールは root として crontab の行の先頭に書かれるので、「 /bin/sh -c ...」や改行を含むスケジュールはコマンドになってしまう。Web プロセスが確認するだけでは足りない。境界はエグゼキューターである。
- ツールはここにインストールされているものだけを残し、落としたものは一覧にする（`missing_tools`）。そうすれば、利用者は確認する前にそれを目にする。スキルは名前として渡され、エグゼキューターが以前と同じくインストール済みのものを残す。
- `rag` は、RAG タブからの書き込みと同じく `rag_settings.fValidateSettings` を通り、ライブラリの文書は、パッケージ自体が持ち込むファイルと保存容量の上限に収まらなければならない。
- ホームのパスはすべて `agent_home.fValidatePath` を通る。相対パスであり、`..` を含まず、除外されたトップレベルの名前（後述）であってはならない。
- `.zip`（`ZipSource`）は、外へよじ登るメンバー名、リンク、暗号化されたメンバー、1 MiB を超えて 200:1 より大きく展開されるメンバー、または合計で 8 GiB を超えるものがあれば拒否する。リポジトリのアーカイブは通常ファイルだけを残す。その中のリンクは、たどらずにスキップする。

テンプレートから作成するときに指定するのはテンプレートだけであり、それ以外は何も指定しない。サーバーがそれをダウンロードして読む。自前のツールや自前のスケジュールを運べるリクエストがあれば、ブラウザーが、利用者が一度もチェックしていない権限をエージェントに渡せてしまうからだ。ダイアログは空のエージェントを最初に置き、次に `.zip`、次にテンプレートを置く。テンプレートの説明は、各テンプレートの `agent.json` から画面の言語のものを取る（`fPickDescription`。その言語、なければ en-US）。

**インポートは 3つの段階からなる**。ライブラリは数百 MiB になることがあり、HAProxy は 300秒間何も送らないリクエストを切断するからだ。ブラウザーは `.zip` を分割して `/opt/boa/imports/<id>/`（`boa`、0700。両方のインストーラーが作成し、Web のユニットの `ReadWritePaths` に挙がっている）にアップロードする。`fFinishImport` はそれを丸ごと確認し、何をインストールすることになるかを返す。利用者が確認すると、`fStartImport` が Web プロセスのスレッドでそれをインストールし、そのスレッドが進捗を `job.json` に書き、ブラウザーがそれをポーリングする。状態はファイルなので、どのワーカーでもポーリングに応答できる。スレッドが 3分間書き込みをやめたジョブは、中断されたとみなされる。そのプロセスが再起動されたということだ。エージェントが存在した後の失敗では、そのエージェントを再び削除する（`fInstallPackage`）。

**エクスポートはストリーミングする**（`fExportAgent`）。`.zip` は送信しながら書かれるので、数百 MiB のライブラリを持つエージェントも、メモリに保持されることなくエクスポートされる。crontab からは、このアプリケーションがエージェントを実行するために書いた行だけが、その 5つのフィールドとして運ばれる（`fReadSchedules`）。それ以外の行は誰かが入力したコマンドであり、コマンドを運ぶパッケージは、届いた先のマシンでそれを実行してしまう。

**ホームはエージェントとして読み書きする**（`agent_home`、エグゼキューターの動詞 `agent_home`）。エグゼキューターは、RAG ワーカーを起動するのと同じように、そのモジュールをエージェントのユーザーとして起動する。そのため root が、エージェントが並べ替えられるツリーをたどることは決してなく、ホームに仕掛けられたリンクも、エージェントがもともと行けない場所にはどこにも通じない。どちらの方向でも除外するのは、システムがそこに置いているもの（`chat.jsonl`、`runs.jsonl`、API 呼び出しの記録、`run.lock`、`attachments/`）、パッケージの中に独自の置き場所があるもの（`memory.md`、`rag/`）、ログイン済みのセッションを持つブラウザープロファイル、そしてホームのトップレベルにあるすべての隠しエントリである。インポートされた `.ssh/authorized_keys` は侵入口になり、`.bashrc` はコードを実行する。どちらも、まれな正当な用途に見合うものではない。

テンプレートの 1つ、`web-navigator` には crontab がない。これはブラウザーのためのテンプレートであり（ほかのテンプレートが読むだけのところで、ページを開き、ログインし、クリックし、フォームに入力する）、その作業は利用者がたった今頼んだことであって、朝の 4時に行うものではない。セッションを持つブラウザーに必要な規則は、そのプロンプトに書いてある。認証情報を決して入力しないこと、購入や送信を決して完了させないこと、そしてページを指示ではなくデータとして扱うことである。

`rag-consultant` にも crontab はない。自分の RAG ライブラリから質問に答えるテンプレートである。`agent.json` に `"rag": {"enabled": true}` と書かれている唯一のテンプレートだ。ランナーは、エージェントのライブラリがオフの間は `rag.*` ツールを渡さないので、これがなければエージェントはツールをまったく持たない状態で作成されてしまう。パッケージの `rag` は `pRag` として `exec_daemon.fVerbCreateAgent` に届き（そのためにリクエストの本文が読まれることはない）、そこで `rag_settings.fValidateSettings` を通る。RAG タブからの書き込みが通るのと同じ確認である。テンプレートはライブラリをオンにできるが、そのタブが与えられないものをライブラリに与えることはできない。その `max_tokens_per_run` が 40000 なのは、ランナーが抜粋の予算を、`max_tokens_per_run` からプロンプト、履歴、4096 を引いた値として決めるからだ。既定の 16384 では、抜粋の入る余地がなくなる。そのプロンプトはツールをありのままに説明し（`rag.read` が返すのは抜粋とその前後であり、文書ではない）、`fResolveCitations` が検証する `[rag:REF]` のマーカーを付けるよう求める。

### 2つの提供方法と、インストール時の選択

localhost の 11080 と 11443 で提供し、その前の 80 と 443 に HAProxy を置くか、80 と 443 で直接提供するかのどちらかである。インストーラーはそれを尋ね、答えを `config/ports.conf` に記憶する。更新では二度と尋ねず、マシンが待ち受けるポートを黙って変えることもない。

違いは数字だけではない。direct モードでは bind から `accept-proxy` を外さなければならない。443 に直接接続するブラウザーは PROXY ヘッダーを送らず、それを要求する bind は本物のクライアントをすべて拒否してしまうからだ。

`direct` モードでは、マシン自身の HAProxy は単に放っておかれるのではなく、引退させられる。`fRetireMachineProxy` はそれを停止し、Alpine ではすべてのランレベルから外し、Debian では無効化 **してマスク** する。そして `/etc/haproxy/haproxy.cfg` を、このインストーラーが書いたものなら削除し、ほかの誰かが書いたものなら `haproxy.cfg.before-boa.<date>` に移す。停止するだけでは足りない。有効なまま残ったものは、このアプリケーションが動き出す前の次の起動時に 80 と 443 を取ってしまう。そして systemd の下では、パッケージのアップグレード、ほかのユニットの `Wants=`、あるいはただの `systemctl start` が、無効化されたものさえ呼び戻しうる。マスクされたユニットは何からも起動できず、`/etc/haproxy/haproxy.cfg` のない haproxy には起動の元になるものがない。その後も 80 や 443 を保持しているものがあれば、ログでそれを名指しする。このモードではプロキシはそれらのポートなしには起動できず、30秒後の「the application did not answer」からそれを読み取るのは、はるかに悪い知り方だからだ。

意図的に「行わない」のは、haproxy パッケージの削除である。`boa-proxy` は `/usr/sbin/haproxy` そのものだ。gunicorn の前で TLS を終端して PROXY ヘッダーを読み、`direct` モードでは 80 と 443 に bind するのはまさにそれである。そのためパッケージを purge すれば、どちらのモードでも、アプリケーションには待ち受けるものが何も残らなくなる。引退させるのはマシンの HAProxy の*サービス*であり、それはたまたま同じバイナリを使う別物である。`proxied` に戻るときは、ユニットを有効にする前にマスクを解除する。そうしなければ、戻る道は、このインストーラー自身がかけたマスクのせいで「The machine's HAProxy would not start」で終わってしまう。

両方のテストマシンで `--update --ports direct` を実行して計測したところ、ユニットは Debian ではマスクされ、Alpine ではどのランレベルにもない状態になり、`/etc/haproxy` には設定が残らず、アプリケーションは 443 で 200、80 で 301 を返した。戻る道である `--update --ports proxied` では、ユニットは再び有効かつ稼働中になり、11443 と 443 で 200 を返した。7つのテストが、偽のサービスコマンドに対してこの関数を実際に実行する。マーカーのある設定とない設定について、両方のモードで行う。そしてそのうちの 1つは、将来のバージョンが `apk del haproxy` や `apt-get purge haproxy` に手を伸ばせば失敗する。

### 確認メッセージは、利用者が見ている場所に表示する

`Settings saved` は以前、内容の列の一番上に書かれていた。短いパネルならそれでよいが、長いパネルでは役に立たない。エージェントの「ツール」タブの一番下にある「保存」ボタンを押すと、そこから数画面上、つまりブラウザーが描画している範囲の外にメッセージが出たので、保存しても何も起きなかったように見えた。

今は、内容の列の上の中央に出るポップアップであり、その列の子ではなく兄弟にあたる `fixed` のレイヤーに置かれている。`fixed` であることが肝心な点だ。列の中で中央に置けば、それは*文書*の中央になり、長いタブでは数画面下で同じバグが起きるだけである。レイヤーはサイドバーのところで止まる。エージェントの一覧の上に描かれたメッセージは、エージェントの一覧に属するものに見えてしまうからだ。またレイヤーはポインターイベントを受け取らないので、メッセージが出ている間も、その後ろにあるものは何も動かなくならない。

表示し続ける時間は、このブラウザーの設定である（`boa.noticeSeconds`、「設定」→「インターフェース」）。テーマや言語の隣にあり、理由も同じだ。3秒は 1語には十分だが 1文には足りず、メッセージがそのどちらになるかは、誰が読むかによって変わる。エラーは例外で、この数値を完全に無視する。エラーは閉じられるまで待つ。利用者が画面に目を戻したときに、まだそこになければならない唯一のメッセージだからだ。

メッセージには 3つの色があり、3つ目は、ほかの 2つでは言えないことのために存在する。緑は実際に行われた保存、赤は失敗、そして琥珀色は **`No changes to save`** である。「保存」が押されたが、フォームの中身はすでに保存されているものとまったく同じだった、ということだ。それを緑で報告するのは何も言わないより悪い。何も書かなかった保存の後の「設定を保存しました」は、自分の編集が反映されなかったことに誰かが気づくのを妨げる唯一の文だからだ。そして赤では、何も問題がないのに失敗を主張することになる。

保存するフォームはどれも、同じやり方でそれを確認する。送信する*はずの*ペイロードを JSON として、フォームにサーバーから値を入れたとき、または最後に保存したときに取ったスナップショットと比べるのである。エージェントの設定は、そのペイロードを 1つの関数 `fCollectAgentPayload` で組み立て、それを保存にもスナップショットの取得にも使う。同じフォームを読む 2つのものがずれていけば、一方が一度も見なかったフィールドについて「変更なし」と報告してしまうからだ。ブラウザーの設定パネルは、「未保存の変更」の表示のために、すでにそうしたスナップショットを持っており、それがこの問いにも答える。

例外は **新しい** エージェントである。そのフォームはテンプレート自身の値を持っていて、一度も保存されていないので、「保存」を押すと、何もすることがないと伝えるのではなく、その値を書き込んでチャットへ進む。

### 色は状態、動きは活動

エージェントのアバターを囲むリングは 2つの異なる事実を伝え、それを 2つの異なる手段で描く。そうすれば、どちらも調べる必要がない。エージェントがオンかどうかは、動かない色、つまり緑か赤である。今まさに作業中かどうかは動きであり、光る区間がその緑のリングの上を時計回りに進む。「作業中」を表す 2つ目の静的な色は覚えなければならない約束事になるが、回っているものは教わらなくても理解できる。

これは枠線にぴったり重ねた SVG の角丸長方形として描かれ、オフセットをアニメーションさせた破線で線を引く。そのため **形は静止したまま、光だけがその上を移動する**。SVG を使う理由はそれに尽きる。代わりにリングを回転させれば（円錐グラデーション、円弧、`transform: rotate` の下にあるものなら何でも）、形まで回ってしまい、角が下の角丸の正方形と揃わなくなる。`pathLength="100"` が輪郭を正規化するので、スタイルシートは周の長さに対する割合で記述でき、アバターやその角の半径が変わっても何も計算し直す必要がない。

「誰が作業中か」に答えるには、すべてのプロセスのコマンドラインを読む必要がある。それができるのは root だけなので、これは特権デーモンの動詞になっている。`/proc` を 1回走査すれば、エージェントごとに 1回呼ぶのではなく、すべてのエージェントについて一度に答えられる。サイドバーが 5秒ごとに尋ねられるほど安く済むのは、そのおかげである。同じ走査が `only_if_idle` も支えているので、ブザーと画面とで、エージェントが作業中かどうかの判断が食い違うことはない。

### 期限の来たカードは会話の中で告知される

エージェントのチャットは、そのエージェントに入力されたことだけでなく、そのエージェントが頼まれたすべてのことの記録である。そこで、期限の来たカードのためにブザーが実行を開始すると、そのカードはエージェントの `chat.jsonl` に独立したターンとして書き込まれ、実行の返答がそれを閉じる。会話を開けば、仕事が届いたこと、エージェントがそれに対して何をしたか、それにどれだけかかったかがわかる。

3つの判断がこれを支えている。

**書き込むのはカードが作られたときではなく、実行が始まったときである。** 今夜に予定され、今日の午後に削除されたカードは一度も実行されていない。それが引き渡されたと書いてある会話は、起きなかったことの記録になってしまう。ブザーが目にするのは、まだボードにあるカードだけなので、ブザーが鳴った瞬間に書き込むことが、告知を真実にする。

**ファイルには文ではなく、カードのフィールドを保存する。** `role: "card"` は ID、タイトル、誰が割り当てたか、すぐに実行するよう求められたかどうかを持ち、メッセージのテキストはカード自身の指示である。その周りの言葉はすべて、画面が利用者自身の言語で書く。停止した実行が、英語の言い回しではなく `ceiling: "tokens"` を記録するのと同じ規則である。

**「今すぐ」と「13:45 に」は区別しなければならず、エージェントが起こされる時点では、どちらもすでに過去である。** そのためボードは、後から時計で割り出すのではなく、どちらが求められたか（`run_mode`）を記録する。そして `now` という語は、ブラウザーから `kanban.fValidateRunAt` まで語のまま運ばれ、それが何だったかも記録する唯一の場所でタイムスタンプに変わる。

書き込むのはブザーではなく特権デーモンの仕事である。`chat.jsonl` はエージェントが所有する 0700 のホームにあり、ブザーは `boa` として動いているからだ。デーモンは fork し、エージェントに権限を落とし、告知を書き、それから初めて実行を開始する。そしてホームに書き込めなくても、実行は開始する。告知は仕事の記録であって、仕事そのものではない。

逆向きの失敗は無害ではないので、反対の扱いをする。ターンを開いた **後で** プロセスを開始できなかった場合、デーモンは例外を送出する前に、そのターンに失敗を書き込む。ほかに何もそれを閉じるものはなく、開いたままのターンはカードを未回答のまま残すだけでは済まない。そのエージェントの入力欄を永久に閉ざしてしまうのである。

続く実行は、単なる予定された実行でもチャットのターンでもない。質問がそこにあるので、返答はチャットに書き戻す。しかし会話は **再生しない**。そのプロンプトはカードであり、10 のやりとりを再生すれば、予定された実行のすべてに、誰もしていない会話の費用を負わせることになる。ランナーではそれらは `vWritesToChat` と `vIsChat` という 2つの別々のフラグであり、その区別がすべてである。その帰結として、モデルに何も尋ねる前に止まる実行（オフになっているエージェント、1日の上限）でも、ターンは閉じなければならない。そうしなければ、画面はいつまでも返答を待ち、入力欄は閉じたままになる。

### API ドキュメントはこのアプリケーションのページである

これは CDN から Swagger UI を読み込むのではなく、このプロジェクトが構築する OpenAPI 仕様から描画する。本番サーバーは、外向きのインターネット接続がまったくないかもしれない LAN の機器だからだ。外部のウィジェットではなく自前のページの 1つであることから、2つのことが導かれる。

**選んだ言語に従う**。仕様は英語のままである。それはフィールド名、ID、エラー文字列がすべて en-US である API の契約であり、翻訳した `openapi.json` は存在しない API を記述することになる。翻訳するのはページのほうだ。`fAnnotateSpecForTranslation` が、描画の前に英語のすべての部分に `data-i18n` のキーを付け、ブラウザーはほかのすべてのページと同じやり方でそれを差し替える。そうすれば文字列はフロントエンドの `.json` ファイルに、ほかのすべての文字列と並んで置かれ、匿名の読者に対しても機能する。キーは手で書くのではなくテキストとパスから導き出すので、新しいエンドポイントは自分のキーを持ち込む。翻訳のないキーは英語のままになる。これは、`fApplyTranslations` が知らないキーに対して行うことと同じである。

ほかのすべてのページと同じく、**与えられた列いっぱいに広がる**。以前は 900px の幅を保って中央に寄せていた。散文なら読みやすいが、これには向かない。このページの大半はパラメーターの表と JSON のブロックであり、それらが広い画面の 3分の 1 に押し込められ、両側に空の余白ができていた。

### 画像の添付は明示的なツールの許可である

`browser.screenshot` はファイルを保存し、`image.send` はそれを現在の返信に添付する。後者は別の許可であり、web-navigator テンプレートに含まれている。このツールは PNG のスナップショットを `agents/<id>/attachments/<opaque-id>.png` に保存し、ディレクトリは 0700、ファイルは 0600 である。後で元のスクリーンショットを上書きしても、以前の返信は変わらない。`ToolContext.lAttachments` が、その参照を `AgentRun.fRecordChatAnswer`、またはその失敗報告や実行報告に運ぶ。

Web プロセスのためにそれらの非公開ファイルを読むのはエグゼキューターだけである。その `read_chat_attachment` 動詞は、そのエージェントの記録されたチャットの中にある参照を要求し、ディレクトリのすべての構成要素をリンクをたどらずに開き、画像がエージェントの所有する通常ファイルであることを確認する。PNG は 1 MiB ずつ読む。50 MiB の添付であっても、base64 の応答は既存の RPC の上限を下回る。認証された HTTP エンドポイントは、`private, no-store` を付けてバイトをストリーミングする。フロントエンドは、ローカルの画像 URL を ID から組み立て、モデルが提供した URL からは決して組み立てない。

Telegram では、条件を満たす画像には [sendPhoto](https://core.telegram.org/bots/api#sendphoto) を、縦に長いキャプチャや大きなキャプチャには [sendDocument](https://core.telegram.org/bots/api#senddocument) を、元の PNG で使う。非公開ファイルは multipart のデータとしてアップロードする。公開 URL も、エージェントがボットの認証情報にアクセスすることも必要ない。`telegram_deliveries` は、保留中の各ターンについて、受領が確認されたテキストと画像の部分を記録する。再試行は欠けている部分から再開し、保留中の行を削除すると、それらのチェックポイントも消える。恒久的な失敗は利用者に報告する。どちらの受信箱も、SQLite の UTC のタイムスタンプを Unix 時刻と比べる。それをローカル時刻として解釈していたため、夏時間の間に最近の配信が期限切れになっていた。

### ビルド工程なし

フロントエンドは Jinja2 のテンプレート、素の CSS、素の JavaScript である。本番の対象は自前でホストする Debian や Alpine の機器であり、スタイルシート 1つを変えるのに Node のツールチェーンを必要とするデプロイは、朽ちていくデプロイである。同じ理由で、`/api/doc/` は CDN から Swagger UI を読み込むのではなく、自前の OpenAPI 仕様を描画する。LAN のサーバーは外向きのインターネット接続を持たないかもしれず、それがないと動かないドキュメントは、まさに誰かがデバッグしているときに動かなくなる。

### 音声の文字起こし

OpenRC のサービスを起動するとき、インストーラーは `rc-service` コマンドのディスクリプタ 3 と 4 を閉じる。これはインストーラーが退避しておいた SSH の stdout/stderr のパイプであり、インストーラーが正常に終了した後も `supervise-daemon` がそれを保持し続けることが観測された。通常の出力はこれまでどおり `install.log` に記録される。

`audio_transcription` は検証済みの JSON 設定を1つ `settings.audio_transcription` に保存する。OpenAI、Groq、Mistral、Together は multipart を使い、Hugging Face と Cloudflare はバイナリの WAV を受け取る。いずれも `api_keys` を再利用し、秘密情報をブラウザーに返すことはない。FFmpeg はコンテナ、プロトコル、サイズ、長さ、実行時間に上限を設ける。音声は 120 秒のセグメントに分割される（Hugging Face と Cloudflare の生のエンドポイントでは 30 秒で、長尺の生成オプションに頼らずに済むようにしている）。whisper.cpp とデコードは `boa` として動き、シェルもプロバイダーへの自動フォールバックもない。

`audio_inbox` は送り先、設定、文字起こし結果を SQLite に永続化する。`boa-channel-telegram` の中で、プロセスロックを取ったバックグラウンドスレッドが1本動き、再起動の後にキューを復旧する。予約済みのターン ID があるので、エグゼキューターはエージェントが作業中かどうかを確かめる前に、繰り返された送信を受理済みとして応答できる。ジョブを送信済みにする処理と `telegram_pending` への挿入は、1つのトランザクションの中で行われる。非公開の音声は `/opt/boa/audio/`（0700、所有者は boa）に置かれ、再生にはログインと一致するチャット参照の両方が必要であり、完了したチャットのターンを消去すると削除される。

両インストーラーは、ソースアーカイブの SHA-256 を検証したうえで whisper.cpp v1.9.4 をコンパイルし、`base` をダウンロードする。`whisper_models.json` には、公式の30個すべての名前、サイズ、ハッシュが入っている。モデルをダウンロードするのは root のエグゼキューターだけで、`install_whisper_model` を通して行う。任意の URL やパスは拒否される。途中までのファイルは、ハッシュの検証が済んで初めて見えるようになる。`whisper/` は root が所有し、`boa` は読むだけである。更新ではモデルと音声が残り、バックアップには音声が含まれるがモデルの重みは含まれない。Python インタープリターがない場合は、最低バージョンを確かめる前に依存関係とともにインストールされる。

### プロバイダーへの生のリクエストとエージェントのワークスペース

`AgentRun.fSendRecordedRequest` は、その呼び出しのあいだ、選ばれたプロバイダーに記録器を取り付ける。フォールバックの呼び出しや締めくくりの呼び出しも対象になる。Requests を使うアダプターは `BaseProvider.fPostJson` を使い、これは送信の前に、送るものとまったく同じシリアライズ済みの JSON 本文を記録する。OpenAI と Anthropic の SDK クライアントはリクエストフックを使い、SDK が加えるフィールドを含めた準備済みの本文を、再試行のたびに記録する。記録器は認証ヘッダーを決して保存せず、チャット履歴からリクエストを組み立て直すことも決してない。

`api_calls` は索引を `agents/<id>/api-calls.jsonl` に書き、リクエストごとに完全な本文を `api-call-<id>.json` として1つずつ、エージェントの非公開のホームにモード 0600 で書く。保持処理は、最新の100件を超えた分をリクエスト単位でまるごと削除する。エグゼキューターはそのエージェントが所有する通常ファイルだけを読み、シンボリックリンクと FIFO は拒否する。本文はエグゼキューターのソケットを通って上限付きのチャンクで運ばれ、認証付きの HTTP ルートは元の JSON テキストを `body` の下にそのままストリームで返す。ブラウザーは数値を解析せずに字句トークンを整形するので、大きな整数も文字列のエスケープも損なわれずに残る。

保護された `info.json` は `interface.show_api_calls` を保存し、既定値は false である。これが制御するのは表示だけで、タブが見えていても隠れていても、リクエストは記録される。`dashboard.js` は会話のタブと設定のタブを分け、エージェントを読み込むと常に「チャット」を選ぶ。リクエストのメタデータを定期的に問い合わせるのは「API Calls」が開いているあいだだけで、完全な本文は詳細を展開したときに読み込む。設定の見出しはエージェントを ID で示す。「今すぐ実行」はワークスペースに属し、削除は「一般」の中に専用のパネルを持つ。

入力欄はステータスバーのすぐ上に固定され、スクロールするのは `#vChatLog` だけである。デスクトップの幅では、チャットが表示されているあいだ（`.app:has(#vChatPanel:not([hidden]))`）、`app.css` が `.app` の高さをちょうどビューポート1つ分にし、その高さを flex の列を通じて `.chat` まで渡すので、フォームを見失うようなページのスクロールはそもそも存在しない。820 px 以下ではページは再びブロックとしてスクロールし、`.chat` の高さはビューポート1つ分から `--status-bar-live-height` を引いたものになる。この値は `api.js:fTrackStatusBarHeight` が `ResizeObserver` を使ってバーの実際の高さと常に等しく保つ。スマートフォンではバーが数行に折り返し、固定の見積もりではテキスト欄がバーの下に隠れてしまったからである。入力欄の下にヒントの行はない。`fSetComposerEnabled` がそれをプレースホルダーの2行目として書き（Enter がどう動くか、あるいはエージェントが作業中であること）、`fFitChatInputToPlaceholder` が見えない複製の上でそのプレースホルダーを計測し、決して切れないように欄の `min-height` を設定する。これはプレースホルダーか入力欄の幅が変わるたびに実行される（`fTrackChatInputWidth`）。高さは CSSOM を通じて設定し、`style` 属性は決して使わない。CSP がそれを捨ててしまうからである。

### エージェントごとの Samba 共有

`agents.dDefaultSambaSettings` は、共有オン、読み書き、一覧に表示、認証付きアクセス、ファイル/ディレクトリのモード 0600/0700 を定める。パスワードは最初は未設定である。`info.json.samba` は保護された設定であり、パスワードは root だけが読める Samba の passdb の中にしか存在しない。パスワードは stdin を通じて `smbpasswd` に渡され、argv にも、モデルにも、API が返すオブジェクトにも、`info.json` にも決して入らない。

`boa-samba` は TCP 445 で隔離された smbd を動かし、設定とネイティブの状態は root 所有の `/opt/boa/samba/` に、実行時のファイルは `/run/boa-samba/` に置く。homes サービスはない。共有名は `fGetAgentSystemUser` から導かれ、パスは常に `<agent home>/samba` である。認証にはそのアカウントを使い、ファイル操作はそのエージェントの uid で行われる。ゲストアクセスには、エージェントごとの明示的な設定が必要である。インストーラーは無関係な Samba のインストールを乗っ取ることを拒み、ディストリビューションの既定のインスタンスを無効にするのは BoA 自身のインストールの場合だけである。

エグゼキューターはエージェントを作成またはインデックス化した後にフォルダーを作り、ユーザーを削除する前に共有とアカウントを取り除く。両インストーラーは、インストール、更新、復元の後に既存のエージェントの状態を整合させる。排他的なファイルロックが変更を直列化し、設定をアトミックに置き換える前に `testparm` が検証する。`smbcontrol` は設定を再読み込みし、変更された共有の接続だけを閉じる。エージェントの共有を無効にすることは、エージェントの実行スイッチとは独立している。

フォルダーの準備には、`O_NOFOLLOW` 付きのディレクトリディスクリプタと所有者の確認を使う。Samba は共有の中のリンクを拒否し、root の preexec ガードが接続のたびに共有のルートをもう一度確かめる。ガードは信頼できる Python コードを `-I` 付きで実行するので、エージェントの作業ディレクトリからインポートされるモジュールを差し込むことはできない。

バックアップには、共有されたファイルが通常のエージェントのホームのアーカイブを通じて、設定が保護された info ファイルを通じて含まれる。`tdbbackup` は稼働中のネイティブなパスワードデータベースのスナップショットを取り、バックアップにはサーバーの SID も保存される。復元には smbd の停止が必要で、一時データベースを検証したうえで、現在の認証情報とマージするのではなく置き換える。古い smbpasswd 形式を通じたエクスポートは、一部のネイティブアカウントの RID で拒否されたため使っていない。`fVerifyInstallation` は保存されている Web のポートモードを読むので、復元は実際の HTTPS ポートを検証する。明示的な `--ports` フラグのない direct モードも同様である。

参考: [Samba の共有オプション](https://www.samba.org/samba/docs/current/man-html/smb.conf.5)、[TDB バックアップツール](https://www.samba.org/samba/docs/3.6/man-html/tdbbackup.8.html)。

### ローカルでの文書検索

タブのラベルは、HTML と JavaScript のフォールバックも含め、どの言語でも `RAG` である。

`rag_store` はエージェントごとのカタログ（SQLite WAL、FTS5、文書、リビジョン、アップロードのオフセット）を受け持つ。元のファイル名はメタデータであり、ディスク上のファイル名には生成した識別子を使う。`rag_extract` は PDF/EPUB/TXT/Markdown を読み、OCR のためにローカルの Poppler と Tesseract を呼び出す。ページや章の位置を保持し、解析の前に EPUB の展開後のサイズを確かめる。`rag_embeddings` は `AF_UNIX` だけを使い、接続先は固定の `/run/boa-embeddings/engine.sock` である。ホスト名も、プロキシも、クラウドへのフォールバックもない。

文書の編集可能な **文書情報** は、フォームに表示される順（`rag_store.lMetadataKeys`。`fAction` もこれと照合する）に、出版年、タイトル、サブタイトル、著者、バージョン、言語、タグである。文書一覧では、サブタイトルがあればタイトルのすぐ下に表示される。年はテキスト（空か最大4桁）として保存されるので、「不明」と数値は区別されたままになる。`rag_store.fMigrate` は `rag_store.lAddedColumns` に挙げた列、つまりカタログがすでに存在するようになった後で導入された列（現時点では `year` と `subtitle`）を追加する。`CREATE TABLE IF NOT EXISTS` は既存のテーブルを決して変更せず、古いライブラリも復元したバックアップも古いスキーマのままだからである。`rag_search.fSource` はすべての抜粋にサブタイトル、年、著者、バージョン、言語を付けるので、モデルは `rag.list` を余分に呼ばなくても、同じタイトルを持つ文書を見分け、引用の日付と出典を示し、食い違う2つの版を比較検討できる。引用リンクとライブラリ検索は、タイトルと位置だけを残す。これらは場所を示すものであり、サブタイトルはリンクを長くするだけだからである。

`rag_models.json` はベクトル化モデルのカタログである。各モデルについて、固定した URL と SHA-256、次元数、コンテキスト、プーリング、クエリと抜粋の接頭辞、そしてそのモデルで測定した2つの類似度（verified モード用の `min_support` と、検索の下限用の `min_similarity`）を持つ。同梱されているのは2つで、EmbeddingGemma 300M Q8（`default`。768次元、平均プーリング）と Qwen3-Embedding 0.6B Q8（1024次元、最終トークンのプーリング、各クエリの前に英語の指示文を置き、抜粋の前には何も置かない）である。使用中のモデルは実行時設定（`/opt/boa/rag-runtime/settings.json`。root が書き、すべてのエージェントが読める）の `model` であり、`rag_settings.fSelectedModel` と `rag_embeddings.fModel` を通じて読まれる。`rag_runtime` は重みをインストールする。インストーラーは選択されたモデルを、エグゼキューターはそれ以外のモデルを要求に応じてインストールする（`install_rag_model`。スレッドの中で一度に1つずつダウンロードし、進捗は `rag-runtime/status/<id>.json` に書く）。ファイルが本来の名前を得るのは、サイズと SHA-256 が一致してからである。llama.cpp v0.5.0 を、そのモデルのプーリングで、モデル ID を `--alias` として起動する。ネットワークへのアクセスはインストールのときだけのものである。ランタイムはモデルのトークナイザーと検索用の接頭辞を使い、大きすぎる入力を拒否する。SQLite はテキストとベクトルを保存し、USearch は増分の HNSW の世代を保存する。リビジョンの公開は、カタログ上の可視性とインデックス名をアトミックに切り替える。

エンジンは1つなので、モデルはマシン全体に対して選ばれ、変更は root のエグゼキューターが行う（`rag_exec.fRuntime`）。ディスク上にない重みは拒否し、選択を保存し、まだ旧モデルの推奨値のままになっているすべてのエージェントの `min_similarity` を新しいモデルの推奨値に移し（`fFollowModelSimilarity`。誰かが選んだ値はそのまま残る）、`boa-embeddings` を再起動する。設定ファイルだけを根拠に信用されるベクトルはない。`rag_embeddings.fEmbed` はベクトル化の前に、エンジンがどのモデルを提供しているか（`/v1/models`、エイリアス）を尋ね、期待したモデルでない場合や、ベクトルの次元数が誤っている場合には `EngineUnavailable` を送出する。インデックス作成のジョブは開始時のモデルを渡すので、途中で変更があれば、1つのリビジョンに2つのベクトル空間を混ぜるのではなく、ジョブを止める。各文書は、公開済みリビジョンの背後にあるモデルのフィンガープリントを記録する（`documents.model`）。次の巡回で `rag_worker.fWork` は、ライブラリのモデルが選択中のモデルではないことに気づく（`fFollowNewModel`）。すると、未完了のリビジョンのチャンクを捨て、別のモデルでインデックス化された文書をすべてキューに入れ直し、インデックスを忘れる。公開済みのリビジョンは残る。順番が来るまで、その文書は FTS5 だけで検索される。`fSearch` は使用中のモデルの文書だけからベクトルの順位を作り（新しいインデックスを通じて、あるいはインデックスがまだないあいだは保存されたベクトルを1つずつ比較して）、何件の文書が待っているかを伝える `notice` を加える。エンジンの再起動中も、同じキーワード検索へのフォールバックが検索に答える。`rag_verify` は比較の両側に1つのモデルを固定し、しきい値をそのモデルから取る。

`boa-rag` は boa として動き、既存のエグゼキューターに固定のワーカーコマンドの起動を依頼する。`rag_exec` は、文書や SQLite のあらゆる操作の前に UID/GID を落とす。root が本を解析したり、エージェントのカタログを開いたりすることはない。ワーカーは OS のロック、リソース制限、永続的な状態を使う。アップロードの RPC は 256 KiB のチャンク、ダウンロードは 1 MiB のチャンクであり、本全体が1つのメッセージとしてエグゼキューターのプロトコルを通ることはない。ワーカーは前のリビジョンを検索可能なまま保ち、中断の後は完了済みのチャンクから再開する。設定は保護されたエージェントの設定の中に残る。

エンジンの停止は文書のエラーではない。`rag_embeddings` は、ソケットが失敗したときや、モデルの読み込み中にエンジンが 503 を返したときに `EngineUnavailable`（`ValueError` の一種）を送出する。それ以外の拒否は通常の `ValueError` のままである。`fIndexDocument` はこの停止を別扱いで捕捉する。文書は **同じ** リビジョンのまま `queued` に戻り、すでにベクトル化したチャンクはすべて保持され、再びジョブが動くまで理由が表示される。以前の動作、つまり `error` にしてそのリビジョンのチャンクを削除するやり方では、`--update` のたびに大きな本の数時間分の作業が失われた。`boa-exec` が起動したワーカーがまだ動いているあいだに、インストーラーが `boa-embeddings` を止めるからである。`fWork` はキューにある各文書を始める前にエンジンを確かめ（`fIsAvailable`）、停止していればそのバッチを終える。そうしなければ、5秒ごとのスケジューラーの巡回のたびに、最初のチャンクで止まるためだけに文書全体を抽出したり OCR したりすることになる。

`rag_search` は FTS5 と意味的な順位を組み合わせる。絞り込んだ検索は、選択された部分集合を対象に評価する。ランナーは回答の呼び出しの前に検索を行い、RAG が有効なときだけ、読み取り専用の3つの RAG ツールを与える。出典は、設定されたテキストの予算と、控えめに見積もった実行のトークン数によって上限が決まる。引用マーカーは、その実行のあいだに実際に返された出典に対してだけ解決される。回答を生成するプロバイダーはリモートでもよい。ローカル限定の処理が適用されるのはベクトル化である。

3つの回答モードは、プロンプトが言うことだけでなく、**ランナー** が強制することによって違う。`mixed` はモデルが一般知識を加えることを許す。`documental` と `verified`（`runner.lRagModesThatSearch`）では、モデル自身が `rag.search` を呼ばなければならない。それなしに出された最終回答を、`fCheckRagAnswer` が一度だけ差し戻す（`cRagSearchFirstPrompt`）。ランナー自身の検索は利用者の最後のメッセージを一字一句そのまま使うものであり、会話の中（「では第2版では?」）では、会話全体を見て書かれたモデルのクエリなら見つかるものも見つけられない。同じ理由で、空の検索結果が、モデルに尋ねる前に documental の実行を終わらせることはもうない。保証は最後に移った。`fFinishRagAnswer` は、抜粋を1つも取得しなかった実行の回答を固定の文に置き換える。検索を強制するために `tool_choice` は使わない。29個のアダプターのうち、`auto` を送るものもあれば、Cohere は何も送らず、Mistral は `any` を使うので、すべてのプロバイダーにそれを課せるのはランナーだけだからである。

`verified` は `rag_verify` を加える。回答は単位に切り分けられる。単位とは段落と、1つずつ独立に扱うリスト項目であり、フェンス付きのコードブロックは直前の段落に付けられ、その段落と一緒に比較される（例の導入文だけではほとんど何も言っておらず、そのせいで忠実な例が削除されていた）。見出し、「:」で終わる短いラベル、区切り線は対象外である。単位には、その実行で取得した抜粋の中を指す `[rag:REF]` が必要であり、単なる参照でない限り、それらのうちの1つに近くなければならない。単位をクエリとしてベクトル化し、抜粋を文書としてベクトル化して比べるもので、検索と同じ距離を使い、しきい値はモデルの `min_support`（EmbeddingGemma では 0.36、Qwen3-Embedding では 0.44）である。最初に不合格となった回答は、不合格の単位を添えて一度だけ差し戻される（`fBuildCorrectionPrompt`）。その後は、それらの単位が削除され、ローカライズされた1行が何件削除したかを伝える。裏付けのあるものが何も残らなければ固定の文になり、エンジンに到達できなければ回答を出さない（フェイルクローズ）。固定の文（`rag_verify.dFixedTexts`）は、システムプロンプトが回答するよう指示された言語で書かれる。その言語は `dAnswerLanguageLines` にある対応する行で判別され、判別できなければ英語になる。このチェックの限界は測定され、チェックの隣に書かれている。138個の忠実な段落と、別の話題の抜粋への 2,652 件の引用について、どちらのモデルでも両者を分けられるしきい値は存在しない。使用中のしきい値は忠実な段落の約6%（主に短いリスト項目と1行の要約）を削除し、それらの誤った引用の1%未満を通してしまう。同じ話題の抜粋への引用はおよそ4回に1回は通り、抜粋と矛盾する段落も忠実な段落と同じような点数になる。このチェックが捕まえるのは、別のことについての抜粋への引用と、出典のない段落である。

バックアップは root 所有のステージング用の親ディレクトリの下にスナップショットを作り、エージェントの子プロセスに SQLite のバックアップを取らせ、選んだ不変のファイルをハードリンクさせてから、そのスナップショットをアーカイブする。これにより WAL と HNSW の世代の整合性が保たれ、エージェントが差し替えられるスナップショットのツリーを root がたどることも避けられる。復元は途中までのアップロードを取り消し、中断されたインデックス作成をキューに入れ直す。インデックスのフィンガープリントは、再構築のために使える状態で残る。

## 4. 主要フロー

### 文書の検索

インストーラーは、スナップショットを展開する前に、復元するエージェントの古い RAG のツリーを片付けるので、古い SQLite の WAL ファイルやベクトルの世代が復元の後まで生き残ることはない。実行時設定は、インストール済みのモデルの重みを置き換えずに復元される。ワーカーは1回の順番ごとに、最大8件の文書を処理しきるか、最大90秒のあいだ新しい文書を始める。終わらなかったジョブは永続的に残る。ライブラリの応答は、inbox からの取り込みの失敗を示す。ローカルの OCR は、フォントを埋め込んでいない PDF のために Liberation フォントをインストールする。ベクトル化エンジンのビルドでは、ビルド済みの Web UI のダウンロードを無効にしている。

アップロード: `rag_api → exec_client.fRag → rag_exec → rag_worker`（エージェントとして）。インデックス作成: `boa-rag → exec_daemon → rag_worker.fWork → rag_embeddings.fIsAvailable → extraction → local embeddings → publication`。インデックス作成中のエンジンの停止: `rag_embeddings.fRequest → EngineUnavailable → fIndexDocument → state queued, chunks kept → fWork ends the batch → next pass resumes at the first missing chunk`。モデルのダウンロード: `settings_rag.js → POST /api/admin/rag/models/<id>/install → exec_client.fInstallRagModel → exec_daemon.fVerbInstallRagModel → rag_runtime.fStartModelDownload → thread fInstallModel → status file ← GET /api/admin/rag (fDescribe) polled every 2 s`。モデルの変更: `settings_rag.js (fConfirmModelChange) → PUT /api/admin/rag → rag_exec.fRuntime → fIsModelInstalled → fSaveRuntimeSettings → fFollowModelSimilarity → restart boa-embeddings → [each library] rag_worker.fWork → fFollowNewModel → fIsAvailable waits for the new alias → fIndexDocument(pModel) → fBuildIndex/fPublish (documents.model)`。そのあいだは `fSearch → FTS5 only for the waiting documents → notice`。回答: `AgentRun.fExecute → rag_search.fSearch → bounded passages → configured provider → verified citation links`。documental と verified の回答: `model answers → fCheckRagAnswer (no rag.search yet → cRagSearchFirstPrompt, once) → rag.search → model answers → [verified] rag_verify.fVerify → unbacked units → fBuildCorrectionPrompt, once → model answers → fFinishRagAnswer (no passages → fixed sentence; verified → units removed + count, engine down → withheld) → fResolveCitations`。

### メモリの保存とその上限

`dashboard.js:fSaveAgent` は Unicode のコードポイントを数え、`memory` を `info.limits.max_memory_characters` とともに送信する。`api.fCheckMemoryUpdate` は、どんな書き込みよりも前に、提案された上限に照らして（あるいは保存済みの上限を読んで）検証するので、上限を増やすことと、より長いテキストを保存することが1回のリクエストでできる。拒否する場合は、翻訳された `memoryTooLong` または `memoryLimitInvalid` のエラーを返す。続いて `fVerbWriteAgentInfo` が上限を永続化し、`fVerbWriteMemory` が権限を落とす前に検証する。`memory.fWrite` は保護された設定をもう一度確認し、切り詰めることなくファイルをアトミックに置き換える。`memory.append` と `memory.replace` も同じ確認を使い、警告は上限の75%を超えたところで出始める。フォームは、貼り付けた大きすぎるテキストを編集できるように残しておく。

転送の予算は、この上限の最大値に対応できる大きさになっている。エグゼキューターへのリクエストは 6 MiB まで（クライアントが接続の前に確認する）、レスポンスは 8 MiB まで、メモリファイルの読み取りは 4 MiB まで、HTTP の本文は 16 MiB まで（補助面の Unicode 文字をエスケープする JSON クライアントの場合も含む）である。これらは転送の上限であって、モデルのコンテキストの上限ではない。

### ボットは見知らぬ相手に何も見せない

ボットのユーザー名は公開されている。それを見つけた人は誰でも、そのボットとのチャットを開ける。そこで `fIsFromTheConfiguredChat` は、Telegram がすべてのメッセージに付ける `chat.id`（送信者には偽造できない）を設定済みのものと比べ、`fHandleMessage` は一致しないものを、コマンドを振り分ける前、エージェントを選ぶ前に捨てる。`fHandleCallback` はボタンの押下に対して同じことをする。何も送り返さない。答えれば、探りを入れている相手にボットが生きていることを教えてしまう。何も書き残さない。以前は、捨てたことを送り元のチャットの ID とともにログに残していたが、それは他人のデータであり、ボットを見つけたのが誰かの一覧を、このインストールがひそかに溜め込むことを意味していた。残るのは、存在しなかったことになったメッセージだけである。

代償は現実のもので、はっきり言っておく価値がある。誤って設定された `chat_id` は、いまや見知らぬ相手とまったく同じに見え、持ち主自身のメッセージが音もなく消える。設定済みの ID は起動のたびにログに書かれる（`Registered 3 command(s) for chat <id> only`）。比べるべき番号はそれである。「設定済みの」チャットから来たのに、どのエージェントにも届かなかったメッセージは、今もログに残る。そこでは送信者は持ち主であり、ログがなければ「書いたのに何も起きなかった」と「そもそも届かなかった」が見分けられないからである。

フィルターが扱わず、また扱えないのは、チャットの中の「誰か」である。グループを指す `chat_id` は、そのメンバー全員がエージェントと話せるグループである。

同じ考え方で、コマンドの一覧をどこに書くかが決まる。`setMyCommands` はスコープを取り、`default` と `all_private_chats` は Telegram のすべての利用者に対して解決される。つまりそこに書いた一覧は見知らぬ相手に見せるメニューになり、その中に「Server status」があれば、この裏には突いてみる価値のあるマシンがあると宣伝することになる。彼らがそのどれかを実行できることは決してないが、鍵のかかった扉に掛かった看板も、看板であることに変わりはない。`fSetTelegramCommands` は一覧を設定済みのチャットのスコープだけに書き、更新のたびに2つの公開スコープのものを **削除する**。このコードの古いバージョンが書いた一覧は、何かが消すまで Telegram 側に残り続けるからである。`fHideTelegramPublicProfile` は、残りの2つの公開文字列 `setMyDescription` と `setMyShortDescription` を空にする。これらは、空のチャットで「What can this bot do?」の下を埋めるものである。

見えるまま残るのは、ボットの名前、画像、そして「Start」ボタンである。このボタンは、Telegram がボットとの空のチャットに必ず描くもので、どの API でも取り除けない。押すと `/start` が送られ、ほかのチャットから来たものと同様に捨てられる。

### メニューがエージェントではなくツールを載せる理由

Telegram はコマンドメニューのすべての項目の横に `/name` を描く。その文字列こそが項目であり、タップしたときに入力欄に入るものであって、どの API でも隠せない。だからエージェントのメニューは、誰かが見たいと思うエージェントの一覧には決してなりえず、名簿とともに伸びていくだけで、ボットが何のためにあるのかを何も語らなかった。

メニューに載るのは、ボットにできる3つのことである。どのエージェントが存在するかは問いであり、`/agents` がインラインボタンでそれに答える。ボタンの文字はボットが選べるので、ボタンには `os-watcher` とだけ書かれ、ほかには何も書かれない。

残りはそこから導かれる。

- **選択したエージェントは固定される。** ボタンをタップするかエージェントの名前を挙げると、そのエージェントが選ばれ、宛先のないものはすべて、別のエージェントが選ばれるまでそこへ行く。毎行エージェントの名前を書くのは、一度ならよいが、4通目にはうんざりする。選択は `settings` に保存し、プロセスのメモリ上には置かない。サービスは更新のたびに再起動するからである。
- **それでも返信が優先される。** 返信には曖昧さがなく、スマートフォンを手にした人が自然にすることである。ほかに選択を変えるものはないので、たまたま最後に話したというだけで、エージェントが会話を引き継ぐことはない。
- **削除されたエージェントは選択されなくなる。** `fReadSelectedAgent` は、読み出すときに名簿を確認する。誰にも届かないほうが、その ID を引き継いだ誰かに届くよりよい。
- **ボットはインストールの言語で話す。** まず `agent_language`、つまりエージェントが答えるのと同じ設定を使う。ボットの言葉はエージェントの言葉と同じ会話に現れるからである。

### API Calls

```text
AgentRun.fSendRecordedRequest → BaseProvider のリクエスト記録器 → api_calls.fRecordCall
API Calls タブ → GET /api/admin/agents/<id>/api-calls
  exec_client.fReadApiCalls → exec_daemon.fVerbReadApiCalls → api_calls.fReadCalls
リクエストを展開 → GET /api/admin/agents/<id>/api-calls/<call_id>
  exec_client.fReadApiCallBody → api_calls.fReadBodyChunk → ストリームされる JSON テキスト
  fBeautifyJson → fHighlightJsonElement → 安全な DOM
```

### Samba

```text
create_agent → fIndexAgent → samba.fProvisionAgent → samba/ + [agent-xxx]
GET /agents/<id>/samba → read_samba → samba.fReadSettings
PUT /agents/<id>/samba → write_samba → samba.fSaveSettings
  検証 → 保護された info + testparm → smbpasswd (stdin) → reload/close-share
SMB 接続 → root preexec --check-share <id> → Samba の権限 → エージェントの uid
delete_agent → samba.fRemoveAgent → Linux ユーザー、ホーム、索引を削除
--backup → tdbbackup + サーバーの SID → アーカイブ内の samba-backup
--restore → サービスを停止 → ユーザー/データを復元 → ネイティブの passdb を置き換え → 開始
```

## 6. 影響分析

これらを変更すると何が壊れるか。

| コンポーネント | 変更が影響するもの |
|---|---|
| `paths.fNormalizeAgentId` | **システム内のすべてのパス。** 利用者の入力とファイルシステム上のパスのあいだにある唯一の検証である。これを弱めると、どのエージェント ID もパストラバーサルになる |
| `paths.py` の定数 | 4つのサービスすべて、インストーラー、systemd のユニット。`/opt/boa` を変えるなら再インストールが必要になる |
| `deploy/haproxy/boa.cfg` | すべてのリクエスト。`accept-proxy` はマシンの HAProxy が送るものと一致していなければならない。そのバックエンドに `send-proxy-v2` があれば必須であり、なければ bind がすべての接続を拒否する |
| `backend/web/gunicorn.conf.py` の bind | Unix ソケットのままでなければならない。gunicorn に再びポートと証明書を与えると、TLS より前に PROXY が届くことによる失敗が再発する |
| `exec_protocol.lKnownVerbs` | 特権を持つ面。動詞を1つ加えることは、Web のプロセスが root に何かを頼む方法を1つ加えることである。追加のたびに、最初の1つと同じ厳しさの精査が必要である |
| `exec_daemon.fRunPrivilegedCommand` | 特権を持つすべてのコマンド。シェルは決して使わない。そこに `shell=True` を持ち込めば、すべてのエージェント名がインジェクションの入り口になる |
| `agent_api.fAuthenticate` | ボードとチャンネルに対するエージェントのすべてのリクエスト。2つの確認はどちらも残さなければならない |
| `db.cAppSchema` / `cKanbanSchema` | 既存のインストール。マイグレーションの仕組みはない。スキーマは `IF NOT EXISTS` を使うので、**新しい列にはスキーマの編集ではなく、明示的なマイグレーションのコードが必要である** |
| `agent_scripts.cMinimumMinuteStep` | エージェントがどれだけ頻繁に自分をスケジュールできるか。不注意なスケジュールと、前に cron の行が付いただけのループとのあいだに立っているのは、これだけである |
| `paths.lProtectedAgentFiles` | どのファイルが root 所有の引き出しに移されるか。インストーラーのマイグレーションと、エージェントを作るデーモンの両方がこれを読むので、それがどのファイルかについて両者の見解が食い違うことはない |
| `agents.fBuildAgentInfo` | 新しいエージェントだけ。既存の `info.json` ファイルには手を付けないので、新しいフィールドには既定値で読む経路が必要である |
| `exec_daemon.fVerbWriteAgentInfo` | **保存の後も残る `info.json` のすべてのフィールド。** ファイルをキーごとに組み立て直すので、ここで名前を挙げていないフィールドは、誰かが最初に「保存」を押したときに画面が黙って捨てるフィールドになる。リストは `fReadNameList` を通じて読む。これは、キーがないこと（「そのままにしておく」）と空のリスト（「すべて取り除く」）を区別する。`or` で読んでいたときは、最後のツールのチェックを外すと前のリストが復活してしまった |
| `skills.fSelectInstalledSkills` | 何がプロンプトに届き、`skill.read` が何を開くか。索引もツールもこれで絞り込むので、サーバーから削除されたスキルは、約束されたうえで失敗するのではなく、言及されなくなる |
| `providers.base` の中立的な形 | すべてのアダプターとランナー |
| `tool_registry` のインターフェース | `/opt/boa/tools/` にあるすべてのツール。利用者が書いたものも含む |
| `telegram_listener.fIsFromTheConfiguredChat` | 誰があなたのエージェントと話せるか。ボットのユーザー名は公開されているので、この確認が認可のすべてである。弱めれば、ボットを見つけた誰もがあなたのサーバーで実行を開始できるようになる |
| `channels.fSendMessage` のシグネチャ | すべての呼び出し元と、2つの引数を取る2つの送信関数。`pReplyToMessageId` は Telegram と Discord に渡される。人が返事をできるのはこの2つのチャンネルだからである |
| `discord_markdown.cMaxDiscordLength` | エージェントの回答がそもそも届くかどうか。Discord は 2000文字を超える `content` を拒否する。Discord がするのは拒否であって、切り詰めではない |
| `agent_routing.fMatchNamedAgent` | **両方の** リスナーで、メッセージが誰に届くか。最長一致があるからこそ、`@News` と `@News Miner` が2つのエージェントになる |
| `agent_routing.fBuildStatusReport` | 両方で /status が何を答えるか。報告は1つなので、サービスがいくつあるかについて2つが食い違うことはない |
| `discord_listener.fIsFromTheConfiguredChannel` | エージェントがどのチャンネルを聞くか。Telegram と違って、誰が話しているかについての2つ目の確認はない。そのチャンネルに書き込める人なら誰でも実行を開始できる |
| `kanban.lStates` | ボード、API、フロントエンド、そしてすべてのエージェントのプロンプト |
| `run_journal` のエントリーの形 | 書き手（ランナー）と読み手（デーモン、Web）の両方。古い行はジャーナルに残るので、読み手は欠けたフィールドを許容しなければならない |
| `samba` | エージェントのライフサイクル、特権 API、SMB クライアント、両インストーラーのバックアップ/復元。フォルダーのガード、名前とパスの導出、秘密情報の扱いはそのまま保つこと |
| デーモンがエージェントのホームから読むファイル（`runs.jsonl`、`chat.jsonl`、`memory.md`） | `paths.fReadAgentOwnedFile` を通じてのみ読む。デーモンがホームから読む新しいファイルも、これを通さなければならない。そうしなければ、root はエージェントが指し示すものを何でも読んでしまう。決して応答しない FIFO や、マシン上の任意のファイルへのリンクなどである |
| バックアップが保持するもの（`fDoBackup` の `tar` の行） | `/opt/boa/` の下に新しく置く状態のうち、コードではなくインストールに属するものは、そこに加えなければならない。そうしなければ、新しいマシンで復元したときに失われる |
| 実行のカーネルの制限（`runner.cMaxProcesses`、`exec_daemon.cRunTasksMax`、`cRunMemoryMax`） | 1024 を超えるタスクや 2 GiB を超えるメモリを必要とするツールは、これを引き上げなければならない。ブラウザーだけでも、すでに数百のスレッドになる |
| パスとしての `runner.py` | スケジュールされたすべての実行。cron はほとんど環境のない状態でパスを指定してこれを起動するので、ランナーは自分のルートを sys.path に加える。そうしなければ `import backend` が失敗し、トレースバックは cron のメールに送られるが、LAN の中のマシンではそれはどこにも届かない |
| `runner.dAnswerLanguageLines` | どの言語で答えるかをエージェントに伝えるために、システムプロンプトに加える行。その言語 **で** 書かれ、プロンプト自体の規則より優先すると明言する。規則の隣に置いた希望は負ける。これは測定済みである |
| `agent_api.fFilterCardsForAgent` | エージェントが何の存在を知ってよいか。ボードの読み取りはすべてこれを通り、オーケストレーターだけが例外である。代わりにツールの中で絞り込めば、モデルが言いくるめられて無視しうる説明文の中に、セキュリティの規則を置くことになる |
| チャットの吹き出しがどちら側に来るか | 誰が話しているか。カードはエージェントが頼まれたことなので、利用者のメッセージと同じ右側に置く。スケジュールされた実行の報告はエージェントが話しているので、左側のままである |
| `chat.lToolsWorthReporting` | どのツールを使えば、スケジュールされた実行をチャットに載せる価値が出るか。それ以外はジャーナルに残る。そうしなければ、1時間ごとのエージェントが「報告することなし」というメッセージを1日に24回投稿することになる |
| `chat.lAskingRoles` | どのロールが回答を待つか。ターンを開くのに一覧に載っていないロールは、エージェントの作業中も入力欄を開いたままにする。一覧に載っているのに決して閉じられないロールは、入力欄を永久に閉ざす |
| `kanban.cRunNow` | ブラウザー、エージェント、API がそろってタイムスタンプの代わりに送る語。`fValidateRunAt` 以外のどこかでこれを時刻に変えると `run_mode` が失われ、それとともに「今すぐ」と選んだ時刻の違いも失われる |
| `chat.cReplayedTurns` | 各チャットメッセージの費用。再生される各ターンは次のメッセージでもう一度支払われるので、これを増やすと、長い会話ほど次第に高くつくようになる |
| `TestThemes` の `lTextColours` | コントラストのテストがどの色を測るか。テキストとして塗られているのにこのリストから漏れた色は、何も確認しない色になる |
| テンプレートの中の `style=` 属性 | 何にも効かない。`style-src` は `unsafe-inline` なしの `'self'` なので、ブラウザーはそれを捨てる。1つでも現れれば失敗するテストがある |
| `app.css` の `.notice-layer` | アプリケーションのすべての確認メッセージとすべてのエラーがどこに現れるか。`position: fixed` が要である。`absolute` では画面ではなく文書の中央に置かれてしまう。それこそが、このレイヤーが直すために存在するバグである |
| `app.css` の `.app:has(#vChatPanel…)` の連鎖と `--status-bar-live-height` | チャットのテキスト欄がステータスバーの上に留まるかどうか。その flex の列に `min-height: 0` のないブロックがあったり、`.chat` の高さが実際のバーの高さを差し引かなくなったりすると、ページが再びスクロールし、入力欄がバーの下に隠れる |
| `agents.fValidateSchedule` | `.zip` やテンプレートから来たスケジュールが、root として書かれる crontab の中でコマンドになりうるかどうか。これを緩めれば（空白、`#`、改行）、インポートがコードの実行に変わる |
| `agent_home.sExcludedTopNames` / `fIsExcluded` | エクスポートが何を漏らしうるか、インポートが何を仕込みうるか: ブラウザーのセッション、`.ssh`、チャット。名前を1つ取り除けば、それは両方向に通り抜ける |
| `agent_package.lManifestKeys` / `cFormatVersion` | エクスポートされたすべての `.zip` と、すべてのリポジトリのすべてのテンプレート。新しいキーは、このバージョンが読めるようにする必要がある。意味を変えるなら、新しい形式番号が必要である |
| `rag_models.json` の `min_support` | そのモデルで、verified の回答のどの段落が残るか。上げれば忠実な段落が消え始め、下げれば無関係な抜粋への引用が通る。両モデルの各値が何を削除し何を通すかは、`rag_verify.py` のチェックの隣にある表に書かれている。値を動かす前に実際の文書で測り直し、表を更新すること |
| `rag_models.json` にあるモデルの `sha256` または `dimensions` | そのモデルでインデックス化されたすべてのライブラリ。新しいフィンガープリントは新しいベクトル空間である。各ライブラリは次の巡回ですべての文書をインデックス化し直し（`fFollowNewModel`）、大きなライブラリでは数時間かかる |
| `rag_embeddings.fCheckServedModel` / `rag_runtime.fServe` の `--alias` | ライブラリが記録しているもの以外のモデルからベクトルが来うるかどうか。これらがなければ、モデルの変更をまたいで動くジョブが、2つのモデルのベクトルを1つのリビジョンに保存してしまう |
| `runner.lRagModesThatSearch` / `fFinishRagAnswer` | documental や verified の実行が、モデル自身の重みから出たテキストを届けうるかどうか。リストからモードを取り除いたり、抜粋なしの確認を取り除いたりすれば、検索の裏付けのない回答が戻ってくる |
| `rag_search.fSource` | 抜粋についてモデルに伝えるすべてと、引用のリンク先。事前に取得したプロンプトのブロック、`rag.search`、`rag.read`、`fResolveCitations` のすべてがこれを使う。ここにフィールドを加えるなら、これに供給する3つの `SELECT` にもその列が必要である |
| `rag_embeddings.EngineUnavailable` | インデックス作成の失敗が作業を残すか捨てるか。停止に対して通常の `ValueError` を送出すれば文書は `error` になり、ベクトル化済みのチャンクが削除される。恒久的な拒否に対して `EngineUnavailable` を送出すれば、文書は永久にキューに残る |
| `rag_store.cSchema` | 変更の後に作られたカタログだけ。既存のエージェントのライブラリも、復元したバックアップも、古いテーブルのままである。新しい列には `rag_store.lAddedColumns` のエントリーも必要で、それを `fMigrate` が適用する |

### 新しいツール

`/opt/boa/tools/` に `.py` を1つ作り、次を宣言する。

```python
cToolName = "namespace.verb"
cToolDescription = "What the model is told it does."
dToolSchema = {"type": "object", "properties": {...}, "required": [...]}

def fRunTool(pArguments, pContext):
  return "text the model sees"
```

ツールは呼び出したエージェントとして動く。エージェントが届いてはならないものが必要なら、代わりにエージェントAPIに動詞を加え、`agent_api_client` を通じてそれを呼ぶ。

ファイルの所有者は root でなければならない。アプリケーションはそれをコードとしてインポートするからである。

### 新しいスキル

`/opt/boa/skills/` にディレクトリを作り、その中に `SKILL.md` を置く。

```markdown
---
name: BackupVerification
description: One line. This is what every run pays for.
---

The procedure, at whatever length it needs.
```

登録するものはなく、再起動も要らない。`fListSkills` がディレクトリを読むので、次にページを読み込んだときに画面に現れる。エージェントでそれにチェックを入れ、そのエージェントに `skill.read` を与えれば、次の実行からそのプロンプトに入る。

ディレクトリ内のほかのものはすべて、スキルと一緒に配布される。誰でも読めるので、スキルに「このディレクトリの `verify.sh` を実行せよ」と書けば、エージェントはそれを実行できる。

名前はディレクトリ名であり、英字、数字、ハイフンからなり、英字で始まる。ヘッダーの `name:` は人が一覧で目にするもので、ディレクトリ名はエージェントが求めるときに使うものである。

### 新しい特権操作

2. `exec_daemon` に `fVerb<Name>` を書き、`dVerbHandlers` に加える。
3. `exec_client` にラッパーを加える。

すべての引数を、パスやコマンドラインに届く前に検証し、動詞は用途を限ったものにしておくこと。再利用できるほど汎用的な動詞は、たいてい悪用できるほど汎用的な動詞でもある。
