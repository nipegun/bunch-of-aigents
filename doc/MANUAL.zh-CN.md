## 它能做什么

- **智能体就是一个 Linux 用户。** 在 Web 界面中创建一个智能体，就会在系统上创建 `agent-007`，并配有一个其他智能体都读不到的主目录。这就是隔离：由内核实现，而不是用 Python 写成的沙箱。
- **智能体按自己的计划运行。** 每个智能体都有自己的 crontab，归它自己的用户所有并由该用户执行，所以智能体会按时醒来、完成工作，然后退出。
- **你可以和它们对话。** 点击一个智能体就会打开对话：让它做点什么，它会使用自己的工具，完成后给出回答。对话会被记住。
- **每个智能体一段对话，而不是每个人一段。** 到期的卡片会在运行开始时贴进同一段对话，回答出现在它下方，因此智能体的对话就是它被要求做的一切（无论是你还是别的智能体提出的），以及它对此做了什么。
- **它们共享一块看板。** 智能体添加卡片、移动卡片，也能看到彼此的工作。你在 `/kanban/` 上观看，而不必去读日志。
- **任何模型都行，云端或自托管均可。** 内置二十五个服务商：Anthropic、OpenAI、Google、DeepSeek、Mistral、Qwen、xAI 等；位于它们前面的路由服务，如 OpenRouter、Groq、Together、Vercel 等；以及在你自己硬件上运行的 Ollama、llama.cpp 和 vLLM。每个智能体各选各的，还可以配一个备用模型，在主模型不可用时顶上。
- **真正能让它停下来的开销上限。** 按智能体设置 token 数、步数、秒数和每天的运行次数。否则，一个在付费 API 上无人看管的智能体就等于一张空白账单。
- **可配置的记忆。** 在每个智能体的设置中选择它的记忆上限，范围为 1,000 到 1,000,000 个字符（默认 8,000）。超出上限的写入会被拒绝，既不会截断文本，也不会替换已保存的记忆。
- **每个智能体一个文档库。** 上传 PDF、EPUB、TXT 或 Markdown 格式的书籍。文本提取、OCR 和向量化都留在本地；智能体检索相关片段并注明出处。在 **RAG** 中进行配置。向量化模型默认是 EmbeddingGemma 300M；处理器和内存有富余的机器可以在 **设置 → RAG** 中改用 Qwen3-Embedding 0.6B。
- **可以搬迁的智能体。** 智能体的 **导出** 标签页会把它下载为 `.zip`（可以选择附带它的记忆、模型、文档库和主目录文件，但绝不包含密钥），而 **+** 可以在本安装或另一套安装中导入它。现成的智能体来自[模板仓库](https://github.com/nipegun/bunch-of-aigents-templates)。
- **可以扩展的工具。** 每个工具就是 `/opt/boa/tools/` 中的一个 `.py` 文件。放进一个新文件，它就会出现在 **设置 → 工具** 中，并按“自动化”“浏览器”等子标签页分组。
- **它们共享的技能。** 在 `/opt/boa/skills/` 中写一次的流程，可以授予任意多个智能体。智能体自己学到的东西只会困在它自己的记忆里；技能则不会。
- **每个智能体一个浏览器，各有自己的会话。** 智能体可以登录网站、填写表单、点击按钮，而不只是读取页面；它的 cookie 存放在它自己的 0700 主目录中，所以一个智能体的登录不会变成所有智能体的登录。
- **从 Telegram 或 Discord 回复它们。** 用 /agents 选择一个智能体，或者回复某个智能体发给你的消息，你写的内容就会送达它、启动一次运行，并把回答送回你的手机。整个往来的双方内容也都会出现在 Web 界面中该智能体的对话里，所以一个界面仍然能显示一切。
- **Telegram 音频。** **设置 → 音频** 可以选择本地的 whisper.cpp，或者借助已保存的 API 密钥使用 OpenAI、Groq、Mistral、Together AI、Hugging Face 或 Cloudflare。全部 30 个本地模型都可供选择，按需下载。语音回复会以文字形式送达原来的智能体，并显示在网页对话中，还可以选择播放音频。
- **每个智能体一个共享文件夹。** 每个智能体的 `samba/` 文件夹都是一个以其 Linux 用户命名的 SMB 共享，所以你可以从 Windows、Linux 或 macOS 把文件放进去。
- **十五种语言。** 德语、英语（英国和美国）、西班牙语（西班牙和阿根廷）、法语、希伯来语、印地语、意大利语、日语、韩语、葡萄牙语（巴西和葡萄牙）、俄语和简体中文。涵盖界面、告诉智能体用哪种语言回答的那一行，以及两个机器人说的话。

它是为在自己局域网中运行它的单个用户打造的。

## 运行环境

支持两种系统，而且在每种系统上，init 系统都是要求的一部分，而不是可以忽略的细节：

- **以 systemd 为 PID 1 的 Debian。** 十个服务都是 systemd 单元。在用别的东西启动的 Debian 上，没有任何东西能启动它们，所以安装脚本在动这台机器之前会先检查 `systemctl is-system-running`，没有 systemd 就拒绝安装。不要在这样的机器上尝试：结果不会改变。
- **使用 OpenRC 的 Alpine。** 十个服务都是由 `supervise-daemon` 监管的 OpenRC 脚本。无需预先安装任何东西：机器上没有 `openrc` 时，安装脚本会自己装上。

在 Debian 上用 `systemctl is-system-running` 检查：它必须给出回答（`running`、`degraded`、`starting`），而不是打印“System has not been booted with systemd as init system (PID 1)”。容器需要安装 `systemd systemd-sysv dbus`，并以 `/sbin/init` 作为其命令。

除了 init 系统，它还需要：

- `root` 权限。两个安装脚本都不使用 `sudo`，也都不需要它。
- 约 500 MB 磁盘空间，用于应用程序及其 Python 环境。
- `haproxy`，由安装脚本安装。它负责终结 TLS，因为本机 HAProxy 发来的 PROXY 头部在 TLS 握手之前到达，只有代理才能在那个位置读取它。
- 一个可以对话的模型：要么是某个云服务商的 API 密钥，要么是在你能访问到的地方运行的 Ollama、llama.cpp 或 vLLM。

安装脚本还会在 `/opt/boa/whisper/` 中编译 **whisper.cpp v1.9.4**，安装 FFmpeg，并下载多语言的 `base` 模型（额外约 142 MiB）。编译、系统依赖和浏览器还需要额外的磁盘空间。如果缺少 Python 解释器，会先安装它，再检查其版本。

本手册的其余内容在两种系统上都一样。

## 如果你用的是 Alpine

本手册中凡是提到 `systemctl` 或 `journalctl` 的命令，都是 Debian 上的命令。应用程序在 Alpine 上完全相同；变化的是 init 系统和日志的去向：

| 在 Debian 上 | 在 Alpine 上 |
|---|---|
| `systemctl status boa-web` | `rc-service boa-web status`，或用 `rc-status` 查看全部十个 |
| `systemctl restart boa-web` | `rc-service boa-web restart` |
| `journalctl -u boa-web -f` | `tail -f /opt/boa/logs/boa-web.log` |
| `install-update-reinstall-debian.sh` | `install-update-reinstall-alpine.sh` |

那里缺少一项功能，而且不会再回来：没有浏览器，因为 Playwright 没有为 musl 发布构建。浏览器工具仍然留在列表中，智能体调用时它们会说明这一点。

## 安装

每个发行版一个安装脚本，两者接受相同的标志。请以 `root` 身份运行。

### 在 Debian 上

> **机器上必须运行着 systemd。** 先运行 `systemctl is-system-running`：如果它打印“System has not been booted with systemd as init system (PID 1). Can't operate.”，就到此为止。这里安装的每个服务都是 systemd 单元，所以不会有任何东西来启动它们；安装脚本正因如此才拒绝安装，而不是留给你一套什么服务都不提供的安装。

```bash
curl -fsSL https://raw.githubusercontent.com/nipegun/bunch-of-aigents/main/deploy/install-update-reinstall-debian.sh \
  | bash -s -- --install --email you@example.com
```

如果没有安装 `curl`（精简版 Debian 往往既没有它也没有 `wget`），请先装上，否则上面那行会打印 `curl: command not found` 然后停止：

```bash
apt-get update && apt-get install -y curl
```

或者先下载安装脚本，读一遍再运行，这是更好的习惯：

```bash
wget https://raw.githubusercontent.com/nipegun/bunch-of-aigents/main/deploy/install-update-reinstall-debian.sh
less install-update-reinstall-debian.sh
chmod +x install-update-reinstall-debian.sh
./install-update-reinstall-debian.sh --install --email you@example.com
```

### 在 Alpine Linux 上

标志相同，脚本不同：它写的是 OpenRC 服务，而不是 systemd 单元。只需一行，用 `wget` 并通过管道交给 `sh`，因为全新的 Alpine 既没有 `curl` 也没有 bash，而 `wget` 和 `sh` 都由 BusyBox 提供：

```bash
wget -qO- https://raw.githubusercontent.com/nipegun/bunch-of-aigents/main/deploy/install-update-reinstall-alpine.sh \
  | sh -s -- --install --email you@example.com
```

在装有 `curl` 的机器上，可以用 `curl -fsSL` 代替 `wget -qO-`；但如果这样做，要留意那一行，因为 `curl: not found` 通过管道交给 `sh` 后，会打印错误，然后**成功**退出，而什么都没有安装。

安装脚本用的是 POSIX shell 而不是 bash，原因和用 `wget` 一样：全新的 Alpine 上没有 bash 可供 `| bash -s --` 调用。它在安装过程中会顺带装上 bash（每个智能体都会获得一个 bash shell），所以在已经有 bash 的机器上，`| bash -s --` 同样可用。

或者先下载，读一遍再运行：

```bash
wget https://raw.githubusercontent.com/nipegun/bunch-of-aigents/main/deploy/install-update-reinstall-alpine.sh
less install-update-reinstall-alpine.sh
chmod +x install-update-reinstall-alpine.sh
./install-update-reinstall-alpine.sh --install --email you@example.com
```

装好之后有两点不同，两者都是系统本身造成的，而不是设计上的决定：

- **没有浏览器。** Playwright 没有为 musl 发布构建，Alpine 也没有打包，所以智能体调用 `browser.open` 等工具时，它们会说明这一点。`web.fetch` 和 `rss.fetch` 的工作方式与其他地方相同。
- **用 `rc-status` 代替 `systemctl status`**，用 `rc-service boa-web restart` 代替 `systemctl restart boa-web`。参见[如果你用的是 Alpine](#如果你用的是-alpine)。

在 Alpine 上，服务会释放安装脚本的 SSH 输出，所以安装脚本结束时会交还会话的控制权。

### 安装脚本做了什么

1. 创建 `boa` 系统用户和 `/opt/boa/` 下的目录树。
2. 把 Python 依赖安装到 `/opt/boa/venv/`。
3. 生成一张自签名 TLS 证书，除非你已经在 `/opt/boa/certificates/` 中放了自己的 `fullchain.pem` 和 `privkey.pem`。
4. 询问是让应用在 11080/11443 上提供服务、前面由一个在 80 和 443 上的 HAProxy 转发，还是直接在 80 和 443 上提供服务。传入 `--ports proxied|direct` 可以事先回答这个问题。答案会被记住，所以 `--update` 既不会再问，也不会悄悄改掉它。选择 `direct` 会让机器自己的 HAProxy 退役：停止它，把它移出所有运行级别或将其屏蔽；它的 `/etc/haproxy/haproxy.cfg` 如果是本安装脚本写的就删除，如果是别人写的就保留为 `haproxy.cfg.before-boa.<date>`，这样下次启动时就不会有任何东西占用 80 和 443。haproxy 软件包本身会保留：应用自己的代理用的就是这个二进制文件。
5. 创建一个智能体：编排者 `manager`。其他的一切，都是在你按下 **+** 时选择的空白智能体、从智能体导出的 `.zip`，或者[模板仓库](https://github.com/nipegun/bunch-of-aigents-templates)中的模板（`web-navigator`、`os-watcher`、`mail-watcher` 等）。空白智能体是提供的第一个选项。
6. 安装并启动[服务](#服务)中列出的服务：在 Debian 上是 systemd 单元，在 Alpine 上是由 `supervise-daemon` 监管的 OpenRC 服务。
7. 把它做了什么以及你的登录密码写入 `/opt/boa/logs/install.log`（属于 root，权限 0600）。
8. 在宣布完成之前，先向应用请求它的登录页。如果页面没有返回，它会如实说明，把那一刻机器的状况写进同一个日志（curl 对这个请求的处理结果、端口上是否有程序在监听、各服务的状态，以及它们最后打印的几行），并指出这个日志，而不是报告成功。`--update` 还会先把上一个版本恢复回来。

### 密码在哪里

你提供的电子邮件地址是唯一的登录名。密码会为你生成；用下面的命令查看：

```bash
cat /opt/boa/logs/install.log
```

这一个文件身兼二职：既是安装的完整日志，也存放安装时生成的凭据。登录页会写出它的位置，所以谁都不必记住它在哪里。

## 更新与重新安装

```bash
./install-update-reinstall-debian.sh --update      # 保留智能体和数据
./install-update-reinstall-debian.sh --reinstall   # 先删除一切
```

在 Alpine 上是同样的两个标志，用在另一个脚本上：

```bash
./install-update-reinstall-alpine.sh --update
./install-update-reinstall-alpine.sh --reinstall
```

`--reinstall` 会删除所有智能体、主目录、crontab 以及看板。除非传入 `--yes`，否则它会要求确认。

中途夭折的安装（下载失败、网络断开）只要再次运行 `--install` 就能完成：它会从中断的地方接着做；如果 `--update` 发现了这样的安装，也会如实告诉你。

另外两个标志 `--backup` 和 `--restore`，在[备份与恢复](#备份与恢复)中说明。

## 打开界面

在默认的 `proxied` 模式下，应用自己的 HAProxy 监听 `127.0.0.1:11443`（HTTPS）和 `127.0.0.1:11080`（HTTP，会重定向）。这些端口从服务器外部无法访问：为局域网提供服务的是机器自己的 HAProxy，它用 `send-proxy-v2` 转发到 11443，好让真实的客户端地址保留下来。在 `direct` 模式下，应用自己监听 80 和 443，前面没有任何东西。

一切就绪后，打开：

```
https://your-server/
```

除非你在 `/opt/boa/certificates/` 中放了自己的证书，否则证书是自签名的，所以浏览器会警告你一次。

### 本机 HAProxy 应有的配置

指向本应用的后端需要两样东西：

```
backend https-out
  mode tcp
  server srv-https-out 127.0.0.1:11443 check port 11080 send-proxy
```

- **`send-proxy`**，让真实的客户端地址到达应用。没有它，每个请求看起来都来自 127.0.0.1，登录频率限制也就不再按地址计算。
- **`check port 11080`**，让健康检查去敲明文 HTTP 端口，而不是 TLS 端口。针对 TLS 端口的 TCP 检查会连上后不握手就挂断，应用自己的 HAProxy 会把每一次都记录为一次 SSL 握手失败：每两秒一行，永无休止。两个端口属于同一个进程，所以一个有应答就说明另一个也在。不要加 `check-send-proxy`：11080 不接受 PROXY 协议。
- **不要用 `option ssl-hello-chk`。** 它的 ClientHello 早于 TLS 1.2，所以要求 TLS 1.2 的后端（本应用，以及任何现代的 Apache 或 nginx）都无法通过这项检查，并被永久标记为宕机。症状是一个运行得好好的服务返回 503。一个普通的 `check` 就已经能验证端口有应答。

## 登录

打开 `https://your-server/`，用你提供给安装脚本的电子邮件地址和它生成的密码登录。如果你手头没有密码：

```bash
cat /opt/boa/logs/install.log
```

这个文件是完整的安装日志，凭据就在它的末尾；登录页写出它的位置，正是为了这一刻。

**退出登录** 会在屏幕中央打开一个确认框。确认即可结束会话；选择 **取消** 或按 Escape 则保持登录。

只有一个账户。在 **设置 → 账户** 中修改它的密码。修改时还会要求输入当前密码：正是这一点，让这成为你本人的修改，而不是碰巧发现浏览器开着的人所做的修改。修改还会立即结束其他所有设备上的所有其他会话，而当你认为别人也有一个会话时，这正是修改密码的意义所在。

更新之后第一次打开应用时，它会要求你重新登录。更新之前的会话没有记录它们是何时授予的，而遇到“我无法判断”的情况，答案就是询问。

同一地址失败十次之后，登录会关闭十五分钟，即使密码正确也一样。

## 首次运行

1. 用你的电子邮件和生成的密码登录。
2. 如果智能体要使用云服务商，先在 **设置 → API 密钥** 中保存它的密钥：服务商列表只会提供已有密钥的云服务商（参见 [API 密钥](#api-密钥)）。
3. 在侧边栏中按 **+**，创建你的第一个智能体。
4. 选择它的服务商和模型。如果是同一台机器上的 Ollama，默认值就已经正确。要把这一个智能体的费用记到另一个账户上，就给它一个自己的密钥（参见[为智能体指定模型](#为智能体指定模型)）。
5. 编写它的系统提示词：它是做什么的，以及怎样才算“完成”。
6. 给它所需的工具。先从看板工具开始。
7. 按 **立即运行**，然后观察看板。
8. 当它做到了你想要的，再给它安排计划。

## 界面

圆形的蓝色标志上画着三个机器人智能体：浅色面板、深色护目镜、蓝色眼睛，身穿黑色西装和白衬衫，系着深色领带。它们都只露出腰部以上，中间的那个更大。标志出现在登录页、侧边栏和浏览器标签页上。

左侧的侧边栏列出你的智能体。每一项显示它的 ID、名称、运行过多少次以及花了多少 token。每个框的高度都相同，所以过长的名称会以省略号截断，把鼠标悬停在上面就能看到全名。智能体启用时，ID 外面的方框有一圈绿色边框；未启用时则是红色边框。

**智能体工作时，一段亮起的光会沿着那圈绿色边框顺时针移动。** 它告诉你，智能体此刻正处于一次运行之中：不是告诉你它在做什么，只是告诉你它正在做事。你给它发送对话消息或按下 **立即运行** 时，它就开始转动，运行结束时停止，无论这次运行来自你、来自它的计划，还是来自一张到期的卡片。边框的状态每隔几秒检查一次，所以可能会稍有滞后。

侧边栏底部有两个圆点，显示后台服务是否在运行。只要其中一个是红色，智能体就不会运行——参见[出了问题怎么办](#出了问题怎么办)。

**+** 按钮用于创建智能体。

## 初始自带的智能体

安装只会创建一个。

**`manager`（agent-000）** 负责协调其他智能体。它把目标拆分成卡片并分派出去。它从一开始就是启用的。

刻意只有这一个：一套安装如果自带没人要求的智能体，一开始就得先去关掉一些东西。其他的一切，都是你按下 **+** 时提供的模板仓库中的**模板**，或者别人导出的 `.zip`。

## 新智能体从哪里来

按下 **+**，系统会问你从哪里开始：

| 选项 | 作用 |
|---|---|
| **空白智能体** | 没有提示词、没有工具、没有计划任务。由你自己来写。 |
| **从 .zip 文件导入** | 从它的 **导出** 标签页导出的智能体，来自本安装或另一套安装。 |
| **从 GitHub 模板导入** | 从模板仓库的列表中选择一个智能体。 |

**空白智能体** 排在列表首位，因为它是唯一永远正确的答案，其他每一种都只是通往它的捷径。

### 来自 GitHub 的模板

模板放在它们自己的仓库 [bunch-of-aigents-templates](https://github.com/nipegun/bunch-of-aigents-templates) 中，每个模板一个文件夹，所以新模板无需更新你的安装就能到达你那里。当你选择 **从 GitHub 模板导入** 时，服务器会下载这个仓库（一个 `.tar.gz`，保留五分钟），并按字母顺序列出其中的智能体，每个都附有用你的语言写的描述、它自带的工具类别、它多久醒来一次，以及它是否启用自己的文档库。本安装没有的工具会被略去，列表会说明这一点。未通过检查的模板不会被提供，并有一行说明略去了多少个。

以下是仓库目前包含的模板：

| 模板 | 作用 |
|---|---|
| **backup-watcher** | 检查你的备份是否运行过、是否够新，以及大小是否小得可疑。 |
| **cert-watcher** | 在 TLS 证书即将过期、还来得及处理时发出警告。 |
| **disk-cleaner** | 找出是什么占满了磁盘，并说明哪些可以删掉。只提建议，从不删除。 |
| **kanban-watcher** | 每个工作日早上读一遍看板，写一份简短的摘要。 |
| **log-watcher** | 阅读你指定的日志，报告新出现的或突然变频繁的内容。 |
| **mail-watcher** | 监视一个邮箱，并按照你写进它提示词里的规则处理收到的邮件。 |
| **news-watcher** | 阅读你在它提示词中列出的 RSS 订阅源，报告符合你规则的内容。 |
| **os-watcher** | 监视这台机器：磁盘、内存、交换分区、负载，以及各服务是否在运行。 |
| **rag-consultant** | 依据其 RAG 文档库中的文档回答问题，为每个论断注明所依据的片段，文档没有涉及时会如实说明。 |
| **site-watcher** | 检查你列出的网站是否有应答、应答是否够快，以及内容是否仍和以前一样。 |
| **web-navigator** | 驾驶它自己的浏览器，在网站上完成你交代的事情：搜索、登录、填写表单、逐页点击，并报告它找到的东西。 |

`web-navigator` 和 `rag-consultant` 没有计划：你让它们干活时它们才干活，而请求本身就是任务。`web-navigator` 也是那个展示浏览器为何要安装的智能体：别的智能体只读页面，它却会登录、点击、填写表单。它不会输入密码、不会购买任何东西，也不会按下发送按钮：它会走到那一步就停下，并告诉你按哪个按钮就能完成任务。

`rag-consultant` 依据它自己的文档库回答，它也是唯一一个到来时就已启用文档库的模板：文档库关闭时，它的工具会被扣下。在它能派上用场之前，先在它的 **RAG** 标签页中上传文档（参见[本地文档库](#本地文档库rag)），并选择一个模型。它回答中的每个陈述都会链接到其出处文档的对应页；文档没有涉及的内容，它会如实说明，而不是自己去填补空白。它的 token 上限（每次运行 40,000）比其他模板高，因为它读取的片段也要计入其中。

每个模板在你选择之前，都会说明它自带哪些工具类别、多久醒来一次。模板既是一段提示词，也是一组权限：“监视一个邮箱”并不会告诉你它一来就能删除邮件。

每个模板到来时都是**关闭的，并且没有模型**：选择一个模板，你会得到它的提示词、工具和一个建议的计划，然后它会等你选择服务商并把它打开。

它们只是起点。提示词、工具、计划，统统都可以改；其中有几个还会在自己的提示词里说明，在它们派上用场之前需要你填写什么，而不是在凌晨三点出错。

**设置 → 智能体** 会显示列表来自哪个仓库和分支：默认是项目自己的仓库，也可以是一个 fork，或者你自己的、布局相同的仓库。无法访问 GitHub 的机器可以使用一个包含 `archive/refs/heads/<branch>.tar.gz` 的 `file://` 路径，这与安装脚本接受的布局相同。仓库无法访问时，列表会说明是哪个地址失败了；导入 `.zip` 仍然可用。

### 导入 .zip

1. 选择 `.zip`。它会分块上传并显示百分比，所以几百 MiB 的文档库也能传上去。
2. 服务器会先检查整个软件包，然后才做别的事。其中不得包含：指向智能体主目录之外的路径、`.ssh` 或 `.bashrc` 之类的隐藏文件、对话或运行日志，或者带有命令的计划。有问题时会告诉你问题是什么，并且不会创建任何东西。
3. 你会看到它将带来什么：它的描述、工具（以及本安装缺少的工具）、计划，以及它是否附带记忆、主目录文件、文档库文档或模型。确认后，给它起个名字。
4. 它在后台安装，进度显示在屏幕上。文档库文档会逐个上传，并在这里重新建立索引。如果中途出了任何问题，这个智能体会被再次删除，而不是留下一个装了一半的智能体。

导入的智能体到来时同样是**关闭的**。如果它指定了某个服务商，就必须在本安装中设置该服务商的密钥：密钥从不随 `.zip` 传递。

如果你根本不想被问，可以在 **设置 → 界面** 中关闭 **询问新智能体从何开始**：这样 **+** 会直接创建一个空白智能体。

### 没有哪个智能体拥有 root

一个都没有，编排者也不例外。这就是整个隔离模型，值得讲清楚，因为它决定了像 `os-watcher` 这样的智能体能做什么：

- **查看不需要特权。** `df`、`free`、`uptime`、`nproc`、`systemctl is-active` 都能以普通用户身份运行。智能体可以在磁盘被占满之前很久，就看到它正在被填满。
- **修复通常需要特权，而它没有。** 提示词告诉它要准确说出它会运行什么，而不是尝试后失败：一张写着“需要 root：journalctl --vacuum-size=200M 大约能释放 1.2G”的卡片，比一次失败的尝试更有价值。

如果你希望某件事能自动修复，就把那条命令放进 root 自己的 crontab。一个智能体自作主张地以 root 身份删除文件，可不是谁在凌晨三点想要的功能。

## 创建你的第一个智能体

按 **+**，选择空白智能体、`.zip` 或模板，再给它起个名字。这会在服务器上创建：

- Linux 用户 `agent-001`，
- 它位于 `/opt/boa/agents/001/` 的主目录，权限 0700，
- 主目录中的 `info.json`、`system-prompt.md` 和一个 API 令牌。

ID 是最小的空闲编号。`000` 保留给编排者。

新智能体一开始只有看板工具，别无其他，上限也设得比较保守。它没有计划，所以在你给它安排计划或按下 **立即运行** 之前，它什么都不做。

## 与智能体对话

在侧边栏中点击一个智能体，就会看到它的对话。输入你想让它做的事，然后按 Enter；Shift+Enter 换行。

输入框固定不动，就在页面底部状态栏的正上方：只有它上方的对话会滚动，所以它永远不会被遮住，你也不必向下滚动去找它。输入框为空时，它会用灰字提醒你 Enter 键的行为（或者提醒你智能体仍在工作）；在窄屏手机上，它会多长出一两行，确保这条提醒不会被截断。

一条消息就是一次运行：智能体使用它的工具、完成工作，结束后给出回答。这可能需要几分钟，所以在它工作期间输入框是禁用的，回答到达时就会显示出来。每条回答都会显示它的花费，以 token 数和步数计。

回答以 Markdown 渲染（标题、表格、列表、引用和代码块），因为模型就是这样写的。你自己的消息则完全按你输入的样子显示。只有指向 http 或 https 的链接才会成为链接；其他的一律保持原来的文本。

对话会被记住。每发一条消息，最近十轮往来都会重新发给模型，这样智能体就知道你们在聊什么——也正因如此，长对话中每条消息的花费比短对话更高。**清空对话** 会重新开始。

与智能体对话**不**计入它每天的运行次数上限：这个上限是为了拦住无人看管的计划任务，而不是为了不让你打字。每次运行的 token、步数和时间上限则照样适用。

每个智能体都有自己的对话，存放在它自己的主目录中，任何智能体都读不到你对另一个智能体说的话。

对话不只是你输入的内容。当这个智能体的某张卡片到期时，这张卡片会在运行开始的那一刻贴进同一段对话，运行的回答出现在它下方——所以打开一个智能体，就能看到它被要求做的一切（无论是你还是别的智能体提出的），以及它对此做了什么。参见[卡片运行时](#卡片运行时)。

### API Calls

智能体的名称显示在“聊天”和“API Calls”两个标签页的上方。默认只显示 **聊天**。要显示另一个标签页，打开智能体的扳手，选择 **界面**，打开 **显示 API Calls 标签页**，然后按 **保存**。这个选择会针对该智能体保存在服务器上。打开或重新加载一个智能体时，总是从“聊天”开始，即使已经启用了 API Calls。

**API Calls** 显示实际发出的 JSON，包括该请求中发送的完整智能体提示词、对话、工具定义和工具结果。最新的请求是展开的；展开另一次调用即可查看它。智能体运行时会不断出现新的调用，包括失败的请求、SDK 重试以及对其备用模型的调用。缩进和颜色让 JSON 易于阅读，既不必把它渲染成对话，也不会对较大的数字标识符进行舍入。

最近 100 个完整请求与对话分开保存。清空聊天不会清除它们。记录从这个版本开始；更早的请求无法重建。身份验证标头不会被记录。

## 智能体设置

标题显示 **代理 001 的设置**，其中是所选智能体的 ID。**立即运行** 只出现在包含“聊天”和“API Calls”的工作区中。要删除一个智能体，打开 **常规 → 删除代理**，并在对话框中确认其名称。删除是位于“身份”下方的一个单独部分。


对话是点击智能体时看到的内容。其他的一切（模型、工具、上限、系统提示词、计划）都在侧边栏中智能体框右侧的**扳手**后面。

## 导出智能体

智能体设置的最后一个标签页 **导出**，会把它下载为一个 `.zip`，可以用 **+ → 从 .zip 文件导入** 在本安装或另一套安装中安装。它的配置、系统提示词和计划总会包含在内。另有四样东西只有在你勾选时才会包含，每个复选框都会事先说明它会添加什么：

| 选项 | 添加的内容 |
|---|---|
| **记忆** | 它的 `memory.md`，并注明其中有多少个字符 |
| **提供方和模型** | 它使用哪个服务商和模型。绝不包含密钥 |
| **文档库文档** | 其文档库的原件及其信息（标题、年份……）。它们会在导入的地方重新建立索引 |
| **主目录中的文件** | 它的脚本、它的 `samba` 文件夹，以及它在主目录中存放的其他任何东西。其中可能有你不想分享的内容，所以在下载之前会显示文件列表 |

有些东西无论你勾选什么都不会包含：API 密钥、智能体自己的令牌、频道凭据、它的对话、运行日志、浏览器会话，以及主目录中的隐藏文件。它的 crontab 中只有启动该智能体的计划会被带走，别人在那里输入的其他命令则不会：一个携带命令的 `.zip`，会在导入它的机器上运行这些命令。

## Samba 共享文件夹

每个智能体的主目录中都有一个 `samba/` 文件夹，会自动以它的 Linux 用户名导出。例如，共享 **agent-001** 只指向 `/opt/boa/agents/001/samba/`。在“常规”中给智能体改名，不会改变共享的名称。主目录的其余部分和受保护的配置不会被导出。

1. 打开智能体的 **扳手 → Samba**。
2. 输入至少 8 个字符的 **新的 Samba 密码**，选择权限，然后按 **保存**。
3. 打开标签页中显示的 Windows 或 SMB 地址（Windows 上是 `\\server\agent-001`，Linux 和 macOS 上是 `smb://server/agent-001`），用显示的用户名和那个密码登录。

共享一开始就是启用的，在服务器的共享列表中可见，配置为读写访问，访客访问处于关闭状态。在第一次带身份验证的连接之前，请在这个标签页中设置它的密码。以后保存时如果密码框留空，就会保留现有密码。Samba 凭据与 Linux 登录凭据是分开的；设置它们不会解锁智能体的 Linux 账户。

| 设置 | 效果 |
|---|---|
| 共享此文件夹 | 打开或关闭这个资源，而不删除其中的文件 |
| 身份验证 | 默认使用智能体用户名/密码；只有明确选择时才允许访客访问 |
| 权限 | 通过 SMB 只读或读写；智能体仍然可以处理自己的本地文件 |
| 可见性和描述 | 是否出现在服务器的共享列表中，以及它的描述 |
| 新文件/文件夹权限 | 八进制 Unix 模式，初始为 `0600` / `0700`；现有文件保留其模式 |

共享名称和路径是固定的。文件夹对其 Linux 所有者保持私有。保存更改后的访问设置会关闭此共享的现有连接，让客户端以新权限重新连接。其他智能体的共享不受影响。密码本身从不由 API 返回，也不保存在 `info.json` 中。

`--update` 会为现有智能体（包括 `agent-000`）添加 Samba 文件夹和共享。删除智能体时，会连同其主目录一起删除它的共享和 Samba 账户。`--backup` / `--restore` 会保留共享数据、设置、Samba 密码和账户身份。恢复时会检查保存的 Web 端口模式，包括直接在 443 上提供服务的安装。

Samba 使用 TCP **445** 端口，与 Web 代理无关。在 Docker 中，这个端口必须显式发布。BoA 运行它自己的 `boa-samba` 服务，配置和密码数据库都在 `/opt/boa/samba/` 下；它不会覆盖或接管另一个 Samba 服务器的配置，安装脚本也会拒绝接管一个不由它管理的现有 Samba 安装。

有一个服务商需要在密钥框中填两个值：**Cloudflare Workers AI** 用账户 ID 构建它的地址，所以它的密钥写成 `account-id:api-token`，两部分都来自 Cloudflare 控制台。**设置 → API 密钥** 中的框会说明这一点。

模型字段会建议该服务商提供的模型，并在你输入时过滤列表——但它是一个普通文本框，所以今天早上才发布的模型也可以直接输入。这些建议来自 `/opt/boa/config/providers/<provider>.json`，你可以在服务器上编辑它；更新永远不会覆盖你改过的文件。

自托管服务商如果和应用运行在同一台机器上，就不需要别的东西。

**基础 URL** 只对 `ollama`、`llamacpp` 和 `vllm` 显示，它是你自己的服务器监听的地址——默认值是本机上的常用端口，模型和应用运行在一起时它就是正确的。选择云服务商，这个框就会消失：那个地址是固定的，本安装已经知道它，在那里放一个框唯一能起的作用，就是让一个拼写错误弄坏一个正常工作的智能体。备用模型也是如此。

对于云服务商，最简单的方法是设置中的 **API 密钥** 标签页，该服务商上的每个智能体随后都会使用它。要给这一个智能体一个不同的密钥，请以 root 身份把密钥写进它自己的主目录：

```bash
mkdir -p /opt/boa/agents/001/keys
echo "sk-..." > /opt/boa/agents/001/keys/anthropic.key
chown -R agent-001:agent-001 /opt/boa/agents/001/keys
chmod 700 /opt/boa/agents/001/keys
chmod 600 /opt/boa/agents/001/keys/anthropic.key
```

文件名就是服务商名称。每个智能体只读取自己的密钥，所以一个智能体无法花掉另一个智能体的预算。

### API 密钥

设置中有一个 **API 密钥** 标签页：每个云服务商一个密钥，由使用它的所有智能体共享。自托管服务商不在列表中，因为它们不需要密钥。

密钥保存在 `/opt/boa/config/apikeys/<provider>.key` 中。目录权限为 `0700`，文件为 `0600`，都归 Web 用户所有，所以任何智能体都读不到其中任何一个：既读不到别的服务商的密钥，也读不到它自己的。智能体运行时，智能体 API 会把**该智能体所配置的服务商的密钥，且仅此一个**交给它：使用 Ollama 的智能体无法索要 Anthropic 的密钥。

在这个目录改名之前完成的安装，把密钥保存在 `/opt/boa/config/keys/` 中；`--update` 会把它们移过去，并删除旧目录。

值得讲清楚这能保护什么、不能保护什么。正当使用付费服务商的智能体，运行期间确实持有自己的密钥——它需要密钥才能发出调用，而拥有 `bash.run` 的智能体可以把它打印出来。共享存储所防止的，是一个智能体收集它并不使用的服务商的密钥；它还让所有密钥都不放在智能体的主目录中，否则一次失手的备份就会把它们一下子全部暴露。

要把一个智能体的费用记到另一个账户上，就在该智能体自己的主目录中放一个 `keys/<provider>.key` 密钥。它优先于共享密钥。

## 编写系统提示词

系统提示词就是智能体本身。它以 `system-prompt.md` 保存在智能体的主目录中，你可以在界面中编辑它。

有效的做法：

- **说明智能体是做什么的**，用一两句话。
- **说明怎样才算“完成”。** 没有完成定义的智能体，要么停得太早，要么永远不停。
- **说明受阻时该怎么做。** 没有这一条，模型就会自己编出一个绕过障碍的办法。“如果你做不到，就在看板上说明，然后停止”就足够了。
- **告诉它先读看板。** 那是它在两次运行之间唯一的记忆。

无效的做法：告诉它不要使用某个工具。如果你不希望它使用某个工具，就不要给它这个工具——提示词只是建议，工具列表才是强制执行的。

## 智能体记住什么

每个智能体的主目录中都有一个 `memory.md`，这个文件是它从一次运行带到下一次运行的唯一东西。当它学到值得保留的东西时，会用 `memory.append` 写进去，并用 `memory.replace` 整理它。

整个文件在每次运行开始时都会加载，这正是它有用的原因，也是它花钱的原因：每次调用模型，每个字符都要付费。在 **智能体设置 → 记忆 → 记忆上限（字符数）** 中，选择 1,000 到 1,000,000 个字符之间的上限。默认值是 8,000，现有智能体也一样。记忆超过上限的 75% 时，会要求智能体整理它的记忆。

计数器显示当前字符数和所选上限，包括空格和换行符。你可以在同一次保存中提高上限并粘贴更大的记忆。如果文本超过所选上限，那次设置请求中的任何内容都不会保存：请缩短文本或提高上限。之前的记忆保持不变；新的写入永远不会添加 `[truncated]`。以前被丢弃的文本必须从原始来源重新粘贴。完整的记忆仍然必须连同提示词、对话和工具一起，装得进所选模型的上下文。

值得保留的内容：某样东西放在哪里、某条命令最终是什么、你的偏好。而不是它做过什么的流水账——那是看板的事。

你可以在智能体设置的 **记忆** 中自己阅读和修改它。一个智能体一直据以行事的错误事实，值得手动改正。

## 本地文档库（RAG）

每个智能体在 `/opt/boa/agents/<id>/rag/` 下都有自己的文档库。支持 PDF、EPUB、UTF-8 TXT 和 Markdown 文件。安装脚本会准备好本地向量化模型（EmbeddingGemma 300M Q8，约 318 MiB，除非已经选择了另一个模型，参见[选择向量化模型](#选择向量化模型)）、它的 llama.cpp 引擎以及 OCR。文本提取、OCR、文档向量化和查询向量化都在这台服务器上运行。检索到的片段会发送给智能体所选的回答服务商，配置了云服务商时也包括云服务商。没有任何外部向量化端点可用。安装、更新、文档导入、OCR 以及备份/恢复都已在 Debian 13 和 Alpine 3.24 上验证过，包括重启后的服务启动。

1. 打开 **设置 → RAG**，检查本地引擎是否就绪。
2. 打开某个智能体的 **RAG** 标签页，启用检索并保存该智能体。**rag-consultant** 模板到来时就已启用检索。
3. 选择文件并点击 **上传文档**。大文件会分块传输。也可以把完整的文件复制到 `rag/inbox/`，然后点击 **导入 rag/inbox 中的文件**。导入的原件会移入受管理的文档存储。
4. 等待 **就绪**。提取和向量化在后台运行；其他已就绪的文档仍然可以搜索。页面会显示进度和错误。
5. 用 **搜索文档库** 测试一个问题，或者在智能体的普通对话中提问。引文会链接到源 PDF 的对应页，或者原始的 EPUB/文档。

从 `rag/inbox/` 导入时出现的错误会显示在文档列表上方。失败的原件会留在收件箱中，以便修正。索引按有限大小的批次处理，这样小文档就不必在每两本书之间都等调度器轮转一圈。

**文档信息** 控件依次编辑出版年份、标题、副标题、作者、版本、语言和标签。年份可以不填，最多接受四位数字。有副标题时，它会显示在文档列表中标题的正下方。副标题、年份、作者、版本和语言会随智能体检索到的每个片段一起传递，这样它就能区分标题相同的文档，为它引用的内容标注日期和出处，并区分说法不一致的不同版本。替换文件时，之前那个可搜索的文档会一直保留，直到新文档完成索引。如果本地向量化引擎在某个文档索引期间停止（更新、重启），该文档会回到 **排队中**，并显示消息“Local embeddings are unavailable”；等引擎再次响应后，它会从中断的地方继续，无需重新索引。“重新索引”会重建一个文档；“取消”会停止它待处理的工作；“删除”会把它从今后的搜索中移除。语言和版本筛选使用你输入的元数据。EPUB 引文标识的是章节，而不是编造出来的页码。扫描版 PDF 需要服务器上安装 OCR 语言；默认安装英语和西班牙语（`eng+spa`）。不支持的或加密的文件会报告错误，而不是给出一个看似成功却为空的索引。

**回答模式** 决定智能体可以在多大程度上超出它的文档；列表下方的那一行会说明所选模式的作用。

- **文档与常识**：智能体可以同时使用两者，但要分开说明。
- **必须有文档依据**：智能体必须在回答之前亲自检索文档库；没有检索就给出的回答会被退回给它一次。如果这次运行一个片段也没有检索到，你得到的会是固定的一句话“文档库中没有足够的信息来回答这个问题”，而不是模型写的任何内容。
- **仅限文档（经验证）**：与上一个模式相同，另外回答的每一段和每个列表项都必须引用在这次运行中检索到的片段。每一段都会被检查：没有引用、引用了未被检索到的片段，或者意思与所引用的片段相去甚远（用本地向量化引擎衡量），都会让回答连同这些段落的列表一起被退回一次。之后仍然没有依据的内容会被删除，并在最后一行说明删除了多少段。如果没有剩下任何有依据的内容，你得到的就是那句固定的话。如果无法连接到引擎来做检查，回答会被扣下，而不是未经检查就显示出来。

经验证模式做不到的，是证明一个带引用的段落与其片段说的完全一致。在我们的测量中，一个与其片段相矛盾、或在同一话题上添加了内容的段落，得分和忠实的段落差不多；这项检查能抓住的，是引用了另一话题片段的段落，以及完全没有出处的段落。它在两个方向上都不精确：在我们的测试中，它删除了大约每 100 个忠实段落中的 6 个（大多是简短的列表项和一行的摘要，它们能提供的比较依据很少），而指向另一话题片段的引用，被它放过的不到百分之一。代码示例会与引出它的那句话放在一起判断。准确性很重要时，请核对被引用的片段。固定的句子使用 **设置 → 智能体 → 智能体回答所用的语言** 中选择的语言书写，如果没有选择，就使用英语。引文只根据检索到的来源标识符来解析。

每个智能体的默认值：每个文件 128 MiB，原始文档共 2,048 MiB，200,000 个片段，每次运行 8 条结果、最多 16,000 个字符的检索文本。一个保守的字节预算还会限制能与提示词和历史记录并存的内容。**最低相似度** 的初始值是针对所用向量化模型测得的值（EmbeddingGemma 为 0.20，Qwen3-Embedding 为 0.35），字段下方的那一行会说明是哪个值。它是一个搜索分数，而不是概率，而且每个模型都有自己的尺度。如果语义结果太宽泛，就调高它。字面匹配也会参与。API 还额外开放了片段配额和片段的 token 大小。

全局设置控制向量化线程数、并行索引任务数和默认 OCR 语言。**并行索引任务数** 是同时索引多少个智能体的文档库（每个智能体一个任务，其文档逐个处理）；每个任务最多可能使用 4GB 内存，标签会提醒你这一点。它不会加快单个智能体文档库的索引速度：向量化引擎一次只响应一个请求。要想向量化得更快，应该调高 **向量化CPU线程数**。模型是共享的；文档库和权限按智能体划分。重启后处理会继续，保留已完成的文档以及被中断任务中可重用的片段。重新索引失败时，会保留最后发布的版本。只有安装模型时才需要下载；正常的检索可以在没有互联网的情况下运行。本地引擎不可用时会如实报告，绝不会用外部向量化服务替代。

`boa-embeddings` 通过 Unix 套接字提供模型服务；`boa-rag` 负责调度队列。两者都有 systemd 和 OpenRC 单元，并显示在系统设置中。备份包括文档原件、元数据，以及一致的 SQLite/向量索引快照。运行时设置也包含在内，所选的向量化模型也随之包含在内；模型的二进制文件和下载的权重则不包含。恢复时，如果机器上没有所选模型，就会下载它；如果下载失败，会如实说明并继续进行：之后可以在 **设置 → RAG** 中下载该模型，或者另选一个。在恢复的备份中，仍在进行中的上传会被取消。已建立索引的文档库在正常更新后会保留下来。

### 选择向量化模型

向量化模型把每个片段和每个问题都转换成数字，文档库就是靠这些数字来搜索的。**设置 → RAG → 向量化模型** 提供两个模型，而且同一个模型为所有智能体服务：

| | EmbeddingGemma 300M (Q8) | Qwen3-Embedding 0.6B (Q8) |
|---|---|---|
| 下载大小 | 318 MiB | 610 MiB |
| 引擎运行时占用的内存 | 约 600 MB | 约 1.1 GB |
| 索引耗时（同一处理器） | 1× | 约 4× |
| 许可证 | Gemma 使用条款 | Apache 2.0 |

EmbeddingGemma 是默认模型，适合任何机器。Qwen3-Embedding 适合处理器和内存有富余的机器：在测试文档库中那些西班牙语 Python 书籍上，它把关于这些书的问题（0.51-0.79）与无关问题（最多 0.21）拉开的距离比 EmbeddingGemma（0.35-0.67 对 0.17）更大，也把复述某个片段的段落与讲别的事情的段落拉得更开。在那台双处理器的测试机上，它每个片段耗时 2.2 秒，而 EmbeddingGemma 是 0.5 秒。

要更换模型：

1. 在列表中选择模型。下方会显示它的大小、内存、速度和许可证，以及是否已经下载。
2. 如果还没下载，点击 **下载模型**，等进度条走完。下载的文件在使用之前会与其公布的 SHA-256 进行校验。
3. 点击 **保存** 并确认。引擎会用新模型重启；顶部那一行会显示“引擎正在加载此模型”几秒钟，然后变成 **就绪**。

更换会引发哪些事情：

- 每个智能体的每个文档都会重新索引，每个索引任务处理一个文档库，就像新上传的一样。大型文档库需要好几个小时。
- 在轮到它之前，文档仍留在文档库中，可以通过问题中的词语找到它，但不能通过语义找到。在此期间进行搜索时，会告诉智能体有多少文档正在等待，这样它就不会把缺少某个片段当成文档库没有涉及这个问题。
- 每个仍保留旧模型推荐值的智能体，其 **最低相似度** 会改为新模型的推荐值。你设置了其他值的智能体会保留该值。
- 经验证模式用当前所用的模型来比较段落和片段，阈值是针对该模型测得的（EmbeddingGemma 为 0.36，Qwen3-Embedding 为 0.44）。

上一个模型的权重会留在磁盘上，所以换回去不需要下载——但用另一个模型索引过的每个文档，都会再索引一遍。

每个类别都有一个自己的框，并显示这个智能体拥有该类别中的多少个工具：“这个智能体可以读邮箱吗？”是一个决定，所以画成一个框。为智能体打开看板的开关位于 **看板** 框的底部，在它所管辖的工具下方。

- **`bash.run`** —— 以该智能体的用户身份运行 shell 命令。它没有 root，也无法获得 root。当智能体确实需要在这台机器上干活时，再给它这个工具。
- **`kanban.*`** —— 共享看板。凡是应该让人看得见的智能体，至少给它 `list_cards` 和 `add_card`。
- **`channel.write`** —— 发给你的消息。还要在 **频道** 标签页中勾选频道。
- **`web.fetch`** —— 仅限公开页面。私有地址和回环地址会被拒绝。
- **`rss.fetch`** —— RSS 或 Atom 订阅源，以条目列表而不是 XML 文档的形式返回。比用 `web.fetch` 获取同一订阅源便宜得多，还省去了智能体自己解析的工作。两者都位于 **互联网** 下。
- **`script.*` 和 `cron.*`** —— 位于 **自动化** 下。智能体把脚本写进它自己的 `scripts/` 目录，并在它自己的 crontab 中安排运行，用于不需要它思考的周期性工作：脚本自己运行，不花 token，智能体在下一次运行时读取结果。它只能安排自己的脚本，频率不得高于每 5 分钟一次，而且永远碰不到唤醒它自己的那一行。

智能体在自己的主目录里可以做很多事，在主目录之外则什么都做不了。它看不到另一个智能体的存在，更不用说读取它的提示词：智能体目录可以穿越但不能列出，每个主目录都只对它自己的 Linux 用户开放，所以这是内核在拒绝，而不是 Python 中的一项检查。

它也无法改写**它是什么**。授予它的工具、它的开销上限、它的系统提示词和它的 API 令牌，都放在它主目录里一个属于 root 的抽屉中：智能体能读取它们，却无法修改。修改它们的是你，而不是它。关于它自己，它唯一能编辑的是它的记忆。
- **`mail.*`** —— 在 **设置 → 邮件** 中设置的邮箱。见下文。
- **`skill.read`** —— 在 **技能** 面板上勾选的书面流程。两者缺一不可：这里的工具，以及那里至少一个技能。

### 邮件工具

一共四个，它们需要在 **设置 → 邮件** 中配置一个 IMAP 邮箱。智能体永远看不到那个密码：它说出想做什么，由持有凭据的智能体 API 去做。

| 工具 | 作用 |
|---|---|
| `mail.read` | 读取邮件。**不会把任何邮件标记为已读**，所以你自己的未读计数仍然保持原来的含义。 |
| `mail.move` | 把一封邮件归档到同一账户的另一个文件夹。该文件夹必须已经存在。 |
| `mail.delete` | 把一封邮件移到账户的废纸篓（如果有的话）。 |
| `mail.forward` | 转发一封邮件，**只能转发到你列出的地址**。 |

最后这个最重要。收件箱是智能体唯一一个全世界任何人都能写入的输入，所以每一次转发，`mail.forward` 都要由服务器对照你的列表进行检查——不是由智能体检查，也不是靠它提示词里写的什么东西。列表为空时，转发一律被拒绝。

只需要监视的智能体，就只给它 `mail.read`。需要归档时再加上 `mail.move`；给 `mail.delete` 和 `mail.forward` 之前要三思。

底部的 **看板** 复选框会为这个智能体完全关闭看板。不勾选时，它完全拿不到看板工具，也不再添加卡片；如果某个智能体的工作不属于看板，就用这个开关。

## 为智能体赋予技能

技能是一份书面流程：在这里，一项工作是如何一步一步完成的。应用程序不自带任何技能：技能讲的是“这台”机器（这些主机、这套备份、这张证书），所以通用的技能只会是一份没人遵循的流程。你以 root 身份在服务器上编写自己的技能：

```bash
mkdir -p /opt/boa/skills/BackupVerification
nano /opt/boa/skills/BackupVerification/SKILL.md
chown -R root:root /opt/boa/skills
chmod 00755 /opt/boa/skills/BackupVerification
chmod 0644 /opt/boa/skills/BackupVerification/SKILL.md
```

文件以名称和一行描述开头，两者夹在两条 `---` 分隔线之间，其余部分就是流程：

```markdown
---
name: BackupVerification
description: How to check that last night's backups actually ran.
---

1. Read /var/log/backup.log ...
```

然后，`/opt/boa/skills/` 下的每个目录都会在智能体的 **技能** 面板上显示为一个复选框。勾选一个，在 **工具** 中给智能体 `skill.read` 工具，然后按 **保存**。从下一次运行开始，智能体就知道有这个流程，并能在遇到这项工作时去阅读它。

### 既然已有系统提示词，为何还要技能

三个理由，第三个才是关键：

- **提示词说明智能体是做什么的；技能说明一项工作怎么做。** 六个智能体可以共享一个流程，而不必有六份副本各自过时。
- **技能想写多长就写多长。** 系统提示词在每次运行的每次调用中都要付费，所以必须保持简短。技能只付一次费，由读取它的那次运行支付。
- **智能体自己学到的东西会随它一起消失。** 它的记忆存放在一个其他智能体都打不开的主目录里。技能才是存放你希望下一个智能体也知道的东西的地方。

### 编写技能

界面中刻意没有为此提供编辑器：技能所说的内容会直接进入一个在凌晨四点无人看管时运行的智能体的推理过程，所以它和工具一样归 root 所有。你在服务器上编写它们：

```bash
mkdir -p /opt/boa/skills/DatabaseBackup
nano /opt/boa/skills/DatabaseBackup/SKILL.md
```

文件以两行头部开头，然后写它需要说的任何内容：

```markdown
---
name: DatabaseBackup
description: How the nightly dump is taken and where it goes.
---

# Database backup

1. Dump with `mysqldump --single-transaction`, never with the table lock.
2. Write it to /srv/backups/, never to /tmp.
...
```

`description` 是最重要的那一行。它是每次运行都要付费的唯一部分，也是智能体决定是否阅读其余内容时的依据。“How the nightly dump is taken and where it goes”能告诉它何时适用；“Database stuff”则不能。

重新加载智能体的页面，技能就会出现在列表中。

更新永远不会碰 `/opt/boa/skills/`：你在那里写的东西始终归你所有。Web 界面决定哪个智能体获得哪个技能；它不编辑技能。

### 技能可以自带文件

目录中的其他任何东西都会随技能一起提供：

```
/opt/boa/skills/DatabaseBackup/
  SKILL.md
  dump.sh
  exclude-tables.txt
```

智能体可以读取和运行这些文件，所以流程里可以写“运行这个目录中的 `dump.sh`”，而不必写出四十行 shell。`skill.read` 会告诉智能体有哪些文件、在什么位置。

### 它的开销

进入提示词的只有每个技能的名称和描述——每个大约两行。正文由认定自己需要它的智能体用 `skill.read` 获取一次，而且只在那时获取。给一个智能体五个技能，每次运行只花它几百个 token，而不是一万个，所以你可以给它五个而不用考虑账单。

### 如果删除了智能体正在使用的技能

什么都不会坏，也不会有哪个智能体还在承诺它做不到的事：

- 在下一次运行时，它会**从每个拥有它的智能体的提示词中消失**。智能体永远不会被告知一个它读不到的流程。
- 它会**从“技能”面板中消失**，所以没人能再勾选它。
- 这个名称会**一直留在智能体的 `info.json` 中**，直到有东西改写它，所以把目录放回去就能恢复这个技能，不需要做别的事。
- 如果智能体还是请求了它（它可能记得之前某次运行中的名称），它会被告知这个技能在它的列表上但已不再安装，并被告知不要猜测技能的内容。

需要知道一件事：**在技能缺失期间对该智能体按下“保存”，会把它从列表中永久删除。** 界面只保存存在的技能，正是这一点让已删除的技能不会永远残留。请在保存该智能体之前把目录放回去，或者事后重新勾选这个技能。

## 为智能体配备浏览器

`web.fetch` 只读取公开页面，别的什么都不做：不能登录，不能填表单，不能按按钮。如果智能体需要*使用*一个网站，而不只是阅读它，就需要一个浏览器。

它是默认安装的：安装脚本会问一次，默认回答是“是”。它是大约 600 MB 的 Chromium，所以磁盘紧张的机器可以拒绝，之后无论哪个方向都可以改变主意：

```bash
./install-update-reinstall-debian.sh --update --browser no    # 不安装它
./install-update-reinstall-debian.sh --update --browser yes   # 重新加上它
```

答案会像端口一样被记住。然后在智能体的 **工具** 面板上勾选浏览器工具：

这些在 Alpine 上都不适用：那里根本没有浏览器，因为 Playwright 没有为 musl 发布构建。这些工具仍然留在列表中，智能体调用时它们会说明这一点。

| 工具 | 智能体能做什么 |
|---|---|
| `browser.open` | 前往一个页面。cookie 会被保留 |
| `browser.read` | 重新读取已打开的页面、它的某一部分，或它的链接 |
| `browser.click` | 按可见文本或选择器点击链接或按钮 |
| `browser.type` | 填写一个字段，可以选择按下 Enter |
| `browser.screenshot` | 把一张 PNG 保存到它自己的下载目录 |
| `image.send` | 把一张 PNG 附加到网页对话和 Telegram 的回复中 |


`browser.screenshot` 会在服务器上保存一张 PNG。要在对话中显示它，智能体接着用这个路径调用 `image.send`。在 **智能体设置 → 工具 → 图片** 中授予 **image.send**，然后保存。由 **web-navigator** 创建的新智能体已经包含它；现有智能体保留它们当前的授权。

在网页对话中，图片会填满消息的文本区域，并保持其宽高比和完整高度。它也可以按原始尺寸打开。如果对话是从 Telegram 开始的，图片也会发送到那里。又高又大的截图会以 PNG 文档的形式发送。上传失败时，会重试缺失的部分，而不会重复已经送达的文字或图片。

只接受该智能体主目录中的 PNG 文件，每个最大 50 MiB，每条回复最多 16 个。附件保持私有，需要已登录的会话才能查看。要发送一张已有的截图，可以让智能体用它保存的路径调用 `image.send`。

### 每个智能体的会话各自独立

浏览器本身只有一份，位于 `/opt/boa/playwright/`，归 root 所有，对其他所有人只读。**不**共享的是配置文件：

```
/opt/boa/agents/001/browser/profile/     agent-001, 0700
/opt/boa/agents/002/browser/profile/     agent-002, 0700
```

登录了某个网站的智能体，**在下一次运行时**仍然保持登录，因为 cookie 在它自己的磁盘上。而其他智能体都没有登录，因为那个目录是 0700 且属于它的 Linux 用户——是内核在拒绝，没有任何可能出错的 Python 检查。当一个托管产品的所有智能体共用一台机器时，这种隔离正是它无法提供的。

尽管如此，会话 cookie 仍会在浏览器关闭时失效，这里和任何浏览器都一样。网站标记为持久保存的，就会持久保存。

### 它不会做的事

- **不访问私有地址。** `browser.open` 会拒绝 `192.168.*`、`127.*` 等地址，与 `web.fetch` 完全一样。一个刚读过恶意页面的智能体，绝不能被说动去打开你的路由器，而带会话的浏览器干这种事，比一次简单的抓取要顺手得多。
- **没有屏幕。** 它是无头的。`browser.screenshot` 是你看到它所见内容的方式；智能体自己看不了这张图片。
- **没有工具就什么都做不了。** 和其他一切一样，没有给智能体的工具，就是它调用不到的工具，而这项检查在服务器上进行。

如果从未安装浏览器，这些工具仍然会出现在列表中，并回复需要运行的命令。它们不会消失，也不会悄无声息地失败。

## 开销上限

每个智能体有四个上限，每次运行都会停在最先触及的那个上限：

| 上限 | 默认值 | 防范的是什么 |
|---|---|---|
| 每次运行的 token 数 | 16384 | 一段昂贵的对话 |
| 每次运行的步数 | 25 | 一个无休止调用工具的循环 |
| 每次运行的秒数 | 300 | 一次卡住的运行 |
| 每天运行次数 | 48 | 一行过于积极的 cron |

这些并不是杞人忧天。一个在付费 API 上每小时醒来一次、没有上限也没人看管的智能体，就是一张在你睡觉时不断增长的账单。

在智能体的 **历史** 面板上看清它实际用了多少之后，再调高这些上限。

### 备用模型

在 **大模型** 中，第一个服务商和模型的下方还有第二个。只有当主模型**失败**时（没有密钥、没有回应、模型不存在）才会用到它，运行会从同一步骤开始用它继续，并重放到目前为止发生的一切，所以已经完成的工作不会被丢掉。

它**每次运行只尝试一次**。如果备用模型也失败，这次运行就失败：永远轮流尝试两者，只会在故障期间耗尽上限，最后仍然一无所获。切换到备用模型这件事会写进智能体的历史，因为一次悄悄用另一个模型回答、并记到另一个账户上的运行，必须如实说明。

把备用服务商保留为 **无** 是默认设置，意味着一次失败就会结束这次运行。

如果为备用模型选择**同一个服务商**，模型框会填入该服务商目录中的一个*不同*模型，而不是再填同一个。同一个服务商加同一个模型，答不出任何主模型答不出的问题：它每次都会因为完全相同的原因失败。如果你还是把这一对改回了完全相同，字段下方会有一行提示——这是你的智能体，所以这只是警告，而不是拒绝。


当一次运行停在 token 或步数上限时，会再问智能体一次（不带工具，用它自己的一小笔预算），要它给出原本打算给出的回答，这样一次把全部预算都花在收集事实上的运行，就不会以“我要去检查一下系统”收尾。对话会在回答下方注明这一点，因为那个回答可能被截断。时间上限则没有这样的调用：那次运行已经超时了。

这次收尾调用会重新发送整段对话，所以在一次大量使用工具的长运行中，它并不便宜：一次停在 12000 token 上限的运行，实测最终花到了 24901。因此，token 上限是工作的预算，而不是这次运行的硬性最大值。除非触及了上限，否则不会以这种方式花费任何东西。

### 内核额外强制的限制

四个上限由运行本身执行。另有两个由内核强制执行，所以即使出问题的正是运行本身，它们也照样有效：任何智能体同时拥有的进程和线程不得超过 1024 个，所以一条无休止 fork 的命令会停在那里，而不会拖垮整台机器；在 Debian 上，每次运行都位于它自己的、拥有 2 GiB 内存的 systemd scope 中，这也会在运行结束时终止它留在后台运行的任何东西。被内存上限杀掉的运行，会像其他运行一样，在它的“历史”中报告为失败，在它的对话中报告为错误。一个浏览器本身就有几百个线程，这就是这个数字没有设得更小的原因。

## 安排智能体定时运行

在 **Cron** 中编写智能体的 crontab。这是智能体自己的 crontab，归它自己的 Linux 用户所有并由该用户执行，就像你以那个用户身份运行了 `crontab -e` 一样。

每小时一次：

```
0 * * * * /opt/boa/venv/bin/python3 /opt/boa/webapp/backend/core/runner.py --agent-id 001
```

每个工作日 08:00：

```
0 8 * * 1-5 /opt/boa/venv/bin/python3 /opt/boa/webapp/backend/core/runner.py --agent-id 001
```

界面会显示你正在编辑的那个智能体的准确命令行，所以你可以复制它，只修改时间部分。

留空即可删除计划。取消勾选 **已打开**，可以保留计划但让智能体忽略它。

如果你使用的付费服务商按时段定价不同（DeepSeek 在高峰时段的收费要高出好几倍），就应该在这里做出选择。

## 看板

这个页面有两个标签页：**看板**，也就是那三列；以及 **创建卡片**，也就是表单。当前打开的是哪一个记录在 URL 中，所以重新加载和后退按钮都会保持它。保存卡片后会回到看板。

三列：**待办**、**进行中**、**已完成**。

看板是智能体互相留下工作的地方，也是你查看实际发生了什么的地方。每张卡片都带有它的历史：谁创建了它、谁移动了它、何时以及为什么。

卡片有一个标题和一个 **要做什么** 框。标题给它命名；框里写指示，智能体两者都会读。把框里空空如也的卡片指派给智能体，只能让它去猜，这通常就是智能体拿到卡片却什么都不做的原因。

另一个原因是智能体根本看不到看板。智能体只能通过调用 `kanban.list_cards` 来读取看板，否则就完全读不到（看板从来不会放进它的提示词），所以没有这个工具的智能体永远不会知道这张卡片存在。当你选择这样的智能体时，**指派给** 会提示这一点。这是警告，而不是阻止：卡片仍会创建，只要在该智能体的 **工具** 标签页中勾选这个工具即可。

看板上的卡片会显示谁创建了它、谁在负责它、何时创建、标题的前两行、待办内容的前三行，以及**何时运行**。被截断的标题或正文，完整内容都在它的工具提示中。

最后那一行才是值得读的。没有标注时间的卡片并不是逾期了：没人会为它被唤醒，它的智能体会在下一次计划运行时发现它。**移动到** 是手动移动卡片的方式——这个看板不支持拖动。

你可以添加、移动和删除任何卡片。**智能体只能看到和修改它自己的卡片**：一张卡片如果是智能体创建的，或者是指派给它的，就算是它自己的。

这是一堵墙，而不是一种偏好。智能体根本无法得知另一个智能体的工作存在——看不到标题，不知道有多少张，甚至不知道那里有没有东西。让一个智能体移动一张不属于它的卡片，它会被告知它自己没有这样的卡片；不存在的卡片也会得到同样的这句话，因为如果拒绝信息能区分这两种情况，就等于提供了一种逐个 ID 询问看板上有什么的方法。

例外是编排者 **manager**（智能体 000）：它的职责是分派工作并跟进，所以它能读取整个看板。这也是协调工作归它、而不归别人的原因。

破坏性的确认框**没有默认按钮**：它打开时焦点在对话框本身，所以按 Enter 两件事都不会做，你必须说明你的意思。Escape 会取消。点击红色按钮才会继续。

普通的、不会破坏任何东西的确认框，打开时焦点确实会在它的确认按钮上，带一圈高亮，此时按 Enter 就表示“是”。

删除卡片会留下一行记录，记下它曾经存在以及是谁删除的，所以智能体无法抹掉它曾经在做什么的证据。

## 设置

设置按标签页分组，当前标签页记录在 URL 中，所以重新加载或使用书签都会回到你原来所在的位置：

| 标签页 | 里面有什么 |
|---|---|
| **操作系统** | 这台机器是什么、还剩多少内存和磁盘，以及四个服务是否在运行——每个服务运行时显示绿色，未运行时显示红色。以无特权方式读取，和 `os-watcher` 读取的方式相同 |
| **账户** | 唯一的电子邮件地址和密码。修改密码需要提供当前密码 |
| **邮件** | SMTP，用于有事需要通过邮件通知你的时候 |

| **音频** | 转写引擎、服务商、模型下载、语言，以及 Telegram 音频的保留设置 |
| **工具** | 已安装的工具，按“自动化”“浏览器”等子标签页分组 |
| **智能体** | 一次性作用于所有智能体的设置，以及模板来源的仓库和分支。保存在服务器上：由 cron 启动的运行没有浏览器可供读取偏好 |
| **聊天** | 消息框的行为方式：Enter 是否发送，每条回答是否显示它的花费 |
| **看板** | 每列显示多少张卡片，以及是否列出最近删除的卡片 |
| **界面** | 主题、语言、弹出消息停留多久，以及 **+** 是否询问新智能体从何开始 |

在 **操作系统** 中，服务状态与 **这台机器** 的第二列对齐。

聊天、看板和界面的偏好保存在你的浏览器中，而不是服务器上：它们描述的是你在这台机器上的工作方式，手机和台式机的偏好不同也很正常。

### 音频转写

在 Alpine 上，安装和更新完成后会交还 SSH 会话的控制权；OpenRC 会让服务保持运行。

打开 **设置 → 音频**。这些设置保存在服务器上，适用于通过 Telegram 收到的语音消息和音频文件。

1. 选择 **本地 · whisper.cpp** 或 **提供商 API**。转写一开始是禁用的。
2. 如果使用本地识别，选择一个模型，必要时点击 **下载模型**。安装脚本会准备好 `base`；选择器提供全部 30 个官方模型，包括仅支持英语的 `.en` 版本和量化变体，以及手动安装在 `/opt/boa/whisper/models/` 中的 `ggml-*.bin` 模型。界面会显示大小和安装状态。较大的模型需要更多内存和 CPU 时间。
3. 如果使用 API，先在 **API 密钥** 中保存它的密钥。保存了密钥后，OpenAI、Groq、Mistral、Together AI、Hugging Face 和 Cloudflare 就会出现。选择一个建议的模型，或输入该服务商提供的另一个转写模型标识符。Cloudflare 提供它支持的两个 Whisper 变体，并使用 `account-id:api-token` 形式的凭据。
4. 选择语言（`auto` 或 `en` 之类的代码）、最大时长，以及是否保留音频以便播放；点击 **保存**。用语音消息回复某个智能体在 Telegram 上发的消息，就可以试一试。你也可以先用 `/agents` 选择智能体。

初始上限是 600 秒，可以在 30 到 3600 秒之间配置；收到的文件不能超过 20 MiB。处理在后台进行，其队列在更新后依然保留。忙碌的智能体会在文本可用时收到保存的文本。录音中说出的智能体名称不会改变它的目的地。

网页对话会显示转写文本，启用保留时还会显示一个播放器。一份 Ogg 播放副本保存在登录保护之后。禁用保留后，新消息只保留文本。清空对话会删除已完成任务中保存的音频。备份包括这些音频；下载的模型在更新后会保留，但不会被备份。恢复到另一台机器之后，请在“音频”中下载缺少的其他模型。

本地识别在你的服务器上处理音频。API 识别会把音频发送给所选服务商，并可能产生独立于智能体模型用量的费用。本地失败永远不会自动切换到云服务商。Whisper 做的是转写而不是翻译；`.en` 模型只懂英语。音频只通过 Telegram 输入；网页对话会显示结果，但不会添加录音按钮。

对于现有的安装，以 root 身份用 `--update` 运行你所用发行版的安装脚本。它会在 `/opt/boa/whisper/` 下安装 FFmpeg、whisper.cpp 和 base 模型；在配置之前，转写保持禁用。

| Español (Argentina) | Español (España) | Français (France) |

希伯来语从右向左书写，选择它会让整个界面镜像翻转：侧边栏移到右侧，其余内容随之调整。代码、路径和命令仍然从左向右，每条聊天消息则遵循它自己的语言，所以在希伯来语页面上，一条英文回答依然从左向右阅读。

- **Telegram 和 Discord 机器人** 也说这种语言：它们自己的句子、`/status` 报告以及帮助文本。

## 弹出消息

保存了什么东西之后，确认消息会出现在你正在看的面板中央，然后自行消失。它是故意挡在那里的：以前，长标签页底部的“保存”按钮会在页面最顶端显示一行字，离你正在看的地方好几屏远，所以保存看起来就像什么都没发生。

**设置 → 界面 → 弹出消息停留的秒数** 设置停留多久，范围为 1 到 30 秒。默认是三秒：足够读完“设置已保存”，又短到不会一直压在你正要输入的那个框上。

错误消息会忽略这个数字。它们会一直留着，直到你用 `×` 或 Escape 关闭，因为错误是唯一一种在你回头看屏幕时必须还在那里的消息。

颜色表明发生的是三种情况中的哪一种：

| 颜色 | 含义 |
|---|---|
| 绿色 | 已保存 |
| 琥珀色 | **没有要保存的更改**——你按了“保存”，但表单上什么都没改 |
| 红色 | 失败了。会说明出了什么问题，并等你关闭 |

凡是能按“保存”的地方都适用琥珀色提示：**设置**（账户、邮件服务器、API 密钥、频道和浏览器偏好）以及智能体自己的设置。连按两次“保存”，第二次就会告诉你这一点，而不是报告一次并未发生的保存。全新的智能体是个例外：它的表单装着模板的值，而且从未保存过，所以“保存”会把它们写入，并带你进入它的对话。

## 主题

**设置 → 界面** 用于选择配色：

| 主题 | 是什么 |
|---|---|
| **Day** | 柔和的灰色配浅色卡片，适合明亮的房间 |
| **Night** | 深色配色，适合光线暗的房间 |
| **Day High Contrast** | 白色底色、近黑文字、清晰边框。这里没有任何东西用强调色填充：侧边栏中智能体的框只是一个轮廓，你自己的消息用柔化的墨色而不是蓝色填充 |
| **Night High Contrast** | 近黑底色、明亮文字和清晰边框。选中的智能体用灰色填充；选中的标签页有一个闭合的轮廓，与下方的线相连。你自己的消息使用调暗的白色 |

从未选择过的浏览器会从 Day 和 Night 中与操作系统相符的那个开始，并一直跟随操作系统，直到有人选择了一个。此后，选择会像语言一样保存在这个浏览器中，所以手机和台式机不必保持一致。

主题是服务器上 `frontend/themes/` 中的一个 CSS 文件，它重新定义 `--colour-*` 变量。往那里放一个文件就增加了一个主题——代码中没有需要更新的列表。它的名称和描述来自文件顶部的注释：

```css
/*
name: Midnight
scheme: dark
description: 用一句话说明它的外观。
*/

:root {
  color-scheme: dark;
  --colour-page: #101014;
  /* ... app.css 定义的所有 --colour-* ... */
}
```

把它们全部定义好。主题漏掉的变量会保留 app.css 中的值——在浅色主题上，这意味着深色配色中的某个颜色会突兀地留在中间。

这里自带的每个主题，用来绘制文字的每种颜色都达到 4.5:1 的对比度，两个高对比度主题则达到 7:1，即 WCAG AAA。有一个测试会在某个主题不再达标时失败，按其名称所声称的标准来衡量。手动添加的主题不受此约束，但同样的问题也适用于它：一个用没人看得清的红色标记为宕机的服务，就是一个没人注意到的服务。

## 卡片运行时

指派卡片是你给智能体派活的方式，而把它变成一次运行的，是一个名为 **buzzer** 的服务：

    每隔几秒：
      有负责人、时间已过且尚未触发的卡片
        -> 启动该智能体，除非它已经在运行
        -> 在卡片上记录这次触发

添加卡片表单中的 **何时** 决定时间：

| 选项 | 会发生什么 |
|---|---|
| **立即** | 卡片一保存就唤醒智能体。这是默认选项：指派卡片就是在要求完成这项工作 |
| **智能体醒来时** | 卡片在看板上等待。不会唤醒任何智能体；智能体会在它自己的下一次运行时发现它 |
| **安排在指定时间** | 一个 UTC 时间。到时唤醒智能体 |

已经在工作的智能体不会被打断。卡片保留它的轮次，并在下一轮检查时再试，所以安排给忙碌智能体的运行只会晚几秒开始，而不会根本不开始，而且一个智能体永远不会同时有两次运行。一张卡片只会触发一次：要再运行它，就重新设置它的时间。

### 卡片会出现在智能体的对话中

运行开始时，智能体的对话会收到一条点明这张卡片的消息：

    有人在卡片上给你指派了任务：

    卡片 ID：1284
    标题：续期证书
    任务内容：“用 --update 运行安装脚本并报告”
    执行时间：立即

如果卡片是另一个智能体转交的，第一行会说明是谁：*manager 给你指派了一张新卡片*。如果卡片是预先安排的，而不是要求立即执行，最后一行会改为显示时间：`a2026m03d31@13:45`，UTC 时间，与看板上这张卡片显示的时间相同。

这条消息**在运行开始时**才写入，绝不会提前。你安排在今晚运行、却在今天下午删除的卡片，不会在对话中留下任何东西，因为什么都没有运行过。

智能体会像回复其他消息一样在它下面作答，并附上这次运行的花费。有三种情况会在那里留下一行，而智能体并没有做任何事，每种情况都会说明是哪一种：智能体被关闭了、它当天的运行次数已经用完，或者这次运行根本无法启动。这些情况都不会悄无声息，因为一张宣布过却被忽略的卡片，看起来和一个不在工作的智能体一模一样。

这次运行有一件事不做：读取对话。它的指示就是这张卡片。你之前在对话中说过的话，只有在你自己发送消息时才会重放——否则每次计划运行都要为一段没人在进行的对话付费。

交给 **manager** 的卡片会被区别对待：它会被要求决定谁应该做这项工作，并用 `kanban.assign_card` 把卡片转交出去。卡片保留它的 ID、指示和历史，只是换了负责人，接手的智能体会因此被唤醒。这就是委派——而不是为同一项工作再建一张卡片。

## 频道

在 **设置 → 频道** 中配置智能体可以写入的地方：

| 频道 | 需要什么 |
|---|---|
| Discord | 用于双向对话的 `bot_token` 和 `channel_id`，或者只用于发送的 webhook URL |
| Mattermost | 一个传入 webhook URL |
| Telegram | 来自 BotFather 的 `bot_token`，以及 `chat_id` |
| X | 一个 `bearer_token` |

每个已配置的频道都会以绿色显示 **已配置**，颜色与已保存的 API 密钥相同。未配置的频道保持中性状态。

凭据的存放方式确保**任何智能体都读不到它们**。智能体请求服务器发送；服务器读取令牌并发送。消息到达时会带上智能体名称作为前缀，这个前缀由服务器添加，所以任何智能体都无法冒充另一个智能体。

然后，在每个智能体的 **频道** 标签页中勾选它可以使用的频道。它两者都需要：`channel.write` 以及频道本身。

### 从 Telegram 回复智能体

Telegram 和 Discord 是两个也能反向工作的频道。在它的设置中勾选 **允许我从 Telegram 回复智能体**，保存，你就可以回复了。

机器人的菜单中有三个工具，也就是 `/` 按钮所提供的：

| 命令 | 作用 |
|---|---|
| `/agents` | 把你的智能体列成按钮。点一个即可开始与它对话 |
| `/status` | 服务、看板，以及每个智能体及其模型、工具和技能 |
| `/help` | 这三个命令，以及联系智能体的另外两种方式 |

### 别人什么都看不到

机器人的用户名是公开的（任何找到它的人都能打开它），所以菜单**只为你的对话**而写。打开同一个机器人的其他人会看到一个空对话：`/` 下没有命令，没有描述，除了“开始”按钮之外没有任何可按的东西，而这个按钮是 Telegram 在每个机器人中都会画出、任何 API 都无法移除的。

按下它什么也不会发生。监听程序会把每条消息的 `chat_id` 与你设置中的那个进行比较，并在执行任何命令、选择任何智能体之前，丢弃不匹配的消息。

**而且什么都不会记录下来。** 没有回复，日志里没有一行字，也没有任何人写过东西的记录。不属于你的对话的 ID 是别人的数据，保留它就意味着你的安装在悄悄建立一份谁发现了这个机器人的名单。

代价是，设置错误的 `chat_id` 看起来和陌生人一模一样：你自己的消息会被悄无声息地丢弃。每次启动时，配置的那个 ID 都会写入日志，可以拿它来对照：

```bash
journalctl -u boa-channel-telegram.service | grep "Registered"
```

在 Debian 上，频道单元使用 `boa-channel-<channel>.service`。用 `--update` 运行安装脚本，即可自动迁移旧的单元名称。Alpine 保留它的 OpenRC 名称 `boa-telegram` 和 `boa-discord`。

过滤是按**对话**进行的，而不是按人。如果你配置的 `chat_id` 是一个群组，那个群组的每个成员都能与你的智能体对话。

### 选择对话对象

点 `/agents`，再点一个智能体，它会回复：

```
Agente os-watcher:

Envíame tus instrucciones...
```

从那以后，**你写的任何内容都会发给那个智能体**，直到你选择另一个。你可以连问四个问题而不必点任何人的名，这正是它成为一场对话、而不是一个命令行的原因。

有三种方式指定消息发给谁，按以下顺序：

1. **回复某个智能体说过的话**，消息就发给那个智能体，不管当前选中的是谁。回复它的消息（滑动该消息，或长按/右键点击后选择“回复”），输入，发送。
2. **点名**——`@os-watcher check the disk`——消息会发给它，*并且*让它成为选中的智能体。`@001` 也可以，带空格的名称同样可以：`@News Miner what is new` 是一个智能体，而不是两个词。
3. **两者都不是**，就发给你最后选择的那个。

除此之外，没有什么能改变选择，所以智能体永远不会仅仅因为碰巧最后一个发言，就接管你的对话。你删除的智能体会取消选中，而不是继续接收所有消息。

在你选择任何人之前，没有点名的消息会收到智能体列表作为回复，所以任何消息都不会毫无解释地消失。

### 回来的是什么

智能体会在 Telegram 中以回复你所写内容的形式作答，第一行是它的名称：

```
os-watcher:
25G free of 28G on /, unchanged since yesterday.
```

**而且整个往来都在 Web 界面中该智能体的对话里**，你的问题和它的回答都在，你发送的那条消息的时间旁边会标有 `(来自 Telegram)`。无论每一半是在哪台设备上输入的，一个界面仍然能显示智能体被问到的一切以及它说过的一切。

有两点要预料到：

- **忙碌的智能体会如实说明。** 如果它已经在回答别的事情，会告诉你过一会儿再试，而不是把你放进队列——队列会掩盖智能体正在落后的事实。
- **只监听你的对话。** 机器人的用户名是公开的，任何找到它的人都能给它写消息。来自其他任何对话的消息都会被丢弃且不予回复，所以决定谁能与你的智能体对话的，是你配置的 `chat_id`。配错了，就什么都不会发生。

这是长轮询，而不是 webhook：服务器主动连接到 Telegram，所以不需要向互联网开放任何东西就能工作。

如果 Telegram 不接受回答（你屏蔽了机器人、对话 ID 变了、令牌失效了），它会立即从 Telegram 一侧被丢弃；如果一个小时都连不上 Telegram，它也会被丢弃。但它永远不会丢失：整段对话，包括那个回答，都在 Web 界面中该智能体的对话里。

### 智能体的消息是什么样子

模型写的是 Markdown，而 Telegram 只渲染 HTML 的一个小子集，所以在发出时会把前者转换成后者。到达的是格式化后的内容，而不是一堆星号：

| 智能体写的 | 你在手机上看到的 |
|---|---|
| `**25G free**` | **25G free** |
| `` `df -h` `` | 等宽字体的 `df -h` |
| `# Disk report` | 一行粗体字 |
| `- item` | • item |
| 一个表格 | 一个列已对齐的等宽文本块 |
| ```` ```bash ```` | 一个代码块 |
| `[text](https://…)` | 一个链接 |

Telegram 自己没有标题、列表或表格，所以这三种会变成最接近的可读形式，而不是消失。

如果 Telegram 拒绝了格式，**消息会以纯文本重新发送，而不会丢失**。无论如何你都能收到文字；服务器日志会说明发生了什么，这样格式方面的 bug 就会暴露出来，而不是永远悄悄地降级。

机器人自己说的一切（智能体列表、“还在回答别的事情”、`/status`）都使用 **设置 → 智能体** 中设置的语言，也就是智能体回答所用的那种语言。

## 从 Discord 回复智能体

Discord 的工作方式与 Telegram 相同，用的是你自己的机器人。只需设置一次，五分钟就够。

### 创建机器人

1. 打开 <https://discord.com/developers/applications>，按 **New Application**。名字随你起。
2. 在侧边栏中点 **Bot**，然后点 **Reset Token**，复制它显示的内容。那就是 `bot_token`，而且只显示一次。
3. **OAuth2 → URL Generator**：勾选 **bot**，并在其下方勾选 **View Channels**、**Send Messages** 和 **Read Message History**。打开它生成的 URL，把机器人添加到你的服务器。
4. 在 Discord 客户端中，打开 **设置 → 高级 → 开发者模式**，然后右键点击你想让智能体所在的频道，选择 **复制频道 ID**。那就是 `channel_id`。

不需要别的东西。特别是，你**不**需要 Message Content Intent：那个开关是给 Gateway 用的，而这里是通过普通 API 读取频道的。

### 启用它

在 **设置 → 频道 → Discord** 中填入令牌和频道 ID，勾选 **允许我从 Discord 回复智能体**，然后保存。几秒钟之内，日志就会说明哪个机器人在监听、在哪里监听：

```bash
journalctl -u boa-channel-discord.service | grep "Listening"      # Debian
tail /opt/boa/logs/boa-discord.log                # Alpine
```

在你启用之前写下的消息不会得到回复：第一轮会记下频道当前的位置，并从那里开始。

### 与智能体对话

| 命令 | 作用 |
|---|---|
| `!agents` | 列出你的智能体，以及联系每一个时要输入什么 |
| `!status` | 服务、看板，以及每个智能体及其模型、工具和技能 |
| `!help` | 这三个命令，以及联系智能体的其他方式 |

如果你的手指习惯敲 `/agents`，它也可以用。这里没有按钮，也没有斜杠命令菜单：两者都属于 *interactions*（交互），而 Discord 只通过一种本安装刻意不打开的连接来投递它们。

指定消息发给谁的三种方式，就是你已经知道的那些：

1. **回复某个智能体说过的话**，消息就发给那个智能体，不管当前选中的是谁。右键点击它的消息 → 回复，或者在手机上滑动它。
2. **点名**——`@os-watcher check the disk`——消息会发给它，*并且*让它成为选中的智能体。`!os-watcher`、`@001` 和 `@News Miner what is new` 都可以。
3. **两者都不是**，就发给你最后选择的那个。

### 回来的是什么

回答会以回复你问题的形式到达，第一行是加粗的智能体名称，而且**整个往来都在 Web 界面中该智能体的对话里**，你发送的那条消息的时间旁边会标有 `(来自 Discord)`。

长回答会分成几条消息到达，而不是一条被截断的消息：Discord 拒绝任何超过 2000 个字符的内容，所以回答会在行与行之间拆分，最多拆成四条消息。你可以回复其中任何一条，它都会到达同一个智能体。如果内容超过四条消息的量，最后一条会以 `…` 结尾——完整内容在 Web 界面中，也就是它被写下的地方。

### 谁能与你的智能体对话

**能在那个频道里写消息的每一个人。** 这是与 Telegram 唯一的真正区别，值得你花一分钟了解：在那边，机器人会比较每条消息的对话 ID，丢弃不匹配的消息，所以找到你机器人的陌生人什么都得不到。在这边，机器人读取一个频道，任何能在其中发帖的人都能在你的服务器上启动运行。

所以请把智能体放在一个**私密频道**里——只有你，或者你和你信任的人才能看到的频道。机器人不需要访问其他任何东西。

### 如果你只想要提醒

令牌留空，改为设置一个 **webhook URL**：**频道设置 → 整合 → Webhook → 新 Webhook → 复制 Webhook URL**。这样智能体就可以往频道里写消息，仅此而已。监听需要机器人，所以在 webhook 上打开监听开关会被拒绝，而不是什么都不做。

## 编排者

`agent-000` 名为 **manager**，是安装时创建的唯一一个智能体。除了不能删除之外，它在各方面都是一个普通的智能体。

预期的用法：给 manager 看板工具，以及一段提示词，让它把目标拆分成卡片，并按 ID 指派给其他智能体。给其他智能体 `bash.run` 以及它们所需的其他工具，再配一段提示词，让它们处理指派给自己的卡片。

只有当 manager 的卡片写明了怎样才算“完成”时，这才行得通。没写明的卡片只是一个愿望，接手它的智能体会自己做决定。

## “工具”标签页

**设置 → 工具** 显示服务器上安装了什么。每个类别是一个子标签页（自动化、浏览器、频道、邮件、图片、互联网、看板、记忆、操作系统、RAG、技能），并标明其中的工具数量；每个工具都有自己的框，列出它的参数及其含义。当前打开的标签页记录在 URL 中（`/settings/?tab=tools&family=mail`），所以重新加载或使用书签都会保持它。旧的 `/tools/` 链接会重定向到这里，并保留所选的类别。

类别没人命名过的工具（比如某人丢进 `/opt/boa/tools/` 的一个 `.py`）会归入 **其他**，并在它自己的框上写明它的类别。它从头到尾仍然是一个完整的工具，一直到界面都是；只是它不会单独占一个标签页，否则这一排标签会随着每个临时脚本不断变长。

哪个智能体能用哪个工具，是在各智能体自己的 **工具** 标签页上设置的，而不是在这里。

## API 文档

侧边栏中的 **API 文档** 按区域分组列出 `/api/` 下的每个端点，以及它的参数和返回内容。它是根据本安装自己的 OpenAPI 描述生成的，所以不可能与代码脱节：顶部链接的 `openapi.json` 是同一份东西，作为一个文件，可以交给客户端生成器使用。

它和界面的其余部分一样，使用你在 **设置 → 界面** 中选择的语言。规范本身仍然是英文的：在这个项目中，字段名、ID 和错误字符串到处都是英文，而翻译过的 `openapi.json` 描述的会是一个并不存在的 API。

请求体以带颜色的 JSON 显示，就像编辑器那样：字段名一种颜色，值另一种颜色，花括号和逗号则调暗，因为它们只是脚手架。颜色来自你选择的主题，复制一个代码块得到的仍然是有效的 JSON。

这个页面不登录也能阅读，此时单独显示，不带侧边栏。它描述的是 API 的结构，而不是你的任何数据。

## 不需要智能体思考的工作

有些工作是周期性的、机械的：检查一张证书、轮转一个日志、收集一个数字。为此唤醒智能体，每次都要花 token，只为得出一个 shell 脚本不花分文就能得出的结论。

所以智能体可以为自己编写脚本并安排运行。给它 **自动化** 工具，它就可以：

1. `script.write` —— 在它自己的 `scripts/` 目录中放一个 shell 脚本。
2. `cron.add` —— 在它自己的 crontab 中按计划运行这个脚本。
3. 在下一次运行时读取结果，并判断它们意味着什么。

脚本以该智能体的 Linux 用户身份运行，权限与智能体相同，而且**完全不花 token**——它是一个 shell 脚本，而不是一次模型调用。花 token 的是智能体事后读取输出、并决定如何处理。

它不能做的事：

- 安排运行除自己脚本以外的任何东西。crontab 中一条形式自由的命令，事后谁都没法审查。
- 运行频率高于每 5 分钟一次。每分钟跑一次的任务算不上计划。
- 碰唤醒它自己的那一行。那一行归你管，在它的 **Cron** 标签页上。

两半你都能看到：它主目录中的脚本，以及在 Cron 标签页上与你自己的行并列的、运行这些脚本的行。

## 运行报告最终去了哪里

你从对话中启动的运行，会在对话中回答你。由到期卡片启动的运行，也在同一个地方回答。由智能体**自己的 crontab** 启动的运行，没有特定的回答对象（没人问过它什么），所以：

- **总会出现在“历史”中**，位于 **最近的运行** 下：每次运行说了什么，以及花了多少。想知道一个智能体最近在做什么时，就看这里。
- **值得打扰你时，也会出现在对话中**：运行没有完成，或者它改变了你能看到的东西——一张卡片、一条频道消息、一个邮箱。只是查看了一些东西的运行，只留在“历史”中。否则，一个每小时运行一次的智能体，每天都会往对话里贴二十四条“没有什么可报告的”消息。

这些消息上方会注明没人要求它们，而且它们永远不会重放给模型，所以在你下一次发消息时不会产生任何花费。

**从未启动的运行也会出现在“历史”中**，标记为“未启动”。在一个尚未设置 API 密钥的智能体上按 **立即运行**，或者在智能体已在运行时按下它，“历史”中的那一行会告诉你是这两种情况中的哪一种。以前，屏幕会说运行已经开始，然后再也没有任何东西出现，因为原因被写到了一个没有任何东西读取的地方。未启动的运行不计入智能体当天的运行次数，也不算作智能体的一次失败：它什么都没运行。

## 状态栏

每个页面底部的那一条（横跨窗口全宽，侧边栏下方也包括在内）反映的是整个安装的情况：

- **执行器** 和 **智能体 API**，运行时为绿色。只要其中一个是红色，智能体就不会运行，而界面中别的地方都不会告诉你这一点。
- **智能体**：在现有的智能体中，有多少个已打开。
- **看板**：每一列中的卡片数。
- **今日 token**：自 UTC 午夜以来所有智能体花掉的全部 token，以及用了多少次运行。正是这个数字，能在账单到来之前告诉你某个智能体陷入了循环。

在这一条的右端，GitHub 标志和名称 **nipegun** 会在新标签页中打开项目仓库 <https://github.com/nipegun/bunch-of-aigents>。你登录所用的账户不会显示：一套安装永远只有一个账户，所以把它显示出来并不会告诉你任何你不知道的东西。

## 智能体用什么语言回答

用你思考时所用的语言编写每个智能体的提示词，它就会用那种语言回答。这涵盖了对话。但它不涵盖由智能体自己的 crontab 启动的运行：没人用任何语言给它写过东西，而自带的提示词是英文的——所以一套以西班牙语运行的安装，收到的计划报告却是英文的。

**设置 → 智能体 → 智能体回答所用的语言** 可以一次性为所有智能体解决这个问题。它会在每个智能体的系统提示词中加一行，用它所要求的语言书写，说明它优先于提示词中关于语言的任何说法。保持默认值则什么都不会改变：每个智能体用它自己提示词的语言回答。

它保存在服务器上，这与界面语言不同，后者是你浏览器中的一项偏好。被 cron 唤醒的运行没有浏览器。

## 用你自己的语言写提示词

用你思考时所用的语言编写系统提示词。系统中没有任何东西与英语绑定：提示词、记忆、对话、卡片标题以及服务之间的消息，从头到尾都是 UTF-8，带重音符号的字符也不例外。

新智能体得到的默认提示词是英文的，它的最后一条规则告诉智能体用提示词所使用的语言回答。用你的语言把整段提示词重写一遍，那条规则也会随之改变——智能体会遵循它现有的提示词，而不是它最初的那段。

提示词按整行保存，而不是在固定列处折行。文本框会在屏幕上为它们自动折行，让它们保持易读，但不会把换行符写进文件：一条只有一句话的规则始终是一行，编辑它也不意味着要重新排版一整段。

## 备份与恢复

让这套安装成为“你的”安装的一切，都在 `/opt/boa/` 下以及智能体的 Linux 用户中。一条命令就能把它们收集到一个归档中：

```bash
./install-update-reinstall-debian.sh --backup
```

它会写入 `/root/boa-backup-<date>.tar.gz`，仅限 `root`，权限 0600，而且服务保持运行——什么都不会停止。传入一个路径可以写到别处：`--backup /mnt/usb/boa.tar.gz`。里面包括：两个数据库，通过 SQLite 自己的备份 API 复制，所以不会漏掉仍留在预写日志中的任何内容；服务商密钥、频道密钥和会话密钥；证书；每个智能体及其主目录、受保护的文件、Linux 用户和 crontab；在这台服务器上编写的技能和工具；以及安装日志，因为里面有密码。不包括：代码、Python 环境、浏览器，以及这台机器自己的两项选择（端口模式和是否装有浏览器），这样恢复时就永远不会导入另一台机器的选择。

**请像保护这台机器一样，保护好它的私密性。** 它包含每一个 API 密钥、每一个频道令牌以及登录密码。

要在这台机器或一台新机器上恢复：

```bash
./install-update-reinstall-debian.sh --install       # 仅在新机器上
./install-update-reinstall-debian.sh --restore /root/boa-backup-<date>.tar.gz
```

它会要求输入 YES，或者接受 `--yes`。然后它会停止服务，用相同的名称重新创建智能体用户（ID 空闲时也使用相同的 ID），用归档中的内容替换数据库、密钥、证书、智能体、技能和工具，安装 crontab，并启动一切。用备份中的电子邮件和密码登录：两者都会追加到 `/opt/boa/logs/install.log` 中，位于标题 `Credentials of the restored backup` 之下，备份的完整日志则作为 `install.log.restored-<date>` 保存在它旁边。

这台机器上有、而备份中没有的智能体，会把主目录保留在磁盘上，但从界面中消失，因为智能体列表在恢复的数据库中。在 Alpine 上，是在 `install-update-reinstall-alpine.sh` 上使用同样的两个标志。

## 服务

| 服务 | 运行身份 | 作用 |
|---|---|---|
| `boa-proxy` | `boa` | HAProxy：在 11443 上终结 TLS，重定向 11080，并提供 Web 端口服务 |
| `boa-web` | `boa` | Web 界面和 API，位于代理后面的 Unix 套接字上 |
| `boa-exec` | `root` | 创建用户、安装 crontab、启动智能体的运行 |
| `boa-samba` | `root` | 对 SMB 用户进行身份验证，并以各自智能体用户的身份提供每个 samba/ 文件夹 |
| `boa-agent-api` | `boa` | 智能体访问看板和频道所经过的那扇门 |
| `boa-buzzer` | `boa` | 监视看板，在卡片到期时唤醒智能体 |
| `boa-embeddings` | `boa` | 在 Unix 套接字上提供文档库的本地向量化模型 |
| `boa-rag` | `boa` | 调度文档库的索引队列 |
| `boa-channel-telegram.service` | `boa` | 在 Telegram 上监听，让你可以用手机回复智能体 |
| `boa-channel-discord.service` | `boa` | 对 Discord 频道做同样的事 |

```bash
systemctl status boa-proxy boa-web boa-exec boa-agent-api boa-buzzer \
                 boa-embeddings boa-rag \
                 boa-channel-telegram.service boa-channel-discord.service boa-samba
journalctl -u boa-exec -f
```

Debian 的频道单元使用 `boa-channel-<channel>.service`。用 `--update` 更新时，会先停止并禁用旧的频道单元，再启用新的。

Alpine 上运行的是同样的进程；它的频道服务仍然叫 `boa-telegram` 和 `boa-discord`。它们是由 `supervise-daemon` 监管的 OpenRC 服务，每个服务打印的内容都会写入 `/opt/boa/logs/` 下它自己的文件，每周轮转一次：

```bash
rc-status
rc-service boa-exec status
tail -f /opt/boa/logs/boa-exec.log
```

## 安全

这套设计假定智能体迟早会做出你本意之外的事，因为它是一个拿着 shell 的语言模型。

- **每个智能体都是一个独立的 Linux 用户**，它的主目录权限为 `0700`。智能体之间无法读取彼此的文件、提示词或 API 密钥。
- **`/opt/boa/agents/` 的权限为 `0711`**，所以任何智能体甚至都无法列出还有哪些其他智能体存在。
- **任何智能体都永远不以 root 身份运行。** 只有 `boa-exec` 是这样，而且它通过 Unix 套接字只接受一份封闭的操作列表。其中没有“运行这条命令”这一项。
- **运行受内核约束，而不只是受其上限约束。** 任何智能体的进程和线程都不得超过 1024 个，所以 fork 炸弹会停在这个数字；在 Debian 上，每次运行都位于它自己的、拥有 2 GiB 内存的 systemd scope 中，这也会在运行结束时终止它留在后台运行的任何东西。
- **智能体永远看不到频道凭据。** 机器人令牌不是一条消息：它是永久性的授权，可以发送该机器人能发送的任何东西。智能体请智能体 API 发送，由它来发送。
- **智能体只能碰它们自己的卡片。** 参见[看板](#看板)。
- **`web.fetch` 拒绝私有地址**，它会检查解析后的 IP，并在每次重定向时重新检查，所以读到恶意页面的智能体，无法被指使去调用你的内部网络。

它是为局域网设计的，不应暴露在互联网上。

## 出了问题怎么办

**我选择了 `--ports direct`，机器上的 HAProxy 不见了。** 它没有不见，而是退役了：停止运行；在 Alpine 上被移出所有运行级别，在 Debian 上被禁用并屏蔽；它的 `/etc/haproxy/haproxy.cfg` 如果是安装脚本写的就被删除，如果是你写的就保留为 `haproxy.cfg.before-boa.<date>`。在这个模式下，应用自己绑定 80 和 443，任何其他占用这些端口的东西都会让它根本无法启动——一个仍处于启用状态的代理，会在下次启动时抢先占用这些端口，比应用运行得还早。`haproxy` 软件包是故意保留的：`boa-proxy` 就是 `/usr/sbin/haproxy`，在这个模式下，正是它在提供 80 和 443 的服务。

要改回来，用 `--update --ports proxied` 运行安装脚本：它会解除对该单元的屏蔽，重新写入机器的配置并启动它。你的旧文件（如果有的话）仍然以 `before-boa` 名称放在它旁边。

**`boa-proxy` 反复重启，11443 上没有任何东西在监听。** 阅读 `/opt/boa/logs/boa-proxy.log`。如果它显示 `Cannot raise FD limit to 4131`，说明这台机器的文件描述符硬限制低于代理所请求的数量——通常是个小容器。在修复这个问题之前完成的安装，`/opt/boa/config/haproxy.cfg` 中仍然有 `maxconn 2048`。用 `--update` 运行安装脚本会重写这个文件；要当场修复：

```bash
sed -i 's/^  maxconn 2048$/  fd-hard-limit 4000/' /opt/boa/config/haproxy.cfg
rc-service boa-proxy restart        # 在 Debian 上用 systemctl restart boa-proxy
```

然后 HAProxy 会根据它实际能拥有的描述符来确定自己的规模，在硬限制为 4096 时大约是 1987 个连接——远远超过这里的需要。

**安装脚本最后显示“Everything is in place but the application does not answer”。** 安装已经完成，但页面一直没有返回。原因已经写在日志里了：

```bash
sed -n '/Why it did not answer/,$p' /opt/boa/logs/install.log
```

那一段记录了当时机器的状况：curl 对这个请求的处理结果、端口上是否有程序在监听、全部十个服务的状态，以及代理和 Web 应用最后打印的几行。`000` 不是 HTTP 状态码——它是 curl 在说它根本没收到状态码。一个自称 `started`、旁边却写着 `nothing is listening on port 11443` 的服务，是一个每隔几秒就崩溃并被重启的进程，而它自己的日志（往下几行）会说明原因。

在这里失败的更新，已经把上一个版本恢复回来并在运行它了。首次安装没有可以回退的版本，所以它会把一切都留在原处：修复那一段中指出的问题，然后用 `--update` 再次运行安装脚本。

**安装脚本因“systemd is not running”而停止。** 它拒绝安装到 systemd 不是 PID 1 的机器上，因为它写入的每个服务都是 systemd 单元，没有任何东西能启动它们。普通的 Debian 没问题；容器则不行，除非它是为运行 systemd 而创建的：

```bash
apt-get install -y systemd systemd-sysv dbus dbus-user-session
```

然后以 `/sbin/init` 作为命令重新创建容器——已经在运行的容器无法更改它的 PID 1。在 Alpine 上不会遇到这个问题：机器上没有 OpenRC 时，那个安装脚本会自己装上。

**按下“立即运行”后什么都没发生。** 看看侧边栏底部的两个圆点。如果 `执行器` 是红色：

```bash
systemctl status boa-exec
journalctl -u boa-exec -n 50
```


**浏览器显示 503，而服务都在运行。** 机器上的 HAProxy 把后端标记为宕机了。几乎总是因为那个后端上有 `option ssl-hello-chk`：它的 ClientHello 早于 TLS 1.2，而本应用要求 TLS 1.2。删掉那一行，然后重新加载 HAProxy。

**智能体运行了，但什么都没做。** 查看它的“历史”面板。然后手动运行它并观察：

```bash
runuser -u agent-001 -- /opt/boa/venv/bin/python3 \
  /opt/boa/webapp/backend/core/runner.py --agent-id 001
```

加上 `--dry-run` 可以查看它会加载什么（服务商、工具、上限），而不调用模型。

**它说无法连接到模型。** 对于自托管服务商，检查服务器是否在运行、基础 URL 是否正确。对于云服务商，检查密钥文件是否存在于智能体的主目录中，并且归该智能体所有。

**它说某个工具对它不可用。** 那个工具没有在该智能体的页面上勾选。提示词无法覆盖这一点，这正是设计的用意。

**卡片不再出现了。** 要么该智能体的看板复选框没有勾选，要么侧边栏底部的 `智能体 API` 是红色：

```bash
systemctl status boa-agent-api
```

**我想看到智能体做过的一切。** 它的日志在它自己的主目录中：

```bash
cat /opt/boa/agents/001/runs.jsonl
```

每行一个 JSON 对象：何时运行、花了多少、是否完成。
